# WALL-E 总体模块边界清单

记录日期：2026-11-10  
依据：本次语音讨论  
范围：项目总体规划，不归属某个软件版本

本清单先把已明确的方向和还没定的事项分开，便于继续讨论。这里的“已明确”表示职责方向已明确，不表示详细设计已经定版，也不表示功能已经实现。

## 一 已明确的职责与边界

### 1 DOC

- 与负责人协作，形成文档。
- 文档和需求本身有问题时，回到 DOC 处理。

### 2 Coding

- 根据文档编写代码，并配置所需环境。
- 发现文档或需求问题时，交回 DOC；文档问题不直接作为 Coding 内部的实现问题处理。

### 3 Evaluation

- 用 Evaluation 替代原来的 Test 定位。
- 根据证据进行评估，形成评估结果。
- 评估与后续自我反馈的职责要区分：评估负责判断，自我反馈负责汇集线索并跟进改进。

### 4 自我反馈职责

- 先明确这项职责，暂不确定是否必须做成独立的物理模块。
- 汇集评估结果、用户反馈、运行记录、构建记录及其他相关证据。
- 有明确线索时触发后续处理。
- 对评估结果，采用加权评分和阈值判断的方向；为严重问题保留直接进入处理的选项，具体规则待定。
- 持续跟进改进，直到完成验证并结束，或明确暂停。

### 5 Memory

- 整理、关联并持续更新当前项目的代码、文档和结构信息。
- 保留信息来源和更新记录，便于排查问题。
- 不以保存完整的项目演变历史为目标。

### 6 AI 决策与行动的共同要求

- AI 的决策和行动需要留下依据及记录，能够查到做了什么、为什么这样做。
- 不要求每一个动作都先让用户批准；具体自动执行边界仍需明确。

### 7 个人助理

- 暂时后置，本轮不展开具体设计。

## 二 仍待明确的清单

- [ ] 评估结果采用哪些评分因素。
- [ ] 各因素的权重和进入后续处理的阈值如何确定。
- [ ] 什么属于严重问题，何时可以不经过通常的评分门槛，直接进入处理。
- [ ] 用户反馈、运行记录、构建记录等非评估来源，满足什么条件才进入自我反馈处理。
- [ ] DOC、Coding、Evaluation、自我反馈职责和 Memory 之间怎样交接，交接内容、接收责任和完成依据是什么。
- [ ] AI 可以自动执行哪些动作，哪些情况需要用户确认，暂停后如何继续。
- [ ] 各职责最终怎样落到实际模块、流程和代码中，尤其自我反馈是否需要独立模块。

## 三 当前记录边界

- 本文件独立放在项目 docs 目录下的“总体规划”文件夹，不放入任何版本目录。
- 本轮只记录总体讨论，不替代现行版本规格，不合并到正式设计，也不启动代码实施。
- 待明确项继续保留，尚未确定的评分、阈值、交接和自动化规则不补写成既定结论。
