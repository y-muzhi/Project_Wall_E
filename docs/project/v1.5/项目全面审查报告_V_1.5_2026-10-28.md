## 1. 核心判断

**项目正在朝已确认的目标推进，而且已经具备较扎实的数据一致性与操作保护基础；但现有证据还不足以宣布系统已经全面稳健、长期可靠且易用性得到充分验证。**

更准确的定位是：一个主要业务链路已经接通、持续进行交互优化、具有真实模型有限样本证据的本机单用户需求工作台。它已经超过原型阶段，但尚未完成产品质量、恢复运维和验收证据的整体收口。

最值得保留的能力是：真实目标与阅读对象分离、普通讨论不写文档、明确生成／修订直接保存、版本与人工确认分离、原请求幂等恢复、事务保护、取消后的迟到写入隔离、实际模型上下文与用量审计。这些能力直接支撑用户对系统的信任。

当前最需要补齐的不是更多功能，而是以下六件事：

1. 完成已有真实样本的人工语义验收，证明 AI 确实理解并推动用户需求。
2. 把分散的历史记录整理成唯一可核对的当前能力与验收状态表。
3. 建立正常业务数据及相关证据的备份、恢复和启动检查闭环。
4. 检查前端请求长期不返回时的可恢复性，避免共享读取与写入屏障长期等待。
5. 测量并优化主入口加载成本，补齐真实任务的易用性验证。
6. 为当前能力建立可重复执行的离线质量门禁，减少后续版本破坏已有保护的风险。

本轮没有确认新的严重数据破坏缺陷，也不能据此断言不存在此类缺陷。没有完成逐行审计、全量后端回归、浏览器全流程验收或安全渗透测试。

## 2. 审查方法、事实层级与边界

### 2.1 方法

本轮采用“现场基线 → 正式目标 → 核心实现 → 历史证据 → 当前检查 → 风险与行动建议”的顺序。检查重点不是文件是否存在，而是关键保护是否有实际代码、是否有调用路径，以及现有证据能支持多强的结论。

实际阅读包括项目规则、当前断点及需求映射的最新段落、V1.5 前后端目标与公共规则、相关对象／AI 提交／外部依赖／验收规则，以及事务、幂等、HTTP 边界、后台运行、上下文、结果提交、文档写入、前端传输、读取协调、轮询和主输入等关键源码。对超长文件采用章节定位和重点段落抽查；未把目录扫描、搜索命中或被截断输出记为全文阅读。

### 2.2 证据等级

| 等级 | 含义 | 本报告使用方式 |
| --- | --- | --- |
| 本轮实测 | 2026-10-28 实际执行并取得结果 | 可以证明本轮所测范围 |

## 4. 与项目目标的一致性

正式后端定义的目标是：围绕同一需求的多份文档，支持 AI 主导讨论、用户决定出稿、读稿反馈、明确修订与来源同步；程序控制真实状态、权限和提交。

| 目标 | 当前设计及实现方向 | 判断与剩余证据 |
| --- | --- | --- |
| 帮助用户明确需求 | 分层讨论、目标与决定、主题及阶段 | 机制已形成；讨论质量仍需语义审阅 |
| AI 主动提供方案 | DISCUSS 与 progress_delta、建议出稿卡片 | 能表达推荐与推进；不能仅凭结构合法认定推荐有用 |
| 用户决定何时出稿 | 六类 operation、程序绑定与显式授权 | 方向正确，应持续守住普通讨论不写入 |
| 多份文档协作 | Requirement 下多文档、固定来源和目标 | 已摆脱唯一 CURRENT 的旧假设 |
| 降低读写混淆 | selectedDocument 与工作绑定分离 | 安全性提高，但增加了用户理解成本 |
| 持续修改且可追溯 | Revision、来源、审计、确认历史 | 有清晰基础；恢复演练与长期数据规模尚缺证据 |
| 降低反复确认成本 | 明确生成／修订成功直接保存 | 符合已确认决策；建议批次仍独立审阅，语义不同 |
| 保留人工控制 | 五态人工切换、版本确认独立 | 不能为了“更严格”增加关闭或完成门槛 |

总体没有发现项目正在偏离已确认目标的直接证据。更值得警惕的是：技术管理能力越来越丰富，用户完成一次真实需求所需的理解与操作成本是否同步降低，目前没有足够量化证据。

后续判断功能价值时，建议持续追问：它能否减少用户重复解释、降低出错概率、缩短获得可用文档的时间？若只增加可见状态或技术信息，却不能改善这三项，应降低优先级。

## 5. 代码结构与可维护性

### 5.1 架构优势

后端按 requirements、documents、revisions、messages、guide、suggestions、comments 划分业务职责，infrastructure 提供数据库、资源、模型与审计机制。前端沿 API、业务 owner、视图和公共控件组织。设计与代码总体保持既有业务根复用，没有因为新概念大量新增独立服务。

这适合当前本机单用户产品：部署路径短，跨对象事务能够在 SQLite 内完成，故障状态也比较容易追溯。没有证据表明当前应改为微服务、引入另一套聊天 SDK 或重写编辑器。

### 5.2 关键模块的复杂性

上下文、身份继承、编辑快照和资源验证的复杂性主要来源于真实约束，不应仅因文件较长就机械拆分。更有效的措施是：按输入、输出和不变量整理接口；在变更前确认相关专项；把业务规则与纯格式转换分开；限制跨层直接访问。

部分前端源码一行包含多段条件、状态变化和 JSX。代码物理行数因此低估了阅读成本，例如 [composer-view.tsx](../../../frontend/src/guide/composer-view.tsx)。建议在实际触碰模块时逐步格式化和拆出具名处理函数，不进行一次性全仓格式重写。

### 5.3 新旧路径共存

当前仓库仍保留 V1.0 的资源、迁移、协议与历史测试，同时存在 collaboration_v1 新执行链路。这有助于追溯，但带来误用旧入口的风险。服务注释仍写“37 routes”，根 README 仍包含 schema4 和旧默认数据库说明；这些不应被当成当前 V1.5 的启动依据。

建议给活动入口、历史只读兼容、冻结资源和维护工具建立一张简明索引。历史代码是否删除应基于调用关系和保留要求，不以本报告授权清理。

### 5.4 依赖与自动化

前后端均有精确依赖记录。前端 package.json 的版本仍为 `0.6.0`，与产品 V1.5 名称不同；这不会直接影响功能，却不利于发布身份识别。

本地未发现 `.github` 目录，因此没有看到随仓库保存的 GitHub Actions 质量门禁；不能据此排除外部存在其他 CI。现有检查多依赖人工选择工具与记录，后续应把稳定的离线入口变成可重复门禁，避免工具名、当前资源和测试范围之间逐渐脱节。

## 6. 数据一致性与恢复可靠性

### 6.1 已确认的保护

| 机制 | 实现依据 | 作用 |
| --- | --- | --- |
| 事务统一 | [database.py](../../../backend/app/infrastructure/database.py) 的 transaction | 写入使用 BEGIN IMMEDIATE，异常回滚；内部能力不能自行提交或嵌套保存点 |
| 结构与数据约束 | [v1_5.sql](../../../backend/app/infrastructure/schemas/v1_5.sql) | 状态枚举、版本、身份、关联及占用一致性由数据库共同保护 |
| 独占进程 | process_lock 与 worker.start | 先核对既有库，再取得执行归属，不自动建库或迁移 |
| 幂等原请求 | [idempotency.py](../../../backend/app/infrastructure/idempotency.py) | 同键不同业务内容拒绝；成功事实持久化并重放 |
| 不确定提交 | CommitOutcomeUnknown 与原请求核实 | 不把连接失败简单当作未执行，不盲目换键重做 |
| 版本冲突 | 文档及需求命令中的期望版本 | 避免旧界面覆盖已变更内容 |
| 取消与退出隔离 | ExecutionLease、service 生命周期 | 退役后阻止迟到线程继续写入 |
| 历史恢复 | Revision 与人工草稿路径 | 恢复形成新工作版本，不把高水位倒退 |

这是项目最明显的工程优势。尤其是幂等成功回执和业务变更处在同一事务中，明显强于仅在按钮上防连点。

### 6.2 仍需区分的三类恢复

1. **请求恢复**：网络响应丢失后核实原请求；现有代码和测试已有较充分基础。
2. **任务恢复**：进程退出、运行超时或模型返回已保存时恢复状态；已有 worker 与 collaboration_recovery 机制，本轮未重新覆盖全部进程组合。
3. **灾难恢复**：业务数据库、计数审计、准入证据或本机磁盘丢失后的整体恢复；本轮未找到 V1.5 运行说明中的完整操作闭环。

不能把前两项存在当作第三项已经解决。

### 6.3 备份能力存在，运维闭环不足

Database.backup_to 使用 SQLite backup API，拒绝覆盖既有目标，是可复用的良好基础。但当前数据库命令行只暴露 init／check；V1.5 运行说明没有清晰规定备份频率、保留数量、配套审计／准入材料范围、恢复验证步骤及失败处置。

建议先编写恢复清单，再使用独立副本演练：备份 → 新位置恢复 → schema 校验 → 版本及关联核对 → 只读页面／历史核对 → 准入证据验证。演练不需要真实模型调用，也不应覆盖用户当前库。

## 7. AI 执行链路、上下文与成本

### 7.1 权限由程序承担

当前链路包含接受任务、冻结依据、组装 Canonical、投影 Wire、可信计数、实际调用、保存原返回、解析校验和事务应用。模型不能仅靠回复中的目标名决定写入对象。

在 [document_application.py](../../../backend/app/guide/document_application.py) 中，新文档名称与类型需匹配绑定；修订需匹配目标版本；局部修改按冻结范围嵌回原文，并检查范围外字节与身份。此类保护应作为后续版本不可削弱的核心约束。

### 7.2 结果分量分开判断

[collaboration_results.py](../../../backend/app/guide/collaboration_results.py) 将主要结果、讨论进度和实际应用状态分开处理。讨论进度非法不会自动否决已获授权且有效的文档结果；业务未应用时仍保留返回，避免用户只看到一个笼统失败。

这种设计合理，但界面必须帮助用户区分“运行结束”“模型返回有效”“正文已保存”“讨论进度已更新”。COMPLETED 不能在产品体验中被误读为所有业务分量均成功。本轮确认代码存在这些独立事实，未对每一种失败组合重新做页面验收。

### 7.3 上下文策略已有明显进展

相较仅依赖最近聊天窗口，V1.5 已具备长期目标与决定、pending 用户输入、固定来源、按任务选择文档、实际覆盖标识和私有依据分离。编译器对必要内容与可选历史／背景作不同处理，预算不足时不能静默删除必要正文。

还需要验证的是长期使用效果：几十轮纠正之后是否仍保留最终决定；多个文档的相同段落是否被误认为同一依据；多次拒绝出稿后是否重复劝生成；来源变化是否被用户理解。结构检查能排除一部分错误，不能独立证明这些语义效果。

### 7.4 真实调用历史应按原范围解释

10 月 24 日资源 v15 历史记录：整批 29 次计数、25 次 Chat，实际总量 265,615 Token；26 个 EV 中，22 个正常返回通过程序校验，2 个真实输出截断没有半写正文，2 个必要全文超预算没有发送 Chat；6 个候选后处理检查通过。

这是重要证据，但不能描述为“26 个任务全部成功”：其中安全拒绝和截断分别证明了边界，用户任务不一定完成。原始失败也不能因后续修复或新批次成功而删除。

出处：[v15 汇总](../../verification/v1.5/live-verification-v15-once-2026-10-24.md)、[人工语义入口](../../verification/v1.5/manual-semantic-review-v15-2026-10-24.md)。本轮没有新增供应方调用。

### 7.5 长文档输出能力存在已知产品限制

长规格样本已经出现真实截断，程序不半写是正确行为，但不等于完整出稿能力满足需求。输出上限 8192 与完整规格模板的组合，应该作为后续设计要明确处理的容量问题。

建议先测量用户实际需要的文档规模，再决定是否采用分阶段出稿、按章节明确授权等方案。不得直接提高预算、自动续写、追加隐藏调用或把失败改成成功；这些均涉及新业务与成本决策。

## 8. 前端可靠性、性能与易用性

### 8.1 已有改进与价值

最近的独立进展页签、修改建议页签、文档记录收纳、评论定位与处理范围分离、批量接受建议，以及发送快捷键统一，整体上减少了对话内部嵌套和重复信息。

前端已有不可变请求快照、原请求恢复、迟到响应隔离、详情内在途 GET 合并、写入前后屏障、输入法守卫、本地草稿、离开保护及减少动态效果支持。它并非只做视觉美化。

历史请求同步专项在固定隔离场景三轮 API 由 82 次降至 42 次，解码响应字节由 101,678 降至 48,748。该结果支持“减少无关读取”，不支持“真实模型速度提升”或“所有场景固定节省相同比例”。

### 8.2 主入口加载成本已经有实测信号

本轮临时生产构建成功，主入口 `index-*.js` 约 2,475.73 kB，gzip 742.35 kB，并出现构建工具的大块提醒。

[main.tsx](../../../frontend/src/main.tsx) 顶层导入 Crepe，并在挂载 Application 前创建隐藏解析器。这是为了正文校验，不能简单删除；但它也意味着工作台首次可见前需要完成编辑器相关初始化。

建议测量工作台冷启动、首次开文档、长文档解析的可见时间和主线程占用，再判断能否延迟加载编辑器及高亮资源、先显示外壳，或拆分不依赖编辑上下文的读取能力。仅调高 chunk 警告阈值不会改善体验。当前没有浏览器冷启动数据，不能把包体积直接换算为用户等待秒数。

### 8.3 请求长期不返回的恢复风险

当前 ApiClient 将 fetch 交给调用方 signal，没有统一应用级截止时间；DetailReadScope.afterWrites 等待在途写请求结束，GuideRunPolling 也等待当前读取完成后才安排下一轮。

因此，当服务接受连接但响应长期不结束时，存在提交状态、共享读取或观察轮询长时间等待的结构性风险。本轮没有复现真实网络挂起，不将其列为已发生故障。

建议用受控不结束响应验证：等待多久出现可理解提示；能否取消观察；写入是否保持原请求 UNKNOWN；核实动作是否仍可达。对写请求增加超时时，必须保留原幂等键，不能自动重新创建任务。超时不等于服务端未提交。

### 8.4 易用性不能只由组件存在推断

| 用户任务 | 当前有利设计 | 重点观察问题 |
| --- | --- | --- |
| 从一句想法开始 | 零文档讨论、空工作区 | 用户能否直接开始，而非先理解六种操作 |
| 理解 AI 下一步建议 | 进展与主题、推荐 | 是否能迅速看到当前重点和下一步 |
| 生成第一份文档 | 显式操作、直接保存 | 文档名称／类型／结构选项是否造成阻力 |
| 阅读 A、修改 B | 阅读与目标独立、差异提醒 | 用户能否准确复述将修改哪个文档与版本 |
| 从评论提出修改 | 定位与范围独立 | 扩大到章节／全文的后果是否明确 |
| 审阅修改建议 | 独立页签、单项与批量决定 | 是否理解“接受全部”与“应用批次”的区别 |
| 修改后确认版本 | Revision 确认 | 是否误以为需求完成意味着文档已确认 |
| 网络异常后继续 | UNKNOWN 原请求核实 | 是否知道该等待、重读还是发起新操作 |
| 查询历史 | 更多操作下文档记录 | 入口精简后，恢复功能是否仍容易找到 |

建议用真实用户任务记录完成率、误操作、求助次数和恢复成功率。不要以按钮数量少、布局截图整齐或前端测试全通过代替易用性结论。

### 8.5 输入法与无障碍边界

当前快捷键为 Enter 发送，Ctrl／⌘+Enter 换行，保留 IME／229／重复按键保护；本轮自动化检查通过。但既有记录明确合成 IME 不等于 Windows 原生输入法，Meta 事件不等于 macOS 验收。

后续宜覆盖真实中文输入法确认、键盘全流程、放大显示、窄窗口、焦点返回及屏幕阅读器关键反馈。它们是体验证据缺口，不应冒称已发现不可访问缺陷。

## 9. 安全、隐私与部署范围

当前正式范围为本机单用户，后端及 Vite 默认绑定 127.0.0.1，没有多用户账号系统。这与当前目标一致，不能把缺少账号直接判为当前产品缺陷。

积极方面包括：JSON 类型和字段严格解析、8MiB 请求容量控制、参数化 SQL、固定资源与模型配置、凭据从快照和错误中剔除、真实输出与业务应用分离、用量缺失不伪填零，以及后台定期清理部分原始审计。

需要保留的边界：

- 本轮查看的服务入口未见 Host／Origin 白名单或登录认证。若未来开放局域网、反向代理或多用户，现有本机信任边界不能直接沿用。
- 不能仅因未配置 CORS 就宣称接口已抵御所有跨站或本机来源访问；本轮没有进行相关攻击验证。
- 业务正文存在浏览器恢复存储与本地数据库，应在备份、共享电脑使用和删除策略中统一说明。
- 审计保护需要同时兼顾敏感内容、保存期限和准入证据依赖，不能只删除大文件以缩减目录。
- 没有运行依赖漏洞扫描，不提供“依赖无漏洞”或“系统安全认证通过”的结论。

## 10. 文档质量与可接续性

### 10.1 文档基础较完整

正式设计分工清晰；前后端只有两份现行规格；决策、迭代、合并和检查资料按类型／版本组织；保留了失败、调用次数和未覆盖项。很多项目缺少的边界说明，本项目已经建立。

本轮抽查范围为根 README、docs README 及类型根下 v1.5 目录 Markdown，共 122 份，识别到 509 个普通本地 Markdown 文件链接，目标均存在。该检查不校验标题锚点、语义时效、远程 URL，也不覆盖全部历史归档格式。

### 10.2 当前状态被历史增量淹没

问题不是“没有记录”，而是当前结论需要跨多个段落人工归并。

- 根 README 同时出现 V1.5 实施、V1.0 收口、项目从零实施、旧 schema4 和旧默认库说明。
- 需求映射顶部已有 v15 与近期专项结果，后面仍有“当前 v14”“默认 v12”“待真实 EV”等旧阶段描述。
- 10 月 23 日验收矩阵保留当时 EV 未执行状态，后续真实证据在其他文件，缺少逐项最新汇总。
- 运行说明保留多组历史 PID、不同 UI 入口及“服务已运行”字样，现场需要重新确认。

这些历史事实不应删除或重写成成功，但应移入清楚的历史区域；当前区只保留一份有效状态。否则后续模型和维护者很容易恢复旧方案、重复检查，或误读完成范围。

## 13. 下一阶段建议与实施顺序

### 第一批：整理现行事实，完成低风险质量收口

输入为当前设计、映射、验收矩阵及已有记录。整理唯一当前状态表，修正文档元数据与运行入口；保留历史原结果；明确工作区与提交版本差异。交付是无需阅读流水账即可接续的实施状态。

这批不需要新增模型调用，不需要改变用户正文，也不需要新建业务架构。

### 第二批：补齐已有结果的产品判断

使用现有真实样本和来源，逐项审阅讨论理解、纠正生效、拒绝出稿、来源真实性、范围遵守、保存表述及分析覆盖。区分程序通过、语义通过、任务未完成和不适用。

发现问题后先确定是产品设计、上下文选材、模型表达还是程序误拒绝，再决定修复。不要在没有诊断时直接改提示词或扩大调用次数。

### 第三批：可靠性与恢复

用独立数据库和受控传输覆盖：响应永久挂起、提交回执丢失、并发编辑冲突、取消与迟到返回、浏览器关闭后的草稿恢复、备份及新位置恢复。每个场景都检查最终业务事实，不能只检查页面提示。

优先复用现有测试和恢复机制，避免新增第二套重试或任务状态系统。

### 第四批：性能和真实任务体验

先测量，后优化。工作台初次可见、首次文档可编辑、长文档滚动与输入、讨论完成可见时间分别测量。通过任务观察确认六种操作、阅读／目标区分和候选应用是否容易理解。

保持现有轮询决策；未有测量证明时，不以 SSE、WebSocket 或重写状态管理作为默认解决方案。

### 第五批：进入下一版本需求整理

把长规格完整输出、跨文档协作效率、长期决定管理等目标转化为可验收的行为与边界。每个新需求应包含用户收益、授权动作、失败结果、容量范围、恢复方式和验证方法。

本报告建议不自动构成这些新需求的批准，也不启动实施。
