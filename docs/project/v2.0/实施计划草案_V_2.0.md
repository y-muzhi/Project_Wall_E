# WALL-E V2.0 版本范围与实施批次草案

日期：2026-10-31。状态：DRAFT。

本草案依据[《WALL-E V2.0 对话设计结论汇总》](../../../downloads/WALL-E-design.md)及2026-10-31讨论整理，目的仅为划分版本范围、实施依赖和完成条件。它不是正式前后端规格，不替代V1.5现行设计，也不表示代码实施、产品验证或真实模型调用已经获得授权。

## 1. 划分结论

后续工作分为两个部分：

| 部分 | 批次 | 定位 | 是否属于V2.0必须完成的范围 |
| --- | --- | --- | --- |
| 第一部分：V2.0必须完成 | V2-B1 单任务执行闭环 | 建立可控制、可观察的单任务编码流程 | 是 |
| 第一部分：V2.0必须完成 | V2-B2 候选、检查与人工接收 | 确保验收对象固定、检查证据真实 | 是 |
| 第一部分：V2.0必须完成 | V2-B3 实际交付与前后端协作 | 完成从固定设计到目标代码交付的主流程 | 是 |
| 第二部分：后续版本可选规划 | F1 恢复与预算加固 | 提高异常恢复和费用控制的自动化程度 | 否 |
| 第二部分：后续版本可选规划 | F2 选择性撤回及扩展 | 处理撤回、继承和未来并行等复杂能力 | 否 |

V2.0的基本目标是：**让一个固定版本的文档任务，在独立工作区中受控执行、停止、检查，并由用户接收后完成一次真实交付。**

前三批全部完成并取得相应证据，才可考虑V2.0收口。后两批是否实施，由后续版本单独评估；它们不是V2.0的隐藏验收项，也不因列入本草案而成为已决定建设的功能。

## 2. 共同原则与前置验证

### 2.1 已明确且持续适用的约束

1. 使用OpenCode作为编码执行器，沿用项目已接入的国内模型渠道，不重新选型。
2. 执行器读取完整固定设计和实际代码，沿用原文结构，不重新进行语义拆分，不让程序判断任意自由文本的业务含义。
3. 文档工作区与代码工作区分开；任务固定设计Revision，文档后续保存新版本不自动改变原任务。
4. 本期同一主文档最多一个活动代码任务；历史任务保留，终态不复活。
5. 代码、修复、联调和代码冲突处理由AI完成，用户不手工修改代码；文档侧已有人工编辑能力不变。
6. 需求和设计变更经过文档；缺陷修复保留缺陷型记录。
7. 模型说完成、会话空闲或进程退出0不等于业务完成；终止、接收、交付和撤回是不同事实。
8. 复用V1.5已有Revision、模型配置、调用记录、幂等、版本和API基础，不另建同职责的平行系统。

### 2.2 前置技术验证

前置验证是V2-B1的输入，不另立产品批次，也不改变“前三批必须、后两批可选”的划分。

在进入完整实施前，应在隔离环境中核对：

| 验证主题 | 需要确认的事实 | 对设计的影响 |
| --- | --- | --- |
| OpenCode协议 | 锁定版本的实例、会话、消息、问题、权限、事件和中止接口行为 | 决定适配层及稳定关联方式 |
| 消息结果核对 | 超时、回执丢失和服务重启后能否查询原会话及原消息 | 不能证明时保留等待，不自动补发 |
| 模型入口 | 主请求、辅助请求及内部重试是否可见、可归属、可记录用量 | 决定V2.0实际可承诺的预算控制范围 |
| Windows停止 | 受管实例、Shell、子进程和本地服务的归属与停止效果 | 不能确认停止时不得释放工作区写入权 |
| 配置与恢复 | 实际生效配置、会话持久化位置及重启后可核对程度 | 决定V2.0支持的恢复边界 |

模拟服务可以验证失败、超时和丢回执等协议行为，但不能证明真实供应方兼容、计费或长任务效果。真实模型调用另需明确授权、次数和预算；未执行的项目必须标为未验证。

关键技术假设不成立时，应记录实际限制并提交范围或方案调整，不能悄悄把前三批中的必要能力移到后续版本。

## 3. 第一部分：V2.0必须完成

### 3.1 V2-B1 单任务执行闭环

**目标**

建立单个代码任务从创建到执行、问题处理、观察和完整停止的基本流程。

**输入与依赖**

- V1.5现有文档、Revision、模型配置、调用记录、幂等和HTTP基础。
- 第2.2节所列关键技术验证结论。
- 已明确的固定设计、代码起点、工作区、执行配置、授权和基础预算规则。

**必须实现**

1. 创建任务时固定主文档Revision、关联材料、仓库、代码起点和预期交付分支。
2. 服务端以事务和幂等保护创建动作；同一主文档最多一个活动任务，重复创建不产生第二份任务。
3. 按原任务准备独立工作区和受管OpenCode实例；准备失败保留原任务并进入等待，不另建替代任务。
4. 开始执行前核对任务身份、状态版本、固定依据、授权和预算；本地接受动作与OpenCode实际接收分开记录。
5. 创建会话、投递消息、查询状态和保存实际执行记录；结果未知时核对原操作，不按文本相同去重或换键盲目重发。
6. 普通问题保存原文、选项及任务／会话／问题身份，由用户明确处理；可引用固定依据或按现有依据继续，新规则仍须经过文档。
7. 所有实际模型请求关联真实任务，保存可见用量和费用事实；未知费用不按零处理。终止或额度条件不允许时阻止新增调用。
8. 终止先持久化停止意图并阻止新执行，再核对受管会话、工具、子进程及本地服务；未确认停止时保持终止中。
9. 提供最小可用的任务列表和任务工作区，展示固定依据、真实状态、等待事项、执行记录、预算摘要和最后核对时间。
10. 刷新、查询、切页和重连只读取现场，不隐式发起模型、重试、恢复或取消任务。

**本批不包含**

- 通用自动中断恢复和会话重建。
- 完整的选择性撤回。
- 同文档多活动任务并行。
- 面向所有环境的强隔离承诺。

**完成条件**

- 在隔离测试项目中真实走通“创建—准备—开始—执行—提问—答复—继续—终止”。
- 重复创建、重复开始和终止中的重复操作不产生第二份有效任务或第二套执行。
- 消息超时、查询失败和服务不可达时，页面不会把未知结果显示为成功或明确未执行。
- 在V2.0声明支持的运行环境中，停止证据能够覆盖受管子进程；无法确认时不会错误显示已终止。
- 静态核对、离线专项、协议验证及实际环境证据分别记录，不相互替代。

### 3.2 V2-B2 候选、检查与人工接收

**目标**

确保检查和用户接收都指向同一个固定代码候选，避免“检查时一份代码、交付时另一份代码”。

**输入与依赖**

- V2-B1的任务、工作区、会话、操作和停止机制。
- 已采用的检查入口、配置版本、必要环境和结果证据位置。
- 原固定设计中的验收依据。

**必须实现**

1. 执行器空闲或报告完成后，先核对待答问题、权限、工具和写入活动，再固定候选。
2. 候选保存代码起点、实际差异和可恢复快照，覆盖未提交及未跟踪的实现文件，排除凭据、临时数据库和日志。
3. 检查绑定候选、检查项、配置版本、环境和实际结果；通过、失败、无法执行、中断／未知分别记录。
4. 必检项由已采用配置决定，执行器不能删除、降低或改写独立验收依据来制造通过结果。
5. 待交付源码变化后形成新候选；旧候选的检查及人工接收不自动适用于新候选。
6. 检查配置、命令或相关环境变化时，重新判断受影响结果是否仍有效；模型说明不能替代必要检查。
7. 接收页展示固定设计、当前文档版本差异、最终候选、相对目标差异、已做／失败／未做检查和未解决问题。
8. 用户接收具体候选；服务端再次核对任务、候选、检查、目标和状态版本。人工接收只表示接受该候选，不提前声明交付成功。
9. 用户可以登记缺陷并明确继续修复；修复形成新候选并重新执行受影响检查，缺陷型文档记录保留。

**本批不包含**

- 由程序从自由文本自动生成语义验收标准。
- 以历史测试通过替代本次候选检查。
- 多任务并行交付协调。
- 已交付代码的选择性撤回。

**完成条件**

- 候选、检查结果、人工接收三者能够通过固定身份相互核对。
- 候选变化、检查配置变化和目标变化不会被旧页面或旧回执掩盖。
- 检查失败、无法执行和未知结果不会进入待接收。
- 无代码变化或仅有原测试通过时，不会宣称新需求已经实现。
- 至少一个隔离候选完成真实检查和人工接收路径，证据明确对应该候选。

### 3.3 V2-B3 实际交付与前后端协作

**目标**

完成V2.0主流程：后端、前端和联调按真实依赖推进，用户接收的具体候选最终进入预期目标，并能核对Git与数据库结果。

**输入与依赖**

- V2-B2的固定候选、检查、人工接收及缺陷修复流程。
- 实际前后端设计、共同HTTP契约和项目运行／检查入口。
- 目标仓库、分支、预期目标提交及交付授权。

**必须实现**

1. 后端、前端和必要的联调使用不同角色会话，按依赖顺序在同一任务工作区写入，不拆成多个并行业务任务。
2. 后端读取后端设计及相关约束；前端读取前端设计、共同契约和实际后端代码；联调按原设计核对完整调用链。
3. 角色交接核对问题、权限、工具写入、阶段检查和代码现场；模型自报进度或百分比不能触发交接。
4. 全部角色会话共用任务预算，交接不替换固定设计，不生成第二份权威接口说明。
5. 交付前保存任务、候选、人工接收、目标、预期旧提交和计划交付内容。
6. 写入目标时再次核对预期旧值；目标已经变化则停止旧交付计划并重新准备，不强制覆盖。
7. Git执行与数据库记录分步对账；Git成功但写库失败时核对补记，不重复合入。
8. 交付结果不明时保留原操作身份并核对，不把HTTP失败或进程中断直接当成未交付。
9. 停止意图与交付竞态按真实事实记录：已交付代码不得被隐藏，终止不自动触发整仓回滚。
10. 用户接收且实际交付确认成功后，任务才进入已完成；完成不自动包含推送、部署或用户服务更新。

**本批不包含**

- 同目标多任务自动并行合并。
- 复杂继承关系下的选择性撤回。
- 所有崩溃点均能无人值守自动续跑。
- 自动推送、部署或更新用户运行服务。

**完成条件**

- 一个隔离的前后端任务按“后端—前端—联调”顺序完成真实交接。
- 用户接收的候选与实际交付内容一致，目标前后提交和数据库记录可回查。
- 目标分支被外部推进、Git成功写库失败及交付结果未知等场景按设计进入重新准备、补记或等待。
- 至少一个真实任务完成从固定设计到目标代码交付的端到端证据；未获授权的真实模型或用户服务操作不得为了验收擅自执行。

## 4. 第二部分：后续版本可选规划

本部分只保留可能的发展方向。它们可能进入后续版本，也可能经评估后不实施；不应在V2.0验收时作为缺口提出。

### 4.1 F1 恢复与预算加固

**可能目标**

在V2.0基本任务归属、未知结果保护和停止机制之上，提高自动化恢复能力及费用控制的完整性。

**候选范围**

1. 服务或机器重启后的自动现场核对和原会话接管。
2. 会话丢失且旧执行确认停止后的受限会话重建。
3. 更多外部执行中断点的自动恢复，以及无法恢复时的明确降级路径。
4. 主模型、辅助模型、压缩、标题和内部重试的统一可见性与精确归属。
5. 更完整的预算预留、可证明上界、迟到用量、价格精度和对账机制。
6. 更广泛的Windows进程、目录和网络防护验证。

**启动前需要重新评估**

- OpenCode及模型渠道实际能够提供多少稳定关联和用量证据。
- 自动恢复失败时是否比保留等待更危险。
- 硬预算的收益是否值得相应的适配和运行限制。
- 是否需要调整产品承诺，而不是只靠增加程序复杂度。

**明确边界**

F1不是V2.0默认验收范围。V2.0仍必须具备基本的未知结果保护、任务费用归属和安全停止；F1只承接更高程度的自动化和完整性，不用于抽空V2.0必要能力。

### 4.2 F2 选择性撤回及扩展

**可能目标**

在代码已经交付、被继承或被后续修改的情况下，提供有限、可核对的撤回能力，并评估未来并行任务。

**候选范围**

1. 已终止任务的候选或已交付改动撤回。
2. 撤回候选准备、差异展示、检查、用户确认和预期目标保护。
3. 任务来源、代码继承和实际交付关系展示。
4. 文本冲突、已知依赖和无法归属变化的处理。
5. 已完成任务是否允许撤回及其权限边界。
6. 同一文档多个活动任务、独立工作区和目标分支交付协调。

**启动前需要重新评估**

- 是否确有足够频繁的用户场景支持选择性撤回的复杂度。
- Git无文本冲突但存在业务依赖时，产品应提供多少提示和限制。
- 已被后继任务改写或组合交付的代码是否允许自动处理。
- 多任务并行带来的隔离、预算、资源和交付收益是否成立。

**明确边界**

F2不承诺普遍、安全、全自动的语义撤回，也不承诺通过修改一个并发上限开放多任务。若未来不启动本批，不影响V2.0已经完成的执行、验收和交付能力。

## 5. 实施顺序与范围变更

1. 顺序为：前置技术验证 → V2-B1 → V2-B2 → V2-B3 → V2.0收口评估。
2. 每批按真实依赖细分功能单元，打通实际调用路径；不以空实现、固定返回、演示数据或未接入页面代替完成。
3. 每批完成后同步正式前后端设计、需求实现映射、实现进度和验证记录，再进入下一批。
4. V2.0实施启动后，另行建立现行实施计划、唯一当前断点和需求实现映射；本草案本身不记录实时进度。
5. 前三批属于V2.0必要范围，不能因实现困难未经用户决定就转入后两批。关键技术假设不成立时，必须明确报告差异及可选处理。
6. 后两批只有在用户明确启动相应版本规划时才转为实施范围；列入本草案不等于排期、承诺或授权。
7. V2.0收口只核对前三批及共同约束。后两批未实施不记为V2.0缺陷或延期项。
8. 提交、推送、部署、用户服务更新和真实付费调用继续按每次任务授权执行，不因本草案自动获得许可。

## 6. 文档落地边界

本草案是版本范围和实施顺序的讨论稿，不是第三份共同业务规格。

后续若用户认可，应将需要实施的规则分别写入V2.0正式后端和前端设计：后端承载对象、状态、事务、OpenCode适配、费用、Git和HTTP契约；前端承载任务列表、任务工作区、问题处理、候选验收和交付交互。正式规格与本草案的范围结论保持一致，历史汇总和可选规划不复制为多份权威定义。
