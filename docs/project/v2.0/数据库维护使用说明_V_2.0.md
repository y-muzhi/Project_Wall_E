# WALL-E V2.0数据库维护使用说明

本文件说明已实现的离线维护入口。V2整体仍在实施；正常业务库操作及维护窗口需要当前具体授权。工具不停止／启动服务，不调用模型／计数，不自动清理恢复资产。先完成实施及验收，再安排正常数据维护。

## 工具入口

从项目根目录执行：
```powershell
.venv/Scripts/python.exe -B -X utf8 tools/python-v20.py --probe
.venv/Scripts/python.exe -B -X utf8 tools/python-v20.py tools/db-v20.py --help
```

固定项目SQLite，绝不使用系统sqlite3替代。所有数据库及包路径显式绝对；无自动选择业务库。正常启动要求已存在200；151要显式维护，缺失库要单独初始化，不能靠启动应用初始化。

## 原库升级顺序

1. 获准维护后停止接单、核对并停止所属活动、关闭后端及外部SQLite编辑工具，保留原数据库、WAL、审计和配置。取得真实原ProcessLock才可继续。
2. plan传入原数据库绝对路径、全新私有包绝对路径、--maintenance-window-confirmed，另以重复--config-reference声明实际外部配置路径，或明确--no-config-references。工具生成原upgrade_id／plan_sha256；只打印身份摘要，私有包中保留完整计划、typed旧值摘要、实际备份、原审计字节副本与登记引用。配置只保存路径／摘要，不复制正文。
3. rehearse传入同原路径／包／窗口、原--upgrade-id及--plan-sha256；从备份生成独立副本，成功核验后封存演练。失败保留副本；再次显式演练用新文件，不覆盖旧副本。
4. apply使用同参数，重验原计划／备份／演练／来源后仅在原文件内单事务提交。源变或证据不足必须重新准备明确新计划，不能临时补拷、编辑计划或覆盖备份。
5. check核对同原计划下持久事实；独立check-v20只需--database，检查当前200结构／历史／完整性／外键，不操作业务内容。核对完成后的服务启用是另一步实际操作，不由工具自动执行。

所有后续维护动作同时要求原upgrade_id与原计划摘要，不推断“最新包”。程序／发布源码变化使旧计划不可用，不能通过修改计划摘要绕过；需要保留并核对原发布与维护程序。

## 结果与中断

- PLAN_READY：计划封存完成，还未升级。
- PASSED：独立副本演练证据完成，还未操作原库。
- UPGRADED：本次原文件已提交并读回核验。
- ALREADY_COMMITTED：原marker证明此前同身份已提交；不再DDL。retained_data_matches为false／CURRENT_DATA_CHANGED可表示升级后的合法业务变化，历史事实与当前健康分开。
- NOT_APPLIED：当前原151仍与原计划一致。后续执行必须是新的明确维护动作，不自动重试。
- PENDING_RECONCILIATION／UNKNOWN／BLOCKED：保留原库、WAL、包及所有证据；用同身份recover核对，不自动apply、降级、旧备份覆盖或启动服务。提交已完成但外部回执失败只补原结果，不重新执行迁移。

元数据和数据库不组成单一事务；退出码、超时、文件存在不能单独证明提交。正常业务写入后的200禁止直接覆盖为151。

## 独立初始化与资源

init-v20要求明确--database、全新--package及维护窗口确认。仅目标不存在／真正空库可创建200，已有151／未知对象／非空无元数据一律拒绝。check-v20可单独只读核验当前200。

Schema实际发布目录在backend/app/infrastructure/schemas/v2_0/；schema_v20_admission.py绑定真实release／manifest摘要。维护资产中的正常备份／审计副本／演练库无自动过期／覆盖／GC，不能作为测试垃圾删除。资源变更通过tools/schema-v20-release.py的全新release-id发布，不修改旧发布字节；源码／SQL／运行包摘要不符将拒绝。
