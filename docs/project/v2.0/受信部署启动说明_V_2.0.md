# V2.0受信部署启动说明

更新：2026-11-14。本文说明本轮已实现的源码入口和资源契约，不是可执行资源发布单，也不表示当前机器已安装SYSTEM Guard或Coding／Testing已可执行。当前业务Schema为200、固定SQLite3.54.1；资源pin为db20-r49。普通后端启动不会初始化或升级数据库。

## 后端入口与默认行为

普通入口仍为项目虚拟环境的python -B -m backend.app，原HTTP地址127.0.0.1:8000、单worker、无reload。WALLE_DATABASE_PATH与WALLE_FRONTEND_DIST沿原服务约定；启动前数据库必须已经按独立授权完成初始化／升级。本轮没有启停用户服务或维护现有数据库。

| 输入 | 用途 |
| --- | --- |
| WALLE_CODE_DEPLOYMENT_MANIFEST | 操作者明确指定已存在的本机绝对NTFS部署文件 |
| WALLE_CODE_DEPLOYMENT_SHA256 | 对该文件实际原始字节的固定SHA256，小写64位，不能全0 |
| 原WALLE_MODEL_*环境 | 仅明确配置models时复用既有固定Profile及后端API key来源；密钥不进入部署文件 |

部署两项均未提供时保持原文档／只读历史能力，代码执行未部署；不会搜索个人目录或猜测配置。只提供一项、空值、源摘要／严格结构／当前普通用户身份不符时，在create_app／打开业务库前拒绝。配置源、Guard镜像及相关资源固定到本进程生命周期；更换配置不热换在途任务，不自动重启服务。

schema1／DEPLOY20-BACKEND-1包含schema_version、protocol_version、registration、task。schema2／DEPLOY20-BACKEND-2保留四项并要求checks，可明确附models；checks／models为null表示未部署该组，省略models也相同。未知字段拒绝。registration的SID必须为实际当前非提升／非AppContainer操作者，不能填SYSTEM冒充后端。

任何FileIdentity都必须是实际原对象：canonical_path、本机NTFS、16位volume_serial、32位file_id及真实is_directory。不能编造ID、复制显示路径或把ready=true当原生证据。具体严格字段和类型以[部署迭代](../../iterations/pending/v2.0/WALL-E.受信本地部署组装与正常启动迭代V1_V_2.0.md)及实际decoder为准。

TASK预核使用原固定官方ZIP摘要、SDK blob和完整离线闭包，不执行程序或下载依赖。configuration_sha256绑定原运行时config/providers脱敏组，不能填opencode.json文件摘要。安装对象的agent规则初始deny-all，实际会话按原任务授权编译。

独立Testing检查可以没有Coding TASK或模型。SERVICE只能属TESTING；浏览器必须引用两个不同的原SERVICE、端点及清晰的前后端关联。后端不读取Guard的SYSTEM私有准入目录；Guard负责核实其原资源／OS证据。CasePack仍在后端按实际只读闭包／固定范围核验，不能含任意脚本或URL。

models不接收供应方地址、密钥、任意环境键名或价格文本，不升级Profile。model_snapshot_sha256为原ModelProfile.snapshot经shared.canonical_input的UTF-8字节（不加LF）摘要。源元数据不能代替真实供应方上界／Usage／账户价格证据；实际发送仍核对原目录ready、授权、来源、窗口、价格行及预算。当前没有取得正式模型准入，不把测试夹具中的数值用作真实配置。

## Guard独立入口

独立模块backend.runtime_guard只支持SCM OWN_PROCESS服务宿主，不提供普通用户控制台降级。分发入口为专用walle-runtime-guard.exe，必须显式提供--program-sha256、--installation-ref、--manifest、--sha256；前者固定本程序完整guard-program.v1.json原字节，后两者固定部署文件。由installation_ref派生固定WALLE.RuntimeGuard.<installation_ref>服务名，并与持有配置重新核对。普通Python不能替代专用冻结程序，不是浏览器或RPC安装接口。

schema1／DEPLOY20-GUARD-1含原后台程序包、journal及TASK完整组。schema2／DEPLOY20-GUARD-2要求独立runtime(source_parent／runtime_base／runtime_root)、checks，TASK若存在仅提供program／network并引用同一runtime。该拆分让独立CHECK_DRIVER不依赖OpenCode。

ServiceMain先核对实际SYSTEM身份，再固定配置／受保护后台程序manifest／已有目录及实际部署证据，最后创建原journal和首管道，完成后才报告RUNNING。没有新建／修ACL／安装WFP／发布资源的隐藏步骤。SCM控制线程只发取消信号，原资源在ServiceMain同一线程收尾。原后端退出只退役旧连接，Guard可继续等待新后端；未知资源不自动重发或重建。

停止先封闭原控制方／nonce，逐项请求已知Job停止、核对原根退出及Job为空，再一次释放句柄。未知关闭报告非零并保留原owner，不重试未知关闭；必要失败退出仅结束自身Guard进程，不把它解释为业务终止或持久网络／profile／目录已经RELEASE。

专用Guard及后台分发准备使用相同完整清单／文件租约算法，政策和唯一入口分开。Guard只携带实际依赖的固定Git完整闭包及内容政策，不带业务SQLite、前端或正常库；后台仍固定SQLite3.54.1。完整包租约保持Guard服务生存期，运行入口核对实际当前镜像。准备产物不是受保护安装；受保护ACL、SYSTEM安装及正式主机证据仍需独立授权和真实核验。

## 只读检查

新增tools/inspect-code-deployment.py，操作者给定--kind backend或guard，以及明确--manifest／--sha256。可先运行该工具的--help查看参数。

backend模式复用正常来源预核，但不create_app、不打开业务库、不连接Guard或调用模型。guard模式只校验原文件及严格结构，不构造GuardDeploymentOwner，不打开journal／首管道，不产生SYSTEM／OS就绪证明。错误只输出固定DEPLOYMENT_SOURCE_REJECTED，不回显正文、环境和秘密。

检查成功、源码已实现、资源已发布、服务已安装、正式OS／供应方准入和产品验收是不同状态。当前缺失资源保持未就绪，delivery_runtime_admitted也不会因填入部署组而自动开启。首次正式部署后仍须按需求映射完成真实前后端联通、独立检查、明确修复、报告接收及Git交付验收。


## CHECK_DRIVER的固定能力与私有GUI

CHECK20的file_entries可登记固定windows-lpac-policy.json，原始字节由runner manifest固定，最大1024字节，结构为schema_version=1和capability_names。只接受空数组、[registryRead]、[registryRead,lpacCom]三种精确顺序；无文件仍零能力。TASK／项目CHECK不读取此政策，部署环境或任意HTTP／旁文件不能声明能力。主／模拟令牌精确核对SID、数量及属性，不授予网络能力或取消All Application Packages退出／Low MIC／目录隔离。

完整固定浏览器当前使用registryRead+lpacCom。CHECK_DRIVER从活的原控制者受控派生独立AuthenticationId，保持同用户／Windows Session、非提升、无新增组／特权；仅允许固定LOCAL／NTLM认证组移除。随机虚构出站凭据不使用真实密码，不建立网络认证。原Guard持有派生来源，根停止和令牌释放后关闭；普通TASK仍以原控制者为来源。

原根在SDK前创建全新私有窗口站／桌面，碰到已有对象拒绝，只授权实际用户和包SID、保持低MIC；只切换自身进程／线程，并恢复／关闭自己持有的对象。无需修改用户桌面、关闭浏览器sandbox或把浏览器改普通账户运行。

非空能力政策要求正式browser-runtime-admission.json的deployment精确lpac_capability_names及lpac_capability_identity_and_denied_boundaries证据；当前正式检查还要求original_controller_private_logon_source、private_gui_namespace_and_owned_cleanup。旧准入／测试角色／协议首帧均不能补齐。生产派生和核验已有原生专项，SYSTEM中的实际派生令牌赋值、正式WFP与双LPAC SERVICE仍未验证，ready=false。

## Guard准备、原字节核验及启动输入

构建专用程序使用项目固定Python通过tools/python-v20.py运行tools/build-windows-guard.py，明确--output <不存在的新绝对目录>和--program-ref <固定规范引用>。与后台共用requirements-build.lock，构建工具只在临时目录安装；实际源副本／完整成员及清单落盘核验失败不发布。新包没有安装副作用，不写用户服务或ProgramData目标。

walle-runtime-guard.exe --verify-runtime实际检查固定Git完整闭包与CONTENT20-SECRETS-1，禁止意外导入业务数据库模块；--verify-package --program-sha256 <明确摘要>核对实际程序完整包。两种模式均不打开服务／业务库／journal。只读包检查还可通过tools/python-v20.py tools/windows_guard_package.py --verify-package <明确包绝对目录> --sha256 <固定摘要>执行，不接受省略摘要或隐式最新包。

准备启动资源使用tools/python-v20.py tools/windows_guard_bootstrap.py，显式提供--guard-package、--guard-sha256、--backend-package、--backend-sha256、--installation-root、--installation-ref及--output。两个源包必须完整且固定，安装和输出各为不存在的绝对新目录，不能彼此或与源包交叠。准备器在当前普通后台身份下生成guard-deployment.json、install-plan.v1.json和README.md，对实际落盘三文件逐项读回核验，再一次发布整个新输出目录；不创建安装目标、不修改ACL／WFP、不安装或启动服务。

计划只提供最小Guard启动：task／runtime／checks均null，不授Coding／Testing执行或模型权限。service.arguments为严格参数数组，service.image_path为SCM单字段命令行，管理员API按原字段使用，不经Shell拼接。实际安装之前重新核对计划、两个源包、新目标、受保护祖先／文件有效权限及SYSTEM私有journal；仅操作本轮明确全新服务，不能整体提升后台。

安装后的原验证必须包括：SCM OWN_PROCESS及精确参数、普通后台能够以最小只读权限持有其原Guard进程并读取SYSTEM主Token／实际镜像、原管道对端身份、原来源派生赋值与完整停止释放。现有其他系统共享服务查询被拒绝不能直接推断本项目Guard不可行，也不能绕过此项原身份核验；没有实际证据则保持未就绪。任何进程／Token权限授予方案需单独明确规则，不自动修改现有SYSTEM Token或服务权限。

资源清单和启动JSON是正常产品输入，保留原字节；实际检查结果仅记版本verification下Markdown。独立迭代仍保留pending，运行说明不合并正式设计、不授予系统安装权限。

 
## 固定安装请求、原普通后台读者与最小系统检查

先用tools/windows_guard_inspection.py显式--prepared／--plan-sha256核对原计划／部署及两完整程序包。--check-parent必须提供活的原普通读者--reader-pid与16位--reader-created-at；只核对原Token的实际祖先有效权限，不创建目标。当前ProgramData祖先含写属性被严格拒绝，采用新的Program Files候选，未改变父权限。

## 已安装原意图与已知未派发接续
