## R72 之后的恢复采用条件

1. 普通应用的新安装描述从 R72 取得同一原操作的目标目录和实际身份，并关联既有固定程序、结构及前端。沿用原控制目录、稳定锁和环境标识。现有安装加载器将数据代次和数据根固定到首次安装，实施时须给获准恢复的独立根加入受信验证。后续同结构发布和代码回退沿用当时活动根。
2. 维持原计划和控制修订，在锁内核对 R72 凭证、新库身份及旧控制。状态须保持 CLOSED，外发继续冻结。持久化原前后元组后才能排他更新当前指针。覆盖发布前崩溃、发布后丢回执、旧计划／错误根、重复尝试和更晚操作。原代次数据与结果保全且仍可核对。
3. 新部署按 RECOVERY_ONLY 装配并验证原结果与未决执行，然后检查真实应用、固定网关及管理原操作。只有经过已确认的开放条件，才允许浏览器按新代次重新握手。ARM64 整体证据和实际服务接入各自登记。

## 管理登记和宿主恢复的接续验收

1. 从原受信安装锁定管理派发，记录已登记进程和环境的实际状态。正常业务可以维持运行，既有维护继续生效。仅在真正的宿主恢复范围内建立独立宿主恢复门槛，按已核验的部署和数据代次逐环境放行。
2. 游离资源与实际控制分别按已登记根和原操作核对。以 R92–R94 的原快照、安装锚和目录为输入，补齐必要计划、历史回执及外部资源证据，再离线生成新登记代次。管理身份保持，管理安装锚和 SQLite 同时证明新代次，业务控制和数据代次维持现场事实。
3. 以 TC201-REL-14 验收旧键只读、新代次写入、旧登记的成功或空闲记录无法释放现有占用，以及宿主恢复门槛阻止旧开放状态自启。固定候选上验证锁、进程和网关，再单独执行异机取回与独立恢复证据。

用户允许隔离服务、浏览器和离线验证。正式用户服务及数据、模型／计数／付费供应方、采购及 Git 提交／推送不在授权内。以 [当前断点](实现进度_V_2.2.md) 接续，以 [需求映射](../../traceability/v2.2/需求实现映射_V_2.2.md) 判定各单元。
