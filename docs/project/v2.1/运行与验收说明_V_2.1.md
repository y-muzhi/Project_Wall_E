## V2.1持续离线入口

当前版本使用tools/check-v21-offline.py；旧check-v15-offline.py及V1.5工作流保留自己的历史范围。

```powershell
.venv/Scripts/python.exe -B tools/check-v21-offline.py --list
.venv/Scripts/python.exe -B tools/check-v21-offline.py --group core
.venv/Scripts/python.exe -B tools/check-v21-offline.py --group standard
```

默认standard为frontend/core/programs/ai；--group load只跑两项长负载，--group all包含全部。每组可独立执行；--list不运行检查。输出在docs/verification/v2.1的唯一Markdown，分组报告不等于整版验收；运行期间源码变化或临时清理失败会使入口不通过。

本轮通过新入口实跑core与frontend，其余组沿各自独立证据，不宣称一次standard/all通过。新V2.1 workflow配置分4组，长负载只在workflow_dispatch明确选择后运行；本轮未推送/触发GitHub检查。该入口不安装本地依赖，不读本地凭据或调用真实供应方。


## 源库复制与恢复入口

固定源为受支持的core/db20-r54（另支持已固定r48），目标为db21-r7。正常库操作前需确认本轮维护窗口、源/目标与在途任务边界。copy保留源只读，目标文件及其私有父目录均须全新，不先创建目标父目录；未知源、已有目标、活动锁/未决执行会被拒绝。

先保存一个唯一upgrade-id，并对copy/inspect使用相同的源、目标、manifest及ID。以下是参数结构；实际绝对数据库路径应在执行该维护任务时明确：

```text
.venv/Scripts/python.exe -B tools/db-v21.py copy
  --source <源数据库绝对路径>
  --target <全新私有父目录内的目标数据库绝对路径>
  --source-manifest <仓库绝对路径>/backend/app/infrastructure/schemas/v2_0/db20-r54/manifest.json
  --target-manifest <仓库绝对路径>/backend/app/infrastructure/schemas/v2_1/db21-r7/manifest.json
  --upgrade-id <本次唯一ID>
  --maintenance-window-confirmed
```

提交结果未知时，保留两端及原Markdown意图/结果记录，以相同参数改用inspect核实。inspect只检查，不重放DDL；复制成功不自动切服务，目标库开始使用后不承诺双向数据回退。实际隔离演练见[复制升级证据](../../verification/v2.1/copy-upgrade-2026-11-16.md)。本轮没有对正常库执行copy。

## 服务启动边界

服务默认Schema200保持；V2.1必须显式选择已有Schema210数据库。配置名为WALLE_DATABASE_PATH（现有绝对数据库路径）、WALLE_FRONTEND_DIST（该工作区构建资源）；密钥只按既有本地凭据机制提供，不写入项目文档。

原生HTTP入口的显式参数为：

```text
.venv/Scripts/python.exe -B -m backend.app --schema-version 210 --port <已确认可用端口>
```

该入口不初始化数据库。当前独立工作区已准备data/service-runtime-v21/ai-startup.py：无参数只读核对Schema/准入，不读密钥或启动；--start先require_live通过再读本地凭据，以原生8001/Schema210运行。已启动的隐藏宿主backend-ai-host.ps1调用该脚本，前端5174代理8001。不要重复启动或用固定8000的历史入口替代本工作区服务配置。
