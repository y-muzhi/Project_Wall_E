### 1.2 目标与范围

| 内容 | 确定定义 |
| --- | --- |
| 系统目标 | 在现有详情页提供多文档阅读、明确工作绑定、AI讨论及人控出稿／同步 |
| 使用者与使用场景 | 本机浏览器单用户，先讨论、阅读文档再反馈或明确修订 |
| 运行与使用范围 | 沿用现有桌面视口保护；1024px以下受限，不新做移动端 |

### 1.3 填写与实施规则

采用[共享模板](../../templates/统一需求规格说明_完整模板_重构版.md)的5.1—5.6逐页／逐组件定义。对象、应用和HTTP字段以后端设计为唯一正式来源，不在页面重新发明业务许可。保存、业务状态和版本确认采用后端第2章已确认规则；AI技术协议见后端AI-RESOURCE，不在前端定义第二套契约。

### 1.4 术语与缩写

| 正式术语 | 缩写或别名 | 本文含义或定义引用 |
| --- | --- | --- |
| 阅读对象 | selectedDocumentId | 页面正在显示的文档，不等于AI写入目标 |
| 工作绑定 | workBinding | 用户明确接受的目标／来源／范围，源自程序事实 |
| 本地草稿 | composerDraft／editorDraft | 对话输入与编辑内容不同键／不同保存事实 |
| 实际结果 | application_result | 程序是否提交，不能从模型回复推断 |
| 业务与接口契约 | 后端设计 | [后端设计文档](WALL-E.后端设计文档_V_1.5.md)第2—4、6、8章 |

### 1.5 稳定引用与实现定位

BND-WORKBENCH／DETAIL为页面，BND-EDITOR／CARDS／SUGGESTIONS／MODEL-CALL等沿用原组件稳定编号；页面内普通列表／标签不是新应用能力。实现定位在各BND及第2章原模块，不能据编号扩建服务。

## 5. 页面与交互

### 5.1 公共视觉与交互规则

**规则：SHR-UI。**

| 规则或资源 | 适用范围 | 确定表现或资源引用 | 允许的页面差异 |
| --- | --- | --- | --- |
| 公共外壳 | 工作台／详情 | 沿用V1.0 UX-031导航品牌、200／64px、跨页偏好及键盘入口 | 业务加载／失败不可改变外壳；详情文档导航与全局导航分开 |
| 控件状态 | 所有可交互项 | 沿用V1.0 BND-SELECT／FILTER／CONFIRM／TOAST／RECORD-LIST的默认、悬停、按下、focus-visible、禁用及处理中；禁用／处理中优先 | 不取消键盘焦点；点击不叠加多层原生套框；非法输入错误有文字 |
| 排版与颜色 | 正文／辅助面板 | 唯一来源为现有shared/styles.css及V1.0已确认规则：白底细边界、蓝主要交互、绿色完成、圆角公共控件 | 不在不同面板各造颜色／尺寸；长表格代码在所属区横向滚动 |
| 加载／空／错误 | 所有区域 | 首屏骨架限所属区域；后台读取保留最近成功内容和输入，失败只显示局部提示 | 不将整页替换成loading；读取失败与空结果分开 |
| 焦点／菜单 | 输入、复合控件、编辑器与弹层 | 父容器绘制统一反馈；内部原生控件无重复边框；Esc关闭不提交，关闭返原入口，已失效则回所属标题 | 菜单属于组件交互区，不能因离开正文DOM提前销毁 |
| 正式文案 | 状态和提示 | 需求状态、讨论阶段、版本确认、运行、应用结果分别命名 | 不展示投影版本或开发者说明；不恢复已删除重复概览 |

沿用现有Ctrl／⌘+Enter发送、全局导航快捷键及焦点样式。状态／文档／操作选择使用公共SingleSelect键盘行为；Esc关闭配置不提交，点击外部按原控件规则处理；危险操作不能因失焦被触发。

抽屉／弹层关闭焦点回到原入口；请求详情关闭回到对应请求记录。消息更新使用适当aria-live提示，不在模型返回时抢输入焦点。图标按钮有中文可访问名称，禁用理由可读，颜色不作为确认／失败的唯一表达。

### BND-DETAIL 需求详情

#### 5.2 页面入口、布局与展示

| 内容 | 确定定义 |
| --- | --- |
| 页面引用与名称 | BND-DETAIL 需求详情 |
| 页面职责 | 多文档阅读／编辑、需求级讨论及真实运行／记录；阅读选择和写目标分开 |
| 入口与进入条件 | 原需求详情路由＋requirement_id；合法零文档；404不虚构CURRENT |
| 视觉与交互依据 | SHR-UI及V1.0 BND-DETAIL／编辑器，布局增量如下 |

```text
全局导航 | 页头：需求标题／人工业务状态／操作
         | 文档导航／大纲 | 文档工作区          | AI对话／评论／文档记录
         | 文档列表       | 名称 类型 Vn 确认态 | 当前阶段／工作绑定
         | 或当前文档大纲 | 正文／历史／编辑    | 消息、选项、出稿建议
         |                |                     | 输入与操作设置
```

新增文档导航放在详情页内部，不改变全局主导航职责。原左侧大纲区改为“文档／大纲”两种视图，共用一个可收起区域，不常驻再加一列。文档列表显示名称、类型、当前版本、确认标记及来源更新提示；归档项在列表末尾折叠。

中部标题栏始终标明当前阅读文档；AI区始终显示实际工作目标。阅读A、操作目标B是合法状态，目标条显示“修订：B · Vn”及定位入口，不能默默切换为A。

沿用现有全局导航200／64px、详情低于1024px的受限支持和视口保护；本版不额外设计移动端。布局按扣除全局导航及边距后的详情可用宽度W计算，不得仅按浏览器宽度固定四栏。

文档导航宽200px，文档正文最小640px，AI面板最小360px、偏好420px，两处间隔各6px。W≥1212px可同时显示三块，AI宽度不超过可用余量并保留原拖动；不足时导航转抽屉。仍不足同时显示正文与AI时用“文档／AI对话”视图切换，输入与消息owner保持，不挤成不可读细列。

文档导航、正文、右侧消息各自滚动；页头和输入区保持可用，不恢复详情最外层冗余滚动条。滚动位置按document_id＋阅读版本缓存；对话保留现有scroll-position机制。切视图、关闭详情、浏览历史不丢输入或取消业务运行。

**操作补充：文档导航与框架创建**

文档列表每行使用真实按钮，单击只切阅读；名称长时省略并提供完整可访问名称。类型和Vn为辅助信息；确认标记按confirmed_revision_id等于当前Revision派生，不用布尔字段猜测。

“新建文档”弹层选择名称、类型及空白／框架，明确无AI生成。提交走新增POST documents，成功选中V1并可人工编辑；不自动开启AI。AI生成入口放对话建议／操作设置，不与空白新建混淆。

切文档时若有人工编辑，先复用prepareLeave自动保存草稿；草稿保存已确认后允许阅读其他文档，编辑会话继续绑定原目标，页头显示“正在编辑：A”。保存未知／失败则保持原编辑器和本地文本，提供继续编辑／明确离开，不能静默卸载。

**操作补充：人工状态与阶段**

页头SingleSelect展示SHR-STATUS五态，选择后带metadata_version直接提交PATCH；状态不变不发请求。全部状态可自由切换，包括运行、编辑或审阅期间改为“已关闭”，不弹出关闭门槛、不自动取消任务，也不因状态禁用其他能力；具体工作仍服从原互斥和版本规则。

AI区顶部以紧凑条显示阶段和当前主题，展开“大纲与进展”才加载完整discussion。内容按主线→主题呈现预期成果、AI结论、来源、未决影响和用户处置；禁止用完成率数字冒充需求完整性。

主题跳转通过SET_FOCUS程序命令，阶段切换通过CHANGE_PHASE或阶段卡片；都不自动发送Chat。允许用户随后发送指令由AI继续推进。阶段收束可显示未决项并由用户明确带入，不要求先全部清零。

**操作补充：讨论、选项及出稿建议**

普通输入默认DISCUSS，操作标签为“讨论”；当前工作条显示阶段、可空目标和参考数量。AI可给推荐和选项，卡片沿用原控件；推荐不得预先冒充正式选择。正式提交后展开可查看原题、用户选择和填写内容。

CLARIFICATION提交返回MODEL时读取新run；返回卡片待答时原run已结束，其他维护动作可用。相同卡片重复点击使用原命令幂等；其他标签页已回答则展示已有正式答案，不再创建新回答。

DOCUMENT_ACTION卡片直接展示拟生成／更新文档、内容范围、来源版本和待定项。主按钮“生成工作稿”／“更新工作稿”，次操作“继续讨论”或“暂不生成”。点击主按钮一次提交responses并接收运行，不再串联另一次生成命令。

AI在可读回复中提到“可以生成”但没有有效结构化建议时，只展示文本；用户仍可通过操作设置明确选择类型／范围发起，不能从普通文本中提取任意目标执行。多个建议并存必须选具体一条。

**操作补充：操作设置与明确绑定**

沿用现有操作设置入口，采用同一弹出面板显示：操作、目标、新文档属性、范围、参考材料。operation标签使用“讨论、生成文档、更新文档、提出修改建议、比较差异、影响复核”，不让用户直接选内部ASK／MODIFY枚举。

GENERATE要求名称／类型，不存在目标document_id；REVISE／PROPOSE_CHANGES要求已有目标及版本、范围；COMPARE／REVIEW要求明确材料。配置只改本地草稿，提交时绑定真实版本；关闭设置不自动调用模型或保存正文。

阅读区选择文本后沿用scope工具，只把真实document_id、content_version、区块／选区加入拟操作配置；选区本身不授予修改，也不自动设置为AI当前目标。确认使用该范围后目标条更新，发送时服务端再校验。

**操作补充：结果定位及读稿反馈**

用户明确生成／更新后，成功直接保存，不出现二次采用步骤；异常保留原文、原正文及真实原因。只有程序返回CREATED／UPDATED的DocumentEffect后，界面才显示“已生成并保存”或实际新版本；模型文字不能代替该事实。

实际新稿保存后刷新摘要；用户仍处空工作区或本次目标工作区时可定位结果。期间用户已主动切到另一稿件则保持阅读位置，提供定位入口，不抢走当前阅读。目标更新只刷新对应摘要／快照，不重置其他文档滚动。

普通读稿反馈继续DISCUSS；明确修订才发对应动作。格式、截断或越界结果显示原文、“未写入文档”和真实原因，保留原输入，不提供绕过验证的强制写入，也不自动重试。

**操作补充：来源同步与候选**

同步面板依附现有操作设置／候选预览，不另开项目管理页面。依次确认来源文档与固定版本、目标、操作方式、作用范围。来源默认推荐已确认Revision；选未确认稿显示“未确认版本”。参考生成新稿采用GENERATE，明确更新已有目标采用REVISE并直接保存；用户选择“查看修改建议”才采用PROPOSE_CHANGES并审阅候选。

来源在建议后更新时显示“来源已有更新”，列出已选版本／当前版本，提供沿用所选版本或重新准备。目标版本变化不能通过“仍然执行”强行跳过；先刷新并复核。操作接受后查看来源更新不改变该run已发内容。

候选沿用现有逐项接受、拒绝、编辑和完成；预览顶部标明目标及基准版本、来源。完成采用只走程序，不再次Chat。用户读A时审阅B的候选，采用按钮仍明确“应用到B”，结果不写A。

评论中的AI入口继续复用POST comments/{id}/guide-runs，标签明确“根据评论提出修改建议”；目标来自评论归属，不来自当前阅读选择。复核结果中的“提出修改建议”复用原guide-runs并引用该run的固定分析。两者成功都进入现有候选预览，不直接覆盖正文，也不增加平行同步接口。

**操作补充：人工编辑、确认、历史及归档**

人工编辑沿用开始、自动保存、完成、取消及本地恢复；页头明确目标。完成产生一次正式版本，取消只丢该会话，不能删当前文档。恢复历史先读取Revision，用户明确进入基于该内容的编辑流程，完成后形成新版本。

确认当前版本；修改成新版本后显示未确认，保留旧版本确认记录，不锁定继续编辑。界面只以真实确认回执展示确认事实；确认、保存和需求状态分开，不因点击按钮即显示成功，不调用模型或重复保存相同正文。

“保存版本”调整为“添加版本说明”，沿原POST revisions标记当前已有快照；成功提示“版本说明已保存”，不能说新生成了Vn+1。后端语义与解码状态200同步。

改名、归档和恢复复用公共表单／确认组件。归档不是删除，阅读可继续，修改与确认禁用；归档期间仍能查看历史及原始来源。活动操作阻止归档，提示处理入口，不静默取消。

正文应用结果独立显示：已保存Vn、无内容变化、未写入、仅生成建议。progress_result拒绝时仍可看到有效正文结果及进度未更新说明；不能给整个消息画一个成功图标误导全部完成。

输入草稿按需求隔离；编辑恢复按requirement_id、target_document_id、draft_id、基准content_version隔离。布局偏好可跨需求，正文草稿不可。旧测试浏览器存储不迁移，新增命名空间或schema版本后忽略不兼容值，不自动读取成新文档内容。

发送后保留被冻结的method、path、body及Idempotency-Key。网络中断先重放／核实原动作，不能刷新目标后拿原键发新内容。正在UNKNOWN的动作不得被新阅读文档替换；明确撤销本地恢复提示也不等于服务端取消运行。

页面实现定位：requirements/{detail-owner,detail-read,document-owner,detail-layout,detail-frame,departure}.ts(x)，guide/{conversation-owner,composer,polling}.ts；改造必有CURRENT构造假设，需求级会话不随阅读切换销毁。
