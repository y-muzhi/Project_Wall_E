## 2. 技术基线与公共规则

### 2.1 责任分工

| 范围 | 前端责任 | 不承担的事实 |
| --- | --- | --- |
| ApplicationRouter／外壳 | 路由、history、离页保护及页头槽 | 不因页面切换停止CodeTask或替文档执行保存 |
| 任务列表owner | 文档归属、筛选、分页、当前列表读取 | 不从某个文档推测唯一任务身份 |
| 任务owner | 一个task_id的TaskView、命令意图及读取屏障 | 不从模型文本生成完成状态 |
| 创建／设置flow | 未提交值、配置选择、明确授权及原请求恢复 | 不把本机草稿当服务端已批准 |
| 代码／检查／交付／用量reader | 按固定ID懒加载，保留最近成功内容 | 不回读可写工作区作为历史代码 |
| 公共组件 | 显示、输入、焦点、动效 | 不自行请求模型、取得执行权或改变业务状态 |

全局“代码开发”固定打开已有/requirements工作台，使用受控history.nav_intent=CHOOSE_CODE_DOCUMENT提示“选择需求和文档以进入代码任务”；不依赖当前／最近文档或任务，不新增汇总代码列表。无上下文时正常工作台数据／筛选／分页及模块空态可用；用户明确打开需求后进入已有/requirements/{requirement_id}，在原文档列表选择“代码任务”，再进入已核实的文档code-tasks路由。已有文档页的直接代码任务入口保持可用。

nav_intent仅为内部history的可选枚举CHOOSE_CODE_DOCUMENT或null，随上述只读选择路径传递；在文档列表入口完成或离开该选择链时清除。URL不增加任意return_to，直接输入/requirements仍为普通工作台；刷新／后退只恢复读取与选择提示，不猜文档或发写操作。选择历史删除／无权限文档时显示真实失败并保留返回工作台入口。

公共导航增加“代码开发”“测试验收”两个独立入口；Coding原文档入口保留，Testing /testing可直接进入。缓存、请求、草稿、轮询和控制均以(module,id)区分，Coding与Testing同数值ID不共用owner。Testing计划编辑在本模块，Coding自检不能显示为独立测试报告。

### 2.2 SHR-FE20-READ 读取与轮询

请求键为资源种类＋完整所属ID＋规范查询参数＋读取epoch；同owner内相同键仅一个在途GET。复用现有读取共享和独立取消机制，不做全站永久缓存。普通GET失败保留最后成功内容并标记过期；首次无成功内容时显示所属区域错误。任何读取失败、无权限、字段缺失和外部未知均不显示成功空态。

| 触发或区域 | 读取规则 | 不触发的事项 |
| --- | --- | --- |
| 首次进入／返回该路由 | 严格读所属对象；历史选择核对后恢复 | 不START、RESUME、检查或重发POST |
| 可见任务工作区 | 非终态有活动操作或RUNNING／VERIFYING／STOPPING时TaskView每1秒；其他非终态每5秒 | 不按每次TaskView变化重拉全部区域 |
| 终态 | 无未核清调用／交付／活动操作则停止定时；仍有未核清事项每5秒只读摘要 | 不恢复原执行身份 |
| 当前执行页签 | TaskView已确认后每2秒读当前记录页和OPEN问题／权限页；同键不重叠 | 不预取所有记录和原模型请求 |
| 当前检查／交付页签 | 对当前RUNNING或UNKNOWN原记录每2秒读详情；明确结束后停止详情轮询 | 不自动重做检查或Git写入 |
| 当前用量页签 | 活动时每5秒读当前调用页；请求详情只在用户打开时读取 | 不自动读取所有完整模型请求 |
| 任务列表 | 可见且当前页含活动任务时每5秒；无活动任务停止，重新可见时重读一次 | 不逐行展开TaskView |
| 窗口获得焦点／标签页重新可见 | 合并为一次GET同步；同一键已有在途则复用，恢复正常轮询 | 不触发命令 |
| 页签隐藏／离页／标签页隐藏 | 取消所属只读请求与定时；保留输入和原命令句柄 | 不cancel后台业务 |
| resize／缩放／面板开合 | 只调整布局和定位；新区域首次可见才读必要数据 | 不因每个resize事件重读TaskView |
| 读取失败 | 2／5／10／30秒退避，之后30秒；成功恢复原间隔，显式重试可立即一次GET | 不把读重试当模型重试 |

使用浏览器时钟只安排观察，不承诺后台标签页硬实时。相同焦点／visibility事件一轮合并；离页后的迟到响应由task_id＋epoch隔离，不覆盖新任务。TaskView成功但子区域失败时，保留成功摘要，仅标记该区域。


### 2.3 SHR-FE20-ACTION 命令、回执和未知结果

所有V2 Coding／Testing写操作仍复用ApiAction固定method／path／body／Idempotency-Key，expected_state_version来自当前核实任务，重放不改写。普通写命令先按INF-FE20-BROWSER把完整原请求落入IndexedDB并等事务提交；再标记原DISPATCHING后才允许首次发送。未提交的本地记录不作可恢复保证。只有TERMINATE存在下述受限存储故障例外。原键关闭是已保存意图的控制协议，不创建关闭自己的新PendingAction／key；其派发仍须先提交本地关闭状态，见7.4。

| 本地交互状态 | 含义及处理 |
| --- | --- |
| EDITING | 用户尚未提交，允许编辑表单，无后台事实 |
| PERSISTING | 正在冻结并保存原请求，尚不允许HTTP发送；失败保留表单及具体本地原因 |
| SUBMITTING | 原持久DISPATCHING事实已提交，发送原冻结请求；相同意图同步防重入 |
| ACCEPTED | 原202及operation_id已核实并持久关联，仅GET观察，不把接收当完成 |
| CONFIRMED | 原同步成功或原操作真实终局已核实；按7.4原子移入无body终局摘要 |
| UNKNOWN | 超时／断网／解码／存储更新不明，保留原记录，先查询原键／操作 |
| REJECTED | 已核实原REJECTED终局，保留表单；新输入只在该原键终局核清后另明确提交 |

ApiClient沿现有30秒HTTP截止，不限制后台任务总时长。关闭弹层／停止等待只停止本地读取，不取消已接受业务。普通命令IndexedDB未就绪／blocked／quota／超容时不发送，不能偷偷退回内存；设置页和任务页保留表单、显示“命令恢复暂不可用，尚未提交”，提供明确只读重查。草稿／偏好存储失败可以仅提示，不能与命令保存失败混为一种降级。

进入新标签、重开页面、恢复网络或代码设置时，从同origin的待核对记录先读取method／path／key，仅调用原CommandReceiptLookup。FOUND同步成功／REJECTED／CLOSED按原回执核对；202继续原operation；IN_PROGRESS／UNKNOWN／NOT_FOUND都不清理、不中止后台或自动重发，NOT_FOUND不证明不会迟到。没有task_id的任务创建／配置／仓库命令也在全局恢复列表中，不能只依赖任务历史。

用户明确选择“按原请求恢复”时，只有7.4验证完整且recovery_mode=REPLAY_SAME_KEY，才能用原冻结字节／原key重放；不重新prepare生成UUID、不拼当前表单或状态版本。QUERY_ONLY禁止原业务重放，但可查询或明确使用原键关闭协议：Git合作窗口确认不得因持久存储而续期，旧true不能用于新的交付意图；REGISTER_BASE没有来源暂停确认，只可明确按原完整输入／原键恢复。当前后端条件及幂等仍是最终判断；旧实例问题不可转投新会话。

VERSION_CONFLICT及候选／配置／计划冲突保留原请求和当前表单的区别；旧UNKNOWN先核对，不能把新值塞入旧body。已核实拒绝仍须先完成原终局本地保存，后续新提交不覆盖原键证据。

**终止例外：** 恢复存储故障不遮住“终止任务”。用户可明确确认当前task_id后使用原TERMINATE，内存保留本次键并持续GET对应TaskView或TestingTaskView.termination_operation_id／停止阶段；后端按(module,task_id)唯一停止意图天然幂等，新标签按(module,task_id)找到该模块原停止操作，不能只凭相同数字ID查另一模块。新停止仍执行当前版本与可信用户停止权校验，不要求模型／运行资源就绪；STOPPING或终态先返回原事实，不反复新建。该例外不用于预算、配置、答复、捕获、接收或任何其他写动作，不声称内存原键获得跨标签持久性。

### 2.4 SHR-FE20-LIFECYCLE 草稿、焦点与关闭

- 提交前保存本地草稿，提交时固定原动作；成功清理只针对该表单／请求身份，迟到A成功不能清B输入。
- 已接受操作的durable事实由后端保存，离页后无须保持组件挂载来维持业务运行。
- 未提交表单关闭默认保留本标签页草稿；“放弃草稿”是明确本地动作。切换任务不继承上个任务的缺陷、预算或问题答复。
- 确认框初始焦点放取消按钮，表单抽屉放首个可编辑字段或标题；Tab限定当前模态，Esc关闭不提交。busy不能用Esc取消正在提交的命令，但允许显式停止等待并保留UNKNOWN恢复入口。
- 点击内部原生选择器、菜单或引用阅读器仍属于所属交互区域；不能因focus离开原输入DOM就卸载草稿。
- 同时仅一个主模态；从抽屉打开确认时使用同模态内部确认步骤，关闭返原字段。成功导航后不再将焦点拉回已销毁入口；回到现存入口，否则所属页标题。

## 5. 页面与交互

### 5.1 公共视觉、布局及空态

采用V1.5 SHR-UI／SHR-MOTION及现有shared/styles.css、motion.css；全局导航宽度、品牌、页头槽和折叠快捷键保持。新页面内容区使用剩余宽高，业务错误和busy不改变公共导航宽度。

| 项目 | 本期具体规则 |
| --- | --- |
| 内容排版 | 页头仅显示一次任务标题／主状态；固定依据、当前角色和关键动作分区，不堆叠开发者概览 |
| 页面留白 | 新代码页内容外边距24px；1024—1279px为16px。区域间距16px，表单字段间距12px |
| 按钮 | 复用.ui-button、icon-button及公共Confirmation尺寸；普通页内文字按钮最小高度36px，图标32px；工具条flex换行、8px间隔，不用绝对坐标补对齐 |
| 表单 | 可编辑控件与说明同一列；必填错误放字段下；输入法组合期间不触发确认，textarea默认保留Enter换行，只有显式按钮提交 |
| 接收／终止 | 使用原公共确认样式；终止危险色及disabled优先级沿BND-CONFIRM；确认不是业务成功 |
| 状态 | 正在执行、等待处理、正在检查、待接收、正在终止、已完成、已终止分别有文字；颜色为辅助，不以模型“完成”替代 |
| 内容安全 | 代码、日志、错误和原生问题按文本渲染，不执行HTML／脚本／Shell；文档Markdown只用已有安全只读渲染 |
| 分页 | 复用Pagination，20条及越界语义引用后端；筛选后page回1，查询失败不清空旧行 |
| 菜单／弹层 | 沿公共模态注册、焦点和动效；浮层不得覆盖按钮文字或创建额外滚动外壳 |

工作区按扣除全局导航及边距后的可用宽度W布局。任务信息、工具条与页签上方不另嵌一个固定窄容器。执行记录和问题区W≥1104px时双列，问题区360px、间隔16px，记录区最小640px；不足时单列，待处理摘要在前，记录在后。代码文件列表240px、内容最小640px，W不足896px时文件列表转可收起抽屉；前后文本只有内容区≥1120px时并排，各侧至少552px，否则统一差异视图。布局变化不触发业务读取。

页头及页签保留在工作区上方，主体使用剩余高度；执行记录、代码内容、检查列表分别由当前页签主区域滚动；表单抽屉仅中部滚动，页脚按钮保持可见。短窗口或200%缩放时页头工具条流式换行，不能用固定高度裁掉状态／操作。

仅成功读取且确认为空才显示公共EmptyState，图标及单行文案由所属模块必传；无按钮嵌入EmptyState，创建／筛选／重试仍在原工具栏。

来源观察元数据固定于(repository_id,observation_id)，其他标签刷新不替换已选观察或来源commit。选择某分支只把该次观察中的完整OID明确填入commit_oid，之后分支移动不改该字段；直接粘贴commit不要求先有文件观察。目标分支仍按真实观察及交付条件选择，与来源commit分开。观察不可读时保留原选择并提示明确重读，不用latest补历史。

固定起点区域说明：“仅使用所选Git提交；未提交的修改不纳入。登记后会保留此版本，原仓库需保持可读。”没有未跟踪文件选择、来源暂停复选或整包捕获按钮；如需本地改动，提示用户先自行提交后重新选择，不代提交、stash或切分支。选择本身只读；明确REGISTER_BASE创建系统保留引用，不改用户工作目录／索引／分支。源仓库损坏／移走或版本对象不可读显示基线不可用，不从当前HEAD重新登记或悄悄导出备份。

登记只依赖仓库／完整commit及内容／Git校验配置，不依赖模型／执行器ready。未知请求用原PendingAction和完整冻结body核对，允许明确按原key恢复原登记；不会创建新snapshot_id或重放来源true，GET不创建保留引用。已登记基线文件页通过GET /code-snapshots/{snapshot_id}/files只读原提交路径／模式／大小，不列工作目录状态，也没有勾选纳入功能。

批准授权与创建是两个明确动作：授权201只表示批准记录已保存，创建时后端原子绑定。授权已生成而创建失败时保留原授权供同一草稿核对，不重复批准；取消草稿不删除已保存授权。

详情按实际请求、响应、用量／费用分区，技术信息显示protocol_version。capture_status为FULL／REDACTED／INCOMPLETE，分别显示完整记录、已脱敏、记录不完整；脱敏说明不展示秘密，缺响应不伪造空内容。支持原文／格式化、搜索及复制；超大内容只在当前调用显式加载，复制范围明确。尚未结束或响应缺失显示真实状态；不会重新组装上下文、计数或调用模型。关闭详情仅取消读取，重开按同llm_use_id读取；不同task间不得共享未核实缓存。


**特殊交互与生命周期：** 采用SHR-FE20-LIFECYCLE；键盘可见焦点及原生选择器按5.1，弹层Esc／外部点击按2.4关闭本地确认且不提交；busy不能取消已发命令，但可明确停止等待并保留UNKNOWN，焦点返回原触发按钮，失效则本组件首个可用标题。原Unknown动作不销毁／改写body；隐藏只暂停本组件reader，卸载清理监听、定位与迟到回调。不得由销毁触发后台写入。

**视觉依据与变体：** 5.1的可用宽度、双列／单列、按钮流式换行及所属区域滚动；自身不另加公共导航或重复页头。正文若有专属布局采用其明确值。

首期正式测试仅支持预登记参考项目。无同设计参考集时显示“参考测试资产尚未登记，可先保存任务和计划草稿”；计划／资源准备产物不显示可执行，通过真实参考验证并发布包后才允许产品测试。用户不可上传PASS或在候选上生成参考自证；不自动改为诊断运行。

Testing草稿／READY未运行也提供终止，无命令／报告仍可按6.1共享规则完成；不能为满足显示而自动RUN或创建占位命令。

Testing终止严格联合处理：首次及STOPPING为202 TestingReceipt，读取原真实operation；COMPLETED／TERMINATED为200 TASK_ALREADY_ENDED语义的TestingTaskView，termination_operation_id可null，不进入UNKNOWN或等待不存在的停止操作。原CommandReceiptLookup及幂等重放按首次实际HTTP／结构解码，后来状态改变不改原202成200。

**特殊交互与生命周期：** 采用SHR-FE20-LIFECYCLE，未提交输入按实体隔离；IME期间不提交，Esc仅取消本地弹层，busy可停止等待但不取消后台，保留原未知命令；所有弹层／监听随所属owner退役，迟到不串实体。

## 6. 接口、路由及客户端绑定

### 6.1 HTTP及解码

完全采用后端BND-CODE-HTTP。ApiClient沿原success/data/error/meta、请求截止和幂等规则；WalleApi增加代码能力的严格decoder，不放宽旧文档字段。未知状态、缺字段、类型或所属关系不匹配显示“响应暂时无法确认”，该写请求按UNKNOWN，不当作已失败。

ID按正安全整数；Money仍为非负十进制金额字符串。TaskView／TestingTaskView.budget.available_cny必须用独立CnyBalance decoder：有符号、规范6位，禁止+号／指数／负零，-0.000001必须可显示，不套Money拒绝、不clamp0或用浮点抹掉符号。用精确微元BigInt／十进制解析和固定6位余额显示；预算／价格／已核算／预留继续Money，不放宽旧文档金额。其他金额展示小数位不反过来改变请求；字段缺失、null、空数组和0按后端契约区分。不得用Number把“未记录”变0，也不以当前文档／当前候选补缺失历史身份。

CommandReceiptLookup严格解码新增record_status及与lookup_status／原HTTP／outcome的配对；CLOSED是原请求409终局，控制HTTP200不能被误解为业务成功。CommandCloseReceipt使用原注册身份，不通过可变URL拼接任意fetch。

Testing错误decoder合法集合为SHR-TEST-ERROR自动公共边界＋后端各入口专有错误，不复制全体业务编码；AUTHORIZATION_NOT_APPLICABLE保留403及AuthorizationDetails，原拒绝回执同入口严格解码。TERMINATE／RECONCILE不因执行授权、模型、runner或预算未就绪而禁用；管理权失败按PERMISSION_NOT_GRANTED。Page<T>只解码data.items及meta.pagination={page,page_size:20,total,total_pages}，total_pages=ceil(total/20)、空总数为0；page为1—100000，客户端不发送page_size，不接受data内另一层Page／分页字段。

TaskView同一读取的数据构成同一显示快照；其他子区域的时间分别显示，不把不同GET拼成原子现场。提交前冻结明确身份和原expected_state_version；服务端409返回后才展示冲突及当前关联。

CodeCallSummary／Detail及TestingCallSummary／Detail增加usage_status；Coding／Testing新调用四种状态必有，旧文档null不迁移填值。PARTIAL显示“已报告用量，尚未报告完整”，NOT_REPORTED显示“用量尚未报告”，FINAL只表示最终用量已核实，费用仍看实际settlement；DISPUTED显示“用量待核对”。累计值可以增长，原最终重复不叠加费用；页面不自行用单价计算账务。

CodeCallDetail.provider_request_id使用后端不透明文本／null定义，非null不转数字、不trim；旧文档详情的历史空串保持，不放宽其他ID解码。V2代码写入口将原冻结method／path／key／body字节受控导出给CommandRecoveryStore，恢复经注册路径／decoder／origin校验后注入同一ApiClient新句柄；当前ApiAction只含submit、PreparedCommand在WeakMap，尚无这项实现，不能假定JSON.stringify可恢复或另建任意fetch。

未启动任务终止按后端SHR-TASK-UNSTARTED-STOP处理：Coding未开始的PENDING、Testing未运行的DRAFT／READY均可明确终止，不要求先开始、创建实例或运行测试。首次仍202真实原TERMINATE回执，“正在终止”期间保留核对入口；原STOP／CLEANUP证据完整且任务TERMINATED后显示“任务已终止，未启动执行”，不能显示已测试／通过。已分配资源或可能迟到启动尚未核清时继续显示具体停止原因，不用本地缺少PID／实例推导成功。

运行摘要可同时为NOT_PREPARED／NOT_STARTED和stop_status／cleanup_status=VERIFIED，这是未启动停止事实，不强补环境已就绪／阶段已运行；active_process_count=0只按后端已核实空执行范围显示，未知null继续待核对。没有Command／实例／Verification／报告时保留相应未产生状态，不造空执行行或通过报告。执行配置、Guard或模型尚未就绪不阻挡可证明无外发／分配历史的本地停止；确有资源待核对时不可绕过实际停止证据。

页面刷新／跨标签先查原任务、唯一termination_operation_id及原回执；重启恢复或重复终止使用原停止操作，迟到结果不能重开任务。200终态重复和202原停止的严格联合解码保持；Coding活动名额仅由后端TERMINATED释放，Testing不操作Coding。

**准备／发送／恢复／清理的事务顺序**

1. 在内存按登记入口准备并冻结原请求；body原UTF-8字节最多8MiB，与后端请求上限一致，命令元数据另最多64KiB。pending最多100条且原体＋元数据总量最多128MiB；不淘汰未决、用户草稿或旧业务数据。空间不足阻止普通写提交，保留表单。用户后续读取结果不应依赖新增一条命令才能恢复。
2. readwrite事务查[origin,intent_key]：存在则打开原命令／保留新草稿，不生成第二个原意图。不存在才保存PREPARED原请求；必须transaction.oncomplete才可继续，put.onsuccess、内存赋值、离页事件都不够。blocked／versionchange／abort／quota时关闭本轮连接并明确未发普通命令，不关其他应用或原文档数据库。
3. 首次发送再以record_revision／原身份CAS写DISPATCHING、dispatch_count和owner，等该事务oncomplete后从同一冻结输入发送。恢复不调用普通prepare重新生成key；目标是沿原ApiClient受控边界导出／恢复FrozenCommand为新本地句柄，仍使用原ApiClient.commit及WalleApi decoder。当前源码WeakMap句柄和只含submit的ApiAction不能直接JSON序列化，此能力尚待实施，不另建绕过校验的fetch。
4. 新标签／重开／网络恢复先列未决摘要，只GET原回执或已核实operation。BroadcastChannel可通知更新，但唯一index／IDB事务和后端幂等才是正确性依据；不能以localStorage锁、超时、页面消失或owner_id变化证明旧请求未发送。普通列表选择不带出body，详情仅当前用户明确核对时加载；恢复前重验owner_module与注册路径一致，不可信本地module标签不能导航或重放另一模块。
5. 明确“按原请求恢复”前重验body摘要、完整结构、origin及原关联，QUERY_ONLY不提供原业务重放；原数据缺失／损坏仅保留可安全验证的元数据查回执或明确关闭原键，不猜body／新键。允许REPLAY_SAME_KEY时，以原身份CAS记录新的明确发送计次，其他标签只更新观察；旧在途HTTP不能证明已取消，后端原键成功／拒绝终局保证实际业务意图唯一。不是一次自动重试许可，GET不主动派发。
6. QUERY_ONLY仅包括AcceptCode合作窗口确认、带repository_quiescent_confirmed的RESUME；REGISTER_BASE改为普通REPLAY_SAME_KEY，严格按原完整commit／配置／body／key恢复，旧工作目录捕获草案不迁移为新登记；恢复旧true只查原结果或明确关闭未接收原键，不续窗口、不复制给新表单。其余入口仍须原输入／权限／当前条件有效，旧问题不重投新会话。NOT_FOUND继续待核对；可明确走服务器关闭屏障，只有可靠CLOSED后才终结原意图，不能以本地删除获得新键资格。
7. 同步成功必须严格解码并对应原冻结请求；确定拒绝以服务器原REJECTED回执核实。202保存可靠task／operation后持续读，直到原Operation真正SUCCEEDED／FAILED／CANCELLED，或已可靠确认原键CLOSED；UNKNOWN不清理，HTTP404／待批消失亦不清理；无需等待整份CodeTask完成。原事实已确认但本地更新失败时继续保留pending，重开再读同一回执，不重发。
8. 终局确认后一个readwrite事务写CommandReceiptLocal并删除pending；只有这次事务提交才释放该intent入口。迟到结果若发现墓碑只补原对象读取，不复活pending或清理后来新草稿。墓碑保留30天，可仅清理已终局摘要；未决不按年龄过期。“放弃草稿”不能删未决。用户明确取消从未派发PREPARED时，须同事务证明dispatch_count=0并移入CANCELLED_UNSENT；旧发送者提交前必须重验持久门槛，已删除／有墓碑即拒绝。状态／提交不明不能用该取消。
9. 旧PendingAction schema=1／2／3均是未实施草稿；当前共用命令库walle-v2-code-command-recovery技术名／DB version=1不变，记录版本升级4，增加原键关闭状态，并保留模块／Testing owner，不另建命令库。不自动迁移／重放旧格式；若检测到旧记录，仅在元数据严格有效且用户明确选择时只读查原回执，不导入为可重放v4或删原业务草稿。不同origin／不同浏览器／用户清理存储／真实掉电不承诺必然恢复；本期关闭标签后默认不主动删除原凭据。

**关闭未接收原键**

用户可在“待核对操作”详情明确选择“关闭原请求”。先查原CommandReceiptLookup；NOT_FOUND只说明此刻无记录，不证明未发送，但可进入INF-CODE-COMMAND-CLOSE的互斥关闭。按钮旁说明“关闭只能阻止尚未接收的原请求；已接收的操作仍须核对或终止”，不声称取消任务或撤回Git。QUERY_ONLY继续禁止原业务重放，同时允许这项独立原键控制。

1. 严格核对同origin、原注册method／path／key、原identity_sha256和可信目标关系；不需要原body／body摘要有效、旧一次性true或原task已经创建，绝不根据当前表单重建身份。原body损坏但冻结身份摘要有效时可关闭原键，不重放；原path／key／module摘要缺失或不匹配不能关闭或重放。不能确定原三项身份则保持只读核对，不猜新键。
2. 在原pending记录readwrite事务用record_revision CAS写close_state=REQUESTED、close_requested_at，等待oncomplete；原method／path／key／body保持不变。原业务发送／原键重放只有close_state=NONE时可派发。原发送者已过本地门槛或HTTP在途不作为取消证据，最终以服务器接收／关闭事务为准。
3. 通过原ApiClient／WalleApi受控prepareCloseOriginalCommand发送POST /command-intents/close，body={method:POST,path:原path}，Idempotency-Key=原key；不调用普通prepare生成UUID，不发送原body，不递归增加另一份PendingAction或占关闭自己的intent_key。控制请求身份来自已保存REQUESTED的原记录；本地保存失败不发关闭，普通存储故障例外仍仅真实任务TERMINATE。
4. HTTP200必须严格解码CommandCloseReceipt。close_status=CLOSED且original_receipt为FOUND／record_status=CLOSED才确认关闭；也可只读原回执确认同一CLOSED。用一个IDB事务写final_state=CLOSED_UNEXECUTED的CommandReceiptLocal并删pending，才释放原业务intent。result_code=COMMAND_CLOSED，http_status保存原409而不是控制HTTP200；无可靠原摘要时此终局body_sha256可null，其他终局保留原有效摘要。
5. ALREADY_RECEIVED必须携带真实原回执；close_state写ALREADY_RECEIVED，显示“原请求已接收，不能用关闭取消”。若原成功／确定拒绝，按原终局核实；若PROCESSING／UNKNOWN或202继续原操作，不释放pending、不发原业务或新等价请求。终止Task用其原明确入口，关闭不改变任务状态或窗口。
6. 关闭超时／断线／提交未知或本地终局写失败保留REQUESTED和原记录；刷新／online只GET原回执，不自动POST关闭／原业务。用户明确“继续核对关闭”可用相同原身份再发这项自然幂等控制，不能换键。原NOT_FOUND仍不得本地删记录；服务器CLOSED不会按本地墓碑30天清理而过期。
7. 迟到原响应、其他标签和旧reader只能更新原key事实；先检查原墓碑／revision，不复活pending或清后来新草稿。确认CLOSED_UNEXECUTED表示该键今后永不执行，后续明确业务动作才生成新key；Git交付窗口确认重置false并重新确认；基线登记仍使用明确固定commit，不添加一次性来源确认，不能把旧body复制为新意图。

**终止与恢复入口**

Coding／Testing设置页及两类任务原操作区域共享待核对操作列表，包含task_id=null的设置／任务创建前命令；只显示安全目标、时间、状态及查询／允许的原请求恢复，不能回填新一次性确认；提供明确“关闭原请求”，并显示与原操作终止不同的范围。没有未决项成功空态使用公共EmptyState，outline图标、文案“当前没有待核对操作”；读取失败与无数据分开，不显示空列表掩盖故障。该列表在原设置页内，不新增导航页面或通用命令控制台。

### 8.2 程序边界与集成

后续实施需要严格类型、锁定Prettier、真实API解码、写屏障及同键恢复检查；源码变更依原子保存并核对实际开发服务模块／导出。检查范围按当次实施授权执行，不因为本设计自动运行。

SQLite事务、幂等、独立检查、受控模型、OpenCode和Windows完整停止、Git旧值／符号引用／合作窗口竞争及数据库补记由后端真实层验证；前端Mock只能证明当前组件／owner路径。前端不以成功渲染或HTTP200宣称后台已执行。

### 8.3 AI程序验证与效果评测

前端本期不直接调用模型，不新建Prompt或judge。代码任务的AI20-FRONTEND／INTEGRATION、修复及压缩后继续，统一绑定后端EV20-FLOW／EV20-REPAIR／EV20-COMPACTION和DS20-CODE-1固定样本。前端负责其中真实UI断言、输入法／断网／焦点与结果展示，不能以Mock替代真实调用链；具体模型／Prompt／预算／样本／重复次数／失败计入及通过阈值只在后端8.3定义。页面重开／复制／普通读取不追加计数或模型请求，实际真实调用须另按当次授权。

独立Testing的计划起草另由后端EV20-TEST-PLAN评测；测试执行本身不调用模型判分，普通页面、展开结果和恢复不隐式起草／测试。

### 8.4 质量及人工验证

按TC-FE20-32—34登记页面和组件自检，覆盖初始加载、成功空数据、正常、失败／无权限、筛选无匹配／分页越界和恢复。按钮必须在实际容器核对正常、禁用、处理中、历史／编辑／占用状态；不存在的代码手工编辑状态不得伪造为已测。

Chrome／Edge的实际版本、宽窄布局、真实键盘／鼠标／IME及未覆盖分别记录。模拟IME与真实系统输入法、DOM赋值与真实点击分别说明，不逐控件留截图。测试产物先放可清理临时目录；最终只保留docs/verification/v2.0简要Markdown，不留测试JSON、截图、录像或原始日志。

### 8.5 设计完成与软件验收

前端规格定版前应核对所有控件有可调用契约、全部状态和恢复可判定、公共机制实际可复用，以及后端支持范围与页面承诺一致。两个DRAFT共同复核后再按用户决定定版，不因本文写完就EFFECTIVE。

产品完成仍要求V2-B1—B3真实接入和相应证据。未实施／未执行如实保留，类型或构建不能替代浏览器可操作性。提交推送、服务更新和真实调用按新任务授权。
