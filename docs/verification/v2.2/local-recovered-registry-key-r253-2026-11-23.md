# R253 管理恢复后旧请求键只读

2026-11-23，独立 `codex/2.2`。依据 V2.01 后端 4.12.3 和 [恢复前的固定源核对](../../iterations/pending/v2.2/WALL-E.正式恢复前的固定源核对_V_2.2.md)。Windows 运行固定 SQLite 3.54.1，两个独立登记文件分别为 Schema 1 原登记和 Schema 8 恢复登记。实际 Starlette 管理 HTTP 调用产品路由，普通启动的物理容量观测由既有隔离测试适配提供。

- 复现时原代次头返回 409，而把相同旧操作键和原输入装进当前代次请求会返回 202 并受理新 START。恢复触发器只保护旧行，原键查找原先只查当前代次。
- 操作和控制入口现从原登记的代次表及各自复合键索引检查已用于其他代次的键。检查在原登记锁内，先读取当前代次已有回执，拒绝的历史键均返回 `MANAGEMENT_KEY_CONFLICT`。初次安装继续使用原路径，无 Schema 变更。
- 按同一受理入口验证旧操作键、旧控制键均返回 409，新键受理且同代次重复请求返回 200。操作和控制维持各自的键作用域。恢复库只有各一条合法的新操作和控制，旧数据库原字节未变。更换为旧代次身份头仍按原代次冲突拒绝。
- 184 项相关后端专项、16 个子项通过。修改文件的 Ruff F／I、659 个文件的 Ruff 格式、`git diff --check` 通过。仅有既有 Starlette TestClient 弃用提示。固定 SQLite 的两类历史键查询计划分别使用复合索引及主键。原生非空管理登记的宿主、TLS 与旧操作键拒绝见 [R258](local-x86-nonempty-registry-recovery-r258-2026-11-23.md)。
