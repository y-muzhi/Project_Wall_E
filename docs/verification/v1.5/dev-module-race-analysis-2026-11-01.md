## 已确认与仍需区分的结论

事故现场已证明Vite把非空源码返回为空模块，见[恢复记录](dev-module-empty-cache-2026-11-01.md)。本轮在同一锁定Vite8.3.2下复现了能产生该现场的完整机制；此前确实使用过非原子源码覆盖和格式化。但事故发生时没有保留文件事件跟踪，因此不能精确断言两份文件分别由哪一次命令、哪个毫秒触发。旧React URL的504不是已证实根因。

机制由三部分叠加：

1. **保存存在可读到空内容的窗口。** 之前源码生成使用过Path.write_text，格式化实现也通过fs.writeFile直接写回；覆盖模式会先截断旧文件，再写入新内容。此时磁盘最终文件可以完全正确，中间状态仍能被另一进程读取。Python的[open说明](https://docs.python.org/3/library/functions.html#open)明确区分覆盖截断和追加模式。
2. **开发服务把中间空内容转换并缓存，最终写入没有再次使缓存失效。** 锁定Vite代码getCachedTransformResult直接返回已有transformResult；读取源码时用fsp.readFile，空字符串不是加载失败；转换结果写回moduleGraph。其内置Chokidar3.6.0默认awaitWriteFinish=false，change事件使用50ms抑制窗口。同一文件的截断／完成写入紧接发生时，后一次通知可能被抑制。官方[Chokidar说明](https://github.com/paulmillr/chokidar/tree/3.6.0#readme)提供等待写入稳定的选项；本轮以本机锁定实现和实测为准，不用最新文档代替版本事实。
3. **应用最外层启动失败不可见。** index.html先显示加载占位，静态导入main及其依赖。main中的start().catch只在模块链接成功并开始执行后才存在，不能捕获依赖缺少导出的链接失败；没有更外层的导入失败／启动超时处理，所以占位一直保留。这一缺口可由实际源码和事故Console互相核对。

本地依赖定位：frontend/node_modules/vite/dist/node/chunks/node.js的getCachedTransformResult／loadAndTransform、内置Chokidar的_throttle(EV_CHANGE,path,50)及默认awaitWriteFinish；Prettier internal/legacy-cli.mjs的writeFormattedFile委托fs.writeFile。业务文件和依赖文件均只读，没有修改node_modules。

## 隔离复现及对照

使用一次性`node --input-type=module -`脚本，Vite createServer：configFile=false、独立临时root／cacheDir、middlewareMode=true、hmr=false，不监听HTTP、不共享正常5173的模块图或优化缓存。只创建探针模块，不加载用户需求或调用API。

核心步骤：先转换带真实导出的探针；open(file,'w')截断，等待首个change通知；在空窗口内transformRequest；随后写回完整源码并**关闭写句柄**，等待160ms再读磁盘及服务转换缓存。之后以“同目录临时文件写完再rename替换”作控制步骤，再检查新标记导出。
