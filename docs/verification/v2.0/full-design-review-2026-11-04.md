# V2.0前后端完整设计评审（2026-11-04）

## 范围与结论

审阅后端0.14-draft-14（7077行）、前端0.13-draft-13（1604行）全文，包括对象、应用、全部HTTP／内部入口、存储、外部依赖、页面／组件、浏览器恢复、验收及附录；交叉核对当前设计索引与设计进度。重复表格条款按同一规则核对，不将历史已修复FR20／RC20问题重新报为未修复。

本次是设计文本静态审阅，不是实现或第三方协议审计。未运行产品测试、构建、浏览器、OpenCode、模型／计数API、数据库维护或服务启停；未改设计正文、源码、资源、数据及既有记录；未提交推送。Git工作区已有大量V1.5及其他任务改动，保留，不归为本轮结果。

结论：主体职责和恢复原则已有明确设计，但以下收尾、状态和接口契约仍不闭合，不宜直接标为EFFECTIVE。P1为应在实施相关能力前消除的流程／契约问题，P2为会造成实现分歧的规格问题。推导风险与确定文本冲突分开列出。

## 本轮问题

### RV20-01／P1：Coding正常完成没有定义运行资源收尾

- 位置：后端225、1433、1471、1913、6210—6212、6245—6249、6695行。
- 已明确：阶段QUIESCE允许原生宿主存活；COMPLETED由Git交付成功及postcheck核实决定；对COMPLETED终止只返回已完成事实，不创建停止操作。
- 缺口：正常成功路径没有停止原生实例、核对剩余Job／启动步骤、撤销会话凭据及回收本任务WFP／LPAC资源的步骤，也未说明哪个既有操作承担该收尾。不能从“静止”推导已退出或资源已回收。
- 影响：按现有文字可合法地产生“任务已完成、实例仍活着、页面已无可执行终止”的组合，历史任务积累运行资源。此为从正文允许状态推导的风险，尚未运行复现。
- 建议：在原DELIVER／任务完成流程中明确自然完成收尾及其持久证据、失败／未知状态；不伪造用户TERMINATE，也不以任务终态替代进程退出证明。补自然完成后原实例仍活、释放失败、重启恢复的验收。

### RV20-02／P1：Testing终态终止响应无法满足HTTP契约

- 位置：后端2279、2287、2425、5343—5366行；前端1281行。
- 应用规定STOPPING返回原停止操作，终态返回原事实；但HTTP只定义202 TestingReceipt，且该结构operation_id必有。自然COMPLETED任务可能从未产生TERMINATE操作。
- 影响：对已自然完成的Testing任务发终止，没有可合法填入回执的停止operation_id；返回TestingTaskView又不在接口成功分支中，严格客户端会把可确定结果解码为UNKNOWN。
- 建议：明确终态200 TestingTaskView及对应结果码，STOPPING／首次接受202 TestingReceipt；同步客户端联合解码及原幂等回执。不得创建假停止操作填字段。

### RV20-03／P1：Testing状态—动作及创建时绑定资产的迁移不完整

- 位置：后端1031—1032、1055、2180、2275—2279、2419、6739—6746行；前端975、1023、1031行。
- 已定义CREATE可直接带plan／pack，同时“创建为DRAFT”；ATTACH_ASSETS在DRAFT绑定且一经绑定不可换；条件齐备时READY／RUN只允许READY。
- 缺口：未明确创建时资产已齐的DRAFT由哪个写操作／后台事件进入READY；同版本再次ATTACH是否允许及其幂等／CAS语义也未定义。不能由GET偷偷改状态。Testing亦没有Coding那样完整的状态—动作矩阵，预算、RESUME及资源失效后的状态许可未逐一闭合。
- 影响：创建时选好资产与创建后绑定资产可能形成两条不同的准入路径；实现者必须自行补业务规则。
- 建议：定义统一资产绑定／就绪迁移，覆盖CREATE带资产、无资产后ATTACH、准备条件变化、撤销、WAITING恢复、终态预算／绑定拒绝；逐动作说明控制版本及真实事件来源。

### RV20-04／P1：Testing实际权限错误不在HTTP允许错误集合

- 位置：后端2533、2546、5146、5311、5366行及BND-TEST-API各响应表。
- 公共契约将AUTHORIZATION_NOT_APPLICABLE等映射403；Testing创建／追加预算必须核对授权。但各Testing接口复制的错误集合不包含该授权编码，又规定只接受各入口已声明错误、未知编码映射INTERNAL_ERROR。
- 影响：合法的授权不适用拒绝无法同时满足应用语义和接口白名单；终止还须不依赖执行授权就绪，亦应避免被复制的CONFIG_NOT_READY规则误挡。
- 建议：按具体APP逐入口整理结果／错误集合，明确共享自动适用错误与入口特有错误的关系；补错误原回执与前端严格解码。不要只在HTTP状态列表写403却没有对应编码。

### RV20-05／P2：Coding工作区五页签与六页签规则冲突

- 位置：前端424—426、486、1304、1358行；前端832行仍写接收绑定verification。
- 页面正文严格限定execution／code／checks／delivery／usage，并规定未知tab报参数错误；后续路由及TaskLocation加入testing／test_report_id。
- 影响：按前一段实现会拒绝tab=testing，按后一段实现则违反“五个页签”与严格枚举；独立测试区位置不唯一。接收组件的旧verification绑定也与1235行明确只传test_report_id不一致。
- 建议：统一六页签或明确测试区域的其他位置，完整列出URL／history／TaskLocation字段；接收确认统一候选＋独立报告＋计划，不再引用自检作为接收身份。

### RV20-06／P2：全局“代码开发”入口没有确定落点

- 位置：前端69、253—270、1299—1310行；后端6704行。
- 公共导航承诺独立“代码开发”入口，但只设计了依赖requirement_id／document_id的文档任务列表和依赖task_id的任务工作区，没有规定用户尚未选择文档时该入口打开哪里。
- 建议：明确落到现有需求／文档选择流程或补充真正需要的汇总页；优先复用，不能凭空猜最近文档／任务。仅有侧栏标签不能形成可实现的导航契约。

### RV20-07／P2：Testing分页覆盖规则未明确

- 位置：后端98、2408、2523、4560、5164行；前端170、918、1180行。
- 公共规则固定每页20／page上限100000；Testing APP与HTTP新增page_size≤100、id升序并使用Page<T>，前端仍固定每页20。默认20本身不冲突，冲突在公共固定规则与可变size没有例外关系，Page<T>也未给出唯一线级结构以说明与data.items／meta.pagination的关系。
- 建议：统一沿现有固定分页，或明确Testing覆盖条款、page范围、Page<T>展开和meta.pagination字段；前端可以固定请求20，但不能让服务端／decoder各自解释两套结构。

## 另需收敛的产品／技术风险（不是已证实的实现缺陷）

1. 新项目测试包冷启动：后端1154、2231要求同固定设计的正参考代码、缺陷对照及重复验证，1143规定参考集为部署受控登记资源，页面只允许选择。对于用户新建的设计／计划，谁准备正确参考实现及缺陷集、怎样审核登记、没有参考时可完成到哪一步尚未形成可操作流程。这是通用Testing范围的重要前提，不只是缺几个资源文件；应先明确首期仅支持预登记项目还是提供独立准备工作流。不得为了闭环放宽测试可信性。
2. 配置失效后的Coding恢复：后端1417允许AWAITING_TESTING应用配置，774—775要求受影响自检重做，但1422—1423不允许该状态重查／捕获，未明确应用后回到哪个检查状态。需补实例：已发布候选后换CheckSetVersion，如何重做自检／保留发布事实／重新关联报告，避免被迫修复无缺陷代码。
3. 人工覆盖：MANUAL可用于关键行为，报告明示人工范围但没有逐项人工结果记录。若人工接收本身即表示接受这些未自动验证范围，应明确确认文案与责任；若要求人工验证完成，则需定义证据及门槛。当前不应宣称全部需求已经验证。
4. Windows／Guard、固定执行器与Git、模型／价格、检查资源和200 Schema等真实证据仍未取得。正文已经如实登记ready=false，本轮不把“尚未实现／验证”重复列为设计错误，也不宣称这些组合实际可行。

## 排除的误报

- 原键关闭、百万Token舍入、负余额、原观察元数据及累计／最终usage已有当前正文规则，不重复报历史六项。
- 已有报告选择可复用GET /testing-tasks?candidate_id=...读取TestingTaskSummary.report_id，再GET原报告；并非必须新增报告列表接口。应补页面绑定说明，但不认定后端完全缺失能力。
- 本轮不建议引入新的总管Agent、服务、账本或自动重试体系。
