## 4. 既有项目基线与V2.0边界

现有V1.5正式设计的目标是：围绕同一需求的多份文档，支持AI讨论、用户决定出稿、明确修订、来源同步、人工编辑、评论、版本与确认，以及实际请求和用量回查。

正式设计保留两份：

- docs/design/v1.5/WALL-E.后端设计文档_V_1.5.md：业务规则、对象、应用流程、模型上下文、HTTP、存储、恢复和共享验收。

- docs/design/v1.5/WALL-E.前端设计文档_V_1.5.md：页面、组件、交互、编辑恢复和浏览器存储，引用后端契约。

规格修订1.0、EFFECTIVE；不能另造第三份共同权威规格。三类文档、讨论、采用、保存及确认的细节继续沿用现有业务，V2.0需明确扩展点。

技术基线为Windows本机浏览器、Python/FastAPI/SQLite，以及TypeScript/React/Vite/Milkdown。V2.0适配不应默认要求Docker或更换框架。

V1.5明确排除代码生成／部署，故V2.0代码任务是新增范围，不应冒充V1.5已经实现。现有需求五态、文档确认与代码任务执行状态不能混用，是否联动需在V2.0明确。

现有ModelProfile、网关、LLMUse、幂等、版本、Worker、编辑和API客户端等应先分析复用。不能因为新增“代码任务”就复制一套同职责系统；也不能把一次GuideRun硬当作完整长期代码任务。

本轮静态核对了V1.5前后端规格的相关规则，以及ModelProfile、ModelGateway、AuditRepository／LLMUse、GuideWorker、恢复命令、SQL约束和前端调用详情契约。未完整重读或运行验证全部V1.5实现。实际核对基线见第26节。

## 5. 总体分工：当前方案

| 角色 | 负责事项 |
| --- | --- |
| 文档侧模型 | 沿用现有讨论和文档流程，澄清规则、分析影响、提出设计及修订内容。 |
| OpenCode | 读取固定设计和代码，自主搜索、实现、执行允许的检查并修复。 |
| WALL-E程序 | 控制真实身份、版本、工作区、权限、预算、状态、证据、终止和交付，不替模型理解业务语义。 |
| 用户 | 作业务决定、处理问题、授权、采用文档变更、验收接收与任务控制；不手工修改代码。 |

文档是业务依据，代码和实际运行是实现事实，程序记录是执行与费用事实。模型的建议、完成说明和待办勾选均不能替代这些事实。

## 6. OpenCode接入与适配层：当前方案

采用WALL-E后端管理的OpenCode无界面服务，经本机API控制；前端只访问WALL-E。适配层转换任务控制、保存并带回执行事实，不重新拆解业务、不接管原生每一步编码。一轮外部消息可产生多次模型请求、搜索、修改和检查。

OpenCode通过受控模型入口使用国内模型，不直接持有供应商密钥。工具权限、操作系统限制和模型入口分别承担对应职责，提示词不是强隔离。

### 6.1 服务实例、会话与任务绑定

本期方案：一个任务工作区对应一个受管理的服务实例；实例承载本任务的后端、前端和联调等多个角色会话。任务保存长期业务事实，会话保存模型上下文，实例承载API／工具／进程，工作区保存代码。服务重启不自动创建业务任务或新会话。

未来多个任务各用独立工作区和运行实例，不因主文档相同而共享控制通道。同一工作区仍只有一个有效写入者；终止A不误停B。

实例记录包含WALL-E生成的身份、任务／工作区、执行器版本、生效配置版本、会话持久化位置或存储身份、启动时间、进程归属证据、连接信息及当前控制代次。端口可复用、PID可再分配，均不能单独作为身份。重建实例生成新身份，旧事件保留来源但不能取得当前控制权。

会话持久化仍可核实时恢复原关联；丢失时须先确认旧执行停止，再重建会话，明确记录上下文重建，不宣称完整继承模型记忆。固定原文及实际代码优先于摘要。

### 6.2 内部操作与原生接口

OpenCode 1.19.4曾通过无付费模型的临时服务核对以下接口存在性；完整字段、鉴权、恢复和Windows行为未据此验证。原生接口不假定恰好执行一次，事件不假定支持完整重放。

| 适配操作 | 原生接口或方式 | 保存的事实 |
| --- | --- | --- |
| 核对实例 | 服务探测及受管理进程核对 | 可达性、真实实例身份和工作区绑定 |
| 创建会话 | POST /session | 原生会话身份或结果未知 |
| 投递消息 | POST /session/{sessionID}/prompt_async | 明确未发送、确认接收或结果未知 |
| 查询现场 | GET /session/status及会话消息接口 | 当前状态、消息和核对时间 |
| 查询／答复问题 | GET /question及reply／reject接口 | 原问题及实际处理事实 |
| 查询／处理权限 | GET /permission及reply接口 | 结构化请求及实际处理结果 |
| 请求中止 | POST /session/{sessionID}/abort | 中止请求结果，不直接代表执行停止 |
| 接收事件 | GET /event | 消息、工具、问题等增量观察 |

适配接口不向前端直接透传。原生端口、会话ID和错误不能成为绕过任务权限的入口。适配层不把所有异常统一当成可重试失败；超时保留是否可能已执行的信息。

### 6.3 消息投递与关联

首次消息包含目标、角色、固定依据入口、代码位置及执行条件；执行器自行读取全文和代码。后续只补实际新事实：固定依据答复、已生效配置变化、检查失败、缺陷记录和必要交接引用，不逐轮选择源码文件或新增语义任务清单。

每次发送先保存操作及实际内容，再发送。明确未发送且条件有效可继续原操作；确认接收后保存原生关联并观察；可能已接收而回执丢失时查询原会话；无法可靠核对则等待，不补发。创建会话结果未知时也不能连续创建多份。

只有协议提供且经验证的稳定关联信息可证明对应关系；相似文本、标题或接近的时间不能作为可靠去重依据。

### 6.4 事件、查询与原生请求

事件先核对运行实例、会话和任务归属，再保存原生身份及事实、更新待核对事项，满足业务条件才改变任务状态。空闲、完成说明、中止回执或旧实例消息均不能直接决定业务完成／终止。

断线重连查询会话、消息、问题和权限补齐现场；不依赖完整事件重放。数次查询发生于不同时间，不是天然一致快照，固定候选和停止确认等重要动作需在写入控制下再次核对。无稳定事件ID时可保留重复观察，但不能重复产生业务动作。

普通问题保存原文与选项，交给用户处理；权限按结构化工具、对象和已生效范围自动答复或等待。任务已终止、会话失效或授权未生效时不批准。答复前再核对仍待处理，超时先查；question.reject不等于任务abort，拒绝权限也不自动终止任务。

### 6.5 角色交接

本期后端、前端、联调会话顺序写入。角色空闲后，先核对待答问题／权限、工具和写入活动、阶段检查及代码现场；达到阶段条件可按预定顺序自动推进，不逐阶段要求用户重复批准。条件不足则等待，不根据模型自报进度或百分比推进。

交接提供固定设计、实际代码位置、检查、未解决事项及必要说明。前端读真实后端实现和原设计；实现或摘要不能覆盖契约。阶段检查只支持推进，不证明完整需求已实现；最终仍进入候选验收与人工接收。

### 6.6 完整停止与配置核对

持久停止意图先阻止新投递及模型请求，再中止会话、核对工具／子进程／本地服务并处理未停活动。确认不再写入后才已终止。API不可达不证明服务停止，服务退出也不证明子进程停止；不能确认时禁止新写入者接管。

Windows进程组／作业对象等仅为实现候选，须验证实际归属和停止效果。全局、项目、运行时等配置来源及覆盖顺序需按锁定版本核对；不能只记录WALL-E想传入的配置。实际应满足受控模型入口、主辅模型范围、无供应商密钥继承、目录／网络限制和原生重试控制。最终配置无法核实时标准备不完整，不宣称已受控。

## 7. 任务、会话和操作记录：当前方案

三个层次分开：

- 代码任务：长期业务对象，绑定文档、工作区、授权、状态和交付。

- 执行会话：承载OpenCode上下文，可按后端、前端、联调或恢复需要关联多个会话。

- 操作记录：首次消息、继续消息、检查反馈、问题答复、终止及交付等动作均可追溯；首次／继续发起是其中一类。任务级动作允许没有会话关联，面向会话的动作必须指明目标会话。

任务至少保存来源文档、固定版本与摘要、关联材料、代码起点、工作区、状态、等待事项集合与主要原因投影、预算及代码归属。会话保存原生ID、角色、运行实例与状态。

每次发起保存原因、发送内容、接收情况和原生消息关联。状态未知先查询，不按文本相同去重，不盲目重发。

以下字段是本轮详细设计草案，不表示DDL、状态码和全部接口已经定稿。逻辑字段组不要求各自建表；不为每类操作复制一套可靠性机制。

### 7.1 CodeTask最小字段草案

| 字段组 | 主要字段 | 约束 |
| --- | --- | --- |
| 身份 | id、requirement_id、document_id | document_id为主文档；文档与任务一对多。不设document_id或document_id＋版本的任务唯一约束。 |
| 固定设计 | design_revision_id、关联材料的固定版本引用及摘要 | 建立后不可替换；摘要用于完整性核对，不替代原文。材料是内部引用集合，不另建顶层业务对象。 |
| 代码起点 | repository_id、base_snapshot_id、可选来源任务引用 | 固定真实代码起点；复用旧任务代码时保留继承关系，不能据此声明验收通过。 |
| 执行位置 | workspace_id | 准备完成后绑定独立工作区；准备失败保留原任务。仓库／工作区标识的存储形态仍待定。 |
| 生命周期 | status、state_version、waiting_items及主要原因投影 | 控制动作核对版本；多个等待事项分别保存，单一wait_reason不能覆盖完整事实，不猜测业务语义。 |
| 执行条件 | 授权记录、预算额度、模型配置引用 | 扩大权限、预算或改变允许配置必须有明确操作记录，不由执行器自行扩大。 |
| 终止事实 | stop_requested_at、stopped_at | 区分停止意图与确认停止；原生abort回执不是stopped_at的充分依据。 |
| 时间 | 创建、开始、结束、最后核对时间 | 纯查询不增加业务版本；最后核对时间反映观察事实。 |

### 7.2 会话、操作和模型调用归属

执行会话保存任务ID、后端／前端／联调角色、OpenCode原生会话ID、运行实例和最后核对时间。多个角色会话共用任务预算，同一工作区顺序写入；恢复可重建会话，但不改业务任务身份或固定依据。

操作记录保存任务／可选会话、动作类型、固定输入、幂等键、发送与接收事实、原生关联标识和处理结果。所有控制动作定位任务；问题答复另定位会话及原生问题，接收代码另定位候选快照，不能通过文档ID猜“当前任务”。

LLMUse继续表示一次实际模型请求。建议扩展为文档运行或代码执行会话两种归属，恰有一个；每次主模型及摘要、压缩、标题等辅助请求均可追溯至任务。精确外键和历史数据处理仍待设计。

### 7.3 业务版本与观察记录分开

state_version保护开始、等待／恢复、授权或预算调整、终止、固定验收候选及交付等控制条件变化。消息追加、工具日志、用量入账及核对时间使用各自记录身份／序号，不必每次增加任务业务版本。控制请求携带任务ID、预期任务版本、幂等键及动作所需的固定对象身份。

### 7.4 数据关系的当前范围

任务、执行会话和操作记录为不同身份；候选／检查、接收／交付、继承／撤回、调用／预算提供各自可回查事实。逻辑分组不要求每项一张新表或新顶层服务。LLMUse复用扩展、配置和授权引用需在既有存储中具体落位；最终DDL与完整Schema见待定项，不能把本汇总视为数据库迁移脚本。

## 8. 启动准备与执行配置：当前方案

启动输入包括主文档及关联材料的固定原文、身份、版本和摘要；仓库、代码起点和独立工作区；真实工具入口、依赖、运行及检查命令；工具／目录／网络／模型授权、人民币预算和执行限制；原文验收依据及独立检查入口。

代码侧获得固定设计只读副本。主文档全文及必要关联材料完整可读，不用摘要替代硬规则，不每次重复灌入全部源码。供应商凭据不写入消息或设计材料。首条消息说明目标、角色、依据和条件，不另造功能单元，也不宣称程序验证了模型完整理解。

### 8.1 建立、准备与开始

建立任务：核对幂等原结果，在写事务内核对主文档及Revision归属、固定代码起点、创建资格和活动名额，保存待启动任务与回执；不调用模型。

准备环境：按原任务ID建立工作区和固定材料入口，核对真实运行条件。Git、目录和进程准备不放在数据库事务内；中断后检查原资源，失败保留原任务进入等待，不能另建替代任务。

开始执行：本地事务核对状态／版本、工作区、授权、预算，保存启动操作及固定输入；后台再核对或创建会话、投递。WALL-E接受动作不等于OpenCode已接收或业务完成。接口详见第23节。

### 8.2 配置分类

| 类别 | 内容 | 变化规则 |
| --- | --- | --- |
| 固定依据 | 主文档及关联Revision、仓库、代码起点 | 原任务不可替换 |
| 运行配置 | 工具入口、运行方式、检查配置、预定义运行参数 | 允许受控调整，保留实际使用版本 |
| 执行授权 | 目录、工具、网络、模型、预算及执行限制 | 执行器不得自行扩大，变化有明确操作及生效事实 |

修正解释器路径是运行调整；扩大网络范围是授权变化；新增业务规则必须经过文档。程序只接受预定义字段，不分析任意文字来分类。修改已有任务的仓库、代码起点或让多个任务共享写入工作区不能包装成普通配置调整。

### 8.3 启动配置内容

| 配置项 | 最小内容 |
| --- | --- |
| 执行器 | 锁定OpenCode版本、服务连接方式、任务／实例绑定 |
| 工作区 | 实际目录、固定起点、设计只读入口 |
| 模型 | 已批准的精确主模型及允许辅助模型配置 |
| 工具环境 | Python、Node、包管理器等真实入口 |
| 项目运行 | 工作目录、已有安装／启动命令、允许的参数 |
| 检查 | 身份、入口、配置版本、阶段、必检标记、超时、必要环境、结果证据位置及解释方式 |
| 限制 | 调用次数、时长、重试等已授权界限 |

可引用仓库已有配置，不要求用户重新填写全部内容；找到文件不等于环境可用。配置不指定逐文件／逐方法实现清单，AI仍自主探索。

### 8.4 准备事实与检查配置

准备结果区分已核对可用、已发现缺失、尚未核对、核对失败／未知，记录时间和实际入口。启动核实当前阶段必需条件，后续阶段另核对自身条件；未核对的前端条件不能提前显示就绪。环境检查不暗中调用付费模型；真实供应方验证另遵守明确授权和预算。

必检来自已采用的检查配置，不由编码执行器临时降低门槛。AI可运行固定检查、增加补充测试、修复实现、报告检查问题，但不能将失败必检改可选、删除检查后宣称通过或改写独立验收依据迎合实现。

用户不手写检查代码。需建立／修改检查代码时可由AI准备，经明确操作采用并固化新版本；当前执行器不得自行改写正在接受的独立验收依据。配置改变保留前后及原因，重算结果适用性，不能把新门槛追溯成旧候选已通过。

### 8.5 配置调整与生效

有效调整产生配置新版本，会话启动、检查、模型请求和其他执行操作均记录实际使用版本。不影响在途活动的字段可以供新操作使用，在途操作继续关联原版本；影响进程、环境或权限的变化，先阻止相关新动作，确认受影响活动停止再应用。

下次检查超时调整不改变正在运行的检查。更换运行入口或收紧权限不能在旧条件仍生效时显示已应用。配置性暂停使用WAITING及操作记录，不复用表示永久停止意图的STOPPING；成功应用也不解除其他问题／未知结果阻塞。

用户批准权限与运行环境实际应用分别记录：待处理、已批准待应用、已生效、应用失败／未知。只按已生效授权运行。拒绝请求保留事实，由AI在现有范围寻找方案；没有方案则等待，不自动终止任务。

## 9. 前后端分开与联调：当前方案

前后端以不同会话降低单个上下文负担，必要时增加联调会话。不继续拆成页面/方法Agent。本期同一代码工作区按依赖顺序写入。

后端聚焦后端设计，也可读相关前端约束；前端读前端设计、共同契约和实际后端代码；联调按原设计检查完整调用链。相关材料不因角色被硬隔绝。

共同契约沿用已有正式位置。后端当前实现不能覆盖设计，发现偏差修代码；确需改变规则或接口才转文档。实现交接说明不是第二份权威接口设计。

全部会话共用任务预算，阶段执行不是新增业务任务。

阶段自动交接以问题／权限、工具写入活动、检查及代码现场为依据，详见第6.5节。阶段通过不等于完整任务验收通过；用户不在各阶段手工编辑代码。

## 10. 任务状态、等待事项与转换：当前方案

状态码为详细设计草案，不是已发布契约。任务生命周期与操作状态、交付事实、撤回状态及费用状态分别保存，不替代需求人工五态。

| 状态码 | 页面名称 | 含义 |
| --- | --- | --- |
| PENDING | 待启动 | 已建立，尚未确认开始执行 |
| RUNNING | 执行中 | 编码、修复或联调正在推进 |
| WAITING | 等待处理 | 存在阻止下一步的明确条件 |
| VERIFYING | 验收中 | 对固定候选实际检查 |
| AWAITING_ACCEPTANCE | 待接收 | 必检门槛已满足，等待人工接收或交付处理 |
| COMPLETED | 已完成 | 用户接收且实际交付成功 |
| STOPPING | 终止中 | 停止意图持久化，正在核对在途活动 |
| TERMINATED | 已终止 | 已确认执行停止，保留现场和历史 |

占主文档活动名额的状态为PENDING、RUNNING、WAITING、VERIFYING、AWAITING_ACCEPTANCE、STOPPING；COMPLETED和TERMINATED不占。预算不足、问题、断网和停止不明不释放名额。两种终态不复活，后续补记费用、交付和撤回不改回运行。

### 10.1 转换及证据

| 来源 | 条件 | 结果 |
| --- | --- | --- |
| 待启动 | 原生接收确认且开始事实可核对 | 执行中 |
| 待启动／执行中 | 未知启动结果、问题、权限、预算等阻塞 | 等待处理 |
| 执行中 | 无写入活动，候选已固定且检查动作被接受 | 验收中 |
| 验收中 | 必检满足门槛，候选未变化 | 待接收 |
| 验收中 | 明确失败已留证据，允许继续修复 | 执行中 |
| 验收中 | 无法执行或结果未知 | 等待处理 |
| 待接收 | 用户登记缺陷并明确继续修复 | 执行中；旧候选保留历史但失去当前接收资格 |
| 待接收 | 已接收候选实际交付确认成功，且无优先停止意图 | 已完成 |
| 任一非终态 | 终止动作被接受 | 终止中 |
| 终止中 | 执行及在途写入已核清并停止 | 已终止；交付事实单列 |

点击开始、模型说完成、点击接收均不足以直接进入对应最终状态。交付结果未明及其他阶段阻塞也可进入等待，必须保留原阶段／操作身份，不统一跳回编码。

### 10.2 多个等待事项

等待集合记录原因类型、来源操作／问题、时间、处理状态及事实引用；任务投影主要原因和全部未解决事项，不能使用单个不断被覆盖的wait_reason作为完整事实。原因依据结构化事件，不由程序猜自由文本含义。

解决一项只解除其自身阻塞。追加预算不回答问题，问题答复不消除未知执行。恢复动作核对所有与该动作有关的阻塞，恢复原操作或阶段。执行已确认停止时，费用未核清不阻止已终止，但预留独立保留。

### 10.3 控制版本

state_version保护开始、等待／恢复、授权／预算、终止、候选和交付等控制条件变化。消息、工具日志、用量入账、观察时间使用自身身份或序号，不因每次观察增加业务版本。请求携带任务、预期版本、幂等键以及问题／候选等固定身份。

## 11. 操作记录、事务与消息可靠性：当前方案

事件用于进度展示，数据库与实际查询核对确定状态。原生空闲、退出0、模型说完成或原测试通过，均不足以证明新需求已实现。后续反馈只补实际失败、原文出处和未检查范围，不逐轮挑源码文件。

### 11.1 操作状态

| 状态 | 含义 |
| --- | --- |
| PENDING | 已持久接受，尚未进入外部执行 |
| IN_PROGRESS | 已开始尝试执行 |
| SUCCEEDED | 该操作目标事实确认 |
| FAILED | 明确失败 |
| CANCELLED | 确认取消，未留下待核对执行 |
| UNKNOWN | 无法可靠确定是否执行或结果 |

操作状态与同名任务状态属于不同对象。消息操作成功只表示原生接收；答复成功只表示问题接受答复，不等于语义解决；交付成功要求目标实际更新；终止成功要求执行停止。UNKNOWN不因超时转成明确失败，不直接重发。

### 11.2 统一外部执行边界

1. 本地事务核对身份、状态版本和权限，保存操作、固定输入及必要预留后提交。
2. 后台领取原操作，持久记录开始执行，再执行OpenCode、Git或供应商动作。
3. 新事务保存回执、关联事实及允许的状态变化。

调度丢失可发现尚未执行的操作；进入外部执行后恢复先核对。在记录开始与实际发送之间崩溃也可能无法证明未发出；没有成功回执不等于没有发送。本地HTTP幂等不等于原生恰好一次，不按文本相同去重。

| 本地动作 | 同事务保存／核对 |
| --- | --- |
| 创建 | 固定依据、起点、活动名额、任务及幂等回执 |
| 开始 | 状态、启动操作及固定输入 |
| 答复问题 | 原问题有效性、用户动作及答复操作 |
| 请求模型 | 状态／授权、调用记录及预算预留 |
| 接受候选 | 候选／检查／目标核对、人工接收及交付操作 |
| 终止 | 停止意图、任务状态和终止操作 |
| 预算调整 | 预期版本、额度变化及审计 |

事务不包住网络、长检查或Git执行。明确未发出且条件有效可继续原操作；确认接收保存关联并观察；结果未知先查询，证据不足等待。未知费用不清零，未知Git不重复合入。

### 11.3 幂等与操作互斥

先查同键同输入的原成功回执，再对新动作核对版本、状态及前置条件，检查冲突的未结束操作，然后保存。不同输入同键冲突；同键重放不产生新副作用，回执是原动作事实，不假装是当前最新任务状态。

重复开始、接收与继续修复、交付与撤回等不能同时成为有效控制。不同动作竞争返回实际冲突，不静默覆盖。终止可在其他动作未结束时先保存意图，再协调停止及核对，不能要求所有操作先结束才接受终止。

数据库互斥不能代替Git预期旧值核对或工作区单写入者。停止检查与外部执行仍可能交错，控制器须处理晚启动活动，不能靠一次状态检查声称不存在竞态。

## 12. 程序如何处理提问：修正后的方案

程序不理解自由文本语义，也不增加一个模型分类器作为确定性门禁。

分工为：

- 运行事实：在预定义字段/只读材料中提供真实值，执行器自行读取；不是对任意问句匹配固定回答。

- 结构化权限请求：按原生权限名称、对象及授权规则处理。

- 普通问题：保存原文、选项、任务/会话/问题ID，统一等待用户处理，不自动分业务/环境/设计缺失。

用户明确操作可以是：

- 指出已有依据：选择固定版本真实原文，回传出处和内容。

- 补充运行配置：仅更新允许的字段并核对事实。

- 按现有依据自行处理：发送固定继续指令，不添加规则。

- 转文档处理：准备问题材料，按文档侧规则讨论或修订，不要求先终止代码任务。若决定让编码采用新版本，再另行终止旧任务并新建任务。

程序能核对身份、版本、字段、授权和待处理状态，不能证明用户选的原文在语义上充分回答问题。模型自报类型和生成的选项不自动成为有效规则。

提交答复前保存操作记录，核对任务和问题仍有效、依据未变及预算有效。超时先核对，不重复发送。question.reject不是任务abort，拒绝问题不能替代终止。

## 13. 问题移交到文档模型：当前方案

切换工作区或模型不会天然继承上下文。WALL-E按固定结构带入：

- 来源代码任务、会话及问题ID。

- 编码依据的固定文档版本与关联材料。

- 问题原文及原生选项。

- 关联消息、工具结果和代码位置的引用。

- 编码侧已经提供的观察、阻塞原因及用户说明。

程序不先做语义筛选，不编造根因。编码模型的建议是待核实材料，不直接作为设计结论。问题原文保留，完整相关记录按需查看，不每轮全量塞入。

文档模型沿用文档侧已有设计、讨论和决定，再加入本次澄清材料。不能拿编码摘要替代文档上下文。

需要源码事实时提供明确只读入口或快照；没有读取能力就补材料，不能假装已看代码。文档模型不修改代码工作区。

转文档先准备资料，不自动改正文；打开页面不额外发起模型调用。后续调用遵守现有文档触发和计费规则。

移交作为任务内部的关联记录，复用文档侧既有讨论／消息，不另建平行讨论系统。至少保存源任务、会话及问题ID、原文选项、固定设计版本、相关事实引用、目标文档与讨论消息引用、用户动作及实际正文操作结果。准备移交不等于问题解决，打开记录不自动发起模型调用。

## 14. 文档演进、问题回传与任务版本：修正后的方案

分两条路径：

- 原文已有答案：用户指出固定依据，原任务尚未终止时答复原问题，继续同一任务。

- 确需新增或改变规则：允许先在文档侧讨论、编辑、修订并保存新版本；无需停止源任务。新规则不能直接传回旧任务要求实现；要编码采用新版本，应建立新任务。

明确修正：撤销修改正文、发起修订或采用新设计前必须先终止任务的限制。任务依据是持续保留的固定版本；文档更新不自动暂停、终止、换版或判定任务失效。文档侧仍遵守自身编辑、讨论及保存规则。

用户明确选择指出旧依据、在文档侧处理新设计、保持未解决或放弃移交。程序不分析聊天决定发生了业务变更。放弃移交不自动答复问题或恢复执行；文档修订失败不提前终止源任务，也不自动改变其状态。

回执关联源问题、文档讨论、用户动作、旧依据或实际形成的新Revision以及人和时间。V1.5生成／修订有效结果可直接保存，无统一二次采用环节；回执关联真实正文操作，不凭模型文字写成功。正文无变化、修订失败或未解决按实际结果记录。

按任务+会话+问题ID防重复；不同问题不语义合并，可由用户决定共同讨论。文档侧与代码侧提供双向入口。

原任务已终止不复活。要编码采用新版本，终止旧任务并建立新任务；本期同一主文档须等旧任务实际停止、释放名额后再创建。仅保存新设计不要求停止旧任务。历史保留及未来并发规则见第22节。

### 14.1 文档占用与代码控制分开

当前方案：CodeTask不长期占用现有需求级文档讨论／编辑／候选审阅的占用字段。文档侧沿用原互斥，代码侧独立管理活动名额、工作区和执行者。阅读历史、修改文档及更新需求人工状态不自动终止编码；不能因为任务持续存在而锁住文档工作区或全部关联材料。

### 14.2 问题处理分支

| 用户动作／结果 | 代码侧处理 |
| --- | --- |
| 任务固定版本原文已有答案 | 核对所选出处确属固定材料、原问题仍有效且任务未终止；回传原文并继续。程序不证明语义充分性。 |
| 答案依赖后来新增或修改的设计 | 允许保存新版本及处理结论；旧任务仍绑定原版本，不能把新增规则伪装成旧依据答复。采用新版本编码时另建任务。 |
| 讨论后仍未解决 | 保存讨论及事实，原问题继续等待，不自动恢复。 |
| 放弃移交或文档修订失败 | 保留相应事实，不自动答复、终止或恢复源任务。 |
| 原任务已经终止 | 可以补充历史问题结论，但不能答复后复活任务。 |

### 14.3 多任务与版本提示

未来A、B同绑V3时，文档可更新到V4；A、B仍各自绑定V3。程序只显示引用和版本变化，不自动判断业务失效，也不自动停止其他任务。用户决定继续旧任务或终止并重新发起。旧任务按固定版本验收，接收页显式展示“任务依据V3／当前文档V4”及差异入口，不能宣称实现了V4。

示例：A绑定V3并提出库存规则问题；用户进入文档侧讨论，A保持等待；文档修订成功产生V4，问题移交关联真实V4。用户此时再决定继续A，或终止A、待停止确认后创建绑定V4的C。C有新会话、新授权、自身预算，可明确继承A的固定代码快照，但不继承A的验收结果。若修订失败，A不因这次失败被提前终止。

## 15. 权限、预算和调用控制：当前方案

### 15.1 默认授权与实际生效

启动时一次明确正常读取固定设计／本任务代码、搜索及增删改本工作区实现、必要构建检查、启动观察停止本任务服务、明确范围的依赖安装，以及受控模型调用。不逐条打断普通编码；删除文件仍限本工作区。

默认不包含修改固定设计、访问其他任务工作区、获取供应商密钥、扩大网络、推送、部署或操作用户真实业务数据。运行配置只存秘密引用，不显示秘密值；执行器及生成代码不取得供应商密钥。构建、测试和应用仅取得各自必需配置。

结构化权限按工具、对象和已生效范围处理。允许Shell不意味着程序理解任意命令全部行为；WALL-E规则、操作系统目录／进程／网络限制和模型入口共同执行。路径按真实解析结果核对，链接或别名不能绕过范围。Windows方案仍待验证，不将软限制宣称强隔离。

依赖来源、网络目标及相关限制明确后，AI可在范围内自主安装，无需逐包询问。安装脚本仍受同样的目录／网络／进程限制，下载地址获准不等于后续脚本全部获准。模型自报“环境需要”不构成授权。

批准、等待应用、已生效、应用失败／未知分别记录。环境更新未确认时不能仅凭数据库批准放行；拒绝权限不自动终止任务。配置调整规则见第8节。

### 15.2 任务预算范围

每任务独立人民币预算，后端、前端、联调和修复会话共用。实际主模型、弱／编辑模型、摘要、压缩、标题等辅助请求，以及失败和重试均计入真实所属任务，不能只统计可见对话或暗中切国外API绕过额度。

交付或撤回冲突的AI处理也须有预算归属：仍可合法运行的任务按其记录；原任务已终止需AI写代码时另建处理任务，由新任务授权和预算承担，不能复活旧任务。纯程序Git操作不凭空计作模型费用。

问题转文档后沿用文档侧原授权及调用记录，可关联来源任务但不重复计费、不自动借用代码预算或取得无限文档额度。测试脚本若实际调用付费模型也受授权和预算控制，不能借“本地检查”绕过；普通本地检查本身不产生模型费。

### 15.3 金额口径与预留

| 金额 | 定义 |
| --- | --- |
| 授权额度 | 用户允许该任务使用的人民币金额 |
| 已核算金额 | 按可靠用量和对应价格计算的任务账内金额 |
| 未释放预留 | 已准备／发出但尚未完成核算的保留金额 |
| 可用余额 | 授权额度减已核算金额和未释放预留 |

账内核算不是供应商最终账单。新调用须先有足额余额，不能返回后才发现超额。每次请求先识别真实任务／会话，核对状态、授权、限制及有效模型价格，固定参数并计算可证明上界，在事务中保存调用和预留，提交后发送；可靠用量返回后核算并释放差额。多会话并发预留须原子执行，不共享消耗同一余额。

预留覆盖完整请求的工具定义、历史和工具结果等全部计费项，不只本轮用户输入。精确计数优先；无法精确计数时必须有可证明的保守上界，字符估算不是硬上界。价格含适用范围及时间，跨时段按可能适用的范围保守处理。无可证明上界时不作为硬预算可控的自动执行配置放行。

实际金额异常超过预留时保留差异、停止新增调用并等待处理，不能改记录掩盖或继续声称硬预算有效。价格精度、舍入及计数依据仍需精确实现契约与验证。

### 15.4 取消、未知结果与对账

| 请求事实 | 金额处理 |
| --- | --- |
| 确认未发出且取消 | 释放预留，保留记录 |
| 已发出，取得可靠用量 | 核算并释放差额 |
| 错误返回但计费不明 | 保留预留等待核对 |
| 超时、断网、崩溃 | 不按零费用处理，保留预留 |
| 终止但供应商仍可能计算 | 阻止新调用，在途继续对账 |
| 后续可靠证据到达 | 按原调用补记，只核算一次 |

“已终止”不等于“费用已核清”。长期无结果不自动清零或到期释放；页面提示未核清金额。旧任务未知费用不转移、不消失，也不变成新任务免费起点。

### 15.5 受控入口、连续执行与重试

所有主辅请求通过受控入口，任务归属来自运行实例绑定，不依赖模型正文自报task_id。入口限制模型／参数，预留预算、保存请求及用量，在终止／额度不足时拒绝新增调用；执行器不持供应商密钥。目录、进程及网络需实际阻止旁路，仅代理地址或提示词不足以证明受控。

原生正常探索循环与失败重试分别记录。每次真实请求独立，重试关联原请求；正常下一步受剩余额度／执行限制，失败重试还受错误条件及次数限制。未知原请求不视为未发生，不释放后重发。SDK或原生内部重试也须可见且受控。

启动时明确调用次数、运行时长和连续失败等限制，触达后等待，不无限循环、不擅自换模型、不借限制重拆业务。

### 15.6 额度不足与追加

不足时保留代码、会话、问题、候选和检查，展示授权／核算／预留／可用金额、哪个请求未发出、未知费用及执行断点。用户追加或终止；追加只改变总额度，不改变设计、起点或其他权限，不解除未答问题。

恢复核对原会话和原操作，从实际断点继续，不重新发送首次任务。本期等待预算仍占活动名额。历史10元测评已结束，2.27元保守余额及当时空闲价均不是新调用许可或永久价格。

## 16. 代码归属与选择性撤回：当前方案

明确范围修正：代码、修复、联调和冲突处理全部由AI完成；不提供用户手工编辑代码入口或“暂停后手改再恢复”的流程。用户负责设计、问题处置、授权、验收和任务控制。此项不取消文档侧已有人工编辑能力。

任务起点已有代码和其他AI任务改动仍需保护。无法关联受控执行的工作区变化仅视为异常：暂停相关写入并核对，不能自动算作本任务产出或强制删除，也不为其增加正常手工代码流程。

### 16.1 起点、来源与交付分别追溯

| 事实 | 含义 |
| --- | --- |
| 起点快照 | 开始时已有的代码，不算本任务新增产出 |
| 任务产出 | 本任务在起点上形成的实际改动 |
| 实际交付 | 进入目标分支的代码及前后快照 |

来源关系记录从哪个快照／任务继承，交付关系记录通过哪次动作进入哪个目标。B继承A不使A的代码变成B独立产出，但B实际交付可能含A来源内容及B新增内容。不能凭Git作者、文件名或当前差异猜归属。

复用Git提交、引用、worktree和逆向应用，不自建版本控制。候选涵盖实际未提交及未跟踪实现，不纳入凭据、临时数据库、日志。阶段会话串行写入，本期按完整任务接收，不因后端／前端阶段完成自动合入；此交付粒度仍属当前方案。

### 16.2 撤回范围

| 场景 | 可处理对象及边界 |
| --- | --- |
| 未交付且未被继承 | 放弃本任务候选，项目目标代码未变；不制造项目回滚 |
| 已交付 | 撤回指定目标分支中的本任务交付改动 |
| 已被其他任务继承 | 展示关系，不能宣称覆盖这些副本 |
| 已在其他分支、远端或运行服务出现 | 本地撤回不自动代表全部位置撤回；推送部署另授权 |

终止只停执行，不自动回滚。撤回不删除任务历史，也不等于立即删除工作区；固定设计、操作、必要快照保留。后继仍引用的快照不能清理。只清旧目录不能声称代码已从项目消失。

本期明确要求已终止任务可撤回。已完成任务的撤回入口及权限仍为待明确扩展，不据本稿直接开放。

### 16.3 已交付代码的撤回步骤

1. 定位原交付、目标、交付前后提交及真实父关系。
2. 读取当前目标，核对其他交付、无法归属变化和未知操作。
3. 在隔离工作区中，对当前目标逆向应用本任务的实际交付改动。
4. 检查文本冲突、已知继承／依赖及必要检查结果。
5. 展示差异、保留内容、冲突和未验证范围。
6. 用户确认具体候选后，按预期目标执行受控更新。
7. 保存前后提交及执行事实，Git成功但写库失败时核对补记，不重复撤回。

目标变化须重新准备，不在项目工作区整仓reset，不将任务起点全量覆盖当前项目。合并提交保存父关系及差异方向，不能随意选择父提交逆向操作而误删其他任务改动。

### 16.4 冲突与依赖

文本冲突则等待AI处理；有明确后继继承或关联则展示并进入依赖处理；逆向应用无冲突且未发现关联，只能准备候选并检查，不能证明没有业务依赖。A新增接口、B新增调用页面时，删A可能无Git冲突但使B失效。

程序可提供继承链、改动和检查证据，不能理解所有业务依赖；自动准备候选不等于自动证明安全。无法可靠分离的后继改动不强行删除，不自动连带撤回其他任务。

若解除依赖需要改变业务行为或引入替代实现，经过文档和新任务，不能藏在“解决冲突”中直接新增设计。用户不手改代码。

### 16.5 记录与状态

每次撤回保存任务、范围、原交付／候选、当前目标起点、撤回候选、检查、用户确认及实际结果。状态草案为未撤回、撤回中、等待处理、已撤回、无需撤回；等待原因包括冲突、依赖、归属不明或结果未知，不再仅使用“需处理冲突”表达所有阻塞。

任务只显示汇总，真实结果按目标／操作记录。例如“已撤回目标分支中的本次交付；B仍保留继承快照”。不能一个绿色状态暗示所有分支、工作区和运行环境均已撤回。

### 16.6 已终止后的AI处理

终态任务可查询、对账及准备程序可完成的撤回候选。需要AI写代码解决冲突时，建立具有固定文档依据的新处理任务，关联原任务、撤回目标和限制；新工作区、新授权、新预算，原任务保持已终止。原撤回记录关联其结果，实际撤回完成后才更新事实。纯程序可完成的逆向应用不强制新增AI任务。

## 17. 新版本任务与代码继承：当前方案

文档与任务一对多、本期活动上限为1且设计支持未来并发的业务含义已明确。以下代码继承细节仍属当前方案，不表示已经实现或所有细节逐项获确认。

重新发起时：

- 默认从上一个已接收代码版本开始。

- 用户可明确选已终止任务的固定代码快照作为起点。

- 复用表示起点，不表示正确或验收通过。

- 先固定旧现场，再建立新工作区、新会话、新固定设计和授权；旧记录保留。

- 旧任务的问题与代码来源可追溯，旧会话里的决定不能自动变成新设计依据。

记录实际继承关系。新任务已依赖旧代码时，撤旧任务不能自动撤新任务，也不能只清旧目录就声称旧代码从项目消失。依赖解除、冲突处理和已被接收后的撤回语义仍需详细设计，不能承诺所有场景自动安全。

### 17.1 继承后的撤回分支

| 场景 | 处理 |
| --- | --- |
| B继承A快照但未交付 | 撤A不自动修改B工作区；保留B固定起点及来源 |
| A已交付，B随后交付且依赖A | 展示B关联，不自动撤B |
| A未单独交付，B继承后将组合代码交付 | 不能撤整个B冒充只撤A；针对当前代码准备去除A来源改动的方案 |
| B已改写A产生的代码 | 无法可靠分离则等待依赖／归属处理，不强删 |
| 用户决定保留组合结果 | 取消本次撤回并留记录，历史不删 |

清理A目录不能抹去经B交付的A来源代码；解除业务依赖经过文档和新任务。所有代码处理由AI完成，用户选择方案与确认结果，不手工编辑代码。

## 18. 验收、人工接收与实际交付：当前方案

### 18.1 固定候选

执行器空闲或说完成只触发核对。确认写入活动结束后固定候选，保存任务及设计Revision、代码起点／候选快照、真实差异、检查配置版本和必要环境。只记HEAD不足以覆盖未提交实现；复用Git保留实际快照，排除凭据、临时数据和日志。

检查和接收引用固定候选身份，不隐式跟随工作区最新内容。检查在隔离候选副本执行；检查或修复若改变待交付源码，形成新候选，不能用旧身份代表修改后代码。

### 18.2 检查事实与失效

检查入口来自已有配置或用户明确采用的配置，不由程序语义拆设计生成标准。记录候选、检查项、配置／环境、起止时间、实际结果及证据。模型补充测试不替代独立验收。

| 结果 | 处理 |
| --- | --- |
| 通过 | 仅证明指定候选、环境下该项通过 |
| 明确失败 | 保存预期依据、实际结果及缺陷记录，可反馈AI定位修复 |
| 无法执行 | 依赖／环境等条件不足，等待处理 |
| 中断／未知 | 不算通过，核对或按需重做 |

非零不能统一归为本次缺陷。原有失败、新失败和运行问题分别留事实，根因不明不编造。必检全部满足配置门槛才待接收，仍需人工按固定设计核对。无代码变化如实展示，原测试通过不证明新需求实现。

源码变化形成新候选，旧人工接收不适用；检查配置、命令或相关环境变化使受影响结果不能直接沿用；日志／备注／刷新不失效候选；文档当前版本更新不自动使旧任务候选失效。复用检查须有明确配置和可核对依赖，无可靠依据时重做相关必检，模型一句“不影响测试”不是跳过依据。

### 18.3 接收具体候选

接收页显示固定设计及当前文档版本差异、最终候选及相对目标差异、已做／失败／未做检查、未解决问题、执行器说明、仓库／目标分支及预期目标提交。用户选择接收、登记缺陷继续修复、转文档或终止，不猜自由文本意图，不要求额外严格业务JSON才能验收。

接收动作绑定任务、候选、检查依据、目标、预期目标提交、用户和时间；服务端再次核对身份和状态。页面打开后代码变化不能沿用旧接收。人工接收不等于交付，实际交付确认后才可完成。

### 18.4 目标变化与并发交付

多个任务可在独立工作区并行开发，同目标交付协调执行。A使C10变C11后，B读取C11，在隔离位置形成组合候选；冲突由AI处理并形成新候选，执行必要检查、展示相对C11差异，由用户接收；写入时再次核对仍为C11。目标再变则不执行旧计划，重新准备。自动合并无冲突也不能偷偷替换用户接受的组合代码。

WALL-E按仓库／分支协调，Git仍用预期旧值核对，以应对外部工具或其他实例。出现可能被覆盖的无法归属变化时等待，不强制覆盖；此为异常防护，不提供正常用户手改代码入口。

### 18.5 Git与数据库对账

交付前持久保存任务／候选／接收记录、目标及预期旧提交、计划交付提交与代码内容，以及未开始、执行中、未知、成功或明确失败事实。执行受控Git更新，再补记交付和任务完成。

恢复确认已发生则补记，不重复合入；确认未执行且条件有效才继续原操作；目标／环境改变重新核对；证据不足保持未知。当前HEAD不等于交付提交，不证明交付没发生，可能目标后来又前进；须结合保存提交身份和可用历史。Git与数据库不能伪装成一个原子事务。

### 18.6 交付与终止竞态

| 终止时机 | 处理 |
| --- | --- |
| 尚未开始Git交付 | 阻止交付，停相关活动后已终止 |
| Git已经开始、结果不明 | 终止中，核对原操作，不再交付或自动撤回 |
| 停止意图已接受，核对发现代码已交付 | 记录真实交付；确认停止后已终止，并展示“代码已交付、尚未撤回” |
| 已确认任务完成后收到终止 | 返回已完成事实，不改终态；后续撤回按允许范围处理 |

停止意图与交付事实分别保存，晚到结果不撤销已接受的终止，也不能隐藏进入目标的代码。不自动回滚；撤回须核对后继依赖和其他任务改动。完成不自动包含推送、部署或服务更新。

## 19. 终止与中断恢复：当前方案

先在事务中持久化终止意图并进入终止中，阻止新执行和模型调用，再请求abort并核对归属明确的工具／进程确已停止，最后进入已终止、释放活动名额。接口成功不代表全部子进程退出；在途请求继续结算，费用未知不清零。

晚到完成事件只作记录，不能把终止中或已终止改回执行或完成。

浏览器关闭/断网不取消后台任务。WALL-E、OpenCode或机器重启后先恢复观察和核对，不直接重发任务。不能保证网关中断期间执行无感持续。

持久化设计依据、工作区、会话、各类操作、预算和进程实例归属。不能只凭可复用PID辨认进程。

恢复核对：原状态/终止意图、服务/会话、工具和待处理请求、代码快照、未知模型和Git结果。

- 原执行可确认：重新接管，不建第二份。

- 待答问题存在：恢复显示，不重复。

- idle而完成不明：等待核对。

- 非终态任务的旧执行已停且会话完整：核对条件后可继续原会话；终态不复活。

- 非终态任务会话丢失而代码和依据完整：确认旧执行停止后可重建会话。

- 旧活动无法确认：不启动新写入者。

原任务依据不变时可重建会话，不因此新建业务任务；明确记录重建，不宣称继承全部模型记忆。原文和实际代码优先于摘要。

同一工作区单一有效控制和写入。租约失效/失联不证明旧进程已停。Windows具体方案仍待验证。

未知费用不清零，未知消息不重发，未知Git操作不重复。终止意图优先。代码/配置/必要环境一致的已完成检查可复用；中断检查标未完成，按需重做，不默认全量重跑。

终止优先于尚未发送的启动、继续和问题答复；这些操作发送前再次核对停止意图。检查与外部发送之间仍可能发生竞态，控制器必须发现并停止晚启动活动，不能靠一次数据库检查承诺无晚到执行。停止事实不明时保持终止中，不允许新写入者接管原工作区。

执行已停止但费用仍待核对时，可以记录已终止，保留未知费用／预留敞口继续对账；已终止不等于退款、费用清零或代码已撤回。

终止与交付交错的最终规则见第18.6节：已接受停止意图后发现代码已交付，保留交付事实，停止确认后仍已终止；已完成后才收到终止则返回已完成。终止不能自动抹去交付或执行整仓回滚。

终态后费用补记、结果核对及合法撤回均可独立记录，但不恢复原执行身份。需要AI代码处理时按第16.6节另建任务，不借原任务会话和预算继续写入。

## 20. 页面与操作：当前方案

文档侧提供创建代码任务入口，先准备固定设计版本、代码起点、真实环境、模型、授权和人民币预算，点击开始才执行。身份、Revision与确认事实复用现有能力；具体编码资格及是否设置确认门槛仍需设计，不能宣称V1.5已有编码准入。

代码工作区独立，包含：

- 任务信息：固定依据、代码起点、角色、状态、预算与用量。

- 执行记录：消息、工具、检查、问题及处理。

- 代码交付：实际差异、快照、验收和交付。

待处理操作按已知事件/原因展示。原问题、来源时间、执行关联、文档讨论及回执可查。查看设计只读，去文档处理保留双向链接。

待接收视图聚焦最终代码、检查、原文验收和目标；代码变化更新视图。执行阶段按后端/前端/联调事实，不生成重组的功能进度或伪百分比。

显示最后核对时间；失联显示核对中/等待，不假装仍正常执行。

页面结构按“文档→任务列表→任务工作区”设计。当前只有一个活动任务时可提供直达入口，接口和本地状态仍按任务ID定位。已终止可查看和撤回，已完成看交付；历史保留并支持重新发起，受本期活动名额约束。

文档更新后显示“任务依据版本／当前文档版本”及差异入口，不自动控制任务。开始、继续、答复、终止、验收、接收和撤回均定位明确任务；页面不能通过文档ID推断唯一任务。当前版本不因数据模型支持并发而开放多个活动任务。

任务详情同时投影任务版本／阶段、全部等待事项、进行中操作、固定候选、交付／撤回、预算、最后核对时间和可用动作。摘要与大段日志／差异／请求详情分开按需读取，不每次轮询全量返回。前端按钮由真实条件派生，服务端提交时重复核对。

页面明确区分动作已接受与执行成功、用户已批准与权限已生效、任务已终止与费用已核清、已终止与代码尚未撤回。已终止但在途交付确认成功时显示“已终止；代码已交付、尚未撤回”。撤回结果带目标范围及后继保留事实。

不提供代码手工编辑入口；配置、授权、缺陷记录、候选查看和用户确认不等于用户编写代码。刷新、重连、切页、关闭不自动执行／重试／恢复或取消任务。

## 22. 文档任务关系与并发准入：已明确方向及当前方案

已明确的用户要求：

本期同一文档同一时间只允许一个活动任务；设计从一开始支持同一文档同时多个活动任务，以便后续并行提效。这不是文档终身唯一任务，也不再作为待确认问题。

当前方案：文档对任务一对多，结束历史保留；任务各自固定设计版本、代码起点、工作区、会话、权限和预算。同一文档的任务可以绑定相同或不同Revision。提高并发上限不需要重做这些身份关系，但不表示当前已实现多任务运行。

当前准入草案：服务端max_active_tasks_per_document本期固定为1，不能由创建请求自行提高。活动状态口径见第10节；主文档占名额，关联材料仅被读取不占其任务名额。精确配置载体仍待实现设计。

创建事务：先查询幂等原结果，再取得写事务核对身份、版本、起点及活动数量，原子建立任务和回执。SQLite在读取数量前取得写事务，防止并发请求同时看到空名额；不设置任务文档唯一索引，不另维护易失真的活动计数器，事务内不调用Git、进程或模型。文档活动名额与工作区写入互斥是不同规则。

未来同一文档可有多个独立工作区并行执行，但同一工作区仍只有单一有效控制和写入者。终止、预算耗尽、问题和撤回均按任务处理；不能串到同文档其他任务。并发编码与目标分支交付分别控制，后继依赖和选择性撤回仍需详细设计。

## 23. 主流程接口契约：当前方案

以下路径省略项目现有API统一前缀。名称及字段是当前详细设计草案，尚未发布；完整Schema、错误编码和端到端实现仍待落地。既有HTTP响应为success／data／error／meta；code／data／details只属于内部应用结果，不混成外部响应。

### 23.1 统一规则与回执

所有写命令携带Idempotency-Key，沿用小写UUID v4；已有任务控制动作另带expected_state_version。同步本地完成200，持久接受后台操作202。每次HTTP有新request_id，重放返回原操作身份／回执。同键同输入不重复执行，同键不同输入冲突；严格校验未知字段。操作者来自既有运行上下文，不接受客户端自报批准人。

异步回执示意（身份数值仅示例）：

```json
{
  "success": true,
  "data": {
    "task_id": 123,
    "operation_id": 456,
    "operation_status": "PENDING",
    "task_status": "PENDING",
    "state_version": 2
  },
  "error": null,
  "meta": {
    "request_id": "00000000-0000-4000-8000-000000000001"
  }
}
```

202只表示已接受，不显示为执行成功。随后读任务／操作；不能把原成功回执当作最新状态。HTTP报错或响应丢失也不保证外部动作未发生，按原身份核实，不能换键重发碰运气。

### 23.2 创建任务

POST /documents/{document_id}/code-tasks

| 输入 | 含义 |
| --- | --- |
| design_revision_id | 主文档固定Revision |
| material_refs | 关联文档及固定Revision引用 |
| repository_id | 已允许操作的仓库 |
| base_snapshot_id | 真实代码起点 |
| target_branch | 预期交付分支 |
| execution_profile_ref | 已配置的模型／环境／检查配置版本 |
| authorization_ref | 本次有效执行授权 |
| budget_limit_cny | 人民币额度，十进制字符串，不用二进制浮点作为金额契约 |

主文档来自路径，不重复传正文身份。服务端读取核对固定材料，不信任客户端另传正文、摘要或已确认标记；核对活动名额后返回任务和待启动状态，不隐式编码。配置／授权必须解析到真实记录，引用不等于要求每项另建顶层管理系统。编码资格及确认门槛仍待具体化，不把V1.5确认能力误称已有编码准入。

### 23.3 开始、恢复与预算

| 入口 | 输入重点 | 行为 |
| --- | --- | --- |
| POST /code-tasks/{id}/start | expected_state_version | 首次启动，使用已固定任务输入 |
| POST /code-tasks/{id}/resume | 预期版本、恢复的操作或阶段 | 核对全部相关阻塞后恢复原位置 |
| POST /code-tasks/{id}/budget | 预期版本、新预算总额、调整说明 | 同步记录额度及审计 |

预算传新总额，不传重复叠加量；幂等及版本保护并发。追加不扩大权限／换模型，不自动解除未答问题。恢复不接受任意追加业务提示词，不能绕过文档流程。

### 23.4 问题答复与移交

POST /code-tasks/{id}/questions/{question_id}/responses

带会话身份、预期任务版本及action：

| action | 附加输入 | 实际发送 |
| --- | --- | --- |
| CITE_FIXED_BASIS | 任务固定材料中的出处引用 | 服务端读取的原文、版本和位置 |
| USE_FIXED_BASIS | 不添加业务规则 | 固定的按现有依据自行处理指令 |

提交再核对问题待答、会话有效、任务未终止、引用在固定材料内。运行配置通过独立受限操作调整，仅接受已定义字段，不能将任意答案伪装成配置。原生选项完整展示但不自动成为有效新规则。

POST /code-tasks/{id}/questions/{question_id}/handoff仅准备并关联移交材料，返回文档侧入口；不答复、不终止、不自动调用模型。相同源问题去重，记录关联既有讨论，不另建讨论系统。

### 23.5 缺陷修复

POST /code-tasks/{id}/repairs

输入含预期任务版本、当前候选、缺陷型文档固定记录及检查失败／问题证据引用。缺陷记录提供实际行为和原固定设计中的预期依据，是修复记录，不替换设计版本。程序核对身份、关联和明确动作，不证明自由文本一定只是缺陷；改变规则仍走新文档和新任务。

接收修复后旧候选保留历史但不能直接交付，AI形成新候选后重新检查。代码全部由AI处理，无用户手工代码入口。

### 23.6 接收与交付

POST /code-tasks/{id}/accept必传expected_state_version、candidate_id、verification_id、expected_target_commit。仓库及分支从任务／候选读取，不能接收时临时改交付目标。服务端核对候选、检查、问题和目标，保存人工接收及交付操作，返回202。

客户端不得提交“检查通过／交付成功”事实。接收时目标变化报冲突并重新准备；接收后写入前变化由交付记录反映，不强制覆盖。

### 23.7 终止

POST /code-tasks/{id}/terminate，输入预期版本及可选说明，不包含自动撤回。

非终态接受停止意图并返回202；已在终止中返回原停止操作，不发第二套；已终止返回事实；已完成返回已完成，不改终态。版本冲突读取当前状态并保留用户意图，不自动改版本无限重试；普通日志不增加控制版本而阻碍终止。费用和在途交付仍核对，不恢复编码。

### 23.8 撤回

| 入口 | 职责 |
| --- | --- |
| POST /code-tasks/{id}/withdrawals | 指定原交付／候选及范围，准备撤回方案 |
| POST /code-tasks/{id}/withdrawals/{withdrawal_id}/apply | 绑定具体撤回候选及预期目标提交，确认执行 |

准备返回实际差异、依赖、冲突及检查，不把范围隐含为全仓或所有位置。apply不能只传“确认”。需AI修复时关联新处理任务，原终态不复活。先落实已终止范围，已完成入口仍待明确。

### 23.9 查询、投影与错误

已有草案GET /code-tasks/{id}及GET /code-tasks/{id}/operations/{operation_id}分别读取任务和原操作。还需文档任务列表、候选／检查／差异、问题移交、调用预算、交付继承及撤回的只读入口，精确路径及分页Schema待定。

任务详情包含状态／版本、阶段、全部等待事项、进行中操作、固定候选、交付／撤回、预算摘要、最后核对时间及当前可用动作。服务端按结构化条件投影按钮，提交仍重新检查。大日志／差异／请求详情按需读，不每次轮询全量返回。查询、刷新、重连、切页不发模型、不重试、不隐式恢复或取消任务。

| 错误情形 | 页面及控制行为 |
| --- | --- |
| 任务版本冲突 | 刷新真实状态，保留原动作 |
| 主文档名额已满 | 展示可访问活动任务入口 |
| 问题失效／已处理 | 展示真实结果，不重复答复 |
| 候选／检查／目标变化 | 更新候选与差异，不沿用旧接收 |
| 预算不足 | 展示额度、预留和未发送请求 |
| 冲突操作进行中 | 进入原操作记录 |
| 外部结果未知 | 保留原身份核对，不换幂等键重发 |

优先复用既有错误类别，新增错误须进入真实HTTP白名单及接口契约，不原样泄露供应方异常、内部SQL或秘密。具体新增编码与完整details Schema尚待定；本表规定处理语义，不冒充已发布实现。

### 24.4 原生投递与中断

| 中断点 | 恢复要求 |
| --- | --- |
| 操作已存未开始发送 | 恢复原操作 |
| 记录开始后崩溃 | 先核对，不能认定未发送 |
| 原生已接收但回执丢失 | 查原会话；无法证明则等待 |
| 收回执未写库 | 核实补记，不重复投递 |

### 24.5 问题、权限与事件

- 批准但环境应用失败不放行；旧完成事件不撤停止意图。

### 24.7 完整停止与隔离
