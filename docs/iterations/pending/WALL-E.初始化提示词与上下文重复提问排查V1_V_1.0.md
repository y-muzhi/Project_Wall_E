## 1. 用户反馈与排查范围

用户反馈：已经说明模板只作为结构参考，需要先确认需求本身，模型仍反复询问目标、固定仓库范围和 AI 环节。核对实际业务数据库中最新调用 19／20 的 request_snapshot_json、已保存回答、实际模型输出及本地上下文代码。没有新模型调用，没有业务数据写入，没有测试或服务更新；本文件只记录诊断。

## 2. 当前实际请求格式

生产模型为 deepseek-v4-1-flash-260910，temperature=0，thinking.type=disabled，输出上限 8192。每次请求只有两个 Chat messages：

1. system：INITIALIZE_REQUIREMENT@v7 全文，加冻结输出 JSON Schema。
2. user：一个序列化 JSON 输入。字段依次为 schema_version、function_type、action_type、source_type、template、current_document、history、user_input、source、request_metadata。

因此页面对话并非按逐轮 user／assistant 消息原样发送；历史作为 user JSON 的 history 数组提供。原卡片不作为普通历史发送，正式回答已经保存问题、所选名称与填写内容。此次 source=null；任务为 IDEATION、CURRENT 为 v2。

最新调用 20 对应本地 21:56 的用户消息 37。实际 system 为 12059 字符，user JSON 为 293804 字符，Provider 记录输入 126002 token、输出 2075 token，finish_reason=stop。没有输出截断。实际缓存 cached_tokens=66432，不能把此次问题解释为没有命中缓存。

## 3. 可确定的上下文问题

### 3.1 初始完整需求被历史条数上限排除

model_context.py 只读取最近 10 条 TEXT／CARD_RESPONSE，随后才做预算处理。调用 19 的历史包括最初项目描述消息 18；调用 20 的历史为 20、22、24、26、27、29、31、33、34、35，消息 18 已不在实际请求中。

消息 18 包含“面向固定代码仓库与标准软件交付流程”“以统一需求规格为核心”“串联需求澄清、任务规划、代码修改、审查、测试与修复”“上下文选择与压缩”等完整背景。它不是被 Provider 丢掉，也不是本次 token 计数裁剪掉：count_attempts 的 removed_history_ids 为空；在查询时已先被 LIMIT 10 排除。扩大 token 总预算没有解决这层问题。

### 3.2 已回答信息确实传给了模型

调用 20 的实际 history 包含：消息 20／22／26 对核心目标、单一固定仓库、需求澄清的正式回答；消息 29 对自然语言输入、规格草稿＋澄清记录、多轮问答的正式回答；消息 33 的事实确认；消息 34 的程序已写入 v2 回执。

因此此次三道问题不是因为程序完全没回传答案。目标曾有不同选择，但消息 26 是最新明确选择。仓库和 AI 环节多轮一致；模型可以针对具体不清楚的细节提问，却再次返回整组相同问题。当前 system 也明确要求“最新明确选择优先”“已回答的普通问题禁止原样重问”，实际输出未遵守。

### 3.3 内容没有稳定的已知需求记录

当前只有最近历史、正文和固定模板，没有单独常驻的初始用户需求或已知事实集合。事实确认后正文只写入已确认的一行，其他已回答的信息仍主要存在于滚动历史中。也没有显式的“当前已知／待明确／下一步”信息供模型使用。

完整模板为 33301 字符／85865 UTF-8 字节；CURRENT 为 322 个区块，包含 Markdown 与 plain_text 两份表达，正文文本 JSON 为 187363 UTF-8 字节，大部分仍是模板占位。相比之下，当前历史只是短问答及两份冗长事实确认。可以确定请求内容主要是文档模板及其重复表达；不能单凭这些日志断言模型内部的注意力或具体推理原因。

## 4. 可确定的提示词问题

### 4.1 初始化任务偏向逐项生成正文与确认写入

v7 的任务重点是“信息足够时，依据答案拟定具体正文并生成完整声明 CONFIRM”，并把“保留全部锁定标题”置于任务起点。没有明确规定先还原用户完整需求、区分系统目标与实现分工、整理整体需求大纲，再处理正文变更。用户表达“先跟我确认需求”后，调用 20 改回初始三题，说明这一阶段推进没有形成可靠状态。

### 4.2 展示规则已经改变，system 仍要求旧规则

FLOW-003 已取消 message 与 card_text 的等价展示门禁，界面可展示简短说明；实际 v7 仍要求“message必须精确等于card_text，不用摘要替代”，并用大段文字要求每个问题、选项、说明、影响、风险及完整原文在 message 中重新序列化一次。卡片字段已经承载这些信息，system 又要求重复输出。最新返回因此出现“模型说明原文”的旧序列化格式。

### 4.3 写入链路已经改变，system 仍要求模型再次生成补丁

FLOW-004 已把完整事实确认交给 C06 程序事务直接采用；实际 v7 仍要求“CONFIRM选confirm后依完整证明生成confirmed_fact_patches”。提示词与当前程序职责没有同步。消息 34 实际证明直接写入修复已经生效：CURRENT v2，Run15 没有新 LLMUse。这不是当前重复普通问题的唯一原因，但属于明确的新旧规则并存。

### 4.4 问题设计混淆互相兼容的维度

“AI模块与确定性程序协同”是实现分工，“以统一需求规格为核心”是核心产物。最初用户需求同时包含两者；模型反复把它们作为同一单选题的不同选项。调用 19 还把二者描述为互斥。不能用这个单选反复变化就认定用户需求发生矛盾，应把目标、产物、分工分别整理，再只问实际缺口。

## 5. 整改方向（尚未实施）

1. 新冻结提示词版本明确：先理解需求、整理已知与缺口、围绕缺口澄清、形成整体大纲；模板只约束最终组织方式，不能按模板占位逐行机械提问。用户改变协作方式不等于清空已确认内容。
2. 同步 FLOW-003／004：message 使用简短人类可读说明，卡片结构只返回一份；明确已确认具体变更由程序写入，下一轮从新 CURRENT 继续，不再次要求生成相同写入补丁。
3. 初始用户需求与已确认需求形成常驻上下文，不能和普通聊天一起受 LIMIT 10 淘汰。保留来源身份与完整用户原文；不能由模型随意压缩成新的未确认事实。
4. 对既有正式回答按问题维度整理，最新明确回答优先，保留历史修改来源。整理不是正文写入确认；没有用户确认仍不能擅自写正文。
5. 已知／待明确／阶段推进作为清晰上下文提供；普通重复返回仍按 FLOW-003 展示，不恢复拦截、自动重试或额外真实模型调用。
6. 减少完整模板、CURRENT Markdown、plain_text 的重复表达时，需要新输入／冻结版本及对应离线检查；不能直接改历史冻结资源或凭本次排查宣称模型质量已改善。

本轮没有修改生产提示词、预算、模型参数或服务，也未执行用户最新卡片。以上具体输入与输出证据支持本地封装存在问题；模型在已有答案与禁止重问规则下仍返回重复题，也是实际返回行为。日志不提供模型内部推理，不能据此把全部原因归到某一个因素。
