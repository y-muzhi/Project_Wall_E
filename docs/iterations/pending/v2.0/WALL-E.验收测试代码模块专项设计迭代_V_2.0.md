# WALL-E 验收测试代码模块专项设计迭代

日期：2026-11-03（Asia/Hong_Kong）。编号：AT20-01。状态：DRAFT／后续方向专项设计，未排期、未实施、未验证、未合入正式设计。

## 1. 专项定位与本轮边界

验收测试代码模块不是“写几个测试用例”，也不是“运行一次pytest／npm test”。它负责把固定需求转成可审查、可执行、可验证、可维护的验收依据，并向代码任务及自迭代评测提供可信结果。

本专项覆盖：

- 需求行为梳理、验收覆盖计划和测试风险设计。
- 测试用例、断言、测试数据、环境和清理规则的产生与评审。
- 测试资源编译、版本发布、测试自身有效性验证和稳定性验证。
- 公开测试、保留测试、回归测试及人工核对范围的组织。
- 执行结果、失败归因、证据、版本对照和长期维护。

[首个任务管理API定义](WALL-E.自迭代首个验收测试包定义迭代_V_2.0.md)只是其中一个最小案例示例，不再承担整体模块设计。本专项是独立大模块；后续是否进入某个软件版本，仍需单独排期。

本轮只写设计文档，不编写实际测试代码、runner、参考实现或缺陷样本，不安装依赖，不启动服务，不运行测试、浏览器、模型或计数，不修改业务数据库和正式资源。

## 2. 与现有设计的边界

### 2.1 现有基础

[V2.0独立检查设计](WALL-E.独立检查资源与结果准入迭代_V_2.0.md)及后端INF-CODE-CHECKS已经定义：

- PROJECT_COMMAND只记录候选项目自己的命令结果，不能替代独立功能验收。
- CONTROLLED_ASSERTION由受控程序比较外部固定预期。
- RunnerBundleManifest、CasePackManifest、CheckSetVersion及Verification负责资源和执行事实。
- CLI／HTTP／BROWSER受控输入、候选只读副本、独立身份、停止清理和未知结果保护。
- 候选输出、JUnit／TAP／JSON、自报PASSED及退出0不能直接成为独立功能结论。

这些能力目前仍是DRAFT，runner和案例资源未发布，不能称为现有可运行能力。

### 2.2 本专项补什么

现有检查协议回答“怎样安全执行并相信结果”；本专项回答：

1. 应当测什么，为什么这些测试足以覆盖固定需求。
2. 预期结果从哪里来，怎样避免根据错误实现编写测试。
3. 测试数据、状态、环境和跨层流程怎样组织。
4. 怎样证明测试不是空测试、永远通过或不稳定。
5. 测试随需求、候选、runner和环境变化后怎样维护。
6. 测试结果怎样用于WALL-E版本对照，而不是只生成一次绿色报告。

### 2.3 不改变的现有职责

- Revision仍是固定需求依据，不把测试计划变成新的需求正文。
- CheckSetVersion仍选择检查项、阶段和必需范围。
- Verification及VerificationCaseResult仍保存实际检查结果，不另建第二套执行账。
- CodeCandidate仍是唯一被测代码内容，检查不能改候选并自动采用。
- Acceptance仍是真实用户接收事实，测试通过不自动产生Acceptance。
- EvaluationCampaign负责WALL-E版本评测，本模块只提供验收依据和结果。

## 3. 设计原则

1. **先需求，后测试，再看实现**：测试预期来自固定Revision，不来自候选当前输出。
2. **测试也需要验收**：测试代码和测试数据必须先证明有效，才能评价别人。
3. **通用执行，定制业务**：runner、协议和断言操作复用；业务行为、数据和预期按项目固定。
4. **正面与负面同时设计**：不仅检查正常操作，还检查边界、错误、状态不变和恢复。
5. **自动与人工分开**：无法可靠自动判断的语义明确列MANUAL，不伪装自动覆盖。
6. **公开与保留分层**：公开测试帮助构建，保留测试检查泛化；两者都不可由候选修改。
7. **失败不自动重试**：重试不能把不稳定测试涂绿，也不能重复有副作用的操作。
8. **版本变化不追溯改判**：需求、测试、runner或环境变化形成新依据，旧结果保留。
9. **不迷信单一指标**：测试数量、代码覆盖率、通过率和变异检出率都不能单独证明需求完整。
10. **程序边界不由提示词代替**：访问、写入、网络、进程、结果身份和清理由程序及OS边界执行。

### 4.1 四个平面

| 平面 | 主要职责 | 不能承担 |
| --- | --- | --- |
| 计划平面 | 需求行为、覆盖、风险、用例和人工范围 | 不直接判候选通过 |
| 资源平面 | 测试包编译、固定内容、依赖、有效性和发布 | 不在执行中改测试 |
| 执行平面 | 固定候选、受控运行、真实结果、停止清理 | 不理解自然语言或自动补预期 |
| 评价平面 | 结果聚合、失败归因、趋势和新旧对照 | 不伪造人工接收或自动修改WALL-E |

## 5. 对象与数据边界

### 5.1 核心对象

| 对象 | 含义 | 关键规则 |
| --- | --- | --- |
| AcceptanceTestPlan | 某项目／评测案例的验收测试工作身份 | 只作身份和导航，不保存可变正文 |
| TestPlanVersion | 一次固定的验收测试计划 | 固定需求来源、覆盖矩阵、用例、数据／环境计划和人工范围 |
| TestCaseDefinition | 一项可评审的验收行为 | 稳定case_id，含依据、前置、步骤、断言、数据和清理 |
| AcceptanceTestPack | 可执行测试资源身份 | 具体TestPackVersion不可变，沿受控资源目录管理 |
| TestPackValidation | 测试包自身的有效性证据 | 绑定测试包摘要、参考结果、缺陷样本、稳定性和人工评审 |
| Verification | 一次真实执行 | 复用现有对象，不复制为TestExecution新账 |

TestPlanVersion与TestPackVersion分开：前者表达“要测什么”，后者表达“实际怎样执行”。修改计划不自动改变已发布测试包；修改runner也不需要改写业务计划，但必须重新核对兼容及结果适用范围。

### 5.2 不新增的平行系统

- 不建立另一套需求、缺陷、代码候选、模型调用或人工接收系统。
- 不把每次测试执行变成新的顶层业务项目。
- 测试数据模板、fixture、断言库和驱动配置是受控资源子项，不分别建设独立工作流。
- AI测试作者和审阅者是明确任务职责，不建立长期Agent记忆或角色聊天大厅。

## 6. 需求行为与判断依据

### 6.1 从需求条目到可观察行为

测试计划先把固定需求拆成可观察行为，但不改变原业务含义。每项行为至少回答：

- 来源是哪份文档、哪个Revision及哪段原文。
- 谁在什么前置状态下执行什么操作。
- 可以观察到的正常结果是什么。
- 哪些已有状态必须保持不变。
- 非法输入、越界、冲突和不存在对象应怎样处理。
- 是否需要跨页面、跨接口、重启或恢复后才能观察。
- 哪些部分只能人工判断。

“系统应快速”“页面应美观”“代码应优雅”等不能由程序直接生成可靠字面断言，应转成明确指标或人工核对项，不能暗中编造阈值。

### 6.2 Oracle：判断对错的依据

本设计中的Oracle指“怎样知道结果正确”，按可靠性分层：

| 类型 | 示例 | 使用限制 |
| --- | --- | --- |
| 字面契约 | 状态码、字段值、可见文本、退出码 | 必须来自固定契约，不补需求外字段 |
| 状态关系 | 完成时间不变、失败无新增、删除后不可见 | 同时核对目标变化和不应发生的变化 |
| 不变量 | 库存不为负、同一工单不重复、金额守恒 | 不变量需有明确需求依据 |
| 跨层一致 | 页面显示与真实接口／持久化结果一致 | 不能只读同一缓存证明端到端 |
| 参考对照 | 与已审定参考行为比较 | 参考实现也可能错误，仍需需求评审 |
| 人工语义 | 交互可理解性、视觉质量、复杂业务合理性 | 明确MANUAL，不写成自动PASS |
| 模型审阅 | 提供可能遗漏及出处 | 只作建议，不单独决定通过 |

### 6.3 不采用实现反推预期

禁止以下路径：

- 先运行候选，再把实际输出保存成预期。
- 读取候选数据库表结构或内部函数名来决定业务测试。
- 因候选无法通过而降低断言，除非先证明需求或测试有误并发布新版本。
- 用候选自己的测试覆盖率、测试数量或自报结果证明独立验收完成。

## 7. 验收覆盖计划

### 7.1 覆盖矩阵

TestPlanVersion为每个固定行为登记：

| 字段 | 含义 |
| --- | --- |
| behavior_id／basis_refs | 稳定行为身份及真实需求出处 |
| importance | BLOCKER／CRITICAL／NORMAL；来自业务影响评审，不由测试作者随意降低 |
| coverage_kind | AUTO／MANUAL／NOT_APPLICABLE／UNCOVERED |
| positive／negative／boundary | 正常、失败及边界覆盖分别关联用例或说明 |
| state／recovery | 状态不变、持久化、取消／恢复等适用覆盖 |
| case_ids／manual_items | 自动用例或人工核对项的真实关联 |
| reason | MANUAL／NOT_APPLICABLE的具体理由；UNCOVERED只能存在于未发布草稿 |

发布计划时，BLOCKER／CRITICAL不得UNCOVERED；AUTO必须映射实际受控用例，MANUAL不得写成自动通过。覆盖率只是导航，不能替代人工审阅需求是否遗漏。

### 7.2 风险驱动，而不是平均铺测试

优先覆盖：

- 一旦出错会导致数据错误、权限越界、重复副作用或无法恢复的行为。
- 跨模块契约、共享状态、并发及外部依赖边界。
- 历史缺陷和WALL-E新旧对照中曾退化的行为。
- 用户需要反复纠正或模型容易误解的规则。
- 重启、取消、超时、断线和环境不足等容易假成功的流程。

普通展示细节可以较少自动化，但不得因容易测试就把大量低价值测试当作高覆盖。

### 7.3 每个行为的最低思考清单

适用性可以不同，但计划必须逐项决定，而不是默认忽略：

1. 正常路径。
2. 非法输入及边界值。
3. 不存在、冲突、重复及并发。
4. 权限和未授权访问。
5. 状态变化及无关状态不变。
6. 刷新、重启、取消、超时和恢复。
7. 跨层真实联通。
8. 人工语义和视觉范围。

## 8. 测试分层与类型

| 层次 | 主要证明 | 不能单独证明 |
| --- | --- | --- |
| 内容完整性 | 被测候选与固定包一致，输入未被检查修改 | 业务功能正确 |
| 项目命令 | 候选自己的编译、类型、测试等命令真实退出 | 独立功能验收；候选可修改这些命令 |
| CLI／HTTP契约 | 固定输入下的接口和命令行为 | 页面可用、完整跨层流程 |
| 浏览器组件／前端 | 在受控替身下页面交互和展示 | 真实后端联通 |
| 真实端到端 | 真实候选前后端、数据及用户路径共同工作 | 所有语义和视觉质量 |
| 状态与恢复 | 持久化、幂等、取消、重启和异常后的真实状态 | 未声明故障下的普遍可靠性 |
| 安全边界 | 固定权限、目录、网络及测试资源保护 | 通用渗透测试或绝对安全 |
| 非功能 | 需求明确的性能、容量、兼容或可访问性指标 | 未定义阈值下的“性能很好” |
| 人工验收 | 自动测试难以表达的语义和体验 | 命令实际执行及程序事实 |

后端交接、前端交接、联调和最终验收选择不同层次。前端HANDOFF可以使用受控API替身；最终ACCEPTANCE必须包含真实候选前后端联通，不得只用替身。

## 9. 测试用例模型

### 9.1 稳定结构

TestCaseDefinition至少包含：

- case_id、name、version_history及basis_refs。
- level、visibility=PUBLIC／HELD_OUT、required及importance。
- preconditions、fixture_refs、environment_refs。
- 有序steps及step_id。
- 有序assertions及assertion_id。
- side_effect_class=READ_ONLY／PRIVATE_WRITE／RESTART／CONTROLLED_FAULT。
- cleanup、timeout_seconds及结果保存要求。

case_id跨版本保持稳定，便于新旧对照；含义改变时优先新case_id，不在同一ID下悄悄变成另一项测试。

### 9.2 步骤与断言分开

步骤只描述有界操作，断言只描述可观察预期。每个用例至少一个断言；准备数据、启动服务和点击按钮本身不算断言。

断言类型按受控runner支持范围选择：

- 值、结构、字段存在／缺失及类型。
- 集合数量、成员、唯一性和顺序。
- 状态变化及指定字段不变。
- 时间先后、数值范围及明确容差。
- 跨步骤引用的一致性。
- 访问被拒绝、无新增／无删除等副作用约束。

### 9.3 动态值和状态流

真实流程常需要先创建对象，再使用返回ID。后续CasePack扩展只允许数据型绑定，例如：

`bind={from_step,json_pointer,value_type,required}`，后续步骤以受控变量引用该值。

变量绑定不是代码执行，不允许函数、表达式、eval、动态import或候选回调。类型不符、缺字段或绑定失败时结果UNKNOWN／UNAVAILABLE，不拿空值继续执行写操作。现有CHECK20-CONTROL-1尚未定义该扩展；扩展未发布前，需要动态ID的案例不得宣称可执行，也不能用任意脚本绕过。

### 9.4 清理是用例的一部分

每个有副作用用例必须声明数据、服务、进程、文件及网络资源的收尾方式。测试失败、取消或超时也进入收尾；清理未知时保留断言事实，但整项不得合格。

## 10. 测试数据与环境

### 10.1 数据分层

| 数据类型 | 规则 |
| --- | --- |
| 固定输入 | 版本化保存，覆盖正常、边界和非法值；不包含真实秘密 |
| 初始状态 | 通过公开API或受控fixture适配器准备，不能由候选脚本决定评测预期 |
| 派生数据 | 只使用受控变量绑定和确定规则，不随机生成不可复现预期 |
| 时间／随机 | 优先比较关系和范围；需要固定时钟时使用已批准控制入口，不修改用户系统时间 |
| 大规模数据 | 只在明确容量／性能测试中使用，与普通功能数据分开 |
| 故障数据 | 损坏、冲突、迟到、重复及中断输入有独立身份和清理范围 |

### 10.2 环境记录

每次执行固定并记录：候选、测试包、runner、CheckSet、依赖锁及实际解析依赖、浏览器、操作系统支持组合、端口、数据目录和离线替身版本。

环境不可用是UNAVAILABLE，不是产品FAIL。依赖缺失不能在检查中隐式下载；获准的环境准备形成新EnvironmentRecord后才执行。

### 10.3 真实依赖与替身

- NONE：无外部依赖。
- OFFLINE_STUB：验证声明的离线交互，记录替身能力范围。
- REAL_CANDIDATE：被测前后端和持久化必须是真实候选。
- 真实供应商、短信、支付、模型等效果不能用替身冒充；需要时另立渠道验证和预算。

## 11. 测试编写与AI辅助

### 11.1 标准工作流

1. 用户选择固定Revision、代码起点和验收范围。
2. 系统只读取得需求，生成或人工填写TestPlanVersion草稿。
3. 逐行为确定覆盖、风险、正常／负面／边界和人工范围。
4. 形成结构化用例、数据、断言及环境需求。
5. 人工评审需求忠实度、遗漏、可执行性和副作用。
6. 编译为测试包并执行静态资源校验。
7. 进入第12章有效性及稳定性验证。
8. 发布后才可以被可执行CheckSet引用。

创建和编辑计划不执行候选、不启动模型，除非用户明确发起独立AI起草任务。

### 11.2 AI可以做什么

- 根据固定Revision提出行为清单、风险和测试草稿。
- 指出需求歧义、缺失错误规则和无法自动判断的部分。
- 生成结构化CasePack输入、数据建议及需求追溯。
- 根据测试结果提出测试维护建议。

### 11.3 AI不能做什么

- 读取被测候选后反推预期。
- 自行决定需求外业务规则或通过阈值。
- 在同一隐藏上下文中既生成保留测试又执行被测构建。
- 直接发布测试包、修改已引用版本或上传PASS结论。
- 用另一次模型赞同代替人工评审、真实执行或变异验证。

AI起草和AI审阅若使用模型，都需要独立次数、预算和审计。默认不为每个用例串联隐藏规划／审阅调用。

## 12. 测试包自身的验收

### 12.1 四道门槛

| 门槛 | 必须回答 | 未满足时 |
| --- | --- | --- |
| 结构有效 | 资源完整、ID唯一、每例有断言、Schema及容量合法 | 不能发布 |
| 需求忠实 | 人工确认每项预期有依据，覆盖和MANUAL范围合理 | 不能作为需求验收 |
| 缺陷检出 | 合格参考通过，关键缺陷／变体能被指定测试检出 | 不能作为正式评分依据 |
| 稳定可重复 | 预先规定次数的重复执行无未解释波动，清理完整 | 保持未验证或隔离，不靠重试涂绿 |

### 12.2 合格参考与缺陷样本

- 合格参考用于证明测试环境及预期能成立，不证明参考实现业务绝对正确。
- 缺陷样本针对需求中的重要行为设计，例如缺字段、状态不变、错误接受、重复副作用、重启丢失、跨层使用替身。
- 每个BLOCKER／CRITICAL行为至少有一个有效负面控制，或明确说明无法变异的原因及替代验证。
- 变异样本与候选隔离，不进入构建材料，不被测试包在执行中修改。

变异检出率用于发现测试盲点，不作为唯一质量分。大量无关变异被检出，也不能弥补关键行为没有测试。

### 12.3 稳定性与 flaky 测试

- 重复次数、环境和通过条件在看到结果前固定，全部结果保留。
- 出现偶发失败时标为稳定性不足，检查等待、时间、端口、共享数据和清理。
- 不允许自动重试到一次成功后发布。
- 被隔离的不稳定必需测试意味着覆盖不足，不是直接从分母删除。
- 修复测试本身形成新TestPackVersion和新Validation，旧执行结果保持原样。

### 12.4 发布状态

建议资源状态为DRAFT／REVIEWED／VALIDATED／PUBLISHED／RETIRED。状态名不是证据：PUBLISHED必须能回查真实Validation；RETIRED只停止新引用，不删除历史或使旧结果失效。

## 13. 编译与受控执行资源

### 13.1 计划到资源的编译

编译器把TestPlanVersion转为TestPackVersion／CasePackManifest，执行：

- 校验需求引用、用例／步骤／断言ID和资源容量。
- 固定数据、变量绑定、环境及清理依赖。
- 生成公开和保留资源清单，防止可见性标错。
- 计算完整文件摘要并检查无候选路径、秘密和外部地址。
- 输出缺失能力和不支持步骤，不把复杂用例静默删成简单用例。

编译成功只证明资源结构形成，不代表有效性验证或通过候选。

### 13.2 任意测试代码的位置

普通业务用例优先使用结构化CasePack和可信断言库，避免每个项目注入任意Python／JavaScript。确需复杂算法断言时：

1. 将通用断言能力加入受控RunnerBundle，单独评审和验证。
2. 或把项目专用可信测试代码作为独立受控资源包，经代码审查、完整摘要和准入后运行。
3. 候选不得动态加载、覆盖或配置这些测试代码；执行身份仍与被测TASK分开。
4. 测试代码的任意性不能绕过目录、网络、进程、输出和清理边界。

不能因为模块名叫“验收测试代码”，就把未审查脚本直接放进候选目录运行并称为独立验收。

### 13.3 执行选择

- 开始执行前固定selected_check_ids、case集合和断言集合。
- 正式自迭代评测执行该SuiteVersion全部必需项，不因耗时临时减少。
- 交接检查按真实阶段选择，后续候选变化后重新核对全部受影响项。
- 同候选结果复用沿现有严格条件；不跨候选缓存。
- 首期同任务串行，无自动重试、模型裁判或自动AI修复。

## 14. 防作弊与保留测试

### 14.1 公开测试

- 在构建前作为只读固定材料提供，帮助理解验收方式。
- 公开测试通过不等于整体验收通过。
- 构建侧不能修改公开包、runner、结果通道或依赖锁。
- 公开测试的详细程度在计划评审时决定，不能因公开而省略关键负面路径。

### 14.2 保留测试

- 源码、夹具和预期不进入构建工作区、模型上下文、公开差异或普通请求审计。
- 只在固定候选后由评测侧注入受控执行。
- 访问控制由目录身份、权限和真实执行来源执行，不只靠“不要读取”的提示词。
- 保留测试不是绝对保密承诺；其使用记录、异常访问和泄露疑虑必须可审计。

### 14.3 评测前固定规则

- 测试集、必需断言、评分规则和采用门槛在看到候选前固定。
- 候选形成后不得临时删掉失败用例、改MANUAL或降低importance。
- 测试包确有问题时，原结果标为测试依据失效，发布新版本后重新执行；不改写历史为PASS。
- 保留测试反复用于调参后，应承认其已变成开发集，并补充新的保留覆盖。

## 15. 执行生命周期与故障处理

### 15.1 标准生命周期

1. 核对计划、测试包、Validation、CheckSet和候选身份。
2. 固定本次范围和原Operation／Verification／Item。
3. 物化独占候选副本、测试数据和受控资源。
4. 准备真实候选或受控替身，证明端口、进程和端点归属。
5. 按固定顺序执行步骤和断言，逐项保存事实。
6. 停止应用、driver及子进程，核对输入未改和资源收尾。
7. 计算Item及整体资格，展示未覆盖、人工和未知范围。

### 15.2 结果分类

| 结果 | 含义 | 是否可归为产品缺陷 |
| --- | --- | --- |
| PASSED | 必需步骤和断言完整执行且符合固定预期，收尾有效 | 否 |
| FAILED | 可信观察与固定预期明确不一致 | 可以，但仍需人工确认业务归因 |
| UNAVAILABLE | 资源、依赖、隔离或端点能力不可用 | 否，先修环境 |
| UNKNOWN | 已执行但观察、身份、帧、停止或结果无法核清 | 否，先核对原操作 |
| NOT_RUN／CANCELLED | 未执行或明确取消 | 否，不算通过 |

### 15.3 不自动重试

- HTTP写操作、浏览器点击和故障注入结果未知时，只核对原操作。
- 明确需要重新检查时形成新Verification，不覆盖旧Item。
- 迟到事实只补原历史，不恢复旧执行身份或覆盖新候选。
- 超时必须先核清活动停止，不能把“到时”同时当作产品失败和进程已停。

## 16. 结果证据与失败归因

### 16.1 最小证据

每项保存：候选、需求、测试包、runner、环境、步骤、断言、实际有界值、结果、时间、原操作及停止／清理状态。敏感值沿既有脱敏和容量规则处理。

产品正常业务Case记录持久保存；项目开发验证文档仍只留Markdown，不保留第二套临时JUnit、截图、trace或HAR。

### 16.2 失败分流

| 分类 | 判断依据 | 后续处理 |
| --- | --- | --- |
| 产品实现偏差 | 可信测试有效，需求明确，实际行为不符 | 回原CodeTask缺陷流程 |
| 测试缺陷 | 预期无依据、断言错误、fixture错误或参考对照不成立 | 测试包失效并发布新版本 |
| 需求歧义／缺失 | 无法从固定Revision确定唯一预期 | 转文档讨论，不自动补规则 |
| 环境／driver故障 | 无法准备、身份不明或资源异常 | 修环境，形成新环境证据 |
| 结果未知 | 已发生操作但结果或收尾不完整 | 核对原记录，不重放副作用 |
| 人工待判定 | 自动结果不能覆盖语义 | 保持MANUAL／INCONCLUSIVE |

失败归因不能仅凭错误文本由模型猜测。测试失败不应自动触发AI修复；原代码任务仍要求明确缺陷和授权。

## 17. 版本、回归与维护

### 17.1 变化影响

| 变化 | 必须处理 |
| --- | --- |
| 固定需求Revision变化 | 新TestPlanVersion，评审行为／覆盖／用例影响；旧任务仍按原依据 |
| 用例、断言、fixture或可见性变化 | 新TestPackVersion和新Validation，新SuiteVersion引用 |
| runner／断言库变化 | 核对兼容及受影响资源，旧执行不追溯改判 |
| CodeCandidate变化 | 新Verification，旧结果不用于新候选 |
| 依赖／浏览器／OS支持组合变化 | 新EnvironmentRecord，必要项重新执行 |
| 仅页面文案或日志展示变化 | 不影响原事实，但读取展示需保持历史语义 |

### 17.2 回归集维护

- 每次已确认产品缺陷评估是否形成稳定回归用例。
- 每次WALL-E退化优先补入对应评测案例，而不是只改提示词后观察一次。
- 用例删除需说明原需求不再适用或替代覆盖，不得为减少失败而删除。
- 重复用例可以合并资源，但保留原case_id映射和历史比较关系。
- 保留集频繁用于开发后重新划分，不继续宣称完全未见过。

### 17.3 测试资产健康度

持续观察：长期未执行、稳定性不足、无需求链接、无负面控制、只覆盖实现细节、重复高和维护成本高的测试。健康度用于维护优先级，不自动删除测试或改变通过规则。

## 18. 指标与评价方式

### 18.1 测试模块自身指标

- 需求覆盖：BLOCKER／CRITICAL的AUTO／MANUAL／UNCOVERED分布。
- 有效性：合格参考结果、关键缺陷检出及未验证行为。
- 稳定性：预先固定重复次数中的波动、环境失败和清理失败。
- 误报：因测试／环境错误导致的产品FAIL疑似及确认数量。
- 漏报：人工或后续使用发现但自动测试未覆盖的缺陷。
- 成本：测试准备、执行、维护时间及计算资源；模型起草费用单列。

### 18.2 对WALL-E的评价输入

- 首次候选及最终候选的分需求结果。
- 公开与保留测试分别结果，避免只优化公开题。
- 缺陷、返工、人工纠正、真实费用和时间。
- 同一测试包下新旧版本逐case改善／退化／不变／证据不足。

不把“测试数量更多”“代码覆盖率更高”“模型评分更高”作为WALL-E改进的替代指标。

## 19. 页面与交互职责

| 页面／区域 | 主要内容及动作 |
| --- | --- |
| 测试计划概览 | 固定需求、版本、风险、发布状态、有效性和未解决问题 |
| 需求覆盖矩阵 | 逐行为查看正常／负面／边界／恢复、AUTO／MANUAL及真实用例链接 |
| 用例设计 | 编辑结构化前置、步骤、断言、数据、可见性、副作用和清理；显示不支持能力 |
| 数据与环境 | 管理fixture引用、运行时、依赖、真实／替身范围及秘密边界 |
| 测试包验证中心 | 合格参考、缺陷样本、重复稳定性、人工评审和失败原因 |
| 版本与差异 | 比较计划／测试包变化，查看受影响Campaign和历史结果，不编辑已引用版本 |
| 执行结果 | 按Verification、case和assertion查看真实结果、证据、未知及清理状态 |
| 失败复核 | 区分产品、测试、需求、环境和未知，转原缺陷／文档／维护入口 |
| 测试资产维护 | 回归、保留使用、稳定性、重复和长期未执行项 |

### 19.1 交互底线

- 创建／保存草稿不执行测试；AI起草、验证、发布和执行分别是明确动作。
- 发布按钮在缺评审、参考、缺陷检出或稳定性证据时禁用并说明具体原因。
- 已接受动作刷新后恢复原操作，不重复启动服务或执行写步骤。
- 所有区域覆盖加载、空数据、失败／无权限、筛选无结果、页越界和恢复。
- 空计划、空覆盖、空测试、空验证和空执行结果分别使用所属业务文案，不用统一空态。
- 页面不提供任意脚本执行、客户端判PASS、自动重试到通过或修改已发布版本的入口。

## 20. 接口、存储与实现定位草案

### 20.1 后续能力分组

| 能力 | 输入及结果 | 关键限制 |
| --- | --- | --- |
| 计划管理 | 创建Plan、发布PlanVersion、查询覆盖和差异 | 固定Revision；发布不生成候选或执行模型 |
| AI起草／审阅 | 明确范围、资源版本、预算，输出结构化建议 | 不直接发布，不读取保留构建上下文或候选反推预期 |
| 测试资源编译 | PlanVersion→TestPackVersion及不支持项 | 不静默删除复杂断言；完整摘要和可见性检查 |
| 有效性验证 | 参考／缺陷／重复执行→TestPackValidation | 真实证据；无自动重试涂绿 |
| 配置引用 | CheckSetVersion选择已发布包和runner | 未发布／不兼容资源ready=false |
| 执行与读取 | 复用Verification及CaseResult查询 | GET不执行；客户端不上传权威结果 |
| 维护与对照 | 版本影响、回归、保留使用和逐case比较 | 不改写历史，不跨测试包伪直接比较 |

具体HTTP、Schema、状态动作、幂等、事务和恢复矩阵在所属版本后端正式设计中展开；页面细节归前端正式设计，本专项不成为第三份现行共同规格。

### 20.2 实现边界

- 计划、覆盖和用例可以使用独立业务模块；执行仍调用code_tasks检查路径。
- 资源编译、校验和摘要属于受控基础设施，不放在浏览器。
- 测试包和参考资源位于候选可写根外，摘要及引用沿INF-CODE-CONTENT资源机制。
- 模型起草复用LLMUse及授权，不建立无归属测试生成调用。
- 实施后再记录真实代码路径；本专项不声称目标目录已经存在。

| TC-AT-12 稳定性不足 | 固定重复执行出现偶发失败 | 所有尝试保留，包不通过稳定性门槛，不重试涂绿 |
| TC-AT-13 不自动重试 | 写操作超时或浏览器点击结果未知 | 核对原操作，不重复副作用 |
| TC-AT-14 数据隔离 | 两个Run使用同类数据，一个失败取消 | 数据、端口和目录不串联，清理只作用本轮 |
| TC-AT-15 秘密边界 | 测试需要外部真实账户或候选尝试读取秘密 | 默认拒绝，改用批准的假数据／替身或另行渠道验证 |
| TC-AT-16 替身范围 | 前端用API替身通过，最终验收未接真实后端 | 最终真实联通缺项，不得ACCEPTANCE合格 |
| TC-AT-17 候选只读 | 检查编译或测试修改产品输入后恢复 | 不依赖事后散列，权限阻止；发生INPUT_CHANGED则不合格 |
| TC-AT-18 修改测试资源 | 候选尝试修改公开／保留包、runner或结果通道 | 实际拒绝并触发门槛，不采信结果 |
| TC-AT-19 保留不可见 | 构建模型请求、工作区和公开差异检查 | 不含保留源码、夹具和预期，异常访问可审计 |
| TC-AT-20 公开只读 | 构建侧读取公开用例并尝试写入 | 可读但不可写，公开通过不代替保留及真实联通 |
| TC-AT-21 执行前固定 | 执行中出现失败或新候选 | 不临时减少case／断言或替换包，原范围完整保留 |
| TC-AT-22 逐项结果 | 部分case通过、失败、跳过、未知 | 分别保存，不用整体退出码统一涂绿 |
| TC-AT-23 项目报告非权威 | 候选生成全PASS JUnit但受控断言失败 | 独立结果为FAILED，项目报告只作诊断 |
| TC-AT-24 浏览器身份 | 浏览器／候选子进程尝试写权威结果管道 | 无权限；仅绑定CHECK_DRIVER根进程帧可被核对 |
| TC-AT-25 端点归属 | 端口已有其他服务或HTTP200来自非本Job | UNAVAILABLE，不认领用户服务 |
| TC-AT-26 取消 | 执行中取消，部分case已有结果 | 已完成事实保留，剩余不补PASS，完整停止后收尾 |
| TC-AT-27 未知恢复 | 结果帧缺失、回执丢失或服务重启 | 原Item保持UNKNOWN并核对，不新建等价检查覆盖 |
| TC-AT-28 清理未知 | 断言通过但子进程／目录清理未核清 | 保留断言事实，eligible=false |
| TC-AT-29 候选变化 | C1通过后形成C2 | C1结果不用于C2，历史仍可读 |
| TC-AT-30 runner变化 | 同候选使用新runner／断言库 | 受影响项重新验证和执行，旧结果不追溯改判 |
| TC-AT-31 需求变化 | 新Revision改变业务预期 | 新Plan／Pack版本，原任务不自动换依据 |
| TC-AT-32 失败归因 | 产品偏差、测试缺陷、需求歧义和环境故障各一例 | 分流有真实证据，不统一生成产品缺陷 |
| TC-AT-33 测试缺陷历史 | 已执行后发现预期错误 | 原结果标依据失效，不改成PASS；新包重新执行 |
| TC-AT-34 同条件对照 | 新旧WALL-E使用不同Pack或环境 | 不输出伪直接差值，固定条件后重跑 |
| TC-AT-35 指标不替代覆盖 | 测试数／代码覆盖率高但关键行为未测 | 关键缺口仍显示并阻止发布或采用 |
| TC-AT-36 人工语义 | 自动通过但视觉／语义人工未判定 | 显示MANUAL范围，不称全部验收完成 |
| TC-AT-37 非功能阈值 | 需求只写“快速”或另例有明确阈值 | 前者不编造PASS，后者按固定环境和阈值执行 |
| TC-AT-38 页面状态 | 加载、空计划、无权限、筛选无结果、未知恢复及按钮处理中 | 分别正确展示，禁用有原因，刷新不重复执行 |
| TC-AT-39 只读无副作用 | 打开计划、覆盖、结果和版本差异 | 不调用模型、不启动服务、不写候选或测试包 |
| TC-AT-40 完整专项闭环 | 固定需求→计划→测试包→有效性→执行→归因→版本对照 | 所有身份、证据、人工决定、未知和维护历史可回查 |

## 23. 未采用方案与理由

| 方案 | 不采用原因 |
| --- | --- |
| 一个通用业务测试包评所有项目 | 不同项目行为不同，只能复用框架，不能复用业务预期 |
| 只运行候选自己的测试 | 候选可修改测试和报告，不能形成独立验收 |
| 让模型看代码后直接打总分 | 缺少可重复证据，模型赞同不能代替真实观察 |
| 全部测试写成任意脚本 | 权限、结果可信和维护成本高；优先结构化用例＋可信runner |
| 失败自动重试到通过 | 掩盖不稳定和重复副作用 |
| 只用代码覆盖率决定质量 | 覆盖代码不等于验证需求，也不证明断言有效 |
| 测试随候选输出更新 | 会把错误实现变成新预期 |
| 自动接收、交付或修复 | 混淆测试事实、人工决定和代码修改权限 |
| 首期覆盖所有技术栈和非功能测试 | 资源与证据不足；应按真实需求逐层取得能力 |
