# Coding 运行中控制配置应用 V1

日期：2026-11-11。依据 BE 0.17-draft-17 APP-CODE-CONDITIONS、OC20-CONFIG-1、SHR-CODE-SINGLE-WRITER 及 FE 0.16-draft-16 BND-CODE-CONDITIONS。仅独立 pending，不合入设计。

## 本批输入、输出与不变量

复用 C39、TaskConfigurationApplication、原四步骤和独立批准授权。输入为原任务版本、新配置／新授权和原因；输出为同一原操作、应用记录及真实同组观察。原 START／实例配置和已有操作固定输入不改，实例 effective_profile_version_id 保留启动来源，任务采用的控制组由可核实的 C39 历史接续。

先完成已有角色候选形成后、写入窗口 CLOSED 且原命令／问题／权限／费用已核清时的控制配置应用。此分支只支持模型调用数量／输出／连续失败和查询／发送／队列等待限制的变更；所有其他配置内容及授权的目录／命令／网络／交付范围保持相同。需要原生重载的变化仍 PRECONDITION_FAILED；尚未接入的原会话权限合并、正在写入时的受控停止等分支保留 CONFIG_NOT_READY，不冒充本批支持。

接收时仅绑定新授权为待应用、保存旧组和原来源快照，任务 WAITING／CONFIGURATION 阻止新活动；旧组仍是最近核实引用，不自动采用新组。后台重新核对原会话完成／全实例空闲、原 Guard 及根进程、路径，实际 GET config／providers／原会话及受管入口。规则与权限不变，绝不 PATCH config、重启、创建会话或发送模型消息。核对后在同一事务提交新组、授权 EFFECTIVE、应用 APPLIED，旧授权退役，保留原角色和 CLOSED 窗口，不自动 RESUME 或重用旧自检资格。

无法核实保留同一原 C39 UNKNOWN 和非秘密观察，不承认新权限生效；随后只读原身份恢复，不新建应用。STOP 优先，未生效新组取消，原组和历史保持。原初始配置的读取不能被新应用历史误判多条，也不能把原 START 的证据改成新配置。

## 批次及完成条件

1. 明确控制变化分类及不可变启动来源／有效组历史，严格读取与原 C39 投影；离线专项。
2. 接实际 C39 接收、后台原生只读、未知／停止／重复应用，贯通后续角色／修复／模型准入；SQLite／HTTP、实际 NTFS／Guard 证据分开。
3. 前端接原 WAITING 收据、原操作进度、旧／目标／已生效区分和草稿保留；strict／格式及必要宽窄 Chrome。
4. 同步映射和断点。真实模型／计数、用户服务／正常数据、SYSTEM／WFP 安装和提交推送不在本轮范围。

本文件先于本批代码保存，写入当时尚未执行检查；后续实际结果见末节。本限定分支完成不等于 C39 全部边界或 V2 验收完成。


## 实际控制入口补齐（18:30）

核对真实调用发现 TaskModelRoute.process 的 QUEUED 等候使用 HTTP 报文接收固定 15 秒期限，未读取已有 queue_wait_seconds。按原 APP-CODE-MODEL 第 4.3.2 条修复：HTTP 接收期限与消息确认队列期限各司其职；请求完整进入原身份后，读取本任务当前配置及 EFFECTIVE 授权的较小队列上限，冻结本次期限，不因轮询重置，不跨原窗口。等待到期时本入口不投递、不建 LLMUse、不重放原生消息；OPEN 仍重核原身份。属于补齐已有设计，不新增队列、操作或授权。分别补实际本地监听器与新配置模型准入证据，尚未执行不记通过。


## 配置选择的本批范围说明

运行中选择表单明确说明可调整模型调用及等待限制、执行器／模型／环境需新任务，帮助用户选择当前可执行的配置，不把尚未接入的原生权限变更暗示成可应用。沿原表单流式段落显示，不新增按钮／空态或客户端授权，不替代后端同组校验。正常、待核对及最终宽窄布局随本轮实际HTTP Chrome复核。


## 原预算返回和活动操作投影一致

C40明确追加预算可与配置只读核对串行提交；必须保留C39活动身份及最新应用状态，预算不采用新组、不自动继续，C39观察遇版本变化先放弃该次采用再沿原操作重读。所有TaskView生产入口须遵守同一事实，而非只修普通详情GET。前端允许有实际活动操作时配置动作显示OPERATION_IN_PROGRESS，仍不能在无活动操作时伪造该原因；原配置等待必须同时有原C39和应用，避免预算回执丢失进度。


## 尚未覆盖的配置类型

除原生会话权限合并与仍在写入时的受控停止外，仅影响未来检查的命令超时／检查配置，以及捕获／其他执行限制等非六类字段也未由本批接入。实现会明确拒绝，不能把“运行中配置已支持”解释为任意配置热应用。下一批应先按同一原C39影响范围分类，核对检查资源及准入、原生权限和实际OS受管边界，再决定可独立验证的子集；不引入另一套应用表或修改旧START依据。

## 既有继续请求的终态结清竞态

最后扩大原任务页面回归发现，RESUME操作终态先于本地原收据ACCEPTED状态进入组件时，旧effect会提前记“此操作已结清”，后续收据核实后不再结清本地原请求，下一单元持续被本地占用。修复顺序为先完成本地原记录读取，存在原请求时必须同一operation_id且ACCEPTED，然后才核对原操作／持久结清；未知原请求保留原恢复入口。不得用清空IDB或关闭未知请求绕过，也不自动重发原生消息。属于本轮共享恢复入口回归发现的原设计实施偏差。


最终状态文案核对：配置动作CONFIG_NOT_READY须说明运行配置核对服务未就绪，WRITER_ACTIVE才提示先完成原写入／检查，INVALID_STATE说明当前状态不能更换；不能让服务未就绪的空闲任务反复寻找不存在的在途工作。沿原按钮title与状态文字，不新增交互或权限。
