## 1. 本轮确定范围

- CodeSnapshot保留原业务身份／引用，改为“已登记Git提交基线”，只保存仓库、完整commit／tree、内容规则和保留引用等元数据，不另存起点bare内容包／manifest／seal。
- 登记REGISTER_BASE替代CAPTURE_BASE，原POST /code-repositories/{id}/snapshots保留，输入只含完整commit_oid及内容校验配置execution_profile_version_id。分支观察只能帮助选择明确OID，后端不接受分支名／短哈希／HEAD等移动表达式作为起点。
- 未提交修改、未跟踪文件及暂存区不纳入起点；要采用这些内容，用户先在Git提交。源工作目录可以另有改动，系统只读取用户选定提交，不误读为起点，不代提交／stash／checkout。
- 为保证版本可取回，在来源仓库创建仅指向原commit的小型refs/walle/baselines/{snapshot_id}保留引用；这是明确REGISTER_BASE的元数据动作，不是代码备份，不在GET触发，不改用户分支／索引／工作区。原登记操作及保留引用未知结果仍只核对原身份。
- 开发工作区和Testing SNAPSHOT目标从同一固定commit读取／物化。原仓库或对象不可读时CONTENT_NOT_READY，不退回当前HEAD、不换源、不自动复制旧起点包或联网fetch。
- CodeCandidate及DeliveryPlan目标包继续完整封存，候选静止、固定报告／接收、隔离、幂等恢复及未启动终止规则保持。代码版本物化到任务工作区属于执行需要，不另持久化起点备份。
- 原观察元数据继续按observation_id只读；旧未跟踪文件选择入口改为已登记基线的提交文件页，不保留无用的工作目录捕获流程或来源暂停确认。

## C05 原接收实施衔接

原命令的幂等业务输入为仓库 ID、完整 commit OID 和所选执行配置版本 ID。接收事务按已登记仓库对象格式验证 OID，核对所选版本的固定 Git 与内容规则引用，原子预留 CodeSnapshot ID，生成 refs/walle/baselines/{snapshot_id}，写入原操作及原四步固定输入并保存原 202。预留 ID 和引用只进入程序生成的原固定输入，前端不能提交。接收核对配置身份与引用，不以模型／执行器 readiness 阻止 Git 基线登记。此接收单元独立验证，正式 HTTP 写入口在固定 Git 执行者和结果核对接入后打开。读取、接收及重放不会创建引用或预先插入 CodeSnapshot。

## 固定对象批读取

原配置解析作用域确认成功并释放后，同一原步骤在一个新作用域使用固定 cat-file --batch。Guard 复用当前原目录与配置句柄、原配置回执、空全局配置和私有空 hooks，命令行及环境保持固定。后端逐个提交经过类型及格式核对的完整 OID，只消费同一原标准流的相符头、精确长度原始字节和尾分隔符。按对象类型和原始字节重算 OID。并发请求、短写、缺对象、错误类型、超预算、异常 stdout／stderr 或中断均退役本流，进程按原范围核对及清理。正常结束时先关输入、核实无余字节及两流 EOF，再核实退出与原 STOP／RELEASE。预算在整个批次累计，固定提交闭包及根树内容验证共享这一个原 Git 进程。源工作树、引用及对象库仅由固定只读命令读取，C05 的 create-only 另接原写入步骤。

协议参考：[git cat-file 批读取](https://git-scm.com/docs/git-cat-file)、[Windows 管道等待模式](https://learn.microsoft.com/en-us/windows/win32/ipc/named-pipe-type-read-and-wait-modes)。

## 原操作进度读取

复用原 code-operations/{id} 读取，固定展示四个步骤。公开输入只含仓库、提交编号和所选配置版本。VALIDATE_COMMIT 的对象、来源及内容摘要仅供程序执行后续核对，公开步骤仅有状态；只有原 SAVE_BASELINE 成功且指向同一原操作下已保存的快照时，才公开 snapshot_id。保留引用、预留编号及 Guard／标准流信息均不进入公开查询。

## 保留引用的实际事务

固定 Git 入口只接受经 C05 原操作预留的快照 ID 与已验证的完整提交编号。程序固定 update-ref --no-deref --stdin -z，强制关闭自动 reflog，原目标已有普通、符号、打包引用或已有 reflog 时拒绝。前置及锁内核对继续持有原 NTFS 目录、配置与元数据；锁内清单只允许本次目标的 .lock 及必要的 refs/walle/baselines 父目录出现。锁须对应固定提交内容。成功后核对原锁的实际文件身份和原提交内容转成预留的目标引用。中止核对无目标和无原锁，保留 Git 自身可能创建的空目录。

PREPARE、COMMIT、ABORT 各自对应原 STDIO 的实际确认。COMMIT 之前先核对原锁，在私有原作用域中持久追加原 MAY_HAVE_BEEN_SENT 回执，再核对同一锁、权限与取消边界后最多发一次。原步骤外部身份在数据库中固定，追加证据按原作用域和阶段确定唯一文件名。只有正常确认后才一次性保存步骤结果及各回执引用。记录写入未知或发送后断线均保留原证据，使用原目标和原对象核对。实际创建后仍须核对原保留引用及对象，才允许发布快照。

协议参考：[git update-ref](https://git-scm.com/docs/git-update-ref.html)。


### 结果丢失后的只读续核

原 PIN_COMMIT 已有持久 PREPARED／MAY 回执时，先核对原 Guard 退出／封闭及清理证据。只读打开原仓库同名直接引用，核对原固定提交。引用不存在或证据无法确认时保持原未知。能核对时，以同一原操作的 VERIFY_PINNED_OBJECTS 作用域重新读取完整固定闭包及根树，原 PIN 在此期间仍为未知。核实成功后追加 OBSERVED 回执，原 PIN／VERIFY／SAVE 及唯一快照在同一短事务确认。读取中断留存原阶段及其作用域，以原窄权限清理。此路径不启动旧写入进程，也不补发 COMMIT。


### 2026-11-08 后续 API06／19 接入边界

详情与文件页应短事务按原快照、原 REGISTER_BASE、固定配置版本、原 commit／tree／ref 和已登记仓库核对身份。请求不接收目录、引用、对象格式、命令或 scope 参数。事务外在受保护后端读取原直接保留引用及固定对象，不从 HEAD、最新观察、暂存区或工作目录补位。API06 的 ready 和 reason_codes 以本次原来源证据为准。API19 按完整已校验的固定树条目，以 UTF-8 字节顺序和 20 条分页，只投影路径、模式、blob_oid、byte_count。

正式读请求沿同一原成功登记的 VERIFY_PINNED_OBJECTS 作为技术归属，私有为每次实际受控读取分配新的只读 scope。先持久绑定原安装、后端代次、快照、原步骤和固定命令，再允许 CONFIG／OBJECT_BATCH。复用 Guard 标准流、进程上限及 STOP／RELEASE；不得增加或改写业务 Operation／Step、原回执、快照、Git 引用或源码。受保护后端启动时只读取未闭合查询的私有证据，按窄权限核对旧范围并清理。读取失败与空树、分页越界分开。长时间后查询须按 Git 的 files 后端语义处理直接引用由 loose 转为 packed 的情形，保留原仓库身份及精确 commit，不把路径存在或历史成功当成当前就绪。此段记录下一批的实现依据，API06／19 尚未接入。


### 同一登记请求主动续核

对原 C05 仓库、幂等键及完整提交／配置版本进行相同重放，服务仍返回原 202。已登记的工作线程可为原操作排队一次只读续核提示。提示按原操作去重，工作线程最多缓存 256 个；提示满载、线程不可用或进程退出时，原 202 与原操作仍可核对，后续可重放同一原请求。提示不作为持久受理或外部授权。线程仅在原 PIN 为 UNKNOWN 且 VERIFY／SAVE 均未开始时处理，复用旧范围先清理及原证据核对。已结束或仍在正常执行的操作不额外启动。缺引用的核对留在原步骤，来源恢复后可以再次重放原请求。续核识别同一原仓库中 loose 和 packed 的直接引用，按实际优先级核对原提交，遇到符号引用或名称歧义仍保持原未知。查询 GET 不排队，不重发 Git 写入。
