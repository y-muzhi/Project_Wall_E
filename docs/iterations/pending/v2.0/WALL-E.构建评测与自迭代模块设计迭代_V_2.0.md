# WALL-E 构建评测与自迭代模块设计迭代

日期：2026-11-03（Asia/Hong_Kong）。编号：EV20-01。状态：DRAFT／后续方向设计，未排期、未实施、未验证、未合入正式设计。

## 1. 任务、定位与边界

用户提出：通过WALL-E构建实际项目，再由评测系统评价构建结果，用评价依据推动WALL-E自身迭代。本稿按当前项目结构展开这一方向。

本文暂按V2.0设计资料分类，是因为方案依赖V2.0的代码任务能力；它不加入V2-B1—B3必须完成范围，不改变现行V1.5正式设计或V2.0既有草稿。后续真正排期时，再确定所属软件版本及实施批次。

本轮只形成独立设计，不登记为已批准实施，不修改代码、资源、业务数据库、运行服务或Git分支，不运行模型、计数、产品构建或真实评测。

### 1.1 设计依据

- [V2.0设计汇总](../../../design/v2.0/WALL-E.设计汇总_V_2.0.md)：固定Revision、CodeTask、完整代码快照、检查、人工接收和本地Git交付。
- [V2.0后端草稿](../../../design/v2.0/WALL-E.后端设计文档_V_2.0.md)：OBJ-CODE-*对象、受控执行、检查失效、LLMUse及预算规则。
- [Agent职责分工研究](WALL-E.Agent职责分工与持续协作架构研究_V_2.0.md)：新增模型调用必须有可测量收益，不用多个模型的赞同代替事实。
- [项目路线图](../../../project/ROADMAP.md)：RM-003提供消耗概览方向，RM-004提供根据项目数据提出改进计划的方向。

上述V2.0详细设计仍为DRAFT，代码任务尚未实现。本模块的可运行版本必须等待相应基础能力真实接入，不能把本文写成当前已经可执行的评测平台。

### 1.2 核心决定

采用“普通代码任务构建＋独立评测证据＋人工批准改进＋同任务集回归”的闭环。

1. 构建过程复用CodeTask，不开发第二套编码执行器。
2. 验收测试代码独立编写、评审、验证和发布，不能在看到被测候选后临时按照实现补预期。
3. 评测读取固定CodeCandidate和真实记录，并在工作区外运行固定验收测试包及其他独立检查。
4. 评测结果用于定位问题，不直接修改WALL-E。
5. 每次改进形成独立提案，由用户决定是否实施。
6. 改进后的WALL-E作为新版本，在隔离环境运行；不热改正在提供服务的WALL-E。
7. 新旧版本使用相同任务集、验收测试包和可比条件对照，保留退化结果，不只看总分。

## 2. 目标与非目标

### 2.1 目标

- 回答某个固定WALL-E版本“能完成哪些项目、在哪里失败、耗费多少、需要多少人工介入”。
- 能复现一次评测所用的任务、代码起点、WALL-E版本、模型配置、检查标准和预算。
- 能把失败归因到具体构建阶段，并形成带证据的改进候选。
- 能比较改进前后结果，发现质量提升之外的旧能力退化和成本上升。
- 能保留未执行、环境失败、结果未知及人工未判定，不用零分或空结果掩盖。

### 2.2 非目标

- 不允许评测程序自动修改、发布、部署或重启WALL-E。
- 不用模型生成项目、再由同一模型单独评分作为唯一结论。
- 不用一次高分、任务自报完成或普通构建成功证明WALL-E已经改进。
- 不在首期追求覆盖任意技术栈、任意规模项目或统计显著 benchmark。
- 不自动推送、部署生成的项目，也不把生成项目写入用户正常业务仓库。
- 不建设通用Agent排行榜、自由Agent群聊或自动无休止优化循环。

## 3. 总体结构与完整闭环

~~~mermaid
flowchart TD
  S[固定评测任务集] --> C[创建评测批次]
  W[固定被测WALL-E版本] --> C
  B[明确总预算及并行限制] --> C
  C --> R[逐案例建立普通CodeTask]
  R --> P[固定CodeCandidate及真实任务记录]
  P --> E[工作区外独立评测]
  E --> A[指标、关键门槛及问题归因]
  A --> I[改进提案]
  I --> U{用户决定}
  U -->|不采用| K[保留结论与原始证据]
  U -->|批准一次修改| M[隔离修改WALL-E候选版本]
  M --> N[同任务集及保留集回归]
  N --> D[逐案例新旧对照]
  D --> U
~~~

### 3.1 三类职责

| 部分 | 负责什么 | 明确不负责 |
| --- | --- | --- |
| 构建侧 | 按固定设计运行普通CodeTask，形成真实候选、检查、用量和交付记录 | 不自行修改评测标准，不读取保留评测答案 |
| 评测侧 | 固定任务集和被测版本，执行独立检查，汇总指标及新旧差异 | 不替用户接收代码，不自动改WALL-E |
| 改进侧 | 根据已保存证据提出修改范围，经批准后形成新WALL-E版本并回归 | 不把提案状态当作已实施或已有效 |

### 3.2 一次迭代的完成定义

一次完整迭代必须同时具有：

1. 原版本和新版本的固定身份。
2. 相同评测任务集版本及可比执行条件。
3. 每个案例的原构建任务、代码结果和独立评测结果。
4. 质量、效率、人工负担和关键安全门槛的对照。
5. 明确的采用、不采用或证据不足结论。

只完成WALL-E代码修改，或只运行一次新任务，不算完成一次自迭代。

## 4. 业务对象及现有对象复用

### 4.1 对象控制数量

首期只设置三个顶层业务对象：EvaluationSuite、EvaluationCampaign、ImprovementProposal。案例、运行、评分和指标是它们的子记录或关联，不分别扩张成独立服务。

| 对象 | 职责 | 关键固定内容 |
| --- | --- | --- |
| EvaluationSuite | 一组可重复使用的评测任务 | 当前身份及名称；具体内容由不可变SuiteVersion保存 |
| EvaluationCampaign | 一个固定WALL-E版本对一组任务的一次评测 | 被测版本、SuiteVersion、执行配置、预算、运行限制及实际状态 |
| ImprovementProposal | 一项有证据的WALL-E改进候选 | 证据、归因、拟改范围、预期改善、回归风险及用户决定 |

### 4.2 评测任务集

EvaluationSuiteVersion至少固定：

- suite_id、version、created_at及创建来源。
- 有序EvaluationCase列表。
- 指标规则版本、各案例验收测试包及其他必需独立检查版本、人工评分规程版本。
- 开发集、回归集、保留集的用途标记。

EvaluationCase至少固定：

- case_id、名称、任务类型、难度和适用技术栈。
- 主文档及关联材料的固定Revision来源。
- 项目代码起点快照、允许使用的仓库及运行环境。
- 用户硬约束和应交付结果。
- 公开／保留验收测试包版本、其他独立检查包引用及人工核对项。
- 本案例最大模型请求、预算、活动时间和允许人工操作范围。

案例正文、起点、验收测试包、其他检查包或评分规则变化后必须发布新SuiteVersion。进行中的Campaign继续引用旧版本，不静默换题或换评分依据。

### 4.3 被测WALL-E版本

Campaign.subject_build必须能确定实际运行的WALL-E，而不是只记录“V2.0”或当前分支名。至少包括：

- WALL-E完整源码快照或Git树身份；存在未提交内容时使用完整快照，不能只记HEAD。
- 前端实际构建产物身份、后端运行入口及必要依赖锁定版本。
- 提示词、输出Schema、协作资源及代码执行配置的不可变版本引用。
- 主模型、辅助模型、价格版本及OpenCode运行包版本。
- 实际启动实例与该subject_build的关联；启动失败或身份不一致时不得开始计费运行。

改提示词、改上下文选材、改程序流程和换模型都属于不同被测版本。页面需展示主要差异，不能只显示一个自增版本号。

### 4.4 评测运行及结果

EvaluationRun是Campaign下一个案例的一次尝试，至少保存：

- campaign_id、case_id、attempt_no及固定输入。
- 真实code_task_id；一个Run最多对应一个CodeTask，历史不得改绑。
- 最终用于评测的candidate_id；没有候选时明确为null。
- 状态、实际开始／结束、停止原因及未核清事项。
- 独立评测结果、指标值和人工评审状态。

重复运行同一案例形成新Run和attempt_no，不覆盖旧结果。网络回执未知时先核对原Run和原CodeTask，不能补建第二份。

EvaluationAssessment保存一次针对固定候选的独立评价：

- 自动检查项来自受控检查包，记录PASS／FAIL／UNAVAILABLE／UNKNOWN／NOT_RUN。
- 人工核对项记录PASS／FAIL／INCONCLUSIVE／NOT_REVIEWED及具体说明。
- 结果绑定candidate_id、检查包版本、环境记录及实际证据。
- 候选、检查包或必要环境变化后，旧Assessment不能用于新候选。

独立评测可以复用INF-CODE-CHECKS的命令、受管runner及证据机制，但不伪装成purpose=ACCEPTANCE的Verification，也不产生Acceptance。普通CodeTask的接收资格与评测分数保持分开。

### 4.5 改进提案

ImprovementProposal至少包含：

- 来源Campaign／Run／指标及可定位证据引用。
- 问题分类、受影响WALL-E层及判断理由。
- 拟修改的程序、资源、提示词、模型或配置范围。
- 预期改善的具体指标和可能退化的指标。
- 建议对照组、保留集及最大验证预算。
- 状态和人工决定记录。

状态为PROPOSED／APPROVED／REJECTED／VALIDATING／ADOPTED／NOT_ADOPTED。APPROVED只表示允许按该范围形成候选修改，不表示代码已改或有效；ADOPTED必须有后续对照证据和用户决定。

## 5. 评测任务集设计

### 5.1 首批案例来源

优先使用已经明确需求、能够独立检查的小项目，不从互联网随意下载一套与WALL-E实际用途无关的题库。首批建议6—8个案例，覆盖：

1. 只有后端的小模块及持久化。
2. 后端和前端联动的小页面。
3. 在已有项目中增加能力，而非全部从零生成。
4. 修复一个已知缺陷并保持原行为。
5. 修改共享契约后的跨层调整。
6. 检查失败后修复及重新检查。
7. 取消、恢复或结果未知的流程控制案例。
8. 一个超出预算或材料不足时必须停止而非硬做的案例。

具体案例数量和内容在任务集设计时确定。少量案例只能用于发现差异，不能宣称统计显著或普遍优于其他系统。

### 5.2 三类用途

| 集合 | 用途 | 限制 |
| --- | --- | --- |
| 开发集 | 分析问题、调试评测器和形成改进提案 | 允许反复查看详细失败，结果不单独作为最终采用依据 |
| 回归集 | 每次修改后检查已有能力是否退化 | 固定核心行为，变化须说明任务集版本原因 |
| 保留集 | 在采用前检查是否只对已见题目过拟合 | 构建侧不能读取隐藏答案；不用于逐条调试提示词 |

保留集不是绝对不可见秘密，而是使用边界：其独立预期和答案不进入构建上下文，不根据每次保留集失败反复调参。需要反复修改时，应将问题转回开发集并补充新案例。

### 5.3 独立评分依据

优先级如下：

1. 固定设计的明确约束及真实需求覆盖。
2. 工作区外的构建、测试和静态检查。
3. 对固定候选运行的独立行为测试及必要浏览器检查。
4. 人工按固定规程核对语义、交互和代码可维护性。
5. 可选独立模型只读审阅，仅提供有出处的问题，不单独决定通过。

被测任务可以修改项目自己的测试，但不能修改评测方的受控runner、隐藏夹具和预期结果。项目内测试全过不能覆盖独立检查失败。

### 5.4 验收测试代码模块

验收测试代码是评测依据，不是被测项目候选的一部分。本模块负责测试代码及夹具的编写、评审、有效性验证、版本发布和受控执行。它补上“评测器知道怎样运行命令，但拿什么判断需求真的实现”的缺口。

采用“通用测试框架＋按项目／案例定制测试包”，不是用一套通用业务测试代码评所有项目：

| 通用部分 | 每个项目／案例定制部分 |
| --- | --- |
| 测试包目录和资源格式、runner调用及结果协议、版本发布、有效性验证、公开／保留隔离、执行和证据保存 | 固定Revision对应的行为、测试输入和夹具、服务准备方式、业务断言及预期结果、已知缺陷／变异样本 |

通用构建、启动和静态检查可以复用，但它们只证明项目基本可运行。业务验收断言必须来自该项目自己的固定设计。同一案例的测试包用于比较不同WALL-E版本；不同项目只有在确实具有相同固定行为契约时才可复用具体测试包，不能因技术栈相同就共用业务预期。

完整模块职责见[验收测试代码模块专项设计](WALL-E.验收测试代码模块专项设计迭代_V_2.0.md)，覆盖测试计划、需求Oracle、分层覆盖、数据环境、AI辅助、测试自身验收、编译执行、防作弊、失败归因和长期维护。

首个具体定义见[任务管理API验收测试包](WALL-E.自迭代首个验收测试包定义迭代_V_2.0.md)，只是一个最小案例示例，不代表整体模块范围；尚未实现或执行。

#### 测试包与CheckSet的分工

AcceptanceTestPack是受控资源，不新增与EvaluationSuite同等的业务流程。一个不可变TestPackVersion至少固定：

- pack_id、version、适用案例或案例类型及固定设计Revision引用。
- 测试源码、夹具、预期数据、运行入口和内容清单摘要。
- 每项测试关联的需求条目／原文引用及应观察行为。
- 所需运行时、依赖锁、服务端口、测试数据及超时限制。
- visibility=PUBLIC／HELD_OUT，以及有效性验证证据。

CheckSetVersion继续决定“运行哪个命令、必需项和通过证据”；TestPackVersion提供“实际执行哪些验收测试代码和断言”。二者必须同时固定，不能用一个npm test命令名代替测试内容。

#### 编写与评审

1. 测试从固定Revision中的用户可观察行为编写，先写输入、操作和预期结果，再看候选实现。
2. 每项必需测试都能追溯到固定设计依据；无法追溯的新业务预期不能由测试作者自行增加。
3. 人工或独立AI任务可以起草测试，但起草过程与被测构建分开，使用独立预算和记录。
4. 发布前由人工核对测试是否忠实于需求、是否存在重复或遗漏；AI起草不等于测试已可信。
5. 不得根据某个候选的实际错误输出反向修改预期来制造通过。需求确需变化时先形成新Revision，再发布新测试包版本。

#### 测试本身必须验收

TestPackVersion只有满足有效性条件后才能发布为正式评分依据：

- 在已知合格的固定参考结果上，必需测试全部通过。
- 关键测试至少在一个已知缺陷或受控变异结果上失败，证明它不是永远成功的空测试。
- 不存在无断言的必需测试、被跳过或禁用的必需测试、捕获失败却正常退出等伪通过结构。
- 测试数据、端口和外部依赖可重复准备；任意等待、当前时间或外部网络造成的不稳定必须单独处理。
- 验证记录绑定测试包内容摘要、参考结果、环境和实际执行证据。

没有已知合格参考结果时，可以先保存DRAFT并做人工评审，但不能声称测试包已验证，也不能把它作为新版本采用的唯一依据。测试代码自身的缺陷按评测器问题处理，不归为WALL-E构建能力失败。

#### 公开与保留测试

| 类型 | 构建侧可见性 | 用途及限制 |
| --- | --- | --- |
| PUBLIC公开验收测试 | 可作为固定材料只读提供 | 告诉构建者怎样验收；不能修改测试包，公开测试通过仍不是全部评分 |
| HELD_OUT保留评测测试 | 不提供源码、夹具或预期答案 | 检查泛化和遗漏；只能在候选固定后由评测侧注入 |

两类测试使用同一版本和执行机制。公开不等于可写，保留也不意味着可以绕过正常授权访问用户秘密。

#### 固定执行与结果

评测侧把测试包放在候选工作区外的受控只读位置，针对固定CodeCandidate执行。结果至少定位到测试包版本和具体测试项；跳过、超时、环境不可用及结果未知分别保存，不能算PASS。

测试包、断言、夹具或必要环境变化后发布新版本，并同步新的SuiteVersion。旧Campaign保留原结果；不同测试包版本的结果不直接作为同条件新旧对照。

## 6. 指标、门槛与未知结果

### 6.1 首期不做单一总分

首期分别展示四组指标，不把它们压成一个看似精确的总分：

| 指标组 | 具体指标 | 数据来源 |
| --- | --- | --- |
| 结果质量 | 必需独立检查通过、需求硬约束遗漏、人工核对问题、首次候选通过情况 | CodeCandidate、Assessment、固定Revision |
| 流程可靠性 | 是否形成有效候选、返工次数、检查失效处理、停止／恢复是否符合规则 | CodeTask、OperationRecord、Verification及运行观察 |
| 效率 | 全部真实Token及费用、模型请求数、构建活跃时间、等待时间、人工处理时间 | LLMUse、OperationRecord及真实时间记录 |
| 人工负担 | 必要提问、权限／预算处理、用户纠正、无效通知及人工修复次数 | WaitingItem、问题、权限、缺陷及评审记录 |

首次候选通过率的分母、无效Run及环境失败必须同时显示。不得把环境失败静默剔除后提高通过率，也不得把无记录填成0消耗。

### 6.2 关键门槛

以下事件属于门槛，不允许被其他高分抵消：

- 越权读写、访问隐藏评测材料或取得未授权网络／模型入口。
- 超出已证明的预算保护边界，或将未知费用按0处理。
- 取消后继续写入，或旧实例／旧角色重新取得控制权。
- 重复交付、伪造人工接收、把模型自报当检查通过。
- 修改评测标准后仍沿用原分数，或候选变化后沿用旧评测结果。
- 运行后遗留无法核清的进程、工作区写入者或外部副作用。

出现门槛事件时，相关Campaign标记为不可作为采用依据，并停止新增Run；已发生事实和费用继续保留及核对。

### 6.3 时间和费用口径

- 活跃构建时间、等待用户时间、环境准备时间和评测时间分开，不用一个总时长混合比较。
- 主请求、压缩、辅助请求、重试和迟到用量全部进入同一任务账。
- 已结算费用、预留费用和未核清费用分开；预算预留不是实际花费。
- 首次有效结果成本和全部尝试成本都保留，避免只展示最便宜的一次成功。

## 7. 执行、隔离与停止

### 7.1 使用隔离控制环境

评测使用独立的控制数据库、私有存储、仓库根和临时服务端口。案例文档导入为评测环境中的真实Revision，再沿普通CodeTask创建流程执行，不伪造GuideRun、CodeTask或Acceptance。

正常用户需求、业务数据库、正式文档、正式资源和正常Git分支不作为评测清理对象。评测产物有独立归属和清理清单，结果未知时先保留核对，不能按目录批量删除。

### 7.2 构建与评分分离

1. 构建侧只读取得案例允许的需求、关联材料和代码起点。
2. 构建侧在独立工作区运行，受原CodeTask授权、预算及Windows边界控制。
3. 固定候选后，评测侧从私有内容存储生成独立检查副本。
4. 独立检查包由评测侧注入，不出现在构建工作区或模型上下文中。
5. 评分只读固定候选及真实证据，不回读仍在变化的工作区。

### 7.3 不自动接收或交付

普通评测运行到固定候选和独立评价即可结束，不为自动评分伪造用户Acceptance。需要验证人工接收和Git交付时，使用单独专项，由真实用户完成接收，目标只能是隔离仓库的一次性本地分支。

因此，“能否形成合格候选”的批量指标与“完整接收交付流程是否可靠”的专项指标分别报告。

### 7.4 批次控制

- 创建Campaign不启动模型；开始是单独操作，需明确总预算、最大Run数、每案例限制和停止条件。
- 首期串行执行Run。并行只在后续证明预算、端口、仓库、工作区和模型入口均隔离后开放。
- 停止Campaign先阻止新Run，再沿原CodeTask停止当前活动；请求已接受不等于进程已停。
- 重启后按持久Run、CodeTask和外部身份核对，不自动重发未知操作。
- 环境失败与WALL-E能力失败分开，不能用无限重试获得一次成功后覆盖历史。

## 8. 问题归因与改进形成

### 8.1 先区分问题归属

| 分类 | 示例 | 后续处理 |
| --- | --- | --- |
| 评测任务或环境 | 案例矛盾、依赖不可用、评分器错误 | 修任务集或环境并发布新版本，不归为WALL-E改进 |
| 固定设计缺失 | 需求本身未决定关键行为 | 转文档讨论，不让编码模型自行补规则 |
| 材料与上下文 | 必要Revision未提供、错误选材、上下文超限 | 评估上下文装配或资源修改 |
| 后端／前端／联调实现 | 接口偏差、页面遗漏、跨层调用错误 | 定位对应执行职责及交接检查 |
| WALL-E程序控制 | 状态、权限、预算、恢复或交付错误 | 优先修程序，不靠提示词掩盖 |
| 模型或渠道 | 工具协议不兼容、截断、供应方异常 | 区分渠道故障与模型能力，保留实际证据 |
| 评分不确定 | 自动检查无法覆盖语义、人工意见分歧 | 标INCONCLUSIVE并补人工核对，不强行归因 |

AI可以帮助归类和草拟提案，但每个提案必须指向真实记录。没有证据时保留“待分析”，不为了闭环完整而猜根因。

### 8.2 一项改动一次对照

优先让每个ImprovementProposal只包含一个主要变化，例如调整一类上下文选材或修复一个交接条件。多项改动打包后难以判断收益来源，只允许在确属同一不可拆修改时说明原因。

修改WALL-E时仍走普通文档及代码任务流程，目标仓库是WALL-E自己的隔离副本。被测运行实例保持只读，不能在运行中修改自身源码、资源或配置后继续自称是同一subject_build。

### 8.3 与RM-003／RM-004的关系

- RM-003的数据概览可复用本模块的真实用量和耗时口径，但普通概览不等于版本对照实验。
- RM-004可读取Campaign及改进证据，辅助形成ImprovementProposal；它没有自动执行提案的权限。
- 工单机制若后续实施，可把已批准提案转成WALL-E改进工单；工单只是入口，不替代本稿的版本固定和回归规则。

## 9. 新旧版本对照与采用规则

### 9.1 可比条件

对照至少固定同一SuiteVersion、代码起点、检查包、模型配置、执行器及主要资源限制。确需换模型或提高预算时，必须作为实验变量明示，不能同时改多项后把收益归给某一个修改。

每个案例保存旧Run和新Run的成对关系。新增案例可以补充覆盖，但不进入原固定集合的直接差值；另列新集合结果。

### 9.2 对照结论

逐项给出：

- 改善：哪些案例或指标有明确提升。
- 退化：哪些旧通过案例失败，或成本、等待、人工处理明显增加。
- 不变：关键结果没有可见差异。
- 证据不足：运行无效、人工未判定、结果未知或样本太少。

温度固定为0也不能证明供应方结果完全确定。关键案例可重复运行并保留每次结果；次数和预算在运行前确定，不能看到结果后只选择有利尝试。

### 9.3 采用门槛

首期采用需同时满足：

1. 所有关键安全门槛保持满足。
2. 改进提案声明的目标指标有实际改善。
3. 回归集没有出现未解释的关键退化。
4. 保留集提供合理支持，或明确标记样本不足、仅允许继续观察。
5. 增加的费用、耗时和人工负担在可接受范围内。
6. 用户查看对照后明确决定采用。

不满足时不自动回滚或改写历史；保留候选版本和NOT_ADOPTED结论。是否交付到WALL-E实际本地分支仍走现有接收／交付授权，不自动推送或更新服务。

## 10. 页面与接口职责草案

本节只确定后续前后端规格的职责，不形成第三份共同契约。正式实施前，共同对象、HTTP和错误归所属版本后端设计，页面及浏览器状态归前端设计。

### 10.1 页面

| 页面 | 主要内容及动作 |
| --- | --- |
| 验收测试包列表／详情 | 管理测试源码、夹具、需求追溯和版本；查看合格／缺陷参考结果、评审及有效性证据；发布新版本，不编辑已引用旧版 |
| 评测任务集列表／详情 | 管理Suite及版本；查看案例、用途、固定来源、公开／保留测试包和其他检查包；发布新版本，不编辑已引用旧版 |
| 评测批次列表／创建 | 选择SuiteVersion、subject_build、执行配置和总预算；创建与开始分开 |
| 评测批次工作区 | 显示进度、当前Run、费用／未知费用、关键门槛、停止及各案例结果 |
| 单次结果详情 | 链接原CodeTask、固定候选、验收测试项、其他独立检查、人工核对、用量和完整时间口径 |
| 新旧版本对照 | 按案例和指标展示改善／退化／不变／证据不足，不默认只给总分 |
| 改进提案详情 | 展示证据、归因、修改范围、预期及风险；批准、拒绝和采用决定分别记录 |

所有区域覆盖初始加载、成功空数据、正常内容、失败／无权限、筛选无结果／页越界和恢复。空测试包说明“尚未编写验收测试”；空任务集说明“尚未建立评测任务集”；空提案说明“当前结果尚未形成改进提案”；不能用统一营销文案或把读取失败显示为空。

### 10.2 后续HTTP能力分组

| 能力 | 后续入口方向 | 关键限制 |
| --- | --- | --- |
| 验收测试包管理 | 测试包／版本的创建、评审、验证、发布和只读查询 | 发布前验证测试本身；已引用版本不可改，客户端不能上传通过结论 |
| 任务集管理 | Suite／版本／案例的创建、发布和只读查询 | 已引用版本不可改，发布不执行评测 |

| 人工评审 | 按规程保存核对项和说明 | 客户端不能上传自动检查结果或伪造 actor |
| 改进提案 | 草拟、批准、拒绝、关联验证和采用决定 | 批准提案不等于批准无限制修改或付费运行 |

具体字段、状态动作、幂等和恢复矩阵在排期后的后端正式规格中展开；本稿不提前复制一套完整API。

## 11. 分阶段实施建议

| 阶段 | 交付能力 | 进入条件及验证边界 |
| --- | --- | --- |
| EV0 验收测试与评测器离线闭环 | 编写并验证测试包，对已有固定候选运行独立检查，保存Assessment及未知结果 | 先不生成项目、不调用模型；用合格／缺陷参考结果验证测试包、评分器、隔离和证据链 |
| EV1 小任务集基线 | 用普通CodeTask构建少量案例，形成固定版本基线 | V2-B1／B2所需能力已真实接入；真实调用另定总次数和预算 |
| EV2 新旧对照 | 一项WALL-E修改形成新subject_build，运行同任务集并对照 | 能启动两个身份明确的隔离版本；保留退化和全部尝试 |
| EV3 改进提案闭环 | 从证据草拟提案，经批准、验证到人工采用决定 | 不自动改正式资源或运行服务；保留集和使用规则已落实 |
| EV4 可选扩展 | 独立语义审阅、更多技术栈、受控并行 | 有实际收益证据后另行立项，不是首期必须项 |

EV0可以先验证评测系统本身，避免把评分器故障误判成WALL-E能力问题。它仍依赖V2.0固定候选及受控检查基础；在这些能力尚不存在时，只能继续做文档和离线算法准备，不能宣称端到端自迭代已可用。

## 12. 后续验收场景

以下均为未来目标，本轮执行数为0。

| 编号 | 场景 | 必须证明的结果 |
| --- | --- | --- |
| TC-EV-01 任务集不可变 | 已引用SuiteVersion的案例或检查包发生变化 | 原Campaign仍读旧版；新内容只能形成新版本 |
| TC-EV-02 被测版本身份 | 同分支名下源码、资源或模型配置不同 | 不能作为同一subject_build；运行实例身份可回查 |
| TC-EV-03 创建无副作用 | 创建Suite及Campaign | 不发模型、不构建项目、不写Git或启动服务 |
| TC-EV-04 普通任务复用 | 启动一个Run | 只建一个可回查CodeTask，不出现第二套构建记录 |
| TC-EV-05 隐藏检查隔离 | 构建侧尝试读取评测答案或修改受控runner | 实际访问被拒绝，触发关键门槛，不只看提示词声明 |
| TC-EV-06 固定候选评分 | 候选固定后工作区继续变化 | Assessment仍针对原候选，不读最新现场 |
| TC-EV-07 结果失效 | 候选、检查包或必要环境变化 | 旧结果不用于新对象，历史保留且不追溯改判 |
| TC-EV-08 未知与无记录 | 检查UNKNOWN、用量缺失、人工未评审 | 分别展示，不填失败、0费用或通过 |
| TC-EV-09 项目测试被改 | 候选把自身测试改成直接成功 | 独立检查仍按受控标准执行，不能因此通过 |
| TC-EV-10 不伪造接收 | 批量评测形成合格候选 | 不产生Acceptance或自动Git交付 |
| TC-EV-11 预算共享 | 主／辅／压缩／重试及多Run消耗接近上限 | 全部计入Campaign及原任务，达到边界后阻止新增发送 |
| TC-EV-12 完整停止 | 停止Campaign时当前任务有子进程及未知调用 | 不新增Run；原任务完整停止和费用核对分别完成 |
| TC-EV-13 重启去重 | 开始回执丢失、服务重启、浏览器重开 | 核对原Campaign／Run／CodeTask，不重复构建或扣新尝试 |
| TC-EV-14 成对比较 | 新旧版本使用不同题目或检查标准 | 不给出伪直接差值；明确不可比部分 |
| TC-EV-15 退化保留 | 新版本目标案例改善但旧案例失败 | 同时显示改善和退化，不能由平均总分掩盖 |
| TC-EV-16 保留集边界 | 根据保留集反复调参或构建侧读取答案 | 使用记录可见；违反后该结果不能作为独立采用依据 |
| TC-EV-17 提案审批 | AI草拟修改WALL-E的提案 | 只保存PROPOSED；无批准不形成修改或付费运行 |
| TC-EV-18 不热改自身 | 改进任务与当前被测实例同时存在 | 被测版本保持固定；修改只在隔离候选工作区 |
| TC-EV-19 采用决定 | 质量略升但关键门槛失败或费用明显增加 | 不自动采用；展示真实代价并由用户决定 |
| TC-EV-20 端到端迭代 | 固定基线→构建→独立评测→一项修改→回归→对照 | 全部身份、证据、预算和人工决定可回查，未执行项保留 |
| TC-EV-21 测试来自需求 | 起草测试后候选产生不同输出，或测试包含固定设计没有的新规则 | 不按候选输出改预期；无Revision依据的新规则不得进入正式测试包 |
| TC-EV-22 测试有效性 | 同一测试包分别运行已知合格结果和已知缺陷／受控变异结果 | 合格结果通过且关键测试能检出缺陷；证据绑定相同测试包版本 |
| TC-EV-23 空测试与跳过 | 必需测试无断言、被跳过、禁用或捕获失败后正常退出 | 有效性验证失败，不得发布为正式评分依据，不得显示PASS |
| TC-EV-24 测试包不可变 | 已引用测试包的源码、夹具、断言或运行入口变化 | 原Campaign及Assessment保持旧版；修改只能形成新TestPackVersion |
| TC-EV-25 公开与保留边界 | 构建侧读取公开测试，并尝试修改公开包或读取保留包 | 公开包只读可用；任何写入及保留包读取被拒绝并保留证据 |
| TC-EV-26 测试项结果 | 部分测试通过、部分失败、跳过、超时、环境不可用或未知 | 逐项保存真实结果，不用命令最终退出码把未知项统一算作通过 |
| TC-EV-27 测试包版本对照 | 新旧WALL-E使用不同测试包版本 | 不给出同条件直接差值；需用同一固定测试包重新运行后比较 |
