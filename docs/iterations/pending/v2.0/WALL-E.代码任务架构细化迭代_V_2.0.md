# WALL-E V2.0 代码任务架构细化迭代

日期：2026-11-02（Asia/Hong_Kong）。状态：DRAFT／设计细化，未实施、未验证、未合入正式设计。

## 1. 任务与依据

用户要求阅读V2.0设计汇总、分析架构，随后要求“你接着推进”。本轮按当前设计阶段推进：记录架构细化，并编制V2.0后端设计草稿。没有扩大为代码实施、技术试验、付费调用、Git提交或服务更新。

依据为[设计汇总](../../../design/v2.0/WALL-E.设计汇总_V_2.0.md)、[批次草案](../../../project/v2.0/实施计划草案_V_2.0.md)、[设计建议记录](../../../design/v2.0/WALL-E.设计建议记录_V_2.0.md)、V1.5正式设计和实际源码。原对话汇总只作追溯；与现行汇总冲突的材料摘要、自动组合交付、撤回等历史方案不重新引入。

本迭代先于后端草稿保存。本轮细化进入新建DRAFT供审阅，不代表用户已经逐项确认全部技术选择；现有EFFECTIVE设计、V2.0原汇总及历史研究保持原字节。今后合入正式设计仍须用户明确要求，本迭代不自动归档。

## 2. 保留的架构决定

- 文档工作区与代码工作区分开；固定已确认Revision，原文直接关联，不在任务材料上保存摘要。
- 一个代码任务拥有独立工作区和受管OpenCode实例，后端、前端、联调按顺序执行，共用任务预算。
- WALL-E程序处理身份、权限、顺序、预算、检查与结果；OpenCode负责读设计、编码和允许的检查。
- 代码起点、待验收代码、人工接收和实际交付分别固定身份；检查与交付使用相同代码内容。
- 未知投递、未知费用、未知Git结果和未确认停止分别保留，不通过超时、断线或模型说明猜测完成。
- V2-B1—B3全部属于V2.0；F1／F2、独立审阅及路线图方向不成为新增必做项。

## 3. 本轮细化及理由

| 条目 | 草案选择 | 要解决的问题 | 正式定义位置 |
| --- | --- | --- | --- |
| A20-01 任务控制 | 一个代码任务应用模块统一处理动作许可，复用服务级进程归属；适配层只执行并报告事实 | 避免接口、Worker和网关各自推进状态 | 后端第2章、APP-CODE-CONTROL、INF-CODE-RUNTIME |
| A20-02 状态分工 | 任务阶段、等待事项、操作结果、实例／会话事实分开；控制版本不随普通日志增长 | 避免状态组合膨胀及终止频繁冲突 | OBJ-CODE-TASK、OBJ-CODE-OPERATION |
| A20-03 统一代码内容 | 起点和待验收代码共用完整快照机制；检查在独立副本执行 | 防止未跟踪文件遗漏、检查污染或交付时改读现场 | OBJ-CODE-CONTENT、APP-CODE-CAPTURE |
| A20-04 检查依据 | 系统必检入口来自受控配置；项目测试脚本属于被检查代码，不能凭命令同名证明标准未变 | 防止修改package.json等后使检查失去原含义 | OBJ-CODE-VERIFICATION、INF-CODE-CHECKS |
| A20-05 完整目标结果 | 目标预览展示完整代码相对目标的全部差异；不自动三方合并 | 防止只展示本任务改动，遗漏起点差异或目标独有内容删除 | OBJ-CODE-DELIVERY、APP-CODE-DELIVERY |
| A20-06 目标工作树 | 草案采用目标为已有、未被Git列出的任何worktree检出的本地分支；写前再次核对，不自动切分支 | 满足不修改用户索引／工作树的承诺；专用分支为使用建议，不强制命名 | INF-CODE-GIT |
| A20-07 调用归属 | 扩展现有LLMUse为文档运行／代码会话二选一归属；不造虚假GuideRun或CodeModelCall | 现有表要求guide_run_id，不能直接记录代码会话 | OBJ-CODE-USAGE、INF-CODE-DB |
| A20-08 角色返工 | 当前角色可在原设计及授权范围内修复跨层缺陷；不倒退复活旧角色会话，检查按新代码重做 | 补齐前端／联调发现前序实现错误后的路径 | APP-CODE-HANDOFF |
| A20-09 执行条件 | 精确版本、原生关联、有效配置、Windows归属、模型计费能力形成准入证据；失败不伪装支持 | 将安全承诺约束在实际验证过的配置 | 后端附录A、INF-CODE-OPENCODE、INF-CODE-MODEL |

A20-06和A20-08是本轮草案选择，尚无实测证据。技术验证若证明不能兑现，先记录证据和受影响范围，再修改草稿，不通过放宽必要停止、归属或交付保护消除阻塞。

## 4. 复杂度分配

核心对象维持CodeTask、CodeCandidate、CodeDefect／CodeRepair、DeliveryPlan、Acceptance和Delivery。实例、会话、操作、检查、授权是有明确规则的控制记录；材料、价格、观察和移交关联不建设平行业务服务。

实现采用现有FastAPI应用内部模块，不增加分布式服务、消息中间件或通用工作流引擎。代码执行的运行逻辑独立于GuideRun；共享数据库、服务级进程归属、HTTP边界、幂等和模型配置基础。

不为方便接续引入F2的自动代码继承、旧任务复活或撤回。新任务仍通过普通代码起点选择进入；旧工作区不直接授权给新任务。

## 5. 资料核对与技术边界

本轮读取OpenCode官方Server、Config和Permissions说明，以及Git的update-ref和worktree说明。它们仅作为适配设计依据；历史OpenCode 1.19.4记录不是本轮版本锁定或新验证。

后端草稿应给出内部适配输入／结果、任务状态—动作、外部操作恢复、快照发布、检查失效和Git恢复矩阵。未核实的原生消息稳定关联、会话请求归属、有效配置及Windows停止进入附录A，不能用伪造原生字段填空。

本轮不安装OpenCode，不启动模拟或真实模型服务，不读取／修改业务数据库，不执行产品检查。后续真实调用仍须明确次数、预算和重试边界。

### 2026-11-09 原问题移交的实施契约

API25 按结果表返回 200 的只读 HandoffView，事件独立分页。API48／49 按各自结果表、APP-CODE-QUESTIONS 4.4 和前端契约同步返回 201。接口说明中的 202 套用描述与这些详细条目冲突，实施采用结果表。准备移交需要一条实际 PREPARE_HANDOFF 原操作作为现有移交表的外键，使用同事务 VALIDATE／SAVE_FACT。关联已有文档结果只追加事件，通过原命令回执核对。移交只记录源问题、同需求目标文档、任务的固定依据和选定证据，不产生文档发送、正文写入、模型调用或执行恢复。

原 Schema200 不允许 PREPARE_HANDOFF，且没有权限私有观察字段。本轮以新的不可变 db20-r30 增加原操作类型和 NativePermission 的私有原生观察。原 r29 资源保持历史字节。新增权限请求保存 metadata／always，公开读取依旧只有业务投影；无私有观察的历史权限只能核对或拒绝，不能单次允许。
