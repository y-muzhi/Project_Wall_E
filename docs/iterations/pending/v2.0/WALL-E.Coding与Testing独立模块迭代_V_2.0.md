历史[验收测试专项](WALL-E.验收测试代码模块专项设计迭代_V_2.0.md)中的计划、覆盖、用例、测试自身有效性、资源隔离和归因作为复用依据；其“执行仍挂CodeTask”被本轮独立TestingTask替代。历史构建评测／自迭代、最小API案例及验证记录保持原字节，不把它们作为本期必须启用的自迭代流程。

## 2. 已确认的模块分工

- Coding：固定设计→BACKEND→FRONTEND→INTEGRATION→开发自检→发布固定候选；修复根据明确缺陷产生新候选。开发自检不形成独立测试验收结论。
- Testing：独立TestingTask、计划／用例版本、有效性验证、受控执行、报告／缺陷及自身预算和停止。既可选择Coding候选，也可选择已登记仓库固定快照，无须占位Coding任务。
- 衔接：固定设计及候选身份→Testing→报告／Finding→用户明确导入Coding缺陷→修复候选→新Testing任务复测→用户接收。关联、测试、修复和交付均是分别可追溯的动作。
- 测试期间Coding可继续产生新候选；原Testing始终测试原固定内容。报告可在原目标历史中通过，但不能据此接收后来版本。Testing不能修改生产代码、自动修复、接收或Git交付。
- 共享短事务、幂等回执、Operation／Step、Guard／Job、Verification／Case事实、模型审计／预留、固定内容及页面基础设施；新增明确owner引用，不复制整套可靠性系统。
- 终止按模块owner生效；停止Coding不隐式停止Testing，反之亦然。默认无共享可写工作区、端口或活动授权。

## 3. 对象与完整闭环

新增独立TestingTask；TestPlan／TestPlanVersion承载设计依据、可观察行为、覆盖和结构化用例；TestPackVersion／TestPackValidation承载受控资源与参考／缺陷／稳定性证据；TestReport／TestingFinding承载真实结果、归因和已固定原证据；TestingProfileVersion／TestingAuthorization限定运行、资源和模型预算。

沿用CodeSnapshot及CodeCandidate保存受测产品内容；沿用Verification／Item／Case记录真实执行，owner恰为CODING或TESTING。原CodeTask.current_verification_id仅开发自检，接收改引用current_test_report_id；DeliveryPlan／Acceptance引用真实TestReport，不再让Coding内部ACCEPTANCE生成合格事实。

TestingTask目标固定为candidate_id或snapshot_id二选一；同任务设计依据、计划／包／profile及原执行关联必须可核实。诊断范围可以部分；用于Coding交付的ACCEPTANCE报告必须完整四阶段、真实前后端联通，候选曾完成顺序角色交接并发布，且仍为Coding当前候选。

计划和测试包在看结果前固定；变更预期／断言／fixture必须新版本，旧结果不覆盖。发现测试缺陷可撤销版本资格并保留原因与历史，不能把原FAIL改为PASS。

## 4. AI和程序权限

Testing的AI辅助只在明确“起草测试计划／用例”动作中执行，采用后端已有结构化模型调用及LLMUse／预算预留；不创建假GuideRun或Coding任务。固定完整设计与支持能力进入上下文，候选的实现输出不用于反推预期；结构校验通过只保存DRAFT，不自动发布／执行。

测试执行不调用模型判分。可信controller／driver按已发布测试版本执行，生产目标只读、测试包和预期受保护，写入限本次数据／输出目录。公开自检与保留测试、环境不可用／产品失败／测试错误／未知均分开；所有实际调用计Testing预算，未知不退款或自动重试。

## 实施细化（2026-11-10，独立测试配置与批准）

Testing API01—05 复用同一幂等账本、SQLite 序列及已登记的 CommandDefinition／Runner／环境／准入／模型价格身份。配置只引用已登记的真实资源，可保留已登记但运行未准入的版本，读取给出实际 ready 和原因。独立执行器尚未接入时，即使其他资源齐备，执行仍报告 Q20-CHECKS。授权只保存明确批准的配置、TASK 或 PACK_VALIDATION 粒度和预算上限，审批者由本机应用边界注入。组验证固定零模型预算，批准后维持未绑定，任务创建或组验证才原子绑定；不借用 Coding 授权。新入口本轮以离线 SQLite／ASGI 核对，正式资源和执行准备分开。

### 独立计划身份与人工草稿

按正式 OBJ-TEST-PLAN、APP-TEST-PLAN 与 BND-TEST-API-06—14 分批接续。计划目录和版本只读分开。版本首次保存固定主 Revision 和材料；同版本草稿 CAS 编辑行为、用例和歧义，提交完整输入时重验原实体，改选依据另建版本。依据按原文逐条核对。草稿可保留未解决歧义或尚空的步骤／断言；已有动作沿 CHECK20 的数据协议校验，草稿中的声明不授予执行。显式发布才检查真实确认、覆盖与可编译能力。当前尚无已发布独立驱动；手工评审与实际执行资格分别留证。

### 2026-11-10 独立计划编辑接续

先接 BND-TEST-CASE-EDITOR 与 API09／12。新建草稿从实际需求、工作文档和固定 Revision 选择原依据；已有草稿的来源固定，改依据需新版本。行为、覆盖、用例步骤及断言按 CHECK20 字段编辑，显示尚未具备的执行能力。引用保留原文字节；保存只修改 Testing 草稿。原请求使用既有浏览器账本，按计划／版本保留本地输入，冲突时读取当前版本并保留本地输入供人工处理。计划编辑之后继续实现独立测试包身份、封存、有效性验证及准入，沿既有设计逐项区分登记与真实运行。

### 测试包编译与封存实现边界

测试包由已发布计划和安装侧固定资源编译。每个用例只匹配唯一登记目标，按登记目标、阶段集合与公开性分组生成 CHECK20 清单；保留用例文件仍在私有根，普通投影只显示状态和摘要。独立 CheckSet 以受控用例项和内容完整性项覆盖真实阶段；UNCOVERED 从原计划单独保留，不改成 MANUAL。包摘要绑定完整成员闭包和固定资源摘要，参考集匹配固定设计版本的原文摘要及材料顺序。封存只产生准备产物，验证和产品执行仍要求原参考组和实际运行证据。

### 2026-11-10 预登记参考集与原有效性验证

- 参考集由可信启动资源绑定原 NTFS 文件身份、内容摘要、设计／材料指纹及正负样本。API44 只读取该固定登记和 GIT20-BASELINE-1 持久事实，不探测 Git、不返回快照身份、预期缺陷用例或私有位置。只有后续显式验证操作才逐项核对实际可读固定快照及受控执行条件。
- 封存包与固定依据无登记匹配时，按 SHR-TEST-REFERENCE 返回 REFERENCE_SET_NOT_REGISTERED；已有登记字节或基线事实不可用时保留其真实状态。无正负参考时不分配验证孩子，不创建产品报告。
- 有效性验证用原 TestPackValidation 和全量内部 TestingTask 绑定顺序、正负预期、重复、原授权和摘要。孩子实际运行、终止、收尾和完整结果确认以后才能聚合。登记、编译、创建和读取阶段不生成通过结果。

- 原发布请求采用最新一次、同封存摘要且完整的验证。若后来的验证仍在进行或未通过，保留这些事实并拒绝发布；不会从历史重复中择优。发布再次核对原登记、源字节、全部子任务的实际报告、停止／清理、输入完整性和预期缺陷失败。


### 2026-11-10 独立报告与 Coding 关联的实施选择

报告保留历史结论，读时分别复验独立资格和 Coding 交付资格。产品归因要求同 Testing 原 RUN_TEST 的实际受控 Driver 和失败断言、预期以及固定原文。允许后续复核，保存各自原操作；公开原操作省去 actor 身份。Coding 交付另核对集成及验收阶段实际 HTTP／浏览器目标、原进程和 PREPARE 同 Guard 引用；该持久观察约定需随正式独立 Driver 联合取证。明确采用另一份报告清除旧预览，同一报告重验保留既有预览。候选来源的创建草稿按 Coding 任务／候选单独保存，默认验收，仍需独立授权及手动提交。以上落地记录保留 pending。
