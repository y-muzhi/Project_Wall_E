## 2. 通用测试包模板

通用模板编号ATP-TEMPLATE-001，适用于通过本地HTTP服务验收的项目。它只固定结构和执行协议，不包含任何项目的业务预期。

### 2.1 通用目录

~~~text
<acceptance-test-pack>/
  pack.yaml                 # 包身份、版本、可见性、运行入口和环境要求
  traceability.yaml         # 测试项到固定设计条目的对应关系
  public/                   # 可作为固定材料只读提供给构建侧的测试
  held_out/                 # 只由评测侧保存和注入的测试
  fixtures/                 # 固定输入及预期数据
  runner/                   # 受控运行、结果收集和环境清理入口
  validation/               # 合格／缺陷参考结果的验证说明及证据引用
~~~

目录是后续实现目标，本文没有创建这些文件。`held_out`不能进入构建工作区、模型上下文或公开差异；`validation`中的参考结果也不能作为被测项目起点。

### 2.2 通用固定字段

| 字段组 | 必须固定的内容 |
| --- | --- |
| 身份 | pack_id、version、case_id、内容清单摘要 |
| 需求依据 | document_id、revision_id及测试项对应的原文引用 |
| 运行 | 服务准备方式、测试命令、运行时和依赖版本、超时、端口及数据目录变量 |
| 可见性 | 每个测试项为PUBLIC或HELD_OUT |
| 结果 | 测试项ID、需求引用、结果、耗时、失败分类和证据引用 |
| 有效性 | 合格参考结果、缺陷／变异样本、实际验证记录及人工评审记录 |

### 2.3 通用结果规则

- 测试项结果为PASS／FAIL／UNAVAILABLE／UNKNOWN／NOT_RUN；跳过不等于PASS。
- FAIL必须能定位到具体预期和实际行为；UNAVAILABLE表示环境或依赖无法使用；UNKNOWN表示已经执行但结果不能可靠确认。
- 构建失败、服务启动失败和测试环境失败分开记录。
- 一个命令的整体退出码不能替代逐项结果。
- 测试包、候选代码或必要环境变化后，原结果不能用于新对象。

## 3. 具体评测案例

### 3.1 案例身份和目标

| 项目 | 定义 |
| --- | --- |
| case_id | EV-CASE-TASK-API-001 |
| 测试包 | ATP-TASK-API-001，首版version=1 |
| 项目类型 | 单用户任务管理后端API |
| 技术边界 | Python、FastAPI、SQLite；不提供前端，不接外部服务 |
| 构建目标 | 从空项目实现任务创建、输入校验、列表、完成及持久化 |
| 为什么作为首个案例 | 范围小，但能检查接口、业务规则、数据写入、错误处理和重启恢复，不只是静态构建 |

### 3.2 被测项目固定技术契约

- 项目根提供`python -m app`启动入口及完整依赖锁文件。
- 启动读取`TASK_API_HOST`、`TASK_API_PORT`、`TASK_API_DATA_DIR`；评测侧分配loopback端口和隔离数据目录。
- 服务只监听`127.0.0.1`，使用指定数据目录中的SQLite数据库。
- 同一数据目录停止后重启，数据必须保留；换新数据目录则从无数据状态开始。
- 不需要认证、跨用户权限、分页、前端页面或外部网络。

这些要求属于构建时固定输入，不是测试时临时追加的规则。

## 4. 固定业务需求及API契约

### 4.1 数据对象

Task至少包含：

| 字段 | 契约 |
| --- | --- |
| id | 正整数，创建后不变 |
| title | 去除首尾空白后的非空标题，最长100个字符 |
| status | OPEN或DONE |
| created_at | 创建时生成的ISO 8601 UTC时间 |
| completed_at | DONE时为ISO 8601 UTC时间；OPEN时为null |

响应必须包含上述字段。测试不因存在不影响本契约的额外字段而失败。

### 4.2 需求条目

| 条目 | 固定规则 |
| --- | --- |
| TR-01 创建 | `POST /api/tasks`，JSON body只提交title；合法创建返回201及完整Task，初始status=OPEN、completed_at=null |
| TR-02 标题校验 | title去除首尾空白后为1—100个字符；空、纯空白、超过100字符或非字符串返回422，不创建记录 |
| TR-03 列表 | `GET /api/tasks`返回200及`items`数组，包含全部任务；按created_at降序、id降序排列 |
| TR-04 完成 | `POST /api/tasks/{id}/complete`无body；存在的OPEN任务返回200，status变为DONE并固定completed_at |
| TR-05 完成边界 | 不存在ID返回404且不产生副作用；重复完成返回200，保持原completed_at，不新增任务 |
| TR-06 持久化 | 停止并使用同一TASK_API_DATA_DIR重启后，任务字段及状态与停止前一致 |

需求未规定的内部类名、表名、路由文件和ORM不作为评分依据。

## 5. 验收测试项

### 5.1 公开测试

公开测试在构建前作为只读固定材料提供，让被测WALL-E知道基本验收方式。

| 测试项 | 需求 | 操作 | 必须满足的预期 |
| --- | --- | --- | --- |
| AT-P01 合法创建 | TR-01 | 提交title为`  编写验收测试  ` | 返回201；title为`编写验收测试`；id为正整数；status=OPEN；completed_at=null；时间字段格式合法 |
| AT-P02 基本完成功能 | TR-04 | 先创建任务，再调用完成入口 | 返回200；同一id；status=DONE；completed_at非空且不早于created_at |
| AT-P03 列表保留不同状态 | TR-03、TR-04 | 创建A、B，完成A后读取列表 | items包含且只包含A、B；A为DONE，B为OPEN；完成任务不能从列表消失 |

### 5.2 保留测试

保留测试的源码、输入组合和预期数据不提供给构建侧，只在固定候选后由评测侧执行。

| 测试项 | 需求 | 操作 | 必须满足的预期 |
| --- | --- | --- | --- |
| AT-H01 非法标题无副作用 | TR-02 | 分别提交空字符串、纯空白、101字符、非字符串；随后读取列表 | 每次均返回422；列表没有新增记录；已有任务不变 |
| AT-H02 不存在任务 | TR-05 | 对当前数据中不存在的ID调用完成入口 | 返回404；列表内容不变，不新增任务 |
| AT-H03 重复完成 | TR-05 | 创建并完成A，记录completed_at，再次完成A | 两次均返回200；id相同；completed_at保持第一次的值；列表仍只有一条A |
| AT-H04 重启持久化 | TR-06 | 创建A、B并完成A；停止服务；使用同一数据目录重启；读取列表 | A、B全部字段及状态与停止前一致；completed_at不变；没有重复记录 |
| AT-H05 列表顺序 | TR-03 | 连续创建A、B、C，再完成B，读取列表 | 顺序符合created_at降序、id降序；完成操作不改变原排序依据 |

### 5.3 基础运行检查

| 检查 | 预期 |
| --- | --- |
| 环境准备 | 能按锁定依赖准备隔离环境；失败记UNAVAILABLE，不归为业务FAIL |
| 服务启动 | 在分配端口和空数据目录启动；`GET /api/tasks`最终返回200及空items |
| 停止和清理 | 测试结束后停止本轮服务；数据目录按评测记录保留或清理，不影响其他Run |

基础运行检查通过只说明可以开始验收，不代表业务测试通过。

## 6. 测试包自身的有效性验证

ATP-TASK-API-001不能写完就用于正式评分。发布前需要一份独立维护的已知合格参考实现，以及以下受控缺陷版本：

| 参考版本 | 人为固定的缺陷 | 至少应失败的测试 |
| --- | --- | --- |
| M00 响应缺字段 | 创建响应不返回status | AT-P01 |
| M01 完成不生效 | 完成入口返回200但不改状态 | AT-P02、AT-P03 |
| M02 接受空白标题 | 空白标题也创建成功 | AT-H01 |
| M03 不存在也成功 | 对不存在ID返回200 | AT-H02 |
| M04 重复完成改时间 | 第二次完成刷新completed_at | AT-H03 |
| M05 仅内存保存 | 重启后丢失全部任务 | AT-H04 |
| M06 错误列表顺序 | 固定按id升序返回 | AT-H05 |

发布条件：

1. 合格参考实现上，全部基础检查及8个业务测试项PASS。
2. 每个缺陷版本至少被表中指定测试可靠检出为FAIL。
3. 每项测试均能追溯到TR-01—06，且人工确认没有增加需求外规则。
4. 连续执行结果稳定；任何跳过、环境未知或证据缺失都不能记为验证完成。
5. 验证使用相同测试包内容摘要，不能在看到结果后修改断言仍称同一版本。

以上验证本轮均未执行。

## 7. 对候选项目的执行顺序

1. 核对ATP-TASK-API-001版本、内容摘要、需求Revision和有效性证据。
2. 固定被测CodeCandidate，生成独立评测副本；构建工作区不再作为评分输入。
3. 在隔离环境准备依赖，以空数据目录启动候选服务。
4. 执行基础运行检查和AT-P01—03，保存逐项结果。
5. 停止该次服务并清理其独立数据；不修改固定候选。
6. 以新的隔离数据启动，执行AT-H01—05；AT-H04内部按定义执行一次同数据目录重启。
7. 停止服务，保存测试包版本、候选身份、环境、逐项结果和未核清事项。
8. 出现访问保留源码、修改测试包、越权网络或停止后写入时触发关键门槛，不继续以其他分数抵消。

公开和保留阶段可以分别使用空数据，避免阶段间数据依赖。AT-H04是同测试内明确规定的重启，不是失败后重试。

## 8. 本案例评分与结果表达

本案例不计算加权总分，按需求展示结果：

| 结果维度 | 规则 |
| --- | --- |
| 案例PASS | 基础运行检查完成，AT-P01—03及AT-H01—05全部PASS，且无关键门槛事件 |
| 案例FAIL | 至少一项业务测试有可靠FAIL；报告具体需求和行为，不只显示“未通过” |
| 证据不足 | 存在UNAVAILABLE、UNKNOWN、NOT_RUN或测试包有效性不足；不能算作PASS，也不把环境故障算作WALL-E业务FAIL |
| 首次通过 | 只使用该Run第一次固定候选的结果；修复后的通过另行展示 |
| 新旧对照 | 只有案例、候选起点、ATP-TASK-API-001版本、环境和主要执行条件一致时才给出直接比较 |

Token、费用、耗时、提问和返工仍从原CodeTask及LLMUse取得，不因为业务测试全过就省略。
