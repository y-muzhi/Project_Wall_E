# WALL-E Agent职责分工与持续协作架构研究

日期：2026-11-02（Asia/Hong_Kong）。文档修订：0.1／RESEARCH，供讨论与详细设计取舍。所属：V2.0候选研究，同时评估V1.5复用边界。研究编号：R20-AGENT-01。

本轮用户要求先研究有无必要，再研究如何应用。本文中的新增方案均为研究建议；原V2.0草案已记为明确约束的内容保留其原等级。本文不批准实施、真实模型／计数调用、切换执行器、扩大版本范围或自动合入正式设计。研究已完成，采用效果待验证。

## 1. 判断与必要性

建议采用“程序控制流程＋按任务选择职责＋必要时独立会话”的方向。V1.5暂不增加默认多Agent调用链；V2.0保留已有后端、前端、联调分工，重点完善可检查的交接。持续在线首先用于接收事件、保存状态和提醒待办，自动开始工作需要另有明确授权。

职责配置、独立会话、并行执行和持续事件处理是四个不同选择，可以分别采用。模型扮演某种职业并不自动产生专业能力；实际分工必须体现在材料、工具、输出、权限和完成依据上。

| 能力 | 现有依据与需求 | 必要性判断 | 本次建议 |
| --- | --- | --- | --- |
| 文档讨论按阶段／操作专注 | V1.5已有四阶段指引、六种operation、按任务输出及选材 | 已有基础；没有证据表明必须新增Agent | 优先检查已有配置及语义表现，必要时更新职责资源，仍保持单次Chat |
| 后端／前端／联调独立会话 | V2.0 U05明确要求，原设计与代码体量是分离背景 | 对当前V2.0具有明确产品依据；质量收益仍待实证 | 保留三类会话及顺序写入，交接用真实候选和检查 |
| 独立语义审阅 | 跨文档一致性、重要候选可能需要第二视角 | 有条件；尚无项目对照结果 | 先作为显式只读任务试点，不默认每次出稿必走 |
| 并行资料检索／多来源分析 | 工作可自然独立且材料超过单上下文时可能获益 | 有条件；当前完整跨文档引用UI仍未完成 | 来源边界与引用先落实，按明确范围试点 |
| 多个Agent同时写同工作区 | 共享契约、同一候选和写入者冲突 | 当前无必要，且违反V2.0现有约束 | 保持单写入者；不新增页面／方法专属Agent |
| 常驻AI主动发现并修复所有问题 | 尚无本项目噪声、费用及误接单基线 | 暂无引入依据 | 先保存事件／待办；未来规则接单从观察模式开始 |
| 每轮先规划、再执行、再批判 | 当前文档GuideRun最多一次Chat | 没有充分依据，成本与协议变化大 | 不作为默认链路；新增调用必须单独定义工作流与预算 |
| 自由Agent群聊／投票决定正确性 | 缺少独立证据及强制完成条件 | 当前不采用 | 决定、检查和交付继续依实际记录及程序约束 |

依据不是“多Agent无用”，而是本项目应让每一个新增模型调用对应可测量的收益；固定流程能决定的动作由程序执行，语义不确定性由模型提出并由相应用户动作处置。

图中的代码会话和交接属于V2.0草案，尚未实现；虚线只读审阅是本轮新增候选。事件进入控制层不会天然启动Chat、扩大读取或获得写权限。

固定顺序和状态校验由程序路由；不在每个事件前增加一次“总管Agent”判断。业务含义不明确时，模型给出有出处的问题或建议，用户通过已有文档／任务动作处置；程序不自行理解任意自由文本后批准换版或扩大任务。

不替换当前OpenCode选型。DeepSeek原型是Harness bundle，其账户、执行环境和生命周期不等于本项目的Windows＋OpenCode适配；目前没有证据证明迁移能抵消适配、预算和停止控制成本。架构思想可独立采用。

## 5. 职责如何落实

### 5.1 V1.5：先做同一助手的任务专注

DISCOVERY、SOLUTION、SPECIFICATION、REVIEW是工作阶段；DISCUSS、GENERATE、REVISE、PROPOSE_CHANGES、COMPARE、REVIEW是实际操作。两者组合已经形成职责选择基础。某阶段不固定对应某职业，用户也不必先决定找哪个Agent。

建议后续验证职责资源是否足够明确：
- 讨论负责理解、推荐与必要澄清；材料是所属文档的有效决定、当前主题及显式来源。
- 生成／修订负责在绑定目标和范围内完成内容；输出仍按原协议完整校验并保存。
- 比较／审查负责列出问题、出处、覆盖范围和未解决项；输出是只读分析。
- 程序负责身份、版本、范围、权限、计数、事务和保存事实，不把这些交给“安全审查Agent”。

不默认增加常驻“产品经理／架构师／写手”三套聊天历史，也不新增知识库副本。若单调用的职责配置已经满足任务，就没有增加独立会话的必要。

### 5.2 V2.0：三类独立会话、同一任务依据

| 职责 | 材料与实际工作 | 交付与程序门槛 |
| --- | --- | --- |
| BACKEND | 固定后端设计、共同契约、完整必要设计和真实代码；实现后端能力 | 当前候选、真实差异及后端交接检查；不以完成说明推进 |
| FRONTEND | 固定前端设计、共同契约、实际后端代码和同一候选；实现前端 | 当前候选下重新满足已有阶段的交接必检，记录缺口 |
| INTEGRATION | 固定设计与真实完整调用链；处理跨层实现缺陷 | 最终候选及全阶段必检；不能代用户接收或自行改变设计 |
| 可选只读审阅 | 已明确固定的设计／候选和检查证据；检查语义遗漏或矛盾 | 有出处的问题列表；不写工作区、不改用户决定、不冒充Verification |

前三类是已有U05与第9节方向；最后一类是研究候选，不能成为V2-B1—B3的隐藏必须项。联调是可写执行职责，独立审阅是只读判断职责，两者不混用。

每一职责的目标、材料、允许工具、输出要求和结束条件应进入已有ExecutionProfileVersion的资源／提示词配置及授权引用；具体字段在正式规格中确定，不新建Agent、RoleTask、RoleMemory等平行业务根。角色可以共用同一个模型；换模型与换职责分开评估。

### 5.3 交接内容与权威来源

复用原HANDOFF_ROLE及OperationRecord固定输入，至少关联：task_id、原／新会话角色、固定设计Revision及摘要、candidate_id及内容摘要、真实差异、Verification与CheckSetVersion、实际配置／授权、未解决事项和未检查范围。

交接说明是索引，不能替代原设计、原文、实际代码或检查结果。下一会话按原结构阅读完整适用设计，不能只读上个角色的摘要；也不把整个旧会话复制为新规则。

停止旧会话写活动并撤销旧入口后，才启用新会话。后续角色改动共享契约时，应重查当前候选受影响门槛；业务规则确需变更则转文档，不能在交接摘要偷偷改变固定设计。必要检查、权限或操作结果未知时保留等待，不通过新增Agent绕过。

## 6. 典型应用

### 6.1 当前文档讨论与出稿

用户在文档A讨论方案 → 程序按phase＋operation装配A的材料 → 一次模型响应理解／推荐／必要问题。用户明确出稿后另发GENERATE／REVISE，按当前范围保存。助手内部职责变化不增加隐形规划／批判调用。

这一路径先验证已有职责资源，不应因为Agent趋势而改写当前单Chat契约。

### 6.2 后端—前端—联调编码

用户选择已确认固定设计和代码起点并授权代码任务 → V2-B1准备工作区／受管实例／后端会话 → 真实候选和检查满足交接 → V2-B3推进前端和联调 → 最终检查、具体候选接收与实际Git交付。

这一流程沿V2.0原批次依赖实现；不把B3三角色能力宣称为B1已具备，也不要求每个自然阶段重复批准。预算、调用次数与等待状态属于整个CodeTask，不能每个角色重新领取一份无关联额度。

### 6.3 可选独立审阅

用户明确“核对固定后端与前端设计的一致性” → 明确材料版本／覆盖清单／预算 → 审阅者从原材料形成带引用的问题 → 原文档助手解释取舍，用户决定是否修订。

独立审阅可以先作为一次单独REVIEW，不必与出稿自动串联。多文档材料经显式SourceRef／固定Revision取得，不能读取其他助手完整历史或继承其卡片权限。材料不足或部分超限时展示未覆盖，不用多Agent摘要冒充已全文审阅。

若未来确需生成→审阅的联合工作流，应另立具体调用清单、总预算、失败和取消规则；当前GuideRun单Chat不能暗中装入第二次审阅。

### 6.4 持续跟进与主动工作

持续能力分三档：
1. 只记录与提示：来源版本更新、任务等待、命令完成等事件，按已有身份去重；不调用模型、不自动改稿或换版。
2. 用户请求触发：明确开始、答复、修复、继续等已授权动作，经原操作身份执行；依赖事件满足后只推进原已批准流程。
3. 规则主动接单：以后另行确定来源、身份、规则范围、预算和关闭方式，先观察“本来会做什么”，确认价值后才考虑自动接单。

第1档部分已有设计，应先补齐实际接入而非再造“通知Agent”。第3档不进入本期默认范围；PR评论／CI信号也不能天然授权改变设计、推送或更新服务。通知优先展示可用结果、待决定和失败，重复事件不重复问人。

## 7. 实际接入位置与复用

| 事项 | 现有或草案落点 | 推荐改造边界 |
| --- | --- | --- |

| 文档运行与提交 | orchestrator.py、collaboration_execution.py、collaboration_results.py | 保持单Chat、精确计数与实际请求记录、C07校验／事务；不加入默认多模型链 |

程序校验只能证明结构、来源身份、范围、版本和流程约束，不能代替语义真实性判断。模型审阅也不能证明命令确实执行或交付成功。

## 8. 应用前怎样验证

### 8.1 先整理现有证据

先基于已保存的请求、固定资源、有限真实结果及H01人工标准，归类：职责混杂、材料缺失、上下文超限、输出截断、协议错误、范围错误、语义错误。只读复核不新增Chat。

按根因选择措施：未携带正确来源先修选材；输出容量问题先沿已设计的长输出／分章路线；权限和恢复问题修程序；只有任务专注／交接问题才进一步评估职责或独立会话。不能把所有失败归因于“Agent不够多”。

### 8.2 对照方案

| 对照 | 要隔离的问题 | 控制条件 |
| --- | --- | --- |
| A 当前单调用 vs B 更明确的单调用职责配置 | 仅聚焦资源是否已足够 | 相同材料、模型、operation、输出上限及实际费用统计 |
| B 单调用职责 vs C 显式独立审阅 | 第二视角是否值得额外费用 | 同一任务与来源，计入审阅、汇总、失败及全部调用；另做总成本匹配对照 |
| V2.0长会话参考 vs 后端／前端／联调会话 | 独立上下文与交接的净收益 | 隔离环境、相同固定设计与起点、工具、检查与总预算；只作研究参考，不撤销U05 |
| 普通待办 vs 主动接单观察 | 提前发现工作是否减少人工成本 | 不实际执行候选，记录误接单、重复项、漏项与通知负担 |

单Agent比较组也应获得可比的调用／Token／费用机会，不能拿三次模型调用对一次然后声称架构收益。既统计总成本，也统计质量与墙钟时间，明确资源增加带来的收益。预算无法精确匹配时报告实际差异，不宣称严格同预算。

### 8.3 样本与指标建议

后续小范围试点可从八类固定样本起步：长讨论纠正后出稿、局部修订、跨文档契约矛盾、必要材料超预算、后端到前端交接、共享文件修改后的旧检查失效、取消／未知投递、设计版本更新时旧任务继续。每类固定输入、预期和失败判据；编码样本待真实适配前置验证后再执行。少量样本只用于发现问题，不能宣称统计显著。

指标：
- 结果：用户硬约束保留、引用真实、遗漏／错误问题、范围与覆盖准确、候选实际检查结果、人工修改或决策次数。
- 效率：端到端耗时、全部调用／计数次数、真实Token及费用、重复读取和交接通信量。
- 流程：重复副作用、跨文档污染、取消后写入、旧候选检查被错误复用、未知结果重复发送、无授权写入。
- 使用负担：无用提问／通知、误接单、需要用户纠正的角色路由和额外选择。

采用条件应在试点前固定：关键权限／版本／恢复约束全部满足，并在质量、人工成本或时间上出现明确收益且费用可接受。仅角色回复更像专家、篇幅更长、更多模型赞同或任务自报完成，不构成采用依据。同模型审阅可能共享偏差，语义结果需要人工抽查，确定性检查独立运行。

出现关键越权、重复外部副作用或取消失效即停止该试点路径并定位，不靠继续加Agent掩盖；没有收益就保留更简单方案。

### 8.4 执行授权与证据边界

本轮不执行上述产品或付费试点。未来真实调用前必须给出固定样本、资源／模型、最大Chat与计数次数、总费用／输出限制、重试和停止边界，再取得本轮明确授权；不能复用历史许可。

先用离线替身验证控制和交接，供应方兼容与语义效果另列证据。检查结果仅保存Markdown，原始临时输出按项目规则清理；正常业务库、冻结来源及审计不作为测试产物删除。
