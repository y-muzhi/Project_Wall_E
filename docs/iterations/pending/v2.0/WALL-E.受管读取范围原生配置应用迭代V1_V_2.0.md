# 受管读取范围的活动 C39 原生应用 V1（V2.0）

2026-11-13，继续本轮剩余实际推进时段；实施前登记，pending，不合并正式设计。依据BE APP-CODE-CONDITIONS／7.4.3—7.4.4与受管目录编译迭代。当前只是本批实施规则；未实现／未验证不得记成开放能力。

## 支持范围与来源

仅无命令／无网络的READ20-MANAGED-1：workspace必须保留，basis读取可在原START授权包含的边界内收紧或恢复；workspace写入仍固定，不改配置／provider／运行包／agent／OS边界，不扩大到未登记目录。源授权、当前授权和新批准未绑定授权必须固定；普通CONTROL_ONLY继续原流程。

C39使用原4步及原应用／授权表，不新造业务根。源中保存确定的读取授权编译计划；第三步程序nonce、来源／静止／旧权限／目标编译／配置摘要必须持久。调用方必须从已采用业务链产生原创建scope和原生前驱列表；不得让客户端填scope或当前GET建立expected。

## 持久阶段与恢复

1. 接受后阻止新活动，原第二步实际确认原会话静止、配置／providers／Guard同组及NTFS身份；第三步原身份单独持久。
2. 原第三步仅首次原发布者可以发布私有permission意图并PATCH。目标规则确定编译且以deny-all覆盖旧规则；新nonce／相同现有文件都不能获取第二次发送资格。来源／范围／STOP／预算在外发前后复核。
3. 第三步未知只读取原私有意图及GET，不重新PATCH；缺失原意图也不因此自动补发。成功单独持久后进入原第四步。
4. 第四步重新读session／config／providers／受管入口，原配置不变、最终有序permission及当前agent／原静止对象一致，才在原事务APPLIED／EFFECTIVE。失败／未知保留旧业务有效组及成功前缀。
5. 默认后续消息／捕获／问题／权限的session expected从原创建加已采用的原生应用链推导；pending／失败／未知原生ACK不能作为普通继续的基准。CONTROL_ONLY不加入原生历史。
6. 新角色／同角色修复会话从当前业务授权重新编译创建权限，历史权限前驱不跨session复制。取消／停止仍保留已发生事实，不能通过取消显示权限回滚或自动恢复执行。

## 验证边界

分开：纯编译／Schema事务、真实loopback与NTFS、原Guard与实际UI、正式OS／供应方。正常资源登记仍ready=false，无模型／计数、用户业务库／Git目标、服务启停或SYSTEM／WFP安装。首次私有发布、丢ACK、缺意图、并发、STOP、第三／四步未知、重复更新与随后实际继续需各有证据。只完成部分时保留明确当前函数／分支与恢复命令，不能提升完整C39状态。

## 本批联合验证补充

在真实TaskInstanceDriver／原生HTTP调用路径补齐第三步已预留但尚未发布私有意图的中断、第四步配置漂移／权限漂移／固定依据身份漂移。第三步未发布也只读核对，不获得补发资格；第四步任一组不一致保持旧业务授权及成功前缀，恢复一致后仍按原身份只读，不能靠第二次PATCH修正。与普通CONTROL_ONLY／纯编译专项分开留证据。
