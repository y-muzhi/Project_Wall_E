## 2. 额度与文档写作规则

### 2.1 项目费用策略和 GPT 技术上限

| 规则 | 确定值或行为 |
| --- | --- |
| 项目费用限制 | 固定采用「项目费用不限额」。文档、代码和测试的模型路径均按此原则处理。移除因本地预算金额、余额或金额预留不足而阻止请求的分支，以及相应的必填金额和加额前置。继续记录实际用量、可核实费用及费用未知状态。任务、操作及外部能力的授权仍分别校验。 |
| GPT 文档操作输入上限 | 131,072 Token |
| GPT 文档操作单次输出上限 | **100,000 Token**，适用于新建文档、首次出稿和已有正文的修改建议等文档生成／修订请求 |
| GPT 文档操作输入加预留输出上限 | **231,072 Token**，与上面两项一起生效。发送前预检与返回后用量验证使用同一冻结配置。 |
| 计数与审计 | OpenAI 沿用实际请求体计数，额外 framing 预留为 0。冻结新配置及关联资源，核对模型请求参数、上下文预检、实际用量验证、历史快照恢复和请求详情。历史调用按各自保存的配置投影。保留模型返回的真实用量及缺失状态。 |

一般讨论和只读分析不纳入本次长输出配置。实施时须核对当前 180 秒读取超时、响应接收和审计容量能否承载较长回执，分别处理供应方截断、超时、协议失败与存储失败。100,000 为请求配置上限，实际交付依据完整返回及业务验收。变更资源的供应方准入按项目约定另行核实。[当前计数资源](../../../../backend/resources/openai-v6/counting/collaboration-counting.openai-v2.json) · [OpenAI 请求构造](../../../../backend/app/infrastructure/openai_protocol.py) · [OpenAI 网关](../../../../backend/app/infrastructure/openai_gateway.py) · [GPT-6.2 Sol 官方规格](https://developers.openai.com/api/docs/models/gpt-6.2-sol)

**判断顺序。** 先确定业务操作与文档范围，再选对应模型配置。发送前按实际请求体计数，输入不超过 131,072，同时核对输入与 100,000 输出预留之和不超过 231,072。49,152 是现有输入观察值，用量展示可以提示，发送资格按硬上限判断。必需的目标原文、用户指令、授权范围及明确引用按原上下文规则携带。可选历史与邻近背景沿原规则裁剪、复计；仍超限时给出可调整的章节或来源。前端读取正式配置和回执中的值。

**金额与账本。** 新建、开始、恢复、继续步骤、模型调用和 Testing 起草等入口统一核对是否仍有金额门槛。费用未知时显示「费用未取得」，已有用量按真实值显示。请求数、任务授权、状态和供应方限制各自检查。历史授权、已结算、未结算和未知费用的账本事实可回读，新操作的授权和用量关联仍须可审计。

### 2.2 新建、首次出稿与已有正文修订

| 场景 | 行为 |
| --- | --- |
| AI 新建文档 | 用户明确要求新建时，校验有效结果后直接创建并保存首稿。聊天回执显示实际创建结果、文档和打开入口。 |
| 对空白或纯模板文档首次出稿 | 用户明确要求写入时，首次有效结果可直接保存到固定目标。服务器根据实际正文、初始模板来源和历史判断；纯模板包含初始框架中的示例、表格和填写占位。 |
| 修改、补写已有业务正文的文档 | 先生成待审阅建议，经用户确认应用后写入。全篇、章节、区块、补写未完成章节，以及从评论提出的修订，均遵守同一规则。 |
| 讨论、分析或只请求建议 | 按原意图返回分析或建议。直接保存需要明确的首次写入意图和对应授权。 |

首次出稿资格按整篇文档判断，以程序可核实的空白或初始模板快照为依据。已有实质正文的 V1 走审阅流程。对已写过业务正文的文档，清空或恢复模板后按已有文档处理。接受请求时冻结目标、版本、章节及来源；提交首稿前重核资格和版本。期间若有人工或其他写入，原首稿请求返回冲突，保留当前正文与可核对记录。

**首次资格的技术判定。** 通过当前文档和初始模板资源的稳定引用识别原框架，按文档历史判定是否已有有效业务正文。纯模板为相应冻结资源生成的正文，空白文档以实际正文为空为准。资源或历史证据不足时走审阅入口，并说明原因。标题、文档类型、版本号或模型输出中的自报状态不能代替这项判定。用户明确请求「仅提出建议」时直接进入审阅流程，包括空白或纯模板目标。

### 2.3 用户选章，按次串行

1. 用户在当前文档选定章节并发送。以文档 ID、正式内容版本、标题区块 ID 和章节范围绑定。使用冻结来源和本章所需材料；同名章节按区块身份区分。
2. 每次明确发送至多触发一次生成请求，可返回本章多个改动组。重复发送和结果未知沿原幂等意图核实。选章、查看建议、录入决定和确认应用本身不调用模型。
3. 对已有正文，先审阅并应用本章建议，再由用户选择并明确发送下一章。下一次以最新正式版本为基准。无变化、拒绝全部或放弃后，下一次仍以实际当前版本为准。
4. 截断、取消、失败时保留实际结果与恢复入口。本轮可交付范围以已验证的完整结果为准。系统不自动续写、换章或从章节范围扩大到全文。

**章节例。** 「页面与导航」位于 V3，用户选章后发送「统一返回路径」。一次生成得到「页面入口」和「返回与恢复」两组。用户接受后一组、拒绝前一组，再确认应用，得到 V4。选中下一章「组件」，输入区显示 V4 和真实章节标题，本次发送才生成新请求。若上一章全部拒绝，下一章使用实际仍有效的版本。这个顺序约束当前章节工作流，待审批次本身不占用其他文档，也不阻止当前文档的独立人工操作。

## 3. 业务对象与版本

### 3.1 对象职责和字段

| 对象 | 保存或读取的信息 | 约束 |
| --- | --- | --- |
| 正式文档与 `Revision` | 文档 ID、当前内容版本；各正式版本的 Markdown、区块状态和来源。 | 同一文档内版本递增，`document_id + source_content_version` 可唯一对应快照。变更确认沿现有文档版本语义。 |
| `GuideRun` 与 `LLMUse` | 用户原指令、发起入口、固定目标、范围和来源、本次配置、发送与实际结果、用量。 | 本轮接受时冻结写入意图及资格。审计快照与模型实际请求分别可追溯。 |
| `SuggestionBatch` | 沿用运行 ID、目标文档 ID、基准及实际应用版本；扩展有序分组关系与审阅决定版本。 | 一轮成功生成建议对应一批。基准版本与来源在批次生命周期内固定；应用版本仅在实际产生新正文后记录。 |
| `Suggestion` | 该条所属组和顺序、区块 ID、补丁操作、表格选择器、有界说明、新内容及用户决定；原文可由基准确定。 | 每条归属一组。预览使用真实区块，拒绝跨文档、跨范围或定位不唯一的改动。历史记录按已有格式读取。 |
| 操作回执 | 运行或已提交业务事件、目标文档／范围、实际业务结果、可用的批次和版本引用。 | 从真实结果投影到时间线，运行完成与文档保存分别表达。回执由程序生成，模型只提供可校验的改动内容。 |

分组在既有批次内表达，每组至少有标题、简短原因、顺序及实际建议列表。没有独立的业务根。模型可把同一章中关联的几处修改放进一组，也可拆出多组独立修改。组 ID 由程序在批次内分配。组整体接受或拒绝；当补丁可以独立成立时，将其拆为可分别决定的组。组内任何一个补丁会影响其他补丁时，组合校验要保证组的完整性。组数和涉及位置数由程序从有效建议计算。

本稿采用单调递增的**审阅决定版本**，以下以 `decision_version` 指代。修改决定后递增；确认应用之前比较该值，避免两个窗口的决定互相覆盖。已有批次可从其已有决定和顺序投影，历史实体、ID、内容和应用版本保持原记录。

### 3.2 V3 基准示例

| 事实 | 版本和显示 | 能执行的动作 |
| --- | --- | --- |
| 正式 V3 已生成待审建议 | 普通阅读显示正式 V3；修订视图以 V3 显示原位增删，右侧标明「基于 V3 · 待审阅」 | 定位、决定，核对后应用 |
| 已确认应用，实际保存 V4 | 正式阅读显示 V4；从已应用回执进入时按 V3 和 V4 查看本批实际差异 | 打开 V4、回看本批 |
| 应用前其他写入已生成 V4 | 新正式内容为 V4；旧批次的预览继续用 V3，并显示两者版本关系 | 只读查看旧批次，基于最新版本重新核对或重新生成 |

### 3.3 批次生命周期

| 状态 | 进入条件 | 可做的事 |
| --- | --- | --- |
| 待审阅 | 结构、范围及补丁通过校验，批次和建议已持久化。 | 查看、接受、拒绝、放弃。至少一组待处理时可继续审阅。 |
| 基准已变化 | 当前正式版本与批次基准不同。 | 在原快照查看旧建议。重新发起基于最新版本的修订。此状态从真实版本计算。 |
| 已应用 | 用户确认，事务提交了至少一项实际正文变更。 | 查看基准和已保存版本，以及本批实际应用的改动。 |
| 已结束，正文无变化 | 全部拒绝，或接受的结果与基准正文等价。 | 查看决定及来源。 |
| 已放弃 | 用户明确结束原批次。 | 只读查看原记录及决定。 |

「结果待核实」是客户端在命令结果未知时的显示，由既有命令回执恢复；它不代替实际批次状态。生成失败、取消或无有效改动以运行结果记录。首稿直接保存时记录文档和版本，已有正文的修订通过真实批次进入审阅。

## 4. 应用能力与执行流程

### 4.1 接收请求与路由

1. 读取显式操作和当前用户指定的输入。目标已有文档时核对同需求归属、可维护性和期望内容版本。申请全篇修订与申请章节修订分别绑定已声明的范围。
2. 已有目标的「修订」由服务器按 §2.2 判定首次出稿或审阅。用户选「提出修改建议」以及评论入口均提交待审阅流程；新建须有名称、类型及明确创建意图。读取或分析照常走各自只读动作。
3. 写入请求先固化幂等事实、目标版本、来源、范围、最终执行分支和资源。等待模型期间，其他文档操作按各自权限执行。就同一章节流程，原请求尚在运行时以查看、取消或核对原请求为入口。
4. 收到完整输出后核对范围、来源与版本。首次出稿提交前复核仍有资格和基准未变。修改建议创建前复核冻结目标及补丁；生成过程中正文变化时，以冻结基准形成可读预览的前提是全部候选仍能在原快照验证，旧批次明确只读。无法验证原快照时记录生成失败。

### 4.2 章节输入和模型返回

页端只传已选文档、当前正式版本和合法章节引用。服务器按区块路径解析章节边界，计算获准区块及可用操作。带上用户原指令、该章原文、必要祖先标题、相关已确认决定和显式引用；其他章节仅在有确切用途时作为只读背景。一次发送至多一次生成请求。现有独立计数和本地文本校验依 §2.1 执行。

模型返回简短摘要和按意图组织的变更大纲。每组引用已经授权的区块或表格行，返回操作、必要的表格选择器及新内容。程序从冻结快照解析原文、形成旧内容证据、生成顺序并校验组合；模型不负责确认文档版本或声明「已应用」。表格行替换、插入、删除和段落替换沿现有补丁语义。保持既有每批最多 100 条底层补丁的行为，超过时返回可理解的范围错误，便于用户选更小章节或子区块。完整的新建文档与空白首稿使用对应成品结构。

| 返回情况 | 可持久化的结果 |
| --- | --- |
| 有效新建／首稿 | 文档、实际版本和创建或保存回执。 |
| 有效修订结果 | 建议批次、分组、具体补丁和待审阅回执。 |
| 模型判断无需改或补丁等价 | 「无变更」回执。 |
| JSON 截断、结构错误、未授权目标、组合冲突 | 失败及原因进入运行回执和审计。正式正文不变。 |

### 4.3 审阅、应用和取消

1. 打开建议时读取基准快照和已保存的决定。用户可以按组接受、拒绝，或放弃整个批次。组决定在一次事务内更新关联建议；失败时重新读取真实决定。已有的逐条编辑能力，仅用于可独立决定且符合相同目标／范围检查的条目。
2. 用户点「应用修改」确认接受集合，服务端读取完整决定，复核审阅版本和内容版本。还有未处理组时提示先处理，避免用户误以为未选择部分也会合入。用实际基准重新校验原文、来源、范围和补丁组合。
3. 只将接受或人工核准的有效结果提交为正式文档。保存后回执给出真实版本和是否产生变化。全部拒绝或应用结果等价时结束批次，无新版本。
4. 等模型时取消对应运行；待审阅时放弃对应批次。确认请求已提交但结果未知时优先核对原命令。若提交已经成功则显示实际版本。

### 4.4 实际写入按文档串行

- 等模型和待审建议均为非写入阶段。同一需求的其他文档可独立阅读、编辑、新建和操作。当前文档可继续阅读、定位、查看历史或准备人工草稿，正式提交时采用下述互斥规则。
- 同一文档的人工提交、AI 首稿保存、建议应用、恢复产生新正文等写入依次完成。事务内复核文档、版本、范围、原文、结论有效性及幂等；前一笔已改变基准时，后来的旧提交返回冲突。保留人工草稿及建议决定用于恢复，避免用旧文本覆盖已提交版本。
- 正文快照、正式版本、审计、锚点及批次结果按现有业务事务一次记录。回执未知时只核对原请求。模型运行的完成、失败或取消释放该运行的状态；未审建议不占用需求。文档的归档、权限和源版本仍按各自业务契约校验。

| 场景 | 处理 |
| --- | --- |
| A 文档等待模型，用户编写 B 文档 | B 的人工编辑、创建及 AI 操作按 B 的真实状态判断。A 的等待状态不作为 B 的禁用原因。 |
| 同文档 V3 的人工草稿提交和建议应用竞争 | 两个请求独立保留，真实写入依次校验和提交。一方产生 V4 后，另一方收到版本冲突；服务端保留草稿或批次。 |
| 两个窗口修改同一批次的决定 | 第一个保存后审阅决定版本递增。后一个从实际决定和版本恢复，再决定是否重提。 |
| 用户重复确认或响应丢失 | 同键同业务输入返回原成功事实；同键不同输入沿项目幂等错误处理。 |

## 5. 页面交互

### 5.1 AI 操作回执

AI 业务动作在聊天时间线显示为一条可展开回执。它使用既有运行或程序结果，显示动作名称、目标、业务状态和可用入口。文档操作统一显示与动作对应的「查看修改建议」「打开文档」或「查看运行详情」。建议入口以实际批次为依据，应用状态以正式保存回执为依据。截断、失败、取消、无变化和结果未知分别展示。运行终态可在详情读取，聊天主状态能直接看出正文是否写入。

正文、增删和大纲在目标文档的审阅工作区展示。请求详情可供只读追溯原始调用。无效或截断的原始载荷放在审计详情，聊天显示对应业务提示。普通对话继续使用消息。更新讨论进展等有实际结果的 AI 业务动作也采用同一回执形态。

| 实际结果 | 收起状态 | 主入口及展开内容 |
| --- | --- | --- |
| 等待模型 | 文档修改建议 · 生成中 | 查看运行，可用时取消。摘要显示目标文档、章名和基准版本。 |
| 建议已保存 | 文档修改建议 · 待审阅 | 查看修改建议。展开显示已经验证的组数、修改位置数和来源摘要。 |
| 首稿已保存 | 首次出稿 · 已保存 Vn | 打开文档，展开显示保存事实和目标入口。 |
| 已应用、无变更或已放弃 | 显示确定结果 | 已应用可打开新版本或回看修订；无变化和放弃显示说明。 |
| 生成失败、取消或版本冲突 | 显示实际失败状态 | 显示正文效果及原因。请求详情保留原审计，适用时可创建新一轮。 |
| 提交结果待核实 | 等待核实 | 核对原请求，保留未提交输入或决定。 |

回执以同一运行或已提交操作为识别键。刷新、重新打开对话或收到后续状态时更新原位置。操作生成后可留在当前聊天，用户触发入口才打开文档。切回对话时还原原阅读位置。

### 5.2 原文修订与右侧建议

选择「查看修改建议」时，根据回执打开绑定的文档及版本，进入正文修订视图并打开右侧「修改建议」。参照飞书修订模式的正文原位标记、右侧项联动定位和接受／拒绝动作，使用 WALL-E 的组件、键盘和焦点规则。[飞书帮助中心](https://www.feishu.cn/hc/zh-CN/articles/364198000460-%E4%BD%BF%E7%94%A8%E6%96%87%E6%A1%A3%E7%9A%84%E4%BF%AE%E8%AE%A2%E6%A8%A1%E5%BC%8F)

- 段落在原句标记删除和插入，区块在原位置显示变化；表格尽可能定位到行或单元格。使用文字和语义同时区分增删。复杂替换可就地折叠并展开具体差异。
- 右侧呈现变更大纲、原因、涉及位置数、状态和审阅操作。一处正文可能关联多处内容时，保留组内位置导航。打开、切换或关闭审阅视图不改变正式 Markdown、正式版本或人工草稿。
- 最新基准可以审阅、确认应用。旧基准可读，明确说明当前正式版本及为何暂不能应用。分别处理无建议、无权限、读取失败、定位失败和待核实操作。保留阅读、返回对话及原键核实入口。

底层可行性已有隔离样例。2026-11-25 使用 WALL-E 正文编辑器在 Edge 验证了段落行内增删、按原区块定位表格行、打开／关闭标记后正文和版本数据一致。该样例只覆盖显示机制。完整的右侧联动、复杂表格、章节替换及写入尚待实施验证。[正文编辑器](../../../../frontend/src/documents/editor.ts) · [现有建议定位](../../../../frontend/src/suggestions/targets.ts)

### 5.3 进入、定位与退出

1. 打开回执后，以批次身份读取目标及基准版本。正文区域加载实际版本，右侧加载建议，中间区域标示「修订预览」及基准。两个依赖有任一读取失败时保留可用内容，并给出重试入口。读到另一个文档的版本时禁止叠加。
2. 点击右侧项时滚动并突出对应正文位置；点击正文标记可打开对应建议项。同组有多处位置时支持上一处／下一处。重复段落、同名标题和重复表格值按稳定区块和选择器定位。定位失败保留列表与决定，显示该处无法精确定位，允许查看基准快照。
3. 右侧顶部显示批次名、基准和状态。列表从改动大纲进入组。底部显示待处理数、确认应用和放弃。确认应用前可折叠详情但保留选择。窄屏保持正文和右侧入口可达，允许在建议列表与正文位置之间返回。键盘定位、返回焦点和共享确认组件沿项目规范。
4. 在编辑器的显示层叠加语义标记，再和既有正文标记合成。段落文本粒度可高亮增删。整段或区块插入使用邻接锚点；复杂表格或整节替换在原位置展开结构化预览。待审阅增删只属于该批预览。关闭修订时移除该批标记，继续显示可用的普通正文。

### 5.4 异常和可用状态

| 情形 | 状态与恢复 |
| --- | --- |
| 加载后无有效建议 | 使用共享空态，显示「暂无修改建议」。已知运行失败或取消时，转到真实回执原因。 |
| 基准旧于当前，或参考来源变化 | 明示当前正式版本和基准。旧版仍可看；无法确认应用时说明哪项核对未通过。 |
| 用户只读、文档归档、正在提交或正在核实 | 依据当前权限启用定位和查看。提交控件在对应情况下禁用，并显示具体原因。 |
| 批次已应用或放弃 | 核对实际状态后转只读历史。已应用展示保存版本及本批真实差异。 |

## 6. 接口与回执契约

### 6.1 调用入口和改动点

下表中的路径省略 `/api/v1`。现有接口照原权限校验；「新增」或「扩展」描述事项 20 的目标契约。

| 入口 | 目标输入及回复 | 实施说明 |
| --- | --- | --- |
| `POST /requirements/{requirement_id}/guide-runs` | 沿用 `document_id`、`expected_discussion_version`、`operation`、`instruction`、`target`、`scope`、`source_refs` 等原请求字段。接受成功返回 202 和运行身份。 | 无需新增一套章节请求。已有目标含 `expected_content_version`；按实际文档判定本轮直接保存或进入建议，保存该判定。 |
| `POST /comments/{comment_id}/guide-runs` | 沿用已授权的评论、目标和范围。 | 结果进入同一审阅通道。 |
| `GET /guide-runs/{guide_run_id}`、`GET /model-calls/{llm_use_id}` | 实际运行、业务效果、正常快照及请求详情。 | 用已有业务效果和文档／批次引用投影回执。普通聊天读取不依赖逐条打开请求详情。沿用请求详情的原有读取校验。 |
| `GET /suggestion-batches/{batch_id}` | 沿用批次和建议详情；扩展审阅投影，包含基准与应用版本引用、分组、审阅决定版本和实际可用动作。 | 新投影采用 `include_review=1`，兼容严格旧解码的默认形状。基准快照引用由后端按目标归属解析。 |
| `GET /revisions/{revision_id}`、`GET /requirements/{requirement_id}/current-document` | 读取同文档的实际基准快照、应用版本或当前正式正文。 | 核对响应归属后绑定预览。旧基准使用版本读取；当前内容以当前文档接口为准。 |
| `PUT /suggestion-batches/{batch_id}/groups/{group_id}/decision` | 新增原子组决定入口。请求含 `decision` 和 `expected_decision_version`，结果返回该组新状态和新决定版本。 | 组决定只允许接受／拒绝。由所属批次确定目标及条目。组内决定一次更新，响应与同一次数据库事实一致。原单条和接受待处理接口仍需遵循原子组约束，避免绕过。 |
| `POST /suggestion-batches/{batch_id}/complete` | 继续使用 `expected_content_version`；新分组批次增加 `expected_decision_version`。返回完成事实、实际应用版本或无变化。 | 旧格式按原输入读取和核实。新批次要求两项版本均匹配，按 §4.3 提交一次。 |
| 现有取消、放弃、原请求核实入口 | 运行 ID／批次 ID、原幂等键或现有控制字段。 | 核实结束效果，保持放弃与正文提交的互斥。 |

### 6.2 审阅字段与校验

| 字段 | 定义 | 校验 |
| --- | --- | --- |
| `base_revision_id` | 目标文档基准正式版本的快照 ID。 | 与 `target_document_id`、`base_content_version` 一致。无法解析时回报基准不可读。 |
| `applied_revision_id` | 实际应用新版本的快照 ID，可空。 | 应用结果确实改变正文时才有值；必须与应用后版本一致。 |
| `groups` | 有序列表。每组有 `group_id`、`title`、`reason`、`suggestion_ids` 和从实际决定得出的状态。 | 组 ID 在批次内唯一，每条建议只归一组；组列表覆盖本批所有有效建议。 |
| `decision_version` | 批次决定的正整数序号。 | 所有组级、单条和批量决定复用同一并发判断。明确应用时使用确认界面所读的版本。 |
| 可用动作与原因 | 由权限、基准、生命周期及真实决定算出。 | 读取端可用于提示；命令端必须重新校验。 |

用户写命令继续使用 `Idempotency-Key`。正文冲突复用 `CONTENT_VERSION_CONFLICT`，目标失效复用 `TARGET_STALE`，尚有待处理建议使用既有 `BATCH_PENDING`。决定版本不匹配按审阅状态冲突返回实际版本和重读入口，避免自动重提。供应方失败是已接受运行的结果，由运行读取返回。历史分组投影与错误映射均需严格验证请求、目标和响应归属。[运行契约](../../../../backend/app/guide/http_models.py) · [建议契约](../../../../backend/app/suggestions/http_models.py) · [版本接口](../../../../backend/app/revisions/api.py)

### 6.3 请求节选与例子

同一「页面与导航」章节可在不同文档中重名。以下示例以区块 ID 42 绑定示例文档 10 的 V3，其他必填字段沿原接口。版本快照里的章节授权另由服务器派生。

```json
{
  "document_id": 10,
  "operation": "REVISE",
  "target": {"kind": "EXISTING", "document_id": 10, "expected_content_version": 3},
  "scope": {"scope_type": "SECTION", "scope_ref": {"block_id": 42}}
}
```

假设完成审阅后的 `decision_version` 是 4。确认应用请求体为 `{"expected_content_version":3,"expected_decision_version":4}`。成功回读显示保存的 V4。另一个窗口已先改变决定时，即使文档仍是 V3，也必须先读取新决定，再由用户重新确认。

## 7. 存储、配置与上线边界

### 7.1 数据演进与事务

- 优先沿已有 `requirement_documents`、`revisions`、`guide_runs`、`llm_uses`、`suggestion_batches` 和 `suggestions` 扩展。分组与决定版本采用有明确版本的增量结构。既有建议的原文、新文、ID、决定和应用记录保留。历史批次可按原条目顺序投影，不从旧 AI 文本推断新大纲。
- 修订 4 明确存储方式。模型返回组标题、原因和建议序号。程序验证组顺序及覆盖范围，在同次提交中把分组绑定到运行持久化结果和实际建议。决定版本为初始值 1 加本批已成功提交的单条、组级与批量决定次数，按现有持久幂等回执计算。比较版本、写入决定及保存回执使用同一写事务；同键重放返回原结果且不递增。分组合同独立冻结，历史无分组批次按单条投影。审阅基准与应用版按目标文档 ID 和内容版本解析现有 Revision。
- 以文档 ID 和期望内容版本作为正式写入的事务条件。等待供应方、读取和展示预览在写事务之外。事务内写入当前正文、版本、来源、回执和批次结果；失败则回滚。生成建议的保存事务只更新建议和关联回执。
- 旧需求级占用投影曾承载人工草稿、运行和候选审阅。接入时按这些实际调用者分别改用运行 ID、文档 ID 或批次 ID 核对归属，检查创建、恢复、轮询和取消入口，确保释放正确的旧记录。切换前核对在途工作及正常草稿。以独立数据库验证增量结构和历史读取，生产发布依当前任务授权。
- 费用策略相关历史金额和账本关联可追溯。分批更新查余额和预算的调用方，核对代码任务、测试起草和恢复的金额准备与结算路径。保留未知回执的核实及供应方实际用量链路。[代码调用账本](../../../../backend/app/code_tasks/coding_model_ledger.py) · [测试计划调用](../../../../backend/app/testing/planning.py)

### 7.2 请求配置与容量

同一服务同时按操作选择文档长输出配置或原只读配置。冻结资源明确模型和每次请求实际采用的额度。依据 `GuideRun` 或调用快照恢复历史配置，校验 Prompt、输出结构、计数定义和快照摘要一致性。历史已接受的请求继续按其实际冻结配置恢复。

离线覆盖接近 100,000 Token 的合成回执、超出容量、输出截断、超时、取消、异常用量，以及输入接近 131,072 的预检。核对已有 4 MiB 审计门槛与读取超时，若不能承载所定义的正常结果，实施时调整容量或传输等待方式并验证关闭和恢复。后端锁定实际发出请求与真实审计的对应关系。真实的供应方长输出验证另记次数及用量。

## 8. 实施顺序与验收

### 8.1 实施顺序

| 批次 | 实施范围 | 完成条件 |
| --- | --- | --- |
| 1 · 费用与模型配置 | 调整业务费用准入和相应页面，发布新的 GPT 文档操作配置，校验历史读取 | 本地金额不会中断合法操作；新文档调用快照准确记录三项上限；比旧上限长的合法响应可进入后续校验；供应方截断可区分，历史请求仍显示其实际限制 |
| 2 · 写入、建议与版本 | 收敛首次保存及已有正文建议路径，持久化分组，改写同文档提交互斥与回执 | 空白、纯模板首次出稿直接保存；有正文时只生成建议；同一版本的两笔并发提交最多一笔修改正文；不同文档的编辑或生成不被待审建议阻塞；取消、失败及重复确认可重读真实结果 |
| 3 · 回执和审阅视图 | 接入聊天操作回执、原文修订、右侧定位、版本提示和应用反馈 | 在普通、窄宽、历史、失败及过期状态验证。聊天的「查看修改建议」打开正确批次，正文按基准显示，退出可返回原阅读位置。截断不显示原始 JSON 气泡，也不出现可执行应用按钮。 |
| 4 · 逐章联调 | 从选章到结果、审阅、应用和选择下一章，核对关键恢复场景 | 可用两个有上下文关联的章节证实每次明确发送只有一次生成请求，第二章使用第一章应用后的真实版本。浏览器检查段落、表格、整节替换、全部拒绝、失效批次和按钮原因。 |

### 8.2 必验场景

每项执行时记录入口、原版本、调用或写入次数、实际响应、最终版本及未覆盖项。按场景使用离线测试、隔离 HTTP、浏览器或已授权的供应方验证。

| 编号 | 操作或夹具 | 通过条件 |
| --- | --- | --- |
