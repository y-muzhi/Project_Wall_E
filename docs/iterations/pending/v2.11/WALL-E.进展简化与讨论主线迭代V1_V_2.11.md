# WALL-E V2.11 进展简化与讨论主线详细设计

修订 5 · 2026-11-23 · 详细设计评审稿 · 待实施

## 1. 本轮改造解决什么问题

用户隔几天回到一份文档，打开「进展」就能想起上次谈到哪。用户回到对话说“继续”，AI 能接住同一个问题。用户可以随时问路线为什么这样安排、讨论另一种安排、直接指定新的安排。日常操作集中在文档对话，进展页承担阅读、追溯和返回对话三件事。

已确认的产品方向包括简化进展页、主线约束 AI 讨论路径、用户能用自然语言随时改变主线，以及在 AI 聊天框内直接辨认本轮主线操作和当前主线。本文把它们展开为拟实施行为。采用唯一方案的判定、自动接续的时机、首屏默认展示量及新协议字段是本稿提出的设计取舍，尚待评审。

| 现有体验 | 本轮设计 | 已有数据如何使用 |
| --- | --- | --- |
| 进展默认呈现步骤树、步骤详情及维护动作 | 首屏回答当前目标、已定结论、待定问题，可展开整条主线 | 已有步骤、依赖、支线、成果及事件作为事实来源 |
| 用户展开步骤、切换讨论目标、改变步骤状态各有入口 | 看别的步骤只影响阅读；用户说“先聊它”才改变对话目标 | 沿用查看选择与服务端焦点的区别 |
| AI 路线提案通常需要显式采用 | 用户询问时解释，AI 主动建议时等待采用；用户明确指令可以通过一次讨论直接执行 | 沿用路线计划器、提案身份、事件、幂等和版本核对 |
| 同一操作在对话与编辑工具间来回切换 | 只在需要用户决定真实歧义、处理未决写入或恢复失败时呈现对应操作 | 旧提案、失败回执和历史查阅入口仍有去处 |

本设计以需求下当前一份文档为作用域。权限设计和邮件设计分别属于不同文档时，“去谈邮件设计”要先识别用户是想在本份主线增加话题，还是要切到别的文档。只有指代影响目标文档时才询问。打开参考文档或提到另一份文档，均不扩大本次修改范围。

## 2. 一段连续的实际体验

下面的会话使用同一份《团队邀请设计》。示例中的标题、结论和人物仅用于说明验收输入。

| 时点 | 用户看到或说的话 | 对话应如何接 | 保存后的进展 |
| --- | --- | --- | --- |
| 首次打开 | 文档为空，尚无讨论 | 进展显示“还没有讨论这份文档的目标”。「开始讨论」打开输入区 | 此次查看没有创建步骤或运行 |
| 说明用途 | “我们要把团队邀请功能定下来，供前后端开发。” | AI 说明建议先定谁能邀请，再定邀请有效期，最后处理通知；用一句话解释依赖 | 路线仍是建议，回到对话可查原建议 |
| 采用路线 | “就按这三步，先定权限。” | 保存路线，接着讨论谁可发起和撤销 | 主线为权限、有效期、通知；当前焦点为权限 |
| 定下一点 | “管理员发邀请，部门负责人只能看本部门的。” | 记录两个可追溯的决定，根据目标继续核对撤销权限 | 已定两项，待定“谁可以撤销邀请” |
| 临时插问 | “顺便问下，邮件退信怎么办？” | 回答退信问题。用户问得具体时可以展开，不必强行用一个问题拉回 | 焦点仍为权限。临时解释留在原对话 |
| 隔日接续 | “继续。” | 直接接“上次定了发起和查看，还差谁能撤销邀请” | 不再重复确认已经定下的角色 |
| 改路线 | “先不谈撤销，把有效期拆成默认时长和续期，挪到最前面，先谈默认时长。” | 一次处理拆分、调序和切焦点；说明仍为权限保留撤销问题 | 顺序为默认时长、续期、权限、通知；焦点为默认时长 |
| 纠正 | “我说的是提前聊，顺序还是把权限定在最前。” | 按本句纠正顺序，保留已经明确的拆分和当前焦点 | 顺序为权限、默认时长、续期、通知；仍讨论默认时长 |
| 形成正文 | “默认七天，就写到有效期这一节。” | 确认“七天”是用户决定；正文按已有写入流程解析目标和范围，分别反馈决定与写入结果 | 只有正文成功回执才能标记已写入相应版本。写入失败仍可找回已定的七天 |

## 3. 主线的对象、归属与不变量

### 3.1 各类事实的含义

| 概念 | 稳定身份和来源 | 谁能改变、改变什么 |
| --- | --- | --- |
| 文档目标 | 单文档主线头、目标版本、目标文字和来源 | 用户可以指定或采用 AI 提案。变更目标后重验既有评估的适用性 |
| 路线步骤 | 同文档 step_ref、位置、定义版本、预期成果、依赖 | 改名或调序沿用身份。拆并用新身份及替代关系保留旧步骤履历 |
| 当前讨论焦点 | 服务端 current_step_ref 及可选活动支线；可为空 | 用户切换、明确采用下一目标，或明确要求的复合操作成功后更新 |
| 查看位置 | 文档页当前展开行、详情页签、滚动位置 | 本地阅读选择。关闭面板和翻页均不形成业务事件 |
| 已定结论 | 用户事实、正式回答、用户采用的决定及其来源与有效性 | 更正产生带来源的替代。建议、分析和评估的“充分”本身不构成用户决定 |
| 待定问题 | 真实开放的问题、归属步骤、提出依据及解决依据 | 有回答才解决；“以后再说”保留可找回的位置。问题确已存在才显示为待定 |
| 成果与正文 | 当前或历史 Revision、实际覆盖区块、管理其有效性的关联记录 | 历史写入事实与当前正文仍含该结论分别核验 |
| 提案与回执 | 消息身份、卡片键、冻结依据、原请求与事件 | 提案可采用一次。回执记录实际变更、最终焦点和版本，用于恢复与解释 |

### 3.2 状态如何解释

同一份文档可有多个进行中的步骤，只有一个当前讨论焦点。步骤沿用 PLANNED、IN_PROGRESS、PAUSED、COMPLETED、CANCELLED。讨论得出结论、被明确结束以及拥有已写入成果是三项独立事实。界面只在有结束事件时显示“已结束”；当结论足以推进而步骤仍进行中时，展示已定事项并推荐下一目标。用户说“这步结束，去谈通知”，按已有结束规则记录当时成果、未决项和新焦点。说“这步先跳过”则保留未决项。查看历史步骤可阅读当时结论，重新开展工作时沿用合法重开或替代步骤的处理。

进展读数不依靠完成百分比。一个需要用户决定的问题可能比五个已写好的段落更影响下一步。首屏展示实际事项，整条路线展示步骤顺序和当前标记。

### 3.3 结论如何归到正确的步骤

旧讨论的主题 t、依据 e 和形成步骤 s 分属不同身份域。优先使用已有真实的主题或来源关联。若现有字段不能唯一表达某条已确认依据归属哪个步骤，设计补充最小的**文档、步骤、依据引用**关联，可携带建立关联的事件身份；结论正文、原话与版本沿用既有来源。只有当轮绑定步骤与结论确实相关时才建立关联。文档级决定显示在整条主线的文档目标下；无明确归属的历史依据仍可通过来源阅读。禁止按标题相似、数组下标或编号把 t2 自动当成 s2。

同一条结论对多个步骤适用时可以有多个关联，展示按依据身份去重。用户改口时，沿用依据的 supersedes 关系取得有效版本，保留原始消息。两条来源相互冲突且用户未裁定时，把冲突呈现为一条具体待定问题。拆并后通过成果、问题及明确的依据关联决定去向；只重排不复制依据。不因移出某个步骤连带删除用户事实。

## 4. 进展页逐区域设计

### 4.1 默认首屏和阅读动作

以“定清团队邀请的权限规则”为当前目标，首屏示例为：

> **正在讨论**　谁能创建、查看和撤销邀请？  
> **已经确定**　管理员可以发邀请。部门负责人可以查看本部门的邀请。  
> **还有待定**　谁能撤销尚未接受的邀请？  
> **继续讨论**　　查看整条主线

“正在讨论”取已绑定焦点的目标或预期成果。没有焦点时展示文档目标，并说明尚未选定具体讨论项。首屏拟最多列三条当前有效结论、三条待定问题，多出部分用“查看其余 N 项”在原位展开。N 必须来自完整计数。排序先取本轮点名的未决点，再取阻塞当前预期成果的实际问题，其余依既有路线顺序及稳定引用排序。结论优先展示涉及当前未决点及最近更正的内容。只要有来源，可从条目查看用户原话或对应版本。遇到仅存历史出处时明确说明版本。

「继续讨论」只切换同文档对话并保留未发送草稿。展开整条主线时显示目标、有效步骤顺序、当前焦点和遗留问题；点击一步就地展开其结论与待定。无论窄屏单列还是宽屏双栏，展开、键盘定位、翻页和收起都只改变查看位置。已放弃或被替换的步骤进入可展开的历史。日常页面移出路线编辑器、支线处置、步骤收尾表单；已有未处理写入提案及结果未知的操作保留可达的处理入口。

### 4.2 页面状态与恢复

| 条件 | 用户看见什么 | 可执行动作与恢复 |
| --- | --- | --- |
| 初次进入、读取慢 | 读取状态 | 可返回对话；响应必须匹配当时文档 |
| 支持主线、尚未建立 | 本文档尚无目标的业务空态 | 开始讨论；只读打开不建线 |
| 有旧讨论而没有主线 | 当前可读取的旧主题和来源 | 回到对话接续；创建新路线需要新的用户指令或采用 |
| 有目标、无焦点 | 文档目标、现有路线和待定项 | 用户可用自然语言指定先谈哪项 |
| 有焦点、尚无结论 | 当前目标与实际问题 | 有问题则列出；空数组不生成虚构事项 |
| 所有已知问题均有结论 | 已定事项、推荐的后续目标或自然收尾 | 可继续、改向或明确要求写入 |
| 显示的是旧快照 | 保留同文档上次内容，标注刷新失败 | 重试读取；依赖时效的动作需重新核对版本 |
| 首次读取失败或失权 | 对应错误原因 | 读失败可重试；失权清除受限内容，返回可用导航 |
| 切换文档或离开详情 | 新文档自己的读取态 | 取消原读取或丢弃迟到响应，保留按文档隔离的草稿 |
| 人工编辑、运行占用、待核实 | 已有可读进展和具体占用／恢复提示 | 阅读可用；命令可用性遵循原业务占用，未知结果从原操作核实 |

### 4.3 聊天记录中的主线操作

在触发操作的 AI 回复下显示一条紧凑的系统记录，样式统一为操作名称加实际结果。默认就能读懂，不依靠颜色或悬停区分。用户回翻聊天时，这条记录反映当时发生的事。仅在复合变更多到一行说不清时允许展开细节。

| 实际结果 | 聊天中的示例 | 出现条件 |
| --- | --- | --- |
| 新建主线 | **已新建主线**　团队邀请规则 · 邀请权限 → 有效期 → 通知 | 从尚无主线到第一条路线提交成功 |
| 修改主线 | **已修改主线**　「有效期」拆为「默认时长」和「续期」，均移到「邀请权限」前。当前讨论「默认时长」。 | 已有路线发生实际结构或目标变化；复合事务只显示一条 |
| 仅切换焦点 | **已切换讨论步骤**　邀请权限 → 通知 | 路线结构无变化、当前讨论目标确实切换 |
| 仍在建议 | 沿用已有路线提案显示“建议调整主线”和拟议内容 | 待采用的建议保留原提案状态；采用后将成功记录挂在实际执行的那一轮 |

普通回答、临时插问、单纯新增讨论结论沿用原回复。没有实际变化时可简短回应“已经是这个顺序”。失败或结果待核实时沿用该轮错误／核实提示；核实发现成功后在原位置补齐系统记录。完整业务事实归同一回执，正文回复可继续讨论下一问题，无需逐字复述操作。

### 4.4 输入框旁的当前主线

在讨论输入区复用现有「讨论目标」位置。收起时显示“主线：团队邀请规则 · 当前：默认时长”；其中主线名称取已保存的文档目标，当前项取已绑定步骤。展开后直接在聊天区显示当前有效顺序，在焦点旁以文字标示“当前”，例如“默认时长（当前）→ 续期 → 邀请权限 → 通知”。长标题与长路线在展开区换行。展开只读，不改变焦点或输入草稿。用户直接在原输入框说“把通知提前”即可修改。

尚未建线时，讨论区目标位置显示“尚未建立主线”；已建线但无具体焦点则显示整体目标和“讨论整份文档”。读取失败显示待刷新状态，不能把失败误作未建线。写入模式优先保留原写入范围；当前主线可在同一输入区的上下文详情查看。输入区即使滚动到旧消息也显示当前文档最新已提交状态；另一个文档的状态不得串入。窄屏优先保留操作名称与当前步骤，完整目标和路线可通过点击或键盘展开。

**数据接入。** 聊天消息读取拟增加可选的主线操作回执投影。按文档、触发消息／运行和已提交事件批次关联，只纳入该轮实际执行的操作。投影取操作类型、提交时的目标与步骤名称、顺序差异、前后焦点及稳定批次身份，历史消息据此显示当时名称，即使步骤后来更名也不回写。实时到达、分页重读与重试按同一批次去重。历史记录没有可验证关联时沿用原消息。输入区读取第 6 节的当前摘要及已有步骤分页；从相同文档与版本的读取结果组合顺序。提交成功时同时刷新当前摘要和消息记录；其中一项失败时仅重读对应数据。

## 5. 对话意图、操作与状态转换

### 5.1 一句话怎样路由

以下分类供实现和验收使用，用户无需选择模式。先看整句话在当前对话中的意思，包括否定、引用、条件和最近明确提案。关键词“改”“删”“继续”均不能单独触发操作。

| 输入及上下文 | 本轮输出 | 是否提交路线或焦点 |
| --- | --- | --- |
| “我们怎么走到这一步的？” | 回答当前目标、已采用的路线和相关决定，能查到的引用附来源 | 否 |
| “如果删掉通知，会漏掉什么？” | 用当前步骤、依赖和实际成果比较影响 | 否 |
| “他说‘把通知删掉’，我不同意。” | 理解为表达异议；可解释保留通知的影响 | 否 |
| “权限先别动，删掉重复的‘提醒邮件’那步。” | 保护权限，定位唯一的提醒邮件步骤，预演删减范围 | 校验成功后直接提交 |
| “按刚才那版改。” | 取当前文档明确可采用的方案与冻结内容 | 唯一、仍有效时直接采用；多个方案仅问指哪一个 |
| “你觉得怎么安排更好？” | 描述推荐路线、理由与受影响项，保留可采用的精确方案 | 只形成建议 |
| “先聊续期，路线照旧。” | 接续期问题 | 只改焦点 |
| “把续期挪到权限前面。” | 调整顺序并回应新位置 | 只改路线，原讨论焦点继续 |
| “先别改，我只是问问。” | 对仍待采用的提案保持待选；回应当前问题 | 否；已提交修改需另按当前状态作纠正 |
| “可以。” | 检查上一轮唯一待答问题究竟是业务结论、路线建议还是写入提案 | 只承接对应对象和已有权限。模糊认可不能同时驱动多类修改 |

用户一句话同时提出意见和修改时，分清作用域。例如“我觉得以后要加短信，这次先把邮件通知提前”只执行后半句。若执行需要用户尚未给出的决定，保留已经说清的指令和所针对的版本，在原对话问一个能消除歧义的问题。后续答复组合成一项操作，重新核对当前版本。用户中途改问别的问题，不把新话题解释成对旧问题的确认。

### 5.2 改动字典

| 操作 | 输入、前提与默认值 | 成功状态与具体反馈 |
| --- | --- | --- |
| 建立路线 | 文档尚无路线；明确目标和步骤。用户只给用途时先建议，指定“照此建立”时执行 | 建立目标、步骤及必要依赖；用户明确指定第一讨论项时设置焦点 |
| 改整体目标 | 用户说明新目标；冻结旧目标版本 | SET_GOAL 并记录来源。既有评估按新目标重验，既有路线只调整明确受影响的部分 |
| 增加、改名 | 新增有位置就用该位置；无位置且无依赖时默认追加。改名绑定原步骤 | ADD_STEP 或 RENAME_STEP；引用旧名称的来源仍在，反馈最终名称与位置 |
| 调整成果要求 | 明确哪个步骤、增加或更新哪项预期成果 | UPDATE_RESULT 或 ADD_RESULT；既有正文关联按新定义核对 |
| 调序 | 解析移动项与锚点，两者均属于发送时的本份路线 | MOVE_STEP，保留身份和焦点。新顺序与有效依赖矛盾时说明具体冲突 |
| 拆分 | 旧步骤、新步骤、每个旧成果与开放问题的去向；临时引用在本批声明 | 组合 ADD_STEP、CANCEL_STEP 及成果承接。新焦点可引用本批新建步骤 |
| 合并 | 明确被合并项和新目标；保留下游依赖、问题及来源的有效去向 | 建立替代步骤并移出原步骤。重复来源去重，同名但不同决定分别保留 |
| 移出、暂缓、恢复 | 区分“这版不做”“晚点再谈”和“刚才那项恢复”。核对已有成果、活动支线和当前焦点 | 准确反映移出或暂缓及返回位置。历史已取消步骤的恢复若需新步骤承接，说明继承关系 |
| 正式结束、重开 | 明确要求结束或重开特定步骤。结束时读取当时成果、未决项、正文与定义版本 | 复用 COMPLETE_STEP 或 REOPEN_STEP。未处置问题沿用开放，未落地成果保留待完成，回复指出遗留事项 |
| 回退上次调整 | 绑定实际事件、用户期望恢复的部分及当前版本 | 新增一笔纠正事件。仅恢复用户点名的顺序或目标；期间新增决定仍保留 |

删除当前焦点后，若用户已指定接续项，采用该项。若唯一替代步骤完整承接当前目标，直接衔接。若当前步骤已移除且有多个实质不同的去向，在整批提交前让用户选一次。用户明确说“先不选下一步”时可将焦点置空。复合操作里无法确定一项旧成果归属时，不先提交已理解的前半批。

### 5.3 AI 如何选择下一步

主线是 AI 的工作依据。用户点名的问题优先于默认顺序。用户只说“继续”时，先取当前焦点下上次停住的问题；若它已解决，取阻塞当前成果的下一项；若现有问题均已解决，承接上一轮明确推荐且仍有效的下一目标。多个目标同样可行时，AI 推荐其中一项并解释理由，只有取舍会实质改变成果时才请用户选。没有后续目标则总结已有结论或提示已具备出稿条件。这套规则允许一次回复止于直接回答。

临时插问只改变本轮谈什么。用户对插问形成明确决定时可记录为文档级或相关步骤的依据，但仍保留原焦点。“今天起先把邮件方案定下来”才持久调整焦点。自然转场不会自动结束原步骤、接受路线提案或确认正文版本。

## 6. 后端读取契约与事实投影

### 6.1 现有入口和拟增字段

当前前端 getFormationSummary 通过 `GET /api/v1/requirements/{id}?expand=discussion&document_id={doc}` 取得 `discussion.formation_summary`；现有严格解码版本为 `formation_read_v21_1`。步骤、问题、支线与历史有独立分页接口。现有 summary 含目标、焦点、计数和可用操作，无法单凭这些计数回答“具体哪件事已经定了”。

设计采用显式选择新读取视图：同一 GET 增加可选查询 `progress_view=brief`，要求同时提供文档和讨论展开。响应在 discussion 下增加 `progress_brief`，原 formation_summary 保持原有形状；两者在同一个读取快照内生成。原客户端继续使用原查询。新前端的请求合并键须包含 progress_view，缺失已请求字段作为读取失败处理。旧数据或不支持主线的读取分支按实际能力显示旧讨论。此参数和下表字段均为拟新增契约。

| progress_brief 字段 | 值与约束 | 用途 |
| --- | --- | --- |
| document_id、discussion_version、formation_version、revision_id | 文档与版本取同一快照；未建线时 formation_version 可空 | 拒绝错文档及旧读取；可对照同轮 AI 依据 |
| goal、focus | goal 取当前整体目标；focus 可空，有值时含真实 step_ref、标题和本步目的 | 渲染首行；存在步骤与已有焦点分开 |
| decisions | 有效结论行数组，每行含 evidence_ref、text、source_refs、关联步骤引用及可核验的正文关联 | 只展示能追溯到用户决定的事实 |
| issues | 实际开放问题行数组，含 issue_ref、step_ref、question 和可用来源 | 首行待定及继续讨论的依据 |
| decision_total、issue_total | 当前目标可见行的完整数量；首屏返回前三行 | 控制展开，避免把三条样本误作全量 |
| next | 可空；有值含真实目标或问题引用、推荐理由及依据版本 | “继续”的候选；过时建议不参与自动接续 |

首次读取只投影首屏所需内容。结论超过三条时按文档与步骤扩大同一视图读取，拟允许 `progress_limit`（默认 3，最大 20）及对应分组的游标；问题和步骤的完整列表优先复用已有分页读取。游标绑定文档、分组、排序和读取版本。版本变化则放弃旧游标重新读取第一批，可保留展开意图。跨页定位按步骤身份，不按页面序号猜测。

### 6.2 结论、待定和写入的判定顺序

1. 按文档权限和真实归属取当前焦点与候选依据。移除已明确被替代的旧依据、纯 AI 推荐和无法核验为用户决定的条目。
2. 在可关联到当前步骤的有效依据中按稳定身份去重。历史已关联正文取真实 Revision；当前覆盖有效才标为“当前正文已写入”。旧版本覆盖只能展示“曾写入 Vn”。
3. 未解决且属当前目标的问题进入待定。已暂缓问题在整条主线里保留。若用户更正使某问题再次开放，显示最新未决内容并可追溯此前答复。
4. 一条消息可以同时贡献用户事实、问题和修改意图。程序核验不同引用和操作类型，不以整段回复替代逐项归属。
5. 将相同的有效结论引用、焦点和待定项交给 AI 选材。页面和模型材料可以因展示／输入预算使用不同长度，但同一身份的状态与正文版本必须一致。

以下为拟新增 progress_brief 成功片段，使用示例标识。前端还需解码外层已有响应壳。最近明确点名的问题直接带真实引用；无推荐时 next 为 null。

## 7. 模型上下文、输出与程序权限

### 7.1 一次真实请求里应该有什么

| 材料 | 来源及用途 | 预算或材料不足时的处理 |
| --- | --- | --- |
| 最新用户输入和引用的上一轮提案 | 当前消息、唯一提案消息与卡片身份、未采用或已采用状态 | 保留原话和可见别名。摘要里出现“用户同意”不能代替实际用户消息 |
| 文档整体目标与路线顺序 | 当前主线头、版本、简短的步骤身份／标题／依赖 | 优先覆盖当前焦点、相邻步骤和点名目标；记录省略范围 |
| 当前焦点、已有结论与待定点 | 与进展页共用有效事实投影 | “继续”依赖的上次停住事项跨近期窗口保留。旧结论已经被替代时只携带必要的更正关系 |
| 变更涉及的成果、问题和支线 | 受影响步骤的完整承接材料，包含本次真正提供的引用 | 能由程序确定的目标先定向装载。未读实体不授予修改权限 |
| 版本、覆盖及来源 | 现有 formation.basis、coverage 和材料别名映射 | Wire 只公开所需绑定值；真实权限和幂等依据在程序私有快照 |
| 正文及历史 | 按本轮任务实际选材；纯调序通常只需路线材料和必要成果引用 | 一条原文按现有资源规则去重。计数、审计和实际 Wire 一致 |

目前 model_material.capture_material 已冻结目标、所选步骤、问题、成果、评估和覆盖。设计需补简明顺序、有效结论与长期未决事项。用户对远端步骤说“拆一下最后两步”时，按发送快照中有效步骤排序确定目标，检查输入是否完整包含两步的承接材料。若同一轮不足以安全拆并，保留原请求，明确缺哪一步或哪项材料；可从本地读取的缺口由程序先补，后续需要模型重新判断时由正常交互接续。阅读页面、展开来源或核实回执均无额外模型调用。

### 7.2 输出结构与执行边界

沿用单轮讨论与九个模型输出根字段。本稿建议发布新的版本化讨论资源，扩展既有路线提案载荷；历史运行与待采用卡按其原资源解码。纯问答且没有进展变化时，原协议允许的空结果保持有效。一般事实或问题更新沿用 progress_delta；重大路线修改仍走路线计划器，同一批重大变更只由一个入口提交。纯焦点调整可交给同一执行适配层转换成既有选择命令，无需伪造一个路线结构变更。

| 模型表达 | 必需信息 | 后端处理 |
| --- | --- | --- |
| 建议方案 | 可读建议、拟议变更和冻结依据 | 保存可采用提案，返回唯一引用；等待具体用户选择 |
| 用户直接指令 | 当前用户消息别名、定位到动作与对象的原文片段、规范化变更、成果承接、可选最终焦点 | 核对证据、范围和业务不变量，提交完整计划或给出精确缺口 |
| 用户采用先前方案 | 本轮用户原话、目标提案身份和冻结内容摘要 | 从服务端读回原提案并消费一次，不接受模型重新拼写成“同一方案” |
| 询问或澄清 | 可读解释或一个必要问题，可带真实来源 | 保留原路线，明确哪些信息会决定下一步 |
| 复合指令 | 一组路线改动及最终焦点；焦点可指向同批已声明的新步骤 | 所有新身份解析完毕后统一执行。若任一子项不成立，整批拒绝 |

最终焦点须明确区分三种取值：保留原焦点、设为某一步、回到文档整体。只调序默认为保留；显式清除焦点才能回到文档；已删除焦点的批次必须给出有效去向。协议需将这三者定义成互斥分支，并对空值、临时引用、未携带引用分别校验。

模型只负责解释语义与提出动作。程序能验证消息归属、引用原文、命令集合和事务条件，无法仅凭文字片段证明理解了反问或否定。因此“如果删掉会怎样”必须纳入模型效果检查；校验片段存在、动作 Schema 合法都不算通过这项验收。遇到真实语义歧义才追问，明确指令无需每轮点击确认。

### 7.3 示例指令在三层的形状

用户原话为“把有效期拆成默认时长和续期，放到权限前面，先聊默认时长”。假定本轮材料明确给出权限 s1、有效期 s2 以及旧成果的实际引用。下列为设计示意，其中本地临时身份按资源 Schema 编码。

| 层 | 拟产生的内容 |
| --- | --- |
| 模型可见 | 当前文档目标、冻结版本、s1 和 s2 的定义、旧成果、已有问题、路线简表、本轮原话 |
| 拟议动作 | 在 s1 前声明两个新步骤及预期成果，按用户要求排列；将 s2 的各项旧成果映射到对应新成果；迁移仍开放的问题；使 s2 退出有效路线；最终焦点指向第一个新步骤 |
| 程序私有 | 重新验证文档、用户来源、实际版本、完整旧成果集合、依赖边、幂等身份及原始消息。规划通过后分配真实引用 |
| 用户结果 | 成功才显示“已拆成默认时长、续期，现在讨论默认时长”。一项“过期后能否续期”若无法判断该归默认时长还是续期，只问归属并保留旧路线 |

## 8. 提交、并发和恢复

### 8.1 正常时序

1. 在现有普通讨论入口接收消息，按当前文档冻结讨论、主线及正文版本。接收消息或生成一条建议本身不代表路线已改。
2. 复用现有模型输出校验、卡片及来源注册。新路径把用户直接指令或明确采用的方案转换成受限的服务端动作，浏览器不接受模型直接分配的实体身份。
3. 在已接收运行的结果持久化路径中，根据真实运行归属获取业务事务；既有空闲用户命令入口与运行占用之间的校验保持各自职责。运行完成前不从前端模拟多个独立 PATCH，以免自锁或半批提交。
4. 先构建完整路线计划，验证所有旧成果去向、依赖无环、开放问题去向、活动支线返回位置和目标可用性。新建焦点使用本批符号身份参与预演，分配真实身份后再次核实焦点。
5. 在同一写事务内保存路线、焦点、来源关联、事件、提案消费和可重放结果。沿用 FormationTransaction，一笔事务至多推进一次讨论与主线版本。首次建线从真实版本 1 开始；纯路线修改不新增正文 Revision。无实际差异的命令返回“已是这个顺序”，不制造路线变更事件。会话消息仍按对话规则保存。
6. 成功回执包含原运行／消息身份、涉及文档、修改前后版本、可读变更、最终焦点及原有事件引用。前端从回执刷新摘要，下一轮按最新事实装配。回复文字若预言了“已改”，只在有对应回执时呈现为成功。

### 8.2 逐类失败与用户可见行为

| 故障时点 | 系统可以确定的事实 | 显示、恢复和重试 |
| --- | --- | --- |
| 模型未返回或输出不符合新协议 | 未取得合法路线计划 | 显示该轮失败，保留原输入；不提交路线或生成虚构成功通知 |
| 用户切到其他文档，原回复晚到 | 原运行绑定旧文档 | 原回执归旧文档；当前页不跳回，不以新文档身份套用旧变更 |
| 两端同时改主线 | 第二个计划的冻结版本已过时 | 回到最新快照，指出变的是哪一步。旧计划不改版本强行重放 |
| AI 建议后用户从别处先采用了同一卡 | 原提案可能已有正式结果 | 返回或定位原回执，不二次应用 |
| 依赖成环、缺成果去向、跨文档身份 | 整批计划无效 | 保持原图；说明具体冲突和与用户有关的选择 |
| 输入超界或缺少完整承接资料 | 当前计划无法由现有材料和事务额度承载 | 告知涉及哪部分。沿用原生路线批次 20 项、64 KiB 的校验，不截断或擅自拆成多次部分成功 |
| 写事务中第二项失败 | 路线和焦点尚未共同完成 | 回滚整批；不出现新路线配旧焦点的页面 |
| 超时发生在提交边界 | 尚不能确定结果 | 原操作进入待核实；使用原请求身份读取回执，不重发 Chat |
| 路线已提交、摘要读取失败 | 修改已经完成 | 提示“修改已保存，进展暂未刷新”；只重试读取 |
| 取消／关闭页面 | 关闭页面不等同取消已受理运行 | 已知提交前取消则保存旧路线；结果未知先查原运行；提交后可用自然语言纠正 |
| 人工编辑、归档、无权限 | 按该文档实际读写能力限制 | 显示具体原因。从交互恢复后重新载入最新版本，保留可读历史 |
| 正文后续被修改 | 已写入旧版本是历史事实，当前文字可能变化 | 重新判断当前覆盖；必要时标为“曾写入 Vn，当前版本待核对” |

### 8.3 历史、恢复与上线兼容

旧讨论和旧提案继续通过原协议读取。曾经明确采用、已确认的历史决定不因新摘要缺关联而丢失，也不能为了填满三行自动补成某一步的结论。旧数据可只读展示可核验事实；首次产生新关系时按当前事务写入。历史提案按原消息、原资源、原绑定采用；新客户端对旧资源不展示“支持自然语言直接执行”的成功假象。

上线顺序建议为后端支持新读取和版本化契约 → 前端支持新旧响应和回执 → 启用具备该能力的讨论资源。后端尚不支持新读取时使用已识别的旧视图；普通网络失败走错误恢复。若撤回新能力，保留已提交的业务事实和事件，允许旧入口读取合法路线；部署回退前应验证旧二进制能否读取新记录和冻结运行，新版载荷由匹配版本解码。发布及数据操作另行授权。

## 9. 实施映射与交付顺序

以下为工作区静态核对位置。路径以项目根为基准。“需补”表示设计差异，实际实现状态以对应代码与验证记录更新。

| 单元 | 复用位置 | 需补与完成条件 |
| --- | --- | --- |
| 事实归属和读取 | backend/app/requirements/discussion.py、backend/app/formation/read_queries.py、read_projection.py | 明确依据到步骤的关联；实现新旧读取与同版本摘要。空态、旧数据、疑似冲突、正文变更各有真实投影 |
| 页面与交互 | frontend/src/api/walle.ts、models.ts、formation-values.ts、frontend/src/formation/read-owner.ts、progress-view.tsx | 严格解码新视图，缩减首屏控件，保留来源、整条路线、未决处理和返回。可用键盘和窄屏完成接续 |
| AI 读取与输出 | backend/app/formation/model_material.py、model_projection.py、model_evidence.py，backend/app/guide/progress_application.py，版本化讨论资源 | 打通实际 Wire、覆盖、计数、结构验证与消息输出。历史九根协议和已接受运行仍可解码 |
| 自然语言提交 | backend/app/formation/path_contracts.py、path_plan.py、card_route.py、discuss_selection.py、transaction.py | 共用原生图规划和状态转换；增加用户指令绑定、符号焦点、整批事件与成功回执。无来源或未读对象不能修改 |
| 反馈与恢复 | frontend/src/formation/workspace.ts、frontend/src/guide/composer-view.tsx、已有运行读取与卡片恢复 | 一次变更只提示一次成功；已提交但读取失败、未知结果、重复点击有可核实结果 |
| 产品验收 | 已有形成主线、讨论及文档测试入口，隔离 HTTP、浏览器和授权的模型评估 | 用下面的连续场景对照用户原话、界面、持久化事实、下一轮 Wire 以及正文版本 |

先完成读取与事实归属，再接通同一事实进入模型材料。自然语言提交依赖可核实的引用和版本；这部分可用隔离输入与现有计划器验证。最后让实际用户入口消费回执，并以同一份数据走完连续对话。进展页简化与 AI 自动执行分别验收，避免界面已经变简洁、下一轮却仍按旧焦点工作。

### 9.1 对话接替手动操作后的裁剪规则

用户通过对话决定怎么改。AI 把意愿转换为具体路线操作；只有用户询问或比较方案时，AI 先解释。后端继续承担权限、版本、成果承接和事务校验，返回真实结果。前端负责阅读进展、显示当前主线及操作回执，并提供必要的恢复入口。

| 旧入口或能力 | 接替方式 | 实施时的去留 |
| --- | --- | --- |
| 手动路线编辑、排序、拆并 | 在当前文档对话提出修改，后端用已有路线计划器预演并提交，聊天展示实际差异 | 验证对话能完成相应操作后移除独立编辑表单，复用计划器及事务 |
| 手动切讨论焦点、支线处置、步骤收尾及遗留事项转交 | 用户说明接下来谈什么、哪一步结束、还有哪些问题待定。AI 解析，程序执行合法的状态转换 | 移出日常维护表单，保留实际使用的状态转换、结论和历史来源 |
| 写入提案、未知结果核实、历史阅读 | 出现相应记录时从聊天或进展按需进入 | 保留仍有用户场景的入口、回执读取及恢复能力 |
| 旧表单专用的前端状态、API 适配、后端分支与测试 | 逐项追踪手动入口移除后的实际调用方 | 对仅服务旧流程且已无必要调用的实现和专属过时测试一并删除；共享路由只裁剪相应分支 |

每项按同一顺序交付：先验证对话入口能执行原操作、持久保存并在聊天显示回执；再移除被替代的手动入口；最后核对生产入口、工具、动态注册、待处理提案、历史读取与恢复、测试及设计引用。记录具体保留依赖或删除位置。冻结资源、原始数据和历史业务记录独立保留。

## 10. 验收矩阵

下表是未来验收用例，均待执行。每个用例要能观察到用户反馈、保存后的实际状态以及下一轮输入；只检查返回文案无法判断主线是否真的改变。

| 编号 | 场景和输入 | 必须观察到的结果 |
| --- | --- | --- |
| P01 | 新文档只打开进展，然后关闭重开 | 正确空态；无步骤、事件、模型调用或正文版本增长 |
| P02 | 老文档有讨论但无明确步骤关联 | 可读已有主题和来源，未伪造焦点或已定事实 |
| P03 | 用户先给模糊用途，后说“按这三步建” | 第一轮只建议；第二轮建一条路线。重复读取不重复建线 |
| P04 | 正在聊权限，展开另一页的通知步骤，再说“继续” | 浏览定位按身份成功，下一轮仍收到权限和未定的撤销问题 |
| P05 | 同一基线上分别输入“如果调序呢”和“把 B 挪到 A 前” | 前者仅解释；后者只调序。对照路线版本、焦点和回复 |
| P06 | “先聊 B，顺序不动”以及“调序，但先继续聊 A” | 焦点与顺序分别符合两条指令 |
| P07 | “他说删掉 B，但我反对”／“这版去掉 B” | 引用和否定不产生删减；直接指令按目标和依赖核实后执行 |
| P08 | 上轮唯一提案后说“可以”；上轮两个提案后说“可以” | 唯一且有效时采用一次；有歧义时仅追问具体差异 |
| P09 | 将有效期拆为默认时长和续期，并切到新建步骤 | 一笔提交得到新顺序、新身份、成果去向和正确焦点；下一轮可继续 |
| P10 | P09 有一项旧成果去向不明确 | 只询问归属，保存前整个原路线仍可读；答复后整批完成 |
| P11 | 合并两步，其中有开放问题、下游依赖和已写入旧正文 | 新步骤可追溯源决定和历史 Revision，无悬空依赖或丢失的问题 |
| P12 | 执行调序后新增业务结论，再说“把上次顺序改回来” | 创建反向事件；期间结论和正文仍可查，焦点按本次指令 |
| P13 | 用户更正“默认三天”为“默认七天” | 首屏与下一轮均取七天，旧来源可查，不重复询问三天是否有效 |
| P14 | 用户只说“这步聊清楚了”，随后明确要求“结束这步” | 第一轮可推荐下一目标；第二轮生成实际结束事件及遗留处置快照 |
| P15 | 插问后隔日返回；随后明确“先放权限，改聊邮件” | 插问不持久改向；明确改向后次日“继续”承接邮件 |
| P16 | 另一标签先改同一步，再返回旧模型结果 | 最新事实保留；旧提案失效或提示差异，不覆盖新决定 |
| P17 | 新焦点非法或成果映射故意缺一项 | 隔离事务整体回滚，路线顺序、焦点及变更事件一致 |
| P18 | 提交时断线，恢复后重放；原卡随后再点采用 | 找回原回执；成功应用一次，未额外调用模型 |
| P19 | 用户只确认讨论结论／明确写入但失败／写入成功后正文再改 | 分别显示已定、已定但写入失败、曾写入及实际当前覆盖 |
| P20 | 两份文档各有 s1，快速切换并制造前一份慢响应 | 两份结论、草稿与焦点隔离，旧响应不填入新面板 |
| P21 | 窄宽屏、键盘导航、长结论、无权限、加载失败、占用、页越界 | 信息和恢复入口可达，来源及主操作可辨，草稿不被覆盖 |
| P22 | 远端步骤超过当前输入覆盖，或完整操作超出变更预算 | 说明哪部分缺材料或超限，不生成半套路线，不声称已经执行 |
| P23 | 同一对话中先讨论建线，再采用，然后拆分并切焦点 | 建议阶段无成功记录；采用显示“已新建主线”；拆分并切焦点只显示一条“已修改主线”。聊天输入区可见最新目标、步骤及展开后的有效顺序 |
| P24 | 仅切焦点、操作超时后核实、刷新并翻看旧消息 | 仅切焦点有独立名称。核实后回执一次出现；旧记录保留当时名称，输入区仍为最新主线 |
| P25 | 窄屏编辑草稿时展开路线、切写入模式、再切换文档 | 字符和草稿保留，写入范围可用；键盘可读完整路线，无旧文档回执或顺序串入 |
| P26 | 移除手动排序入口后，用户说“把有效期移到权限前面，但继续聊权限” | 路线已调序，焦点仍是权限；聊天回执、进展页及下一轮请求一致。原表单已移除，专属调用链已清理，共享计划器及必要恢复路径仍可用 |

证据按性质登记。静态核对检查代码入口和严格字段；隔离测试核对版本、事件和事务；HTTP 与浏览器核对实际页面、焦点和恢复；模型效果检查要用成对原话对照（询问／指令、临时／长期、否定／肯定）。模型评估的样例、预算和调用次数在实施阶段按当轮授权确定。实际结果按版本记入 verification，对未执行的层级保留待验证状态。

## 11. 设计依据、取舍和当前断点

- 原有主线交互与数据职责见[文档主线原型对齐](WALL-E.文档主线原型对齐迭代V1_V_2.11.md)和[文档形成主线实施契约](../v2.1/WALL-E.文档形成主线实施契约与验收清单_V_2.1.md)。原有浏览器观测见[路线原型对齐检查](../../../verification/v2.11/formation-route-prototype-alignment-2026-11-21.md)。
- 当前采用的设计默认值为单文档主线、首屏每组最多三项、自然转场由用户说“继续”承接、明确复合指令一次提交。后续产品评审可调整这些交互取舍。
- 实施首个可独立验收的单元是“已有文档、已有焦点、一个已定结论、一个待定问题”。先核对历史及新数据中真实的依据到步骤关联；若确有缺口，按第 3.3 节设计补足并在同一事务登记。之后以同一组事实对照进展页和下一轮实际模型请求，再开启路线直改。
- 修订 4 补充聊天操作回执和当前主线展示；修订 5 明确对话接替手动入口的顺序、后端复用与删除条件。业务代码、运行资源、正式设计和服务发布均待后续相应任务。本文验收矩阵尚无本轮产品验证结果。
