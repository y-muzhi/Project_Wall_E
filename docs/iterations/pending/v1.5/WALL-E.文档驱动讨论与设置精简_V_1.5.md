## 1. 来源、目标与授权

用户查看进展中的“阶段与用户处置”后，明确认为需求说明、设计等应直接根据文档区分，不值得保留独立阶段切换，收束说明也无必要。随后认可“以当前文档为中心，由文档信息、自然对话及具体操作承接设置功能”的方案，要求先出迭代文档。

本迭代目标：用户围绕当前文档表达工作要求，系统依据文档类型提供默认指引，在正常对话中整理意见及进展；保留必要的操作和材料配置，取消独立阶段管理及通用处置表单。

原文档阶段只新增本文及必要的导航、计划、映射、断点和Markdown静态核对记录。不修改业务代码、运行资源、正式设计、配置或正常业务数据；不执行产品测试、类型检查、构建、浏览器验收、模型／计数API、服务启停、Git提交或推送。该段记录最初文档阶段的授权；后续用户已明确“构建代码吧”，当前实施及检查边界见第8节。

## 3. 已确认业务规则

### 3.1 文档类型与默认指引

1. 当前助手始终属于当前文档；既有目标操作仍只能处理所属文档，关联文档仅作明确来源。
2. 默认关注点由文档真实类型派生，不根据文档名称猜测，也不另存一份可人工切换的阶段。
3. 本轮操作和用户指令决定具体工作。文档类型提供默认方法，不禁止跨维度补充讨论，不增加先完成主题、先确认版本或先通过检查才能出稿的门槛。

| 文档类型 | 默认关注点 |
| --- | --- |
| REQUIREMENT_BRIEF／需求说明 | 问题、目标、角色与场景、范围、约束及成功情境 |
| DESIGN／设计文档 | 推荐方案、业务流程、页面／交互、模块协作及关键取舍 |
| SPECIFICATION／规格说明 | 明确行为、对象与规则、接口／依赖及验收条件 |

4. REVIEW／检查、COMPARE／对照分析作为本次操作，不再建立“检查与完善”阶段。其他既有操作的授权及结果边界保持。
5. GENERATE生成新文档时，以新文档类型选择出稿要求；来源助手的文档类型不覆盖新稿类型。需求说明可以作为设计稿来源，运行仍归原助手；新文档的助手独立，不复制旧对话或进展。
6. 不把phase固定为一个常量来维持原流程。现行执行链路应逐项解除phase.kind、phase_ref、阶段计数及阶段动作依赖，具体字段、资源与存储版本在实施首批核对后确定。
7. 指引、Prompt、Schema、计数、序列化及审计须使用同一实际依据。新规则通过新版本资源发布，历史冻结资源及旧快照保留原字节。

### 3.2 自然对话承接意见

| 用户真实表达示例 | 应整理的含义 | 边界 |
| --- | --- | --- |
| “数据来源这轮先不讨论，先设计推荐流程。” | 本轮先后顺序及暂缓主题 | 不解释成永久取消数据来源 |
| “账号登录本版不做。” | 明确范围限制 | 不等同“已经删除正文中的登录功能”，不把业务“本版”猜成某个content_version |
| “现在继续讨论数据来源。” | 恢复该议题、更新当前工作重点 | 不要求用户先找到旧处置记录并解除 |
| “登录仍不做，但需要匿名用户收藏。” | 保留原限制，补充新的具体要求 | 不因新增要求全盘覆盖旧约束 |

1. 先保存不可变用户原话，再在正常这轮处理中整理主题、依据及当前有效意见；复用现有消息、pending、依据／主题索引与进度增量，不另建平行的决定管理系统。
2. 自由文本按真实来源保留USER_STATEMENT；AI整理的摘要不冒充正式卡片选择或USER_DECISION，继续提供原话／正式回答来源供核对。
3. 必须区分本轮安排、当前文档约束、明确业务范围及具体行动建议。只有用户明确表达的适用范围才能被保存为当前依据；范围不清且会改变后续行为时，简短澄清，不把每条意见变成确认卡片。
4. 明确改变旧意见时，记录新来源及替代范围，更新当前有效说明并保留历史。相同对象、明确范围和用户改向原话须由程序核实；AI单方面提出冲突或改向，不能自行使旧用户要求失效。无法确定替代关系时保留争议及相关原话，按影响决定是否澄清。
5. 后续选材携带当前有效要求和必要冲突依据；旧意见保留可查，不作为与新意见等效的重复有效指令全量堆入上下文。
6. 关联处理尚未可靠完成、无有效增量、失败、取消或提交异常时，原话继续按pending规则保留，不因最近10条窗口移动而丢失。显示“已整理”不代表已证明语义正确。
7. 主题顺序、暂缓及范围意见影响后续讨论组织，不直接改变需求业务状态、版本确认或正文。恢复讨论本身不等于授权写稿。
8. 不增加隐藏的规划、判断或记忆模型调用；有关整理使用原有、已获授权的正常请求。进展读取、展开、设置保存和焦点切换不发Chat或重新计数。

### 3.3 出稿意愿与写入边界

1. 有有效结构化出稿建议时，就地显示实际目标、新稿属性或更新范围、来源及必要影响。主操作为具体的生成／更新，次操作表达“继续讨论”或“暂不生成”。
2. 暂不执行只针对该次建议；保存真实回答及来源，不隐式扩大到整个文档或后续所有出稿。无新成果且用户未重新提出时，不机械重复同一建议。
3. 用户以后明确要求生成或修订，按新请求重新核实目标、范围、内容／来源版本及权限，不要求先撤销旧“暂不生成”记录。
4. 普通讨论、检查、对照分析及意见整理不写正文；明确生成／修订成功直接保存，提出修改建议仍按原审阅采用流程。
5. 文本中出现“可以出稿”不自动执行。复用现有具体行动卡片或明确操作设置，不从普通文本猜测业务目标后暗中发起写入。

### 3.4 关联文档的唯一入口与状态

1. 进展中的“讨论设置”整体移除；AI输入区附近保留一个“关联文档”入口，展示真实关联数量，按需展开文档列表。
2. 当前文档默认是工作对象及相应内容来源，不再作为可选关联项重复勾选；是否发送整篇或指定范围仍由实际操作、选材与预算确定，不能因默认对象而宣称全文一定已发送。
3. 关联文档属于当前文档的持久配置，继续使用所属文档的原绑定／来源机制。面板内部选择为草稿；明确完成保存后发布统一状态，取消只撤销本次未提交选择。保存本身不调用模型或改正文。
4. 操作设置移除另一份同名关联文档清单；后续请求从同一已确认关联状态取材。操作类型、操作范围及新稿属性仍是本次操作配置，完成这些设置本身不提交AI请求。
5. 具体卡片、检查／对照操作确需指定单次材料时，材料属于该次请求或建议的明确参数，展示实际使用集合；不形成第二份长期关联配置，也不静默反写文档级关联。
6. 非文档来源（正式回答、已保存运行材料等）继续按原SourceRef保留和校验；删除关联文档项不能顺带删除这些来源。
7. 来源按真实版本冻结，发送前遇来源变化按既有规则提示、核实或明确确认，不默默替换已接受请求的版本。请求详情按实际selected／快照展示材料，不用关联数量代替实际发送清单。
8. 文档A、B各用自己的关联配置及输入草稿。切换文档不复制关联关系、不将A未知请求改绑到B；生成新文档也不自动继承旧关联关系。

### 3.5 进展的展示职责

1. 保留当前“进展”页签及“大纲与进展”区域，围绕所属文档展示当前主题、已整理结论与来源、待明确问题及已保存的下一步建议。
2. 主题按真实讨论逐步形成，按文档指引组织；无实际主题的维度不逐项铺开“尚无主题”清单，指引维度继续帮助AI查漏，不要求用户逐项填完。
3. 保留可读的主题评估和依据来源，明示AI整理；“已有依据”不等同用户确认、阶段完成或需求完整率。
4. 保留“讨论此主题”等已有明确定位操作。以文档内真实topic_ref定位，不再要求它属于某个当前阶段；不因类型默认指引变化而静默丢弃旧主题。
5. 用户关于暂缓／范围的意见作为相应主题的简短内容及可追溯来源展示；不新增一排必需的处置按钮或另一张维护表单。
6. 不再显示独立阶段标签、下一阶段建议、阶段处置汇总、阶段结束确认及通用讨论设置。“返回对话”、原输入／滚动保留及焦点保护继续复用。
7. 初始加载、无内容、错误／无权限、筛选无匹配或范围越界分别显示；成功空内容用公共EmptyState，不编造主题或建议。读取失败保留最近成功内容和恢复入口。

### 4.1 关键不变量

- 目标、范围、来源、资源、序列化、计数、快照及审计对齐实际同一次请求。
- 其他文档只读引用不带来正文写权限，不继承其他助手的进展／卡片权限。
- 意见更新与讨论索引同事务，版本／占用／幂等保护继续由程序执行；提示词不能代替程序保护。
- 失败保留原输入；未知结果沿原body／key核实；确认已保存后只读取结果，不重新发送模型。
- 旧用户要求只有明确且可核对的用户改向才更新有效范围；AI建议或无来源摘要不能覆盖。
- 无额外隐藏模型调用，普通讨论不因阶段删除而自动获得文档写权限。
