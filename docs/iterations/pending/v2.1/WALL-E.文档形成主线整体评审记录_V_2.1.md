## R01：建立路线后直接进入第一步，步骤自由切换

用户明确：“建立完路线直接就进入第一步”“支持用户去切换步骤，不要限制得太死”“告诉AI当前的节点是什么”。以下为据此收束的数据与交互规则。

| 行为 | 当前规则 |
| --- | --- |
| 首次有效建线 | 同一事务建立全部步骤，首个有序节点IN_PROGRESS，current_step_ref指向它，其余PLANNED；不增加开始按钮或第二次Chat |
| 切换步骤 | “在此讨论”立即选择下一轮节点，不要求先完成／暂停旧步骤、填写原因或满足前置依赖；可反复切换 |
| 生命周期 | SWITCH_STEP只改变current_step_ref并清除不匹配的支线焦点，不修改任何步骤status、定义、成果、Closure或提案内容 |
| 实际开始讨论 | 用户对PLANNED／PAUSED节点发送讨论并被接受时，同次接受事务按实际活动开始／恢复为IN_PROGRESS；无需额外开始按钮。切换本身不触发这一步 |
| 已完成／已放弃节点 | 可以切回来讨论其内容和历史，原状态与完成／放弃记录保持；当前讨论可以指向不在有效路线中的历史节点，不自动重开或恢复 |
| 讨论与写入 | 切换和聊天均不隐含采用内容或写入；实际写入／改范围／结束仍走对应明确动作和原程序校验 |

“当前讨论”是唯一指针，IN_PROGRESS表示已经开始而尚未结束，不再要求它只出现一次。多个未结束步骤可以同时保留IN_PROGRESS；用户看见“当前讨论”徽标即可知道AI本轮处理哪里。已完成节点显示“已完成 · 当前讨论”，历史放弃节点显示“已放弃 · 当前讨论”，不会被画回有效路线实线。需要时显露被选中的历史节点，不要求用户先恢复它。

点击标题查看详情保持只读；明确选择“在此讨论”才更新讨论目标。依赖作为AI上下文和提示，不阻止切换或要求填写理由。程序可记录通用原因“用户切换讨论节点”，无需把审计字段变为用户表单。

### 数据、上下文和在途回复

1. INITIALIZE_PATH只提交目标与有序步骤；模型不填写current_step_ref。程序从实际首节点推导首步焦点及开始事实并同事务保存，不能由模型指定另一节点或标完成。
2. 新SWITCH_STEP请求只带type=FORMATION、action=SWITCH_STEP、step_ref；来源节点由服务端读取。空闲时原生轻量写回，D／F按实际变化递增，V不变；不自动调用模型或暂停其他步骤。
3. DISCUSS请求新增必传discussion_step_ref（可空，表示本轮整份文档讨论）。接受时核实同文档节点存在，连同实际定义／状态和必要材料冻结进本轮Canonical／Wire；不能只改前端高亮却仍发送旧节点上下文。
4. AI回复期间，界面可立即选择“下一轮讨论”节点；不在占用事务中改写运行依据，不因此取消旧调用。下次接受讨论时合并最后一次选择，或在空闲时只回写最后一次有效焦点。中途仅在本地切来切去且最终未生效的选择不伪造服务端事件。
5. 本轮回复／提案／成果建议沿发起时冻结的节点归属，并显示“这条回复对应步骤X”。晚到回复不将UI选择抢回X；下一轮才按新节点执行。工作占用仍约束真正的运行／正文写入，不阻止本地选择下一轮焦点。

### 切换不使无关提案失效

仅改变讨论指针不改变写入用途或路线内容。当前[接入Schema v4](schemas/formation-integration.v4.schema.json)的binding标识为formation_card_binding_v3；formation_digest为去掉根version、current_step_ref、active_branch_ref后的完整FormationState规范化摘要。步骤status、定义、目标、顺序、依赖、成果、问题、支线内容及评估仍纳入摘要。

路线提案确认核实当前D、V／Goal／来源、不可变payload、处置及实际语义摘要；F变化本身不单独判旧卡失效。binding.F和PROPOSAL_BASIS中的F保留真实历史依据，不重写；保存时按当前真实F计算下一版本。纯切换只改变被排除的焦点字段，摘要不变，原卡仍可核实应用。正文／用途或其他纳入摘要的状态确实变化时，仍重新预览，不用焦点宽松规则越过业务校验。

撤回路线提案调整同样按v3摘要核实，切换焦点不妨碍撤回；真实内容变更仍须重新准备。历史binding按其实际发布版本解释，不能将旧摘要当新算法读取。

### 受影响的规则和验收

I02要求：有效顺序覆盖非CANCELLED步骤；current为空或指向同文档已存在节点（含历史），与status独立；active_branch为空或OPEN且return等于current。I05核实完整真实快照，不要求成果全部满足；执行COMPLETE_STEP仍核实真实身份／版本，并自动保留未完快照，不作为切换门槛。REOPEN_STEP不要求先暂停另一步，它是明确更改旧完成状态的独立操作；切换到完成节点本身不需要它。COMPLETE_STEP仍核实本步实际成果；其next_step_ref的选择不受前置依赖拦截，可指向另一同文档节点。明确“结束并继续”可开始／恢复尚未结束的目标；目标已完成／放弃时只定位讨论，保留原状态。

## R02：形成独立可用内容即可提出阶段性写入

用户对“讨论中形成一段能独立成立的内容，AI即可提出写入预览，不必等整个节点结束；尚有争议的部分继续讨论”明确答复“合适”。据此确认：触发粒度是独立可用的内容单元，可以是一段文字，也可以是逻辑完整的几段／列表／表格，不强制等整个步骤完成。

AI主动提出精确写入预览，用户明确确认后才写入真实文档。已确认写入的部分进入成果关联，后续以实际文档为依据；其余部分可以继续讨论。写入不会自动结束当前步骤，不要求每轮对话都生成卡片。原STAGED_WRITE及精确应用契约已覆盖，无新增Schema或程序入口。

系统记录真实切换事件时可自动生成简短说明，用户不填写跳转原因；不对其他业务操作或未同步本地V2.0实现作推断。


## R03：写入预览只读，手动修改沿现有文档编辑

用户明确：“不需要保留，真想改，自己去手动编辑就行了。”预览只读，不新增第二套编辑器或“修改后确认”入口。

预览保持只读，展示目标位置、完整拟写内容或原文前后差异。用户可以确认原提案写入、继续让AI调整形成新提案，或暂不写入；需要手动改文档时沿现有文档编辑能力处理，不强制先采用当前提案。客户端仍不能替换不可变卡片中的精确文本／补丁。

此决定与既有STAGED_WRITE精确应用契约一致，无Schema变更。人工编辑若使旧提案基准不再匹配，继续按既定真实版本校验重新准备，不以预览编辑偷偷重基。

另确认基本事件展示即可：创建、切换、写入、完成、放弃等用时间、操作者和相关节点说明；正常切换不要求用户补解释。来源可按需展开，界面不把内部审计字段变成用户填表任务。


## R04：AI在既定目标内维护路线，重大调整由用户确认

用户对“AI可以在既定目标内补充步骤、细化标题、调整顺序，并记录变化；改变目标、取消或替换既定步骤时展示影响，由用户确认”明确答复“合适”。此边界现为已确认规则。

正常细化无需逐次弹确认，记录基本事件即可；步骤既有进展、原成果和用户决定仍保留，普通维护不代用户完成步骤或写入文档。新增步骤不得借机默默扩大已约定目标或取消原要求；模型不能确定是否超范围时提出调整建议，不先改后追认。

改变目标、取消／替换步骤或改变原成果要求的调整继续展示完整影响与去向，由用户明确采用；AI可整理具体方案，用户不需要填写后台映射字段。人工编辑路线仍保留预览／保存，R04不将所有变更都强制改为AI操作。


## R05：一键结束并衔接推荐节点，不自动发起新讨论

用户对结束步骤后的默认衔接明确答复“合适”。AI建议结束时，简短展示本步已形成的实际文档内容、未处理事项及建议去向、推荐下一节点；由AI整理，用户只核对关键取舍，不填写后台收束表。

用户点击“结束并继续”后，同事务保存已确认的完成依据／必要遗留处置／基本完成事件，讨论焦点直接进入推荐节点。该点击不额外发送AI请求；用户自行继续输入或自由切换其他节点。缺成果或遗留未处置时按R07提示并如实保留，不阻止用户结束；真实身份／版本等程序校验继续执行。

没有下一节点时保留本步完成结果；结束当前路线不自动确认整份文档最终定稿，也不改变需求业务状态。此条沿现有COMPLETE_STEP、next_step_ref和用户确认机制，无Schema或程序入口变更。


## R06：异常恢复先核实，保留已有成果和用户输入

用户对保存超时、保存成功后的显示刷新失败、用户手动改文档导致旧提案依据变化、AI调用失败／中断的处理原则明确答复“合适”。据此确认：

| 情况 | 处理规则 |
| --- | --- |
| 确认写入后请求超时／提交结果不确定 | 先核实原动作是否成功，保留原输入／预览和请求身份，防止重复写入；不能直接宣称失败或成功 |
| 已确认保存成功，但后续界面刷新失败 | 显示“已保存，显示待刷新”；恢复操作只刷新读取，不再次执行写入 |
| 用户手动修改了文档 | 原提案保留并说明依据已变化；重新核对后再写入，不直接拿旧提案覆盖当前正文 |
| AI调用失败或中断 | 已保存文档保持、用户输入保留，允许用户主动重试；不暗中重新调用AI |

统一原则是优先核实／刷新；需要新的AI调用时由用户明确发起，不为恢复隐式添加Chat。既有幂等、真实版本、组件回执和事务保护负责程序保证，界面使用清楚的业务反馈，不向用户暴露内部状态表单。

## R07／Q01：完整性主要提示，允许用户带遗留结束

日期：2026-11-08（Asia/Hong_Kong）。用户对“AI提示缺口，用户仍保留结束的决定权；未写入、未解决事项如实保留，不被算作已落地成果；完整性检查主要作为提示，不一律拦截结束”明确答复“赞成”。Q01已确认。

| --- | --- |
| AI认为内容仍不足／成果尚未写入 | 展示缺口，用户仍可结束；不强制先修改目标、取消原要求或转交完所有事项 |
| 没有选择遗留问题／支线去向 | 保留原OPEN状态和归属，不自动解决／暂缓／放弃／转交，也不要求填写理由 |

| 节点结束 | COMPLETED记录用户已结束本步；界面可显示“已结束”，有遗留则同时显示待处理提示；不宣称需求全部满足或文档定稿 |
| 身份、版本、重复提交或事务异常 | 继续执行既有程序校验；不得伪造保存、关联、用户决定或跨文档归属 |

### 请求、快照与真实成果

当前[接入Schema v4](schemas/formation-integration.v4.schema.json)保留所有身份／版本字段，COMPLETE_STEP允许result_dispositions=[]；issue_dispositions和branch_dispositions同样可空。前端不需要让用户逐项补齐覆盖表。程序基于实际状态补齐Closure：可核实的已有内容／分析保留真实依据，未写入、待复核或无法核实的成果记OUTSTANDING（NOT_WRITTEN／NEEDS_REVIEW／UNVERIFIED），未处置OPEN问题及支线记KEEP_OPEN。

Closure仍是当时的完整事实快照；空请求数组不等于空成果或自动合格。所有expected_results仍保留，未写内容不会生成假Artifact／Revision，也不会自动改成“不再要求”。对AI未验证的完成文字或引用不要求用户兜底填写；程序无法核实充分性时保守记录遗留，而不是以此挡住结束。

没有明确转交时，问题／支线保留原step_ref／return_step_ref及来源；结束时清除不匹配的活动支线焦点，但保留OPEN记录。用户以后可切回已结束节点继续讨论。取消节点、改变目标等仍按R04的明确采用执行，不能用“结束”伪装范围缩小。

结果处置支持OUTSTANDING、问题／支线支持KEEP_OPEN，允许空提交列表；正式Closure由程序补齐后校验。IN_DOCUMENT／ANALYZED不能缺真实依据。I05检查快照真实性及正确归属，不再把“每项必须完成／已处置”作为用户结束门槛。RESULT_NOT_WRITTEN、BRANCH_DISPOSITION_INCOMPLETE等不能仅因真实缺口拒绝结束。

### 结束以后继续补内容

原Closure和结束事件保持不可变；以后实际补写产生新的真实内容／关联事件。有效提案不因步骤COMPLETED而单独失效：仍核实当前D、正文V／Revision、Goal／步骤定义／来源及真实用途。无需仅为了确认这张仍适用的提案先重开步骤；写入本身不自动改掉已结束标记。已取消／用途被改变的节点仍按实际原因重新核对，不混为普通结束。

## R08／Q02：支线登记与回归原则及模型判定机制

日期：2026-11-08（Asia/Hong_Kong）。用户对“普通解释直接聊；影响文档形成且值得跟踪的问题才登记支线；支线有结果后总结影响并返回对应主线，用户仍可深入、不强制返回轮数”答复“合适”，同时追问“怎么让模型判断”。上述产品原则已确认；下述是为回答该问题给出的接入设计，不追记为用户逐字段批准，也不宣称模型效果已验证。

### 输入依据

同一次DISCUSS给模型本份文档Goal、当前节点定义及expected_results、实际已读正文和覆盖／版本、相关已规划步骤与已有支线摘要、当前用户输入和必要最近上下文。已写内容以真实文档为准，历史回复带effect_state；当前步骤／来源均沿本轮冻结快照。不把其他项目或未读全文当作已知依据。

### 判定规范（用于新资源提示词，不额外分类Chat）

1. 能随主流程直接回答的术语解释／背景说明，正常回答，不创建支线。
2. 直接推进当前expected_results的问题，继续当前主线；重要或复杂本身不是分支理由。
3. 现有步骤或已有支线已经能承接时，优先关联／继续它，必要时建议用户切换；不为同一问题重复建节点。
4. 只有问题与文档目标／具体成果相关、需要相对独立探讨或留待跟踪、能说清待解决问题及对主线影响时，才ADD_BRANCH。每次须用question明确问题，relevance简要说明影响，source_refs引用实际触发材料，并给出真实origin／return。
5. 无关话题可正常回应，不能无依据扩大文档路线。不能确定是否值得登记时，保守留在正常讨论；后来明确需要跟踪可再登记，不强制用户每次判断分支类型。
6. 支线已有清楚结果并能引用依据时，UPDATE_BRANCH记录result_summary和实际result_source_refs，再清active_branch_ref回到约定主线处理点；未解决时保留OPEN。用户继续深入则继续，不机械按轮数强制返回，不自动写正文或代用户结束步骤。

模型只需返回正常回答及既有formation_delta的ADD_BRANCH／UPDATE_BRANCH／SET_BRANCH_FOCUS；普通阐述无需结构动作。question和relevance是可核对的简短依据，不要求模型输出内部推理过程，不新增分类器、置信度百分比、另一张确认卡或额外模型调用。

例如当前步骤是正常写入交互：“幂等是什么意思”通常直接解释；“用户确认后保存到哪份文档”直接推进当前步骤；“弱网下无法确定是否保存成功，应如何反馈”若已有异常处理节点则关联该节点，若缺现成承接且需独立跟踪则登记支线。划分依实际路线与预期成果变化，不只匹配“超时”等关键词。

### 程序核实与效果验证

程序检查结构／类型、同文档节点及可用返回点、临时引用声明、来源是否真实携带、旧版本／运行占用和可执行权限；已有支线引用必须存在。resolved必须有结果和真实依据，没有写入事件不能标为文档已落地。字段名正确不等于“语义上值得建支线”，程序不声称能机械证明这种判断；语义近似问题先由模型利用已有清单复用，程序负责真实身份和重复提交保护。

后续使用实际项目对话样例评估普通解释误建、主线问题误分、已有节点重复登记、关键分支漏记和无结果提前返回等现象。结构Schema／示例通过不能替代该语义效果证据；本轮不运行真实模型。用户仍可暂缓／放弃误建分支，明确继续或返回。
