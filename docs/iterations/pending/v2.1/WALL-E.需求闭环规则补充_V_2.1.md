## 2. B01：暂缓问题恢复处理

用户在问题详情中明确选择“继续处理”，执行RESUME_ISSUE；仅查看、切换节点、提及该问题或AI建议均不自动撤销暂缓。

| 原状态 | 当前规则 |
| --- | --- |
| DEFERRED | 可恢复为OPEN；沿同一issue_ref、原描述、来源和当前归属，追加USER的ISSUE_RESUMED事件 |
| OPEN | 对同一恢复请求按幂等／无变化处理，不重复造事件 |
| RESOLVED | 不借恢复暂缓动作改成未解决；新发现由正常讨论判断与原问题的关系并保留原解决事实 |
| DROPPED | 不复活原身份；重新提出时新建问题，引用旧问题及原处置来源 |

原暂缓原因和处置事件留在不可变历史；当前disposition变OPEN，当前处置reason／disposition_event_ref置空，resolution_source_refs为空，不再把旧暂缓显示成当前决定。恢复不改正文、不重开已结束步骤，不恢复相关支线。关联支线另按用户选择处理。

原归属步骤未放弃时可继续处理，包含已结束步骤；其结束历史保持。原归属已放弃时，用户在路线调整中选择新的未放弃步骤，再同批MOVE_ISSUE＋RESUME_ISSUE；仅当问题和关联支线都OPEN时，同批核实支线返回点与问题归属一致；支线非OPEN时保留其历史返回点，不阻止问题独立恢复。未指定合法去向时拒绝整批并保留输入，不猜测替代节点。

契约：原PATCH requirements/{id}的FORMATION分支增加RESUME_ISSUE，携带issue_ref，公共document_id／expected_discussion_version／Idempotency-Key沿用；reason由程序记录“用户继续处理问题”。PathChange增加同名变化{type:RESUME_ISSUE,issue_ref}，支持与明确迁移同批执行；直接恢复和路线调整共用一个恢复算法，变化、事件、D／F和回执同事务，V不变。

## 3. B02：已有结果的支线继续讨论

| 原状态 | 用户入口与变化 |
| --- | --- |
| OPEN | “讨论此支线”只选择焦点，不伪造恢复事件 |
| DEFERRED | “继续讨论”明确恢复为OPEN，记录BRANCH_RESUMED |
| RESOLVED | 同一问题“继续讨论”明确恢复为OPEN，记录BRANCH_REOPENED；原结果与来源保留在恢复事件before快照及旧结果事件中 |
| DROPPED | 历史只读；重新采用创建有旧来源的新支线，不覆盖原放弃事实 |

恢复已有结果时，当前result_summary置null、result_source_refs置[]、当前处置指针清空，避免旧结论冒充新一轮结果；详情独立显示“上次结果”并可追溯旧消息。新一轮形成结果后追加新结果事件。复用同一支线不制造重复问题；确属不同问题时通过正常讨论登记有来源的新支线，不能替换原question来抹去原问题。

RESUME_BRANCH扩展接受DEFERRED／RESOLVED；增加enter_after_resume:boolean，true表示在同一动作中恢复并选中其处理步骤／支线，false表示只恢复，后续再选择讨论。请求带明确step_ref和branch_ref；程序核实step_ref等于支线当前return_step_ref并属于同文档未放弃步骤，可以是已结束步骤。恢复支线不自动重开父步骤、不写正文、不发送Chat。仅焦点动作不把PLANNED／PAUSED步骤改为进行中；实际发送讨论才按R01记录步骤开始／恢复。

原返回点已放弃时，先由用户在路线调整中明确SET_BRANCH_RETURN；如需同时迁移关联OPEN问题，按同批双向约束处理，成功后再恢复。恢复前返回点不合法则说明原因并保留支线，不自动选择第一步。支线恢复为OPEN时重新核实所有关联OPEN问题的归属，需迁移时先由用户明确调整，不默默搬动。

## 4. B03：完整讨论目标及在途选择

用户点击支线标题只查看；“讨论此支线／继续讨论”明确选择其当前处理步骤与支线。程序以真实return_step_ref核实目标，来源origin保持不变；跨步骤选择不要求先完成／暂停旧步骤，也不新增跳转理由表单。

空闲时ENTER_BRANCH携带step_ref和branch_ref，同事务设置current_step_ref与active_branch_ref；RESUME_BRANCH的enter_after_resume=true共用此选择规则。目标版本／归属／返回点失配时整体拒绝，不能先切步骤再留下半个失败结果。仅选择步骤时清除不匹配支线；明确选择整份文档讨论时，两项均为空。

DISCUSS新分支完整目标为discussion_step_ref、discussion_branch_ref、branch_intent，三项均必传：

| 目标 | 字段约束 |
| --- | --- |
| 整份文档 | step=null、branch=null、intent=null |
| 步骤 | step为真实同文档节点，branch=null、intent=null |
| 现有OPEN支线 | step为支线真实处理步骤，branch为真实支线，intent=ENTER |
| 用户明确选择但恢复尚未生效 | step／branch如上，intent=RESUME；绑定原支线状态／处置或结果依据，首次生效时核实并消费 |
| 本次恢复已成功 | 已消费恢复意图；刷新核实仍OPEN后用ENTER，后续DISCUSS不重复恢复 |

运行占用期间允许在本地按文档保留“下一轮讨论目标”三元组；不改当前运行快照、不取消在途调用、不立即恢复支线。下一轮发送时，或运行结束后用户保留的最后一次明确选择生效时，核实最新状态，再将所需恢复与焦点变化同事务执行。用户撤销本地选择不产生业务事件。OPEN目标若已变RESOLVED／DEFERRED，不把旧ENTER升级成RESUME；说明目标变化，用户重新选择。

恢复意图只消费一次：原生恢复成功或包含恢复的DISCUSS接受成功后，不能继续提交旧RESUME；模型后续失败也不使已记录恢复回退。UNKNOWN查原动作，成功后读取失败只刷新。支线之后又有新结果／暂缓，旧意图不得清除新状态；规则见[复核修正](WALL-E.大纲基线复核修正_V_2.1.md)第2节。

回复、提案、评估和来源沿本轮接受时冻结的步骤与支线保存，并显示对应目标。晚到回复只更新原文档数据，不抢回下一轮选择，不清另一文档输入。多页冲突或返回点变化时保留输入与本地选择，刷新后要求明确核对；不能把当前UI高亮直接当已生效的服务端焦点。

纯焦点变化不使适用提案失效；RESUME改变了实际支线状态／结果时按真实受影响用途重新校验，不将其伪装成纯焦点变化。UNKNOWN沿原method／path／body／key查证，不重复恢复或暗中Chat。

## 5. Q03／Q04确认后的设计边界

Q03：无关正文修改不使全部成果失效；相关正常讨论才按实际读取的最新正文与原要求复核。程序核实可追溯关联，AI判断语义充分，两者分开；不足以核实则保留待复核。必要的新关联保留旧来源，不伪造本轮写入；不自动改正文或重开步骤。

Q04：历史保留，继续使用同一文档；取消按累计200步骤／1000支线或问题／2000关联达到上限后要求另建文档的业务约束。实体当前记录与历史分开持久化，使用分页和按需选材，不把终身全量对象塞进一个JSON／一次响应／每轮Canonical。完整关系与计数从同一真实数据库快照核实，不能用已加载页代替全局图；未加载不等于不存在。单次请求、页面和模型上下文仍有技术预算，超限保留原状态与草稿，说明本次需缩小范围；真实存储不足进入明确扩容／恢复，不截断或删历史。

当前0.10不宣称目标物理DDL／所有分页DTO已经生成；它们要结合真实V2.0基线完成。旧单JSON列及整份状态1MiB方案不再是当前存储决定，旧DDL片段仅作历史依据。技术未完成与产品取舍未决分别登记。
