## 1. C21-01：问题与支线的归属一致性范围

问题所属步骤与Step.issue_refs的双向关系始终一致。只有Issue.disposition=OPEN且关联Branch.status=OPEN时，才要求问题的当前处理步骤等于支线当前return_step_ref。

支线DEFERRED／RESOLVED／DROPPED时，保留原返回点及历史关联不阻止问题在明确采用的有效步骤中恢复；不借恢复问题顺带恢复或迁移支线。问题可独立OPEN。

支线之后恢复为OPEN时，重新检查所有关联OPEN问题。若其处理步骤与拟恢复返回点不一致，用户先明确调整支线返回点或问题去向；调整需双向一致且原子提交，再恢复。不得为消除冲突默默搬动问题或支线，失败保留输入和原决定。

## 2. C21-02：恢复意图只消费一次

branch_intent=RESUME表示用户明确选择且尚未生效的恢复动作，绑定选择时的支线身份、状态与原结果／处置依据；它不是持久的讨论模式。

| 时点 | 本地意图与下一次请求 |
| --- | --- |
| 空闲恢复已获得本次成功回执 | 恢复意图已消费；刷新核实支线仍OPEN后，后续DISCUSS用ENTER，不再次恢复 |
| 在途只保留下一轮恢复选择 | 恢复尚未执行，可保留RESUME；首次实际生效时核实原恢复依据、同事务恢复并消费 |
| 恢复与下一次DISCUSS接受同事务成功 | 本次202接受已消费恢复；模型之后失败／取消不撤销已记录的用户恢复，下次用户明确重试用核实后的ENTER |
| 恢复提交结果UNKNOWN | 保留原命令／key查证，不另发一次RESUME或偷偷当作成功；原key成功回执重放不重复产生事件 |
| 已知恢复成功但显示读取失败 | 仅刷新；不能用RESUME重新业务写入，不能把成功回执当当前最新支线状态 |
| 成功后支线又RESOLVED／DEFERRED，或旧选择依据已变 | 已消费的旧意图不得恢复新一轮状态或清掉新结果；保留用户输入，核对后用户重新明确选择 |

不能仅凭当前支线OPEN就伪造“本次恢复已成功”；若OPEN并非本次动作回执所证明的结果，按真实版本／状态重新核对。ENTER对象不再OPEN时不自动升级RESUME；反之，已证明生效的恢复不能继续以旧RESUME提交。

## 3. C21-03：节点状态动作与焦点分离

节点详情选中不等于当前讨论节点。PAUSE_STEP可以明确作用于任一同文档IN_PROGRESS节点；普通COMPLETE_STEP可以明确结束选中的PLANNED／IN_PROGRESS／PAUSED节点，不必先切换讨论。

| 明确动作 | 对现有讨论焦点的影响 |
| --- | --- |
| 暂停／普通结束非当前节点 | 保持当前步骤与活动支线，保留其他进行中节点、输入及下一轮选择 |
| 暂停／普通结束当前节点 | 清除当前步骤及其匹配活动支线；保留支线OPEN记录和历史，不任意选择替代节点 |
| 结束并继续，明确选定下一节点 | 同事务完成目标并按明确next_step_ref转移焦点、清除与下一步不匹配的活动支线（不处置支线），同步本地下一轮目标；未结束目标可开始／恢复，历史目标只定位，不影响其他节点生命周期 |
| 没有指定next_step_ref | 按普通结束处理；不能把缺少下一步解释成清空另一节点的焦点 |

当前目标按事务前的真实状态核实。纯查看／详情选中或晚到回复不授予焦点变更；跨页冲突仍按原D／互斥及UNKNOWN处理。普通状态动作不清空用户本地输入或下一轮草稿选择；明确next_step_ref是新的目标选择，应同步下一轮目标而不清空输入／编辑草稿。
