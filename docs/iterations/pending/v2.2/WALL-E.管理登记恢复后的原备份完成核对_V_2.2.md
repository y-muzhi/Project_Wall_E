# WALL-E V2.2 管理登记恢复后的原备份完成核对

实施依据为 V2.01 后端 3.5、4.12.3、7.9 及备份固定执行和原结果核对契约。登记已经换代并保持派发暂停时，原操作可能仍显示执行中，而固定备份程序已经写入原捕获和完成凭证。

1. 固定处置接收原操作、代次、修订、意图和原暂停快照的明确绑定，复用原 BACKUP 的受理计划、固定策略和捕获授权。当前登记和原快照各自须具有一致的原备份记录。
2. 只在独立日志中登记“原备份已验证完成”。核对原目录中归属同一操作的捕获和完成凭证，绑定原授权、备份 ID、数据库截止点和原核验结果。仅有捕获、计划或旧操作状态时继续暂停该笔的派发复核。
3. 派发复核只消除该备份的对应原操作和唯一帮助步骤所造成的阻塞。环境、资源和其他原操作分别核对。下一代次继承已结事实、原操作及原步骤。
4. 管理站读取原回执，分别显示原状态与处置时间。完成原备份效果核对后，如需把载荷用于恢复，沿独立的固定资产准入和恢复验证流程处理。

原 BACKUP 已在登记中成功结束时，其原生步骤仍有外部标识。须使用相同凭证再核对一次，并校验 SQLite 已存的原结果与固定完成凭证逐字段一致。固定清册将它列为待核对的旧效果，不将其放回在途动作。下一轮换代承接完成处置，避免反复核对同一份已经封存的完成记录。此规则不改变现有成功态备份列表的采用逻辑。

R128–R129 已完成 Windows 隔离验证，后续换代和原生待验。证据见 [R128](../../../verification/v2.2/local-registry-completed-backup-r128-2026-11-22.md) 与 [R129](../../../verification/v2.2/local-registry-reconciled-backup-r129-2026-11-22.md)。验证覆盖原计划及授权被替换、缺少完成凭证、已知完成的原记录被重复核对、不同步骤与不同环境的阻塞、新代次继承和实际管理回执。原生 Linux 和生产接入单独记录。
