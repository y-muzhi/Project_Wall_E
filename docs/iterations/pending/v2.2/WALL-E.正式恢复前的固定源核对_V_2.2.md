# WALL-E V2.2 正式恢复前的固定源核对

状态为实施补充。继承 V2.01 后端 4.12.1—4.12.2、6.6.2 与 7.10。保持旧设计原字节。

受信维护工具在原停写操作和原稳定锁中查询恢复采用的前置证据。固定策略绑定当前安装、原操作、完整当前保全包、选中的同环境已核验备份和明确接受的备份截止时间，以及将来的新代次、部署、已准入固定程序和配置身份。真实当前数据库、审计和原操作结果资产须由当前封存包覆盖。选定恢复点和本次保全分别使用独立身份。确认摘要绑定所选既有恢复包、截止时间、目标代次、固定候选、预留数据根和当前保全编号，由当前外发冻结的控制记录持久持有。随后生成的当前保全内容与原编号绑定。选择较早备份可产生内容差异，原库及已封存资料仍保留。

本轮先准入普通环境的同结构恢复。宿主只读复核封存内容、原结果索引、备份核验回执、正式候选及当前实际控制，产出与原计划确定绑定的回执。再使用同一恢复计划准备和核对新副本时必须重审当前控制和原证据。随后从同一计划锁内准备新数据目录，复用封存恢复机制，以同一原操作和代次继续。新库既按恢复点所属结构转换，也由计划目标的实际固定结构重开核对。成功后固定路径身份和数据恢复回执。继续正式采用前，原维护人员可依据备份的不可变索引核对指定旧代次的原操作结果。当前保全和选中包的代次相同时，以时间更晚的当前保全为准。仅返回安全状态和凭证摘要，未知不推断为未执行。宿主工具仍要求原维护身份，管理页面的原权限核对单独接入。正式采用前，固定工具只读复核独立恢复数据和只读应用实测证明。只读证明须引用同一新代次与部署的实际数据恢复回执、库内容、固定程序、结构与前端索引，独立只读配置摘要另行登记。缺失或来自其他恢复复制件时仍保持原冻结。此阶段不会切换当前部署，也不解除冻结外发。

独立只读副本沿用既有受信安装和探测工具。恢复目标可使用已准入、结构契约相同的固定候选程序和 Schema 文件。安装策略明确固定候选及新数据准备凭证，绑定原冻结控制、选中备份、新数据代次、独立只读部署、实际数据库和恢复回执，并在原锁和数据归属可核对时从该副本复制；程序、前端和 Schema 任一摘要不同均不得安装。独立只读副本仍使用单独的身份和根目录，历史同源备份可以来自当前之前的代次。旧备份演练副本继续沿原同源版本策略。

在只读核验之后，宿主受信工具从同一密封准备数据，为目标代次预置普通应用所需的数据库和计数审计目录。位置固定为稳定环境根下的 `data-generations/<新代次>/data`。宿主检查原锁和仍然关闭的计划、准备及只读证据摘要、目标归属和实际内容，再排他发布代次目录。结果凭证在数据目录之外保留。重试只核验原代次和内容。该步骤不变更活动控制，原代次及准备副本仍保留。

维护工具使用原安装运行 `check-restore-preflight` 和 `prepare-restore-data`。只读副本使用固定候选运行 `prepare-recovery-replica`、`verify-recovery-replica`，后者生成独立受保护的 `local-verified-<编号>.v1.json`。凭该文件回到原维护身份运行 `check-restore-readiness`。宿主以原安装的固定程序执行 `prepare-restore-generation`，其 `--anchor` 指向已固定 SHA256 的 `restore-generation-policy.v1.json`，内含原安装、`restore-target-data.v1.json`、`restore-readiness.v1.json` 的路径及摘要，以及准备目录的已验证身份。成功凭证 `restore-generation.v1.json` 和 `data` 同属新代次目录；原程序和管理入口仍从活动控制读取原代次。

## 普通部署接入和关闭态切换

固定目标配置可在当前源冻结前计算，恢复确认、安装和切换沿用同一目标配置摘要。R72 落盘凭证的摘要由新安装锚引用，位置从环境标识及新代次推导。该摘要不进入配置，避免配置与凭证互相包含。应用仍使用原控制目录和稳定锁。后续同结构发布或代码回退继承当前数据根和固定凭证。回退仅取合格的旧程序证据。

离线切换复用既有关闭态控制及发布转换回执。恢复转换还记录原控制、当前保全、新代次及实际新库的身份。第一次写前重验旧控制、R72 物理数据和审计、同一恢复准备及只读证据。失去响应时按原转换核对，当前指针已前进时不能重新采用。新应用在关闭态重新验证以及普通业务开放后，恢复代次继续保持外发冻结。

恢复后的第一次正式开放先对冻结的新库执行只读核验，再按正常应用入口开放文档读写。首次开放的启动阶段只查询不兼容的未决执行，持久记录开放凭证及控制之前不自动清理、恢复或执行旧任务，以便同一冻结数据在中断后重试。老浏览器的原代次请求须拒绝。后续同代次正常停启仍能核对新开放事实与有效外发冻结。外发冻结时，普通重启仅处置当前数据代次的中断普通请求占用。历史原键、旧后台恢复、旧工作区占用及旧草稿状态不自动修改。持有恢复代次的后续固定程序也先只读复核选中数据，照常保持冻结。

固定普通 Linux launcher 从实际安装根生成旧数据目录的不可达范围。受管启动使用 systemd 的 `InaccessiblePaths` 在进程的文件系统命名空间中隔离原数据路径和其他已就位代次，并剔除修改挂载的能力。普通入口在绑定套接字前核对每个旧数据目录不可遍历且不可打开，失败维持关闭。独立启动时也由受信宿主施加等价隔离，不依赖管理网页或 Agent。宿主的受信维护工具继续按批准范围核对旧库。

## 恢复后查询原代次的结果

恢复转换固定当前保全和所选恢复点的原结果索引摘要。宿主受信导出工具可在切换后从这两份封存包取已校验的状态分片，只发布查询摘要、来源和分片摘要。若两个包来自同一原代次，沿原冻结时较后的当前保全。原结果索引缺少键、原状态仍在处理或摘要核对失败，查询时保持未知。导出不读活动数据库。

管理查询同时核对环境可见性和目录中对该原代次核准的读取身份。目录可登记已准许查询但证据尚未可用的代次，返回未知。客户端仅提交原代次、能力、对象范围和原请求键。响应只含操作安全状态与来源摘要，受保护文件位置和请求正文不会公开。

恢复副本内仍保留旧业务收据。普通应用接收新代次请求时，文档与需求命令的存储键按当前代次限定，并继续使用原 HTTP 请求键。原代次查询仍从已封存资料核对。将已恢复代次作为后续备份源时，源索引只投影该代次创建的有效命令记录；原第一次普通安装继续支持同库既有的未分代键。

## 原维护授权

源停写沿现有维护命令进入。恢复专用策略引用受保护的恢复计划，且须固定原安装、数据代次、部署、配置、控制修订及实际数据库身份。维护控制保存恢复计划的授权摘要。该摘要固定恢复点、截止时间、目标元组、新备份编号和准备目录，当前停写产生的保全凭证允许在原编号下补齐。普通维护仍使用原策略文件摘要。

## 管理确认和原请求受理

受信宿主可先用 `observe-restore-source --candidate-ref <源附着编号>` 取得正常停止的真实源观察。输出区分源控制文件摘要和登记页当前状态的投影摘要，配置以真实控制摘要和库身份摘要为准。

管理端只消费已登记的恢复配置、固定候选、保全策略和恢复点，HTTP 不接受宿主路径。宿主描述预先给出可校验的目标配置、部署及预留的新代次，管理确认在登记事务中首次固定这些身份。预览同时绑定当前关闭控制、明确接受的备份截止时间、数据保全策略与原恢复授权。原请求键重复会返回已有管理操作，修改同一键的意图拒绝。接受后等待受信维护命令领取原操作，未派发时可按原控制撤回。

宿主先以 `enter-managed-restore` 按管理原操作进入实际维护。现场保全与只读证据齐全后，`select-managed-restore` 在同一原操作下安装固定普通部署并选择关闭态目标。目标附着记录由宿主从已批准配置和实际安装锚生成并固定。`start-managed-restore` 复用普通固定启动和容量账本，按选中的部署独占登记新库与新数据根。回执未知时继续观察原进程。管理核对在固定开放回执完整时同事务采用新代次并结束原操作。已有业务入口的同一来源继续受目录授权，后续普通停止释放运行额度，保留代次数据归属。

管理页面列出已登记且匹配源关闭态的恢复配置及已核验恢复点。计划确认明确展示恢复截止、源和目标数据代次与固定发布包，管理员须确认可接受的截止。结果只核对原操作，同一浏览器保存原请求后可在重载时按原键查询。不自动重复派发。

若已取得维护归属，但实际新元组尚未选择，受信宿主可通过 `retire-managed-restore` 在同一锁和原操作下退出原维护。原源仍处于正常停止，保留现有库和已生成恢复资料。浏览器通过原结果核对登记取消。新元组已选时必须继续观察原操作或走明确的新修复路径，即使选择回执丢失也不能按原源撤回。

## 管理登记快照

管理登记使用原固定身份及稳定锁生成自包含 SQLite 快照。`snapshot-registry --registry-snapshot-id <原操作编号>` 绑定登记安装、原代次、当前目录摘要和固定运行包。当前第 2 格式的发布目录包含数据库、只读回执和原安装锚及目录字节。第 1 格式继续支持数据库与回执核对。重试只查同一快照。`verify-registry-snapshot` 使用同一原编号和 `--registry-snapshot-receipt-sha256`，通过受信旧登记安装的保护目录读取资料，活动数据库和当前目录文件不参与核对，仍需固定原目录摘要。外层保护目录、计划、历史回执及新登记代次的受信恢复，沿 V2.01 后端 4.12.3 在后续阶段落实。

### 管理派发暂停

V2.01 后端 4.12.3 的管理登记恢复使用原登记根、原固定宿主控制及独占数据库锁。固定宿主管理动作在同一登记根持有共享派发锁直至归还动作凭证。离线 `pause-registry-dispatch --registry-recovery-id <编号>` 取得排他的共用宿主控制和原登记锁，再按原安装及操作编号持久化暂停。已派发动作或登记写事务尚持锁时，暂停拒绝生效。数据库写入口在持有原登记锁后核对暂停；只读查询、快照与宿主事实核验继续可用。固定 `observe-registry-dispatch` 读取原暂停记录供离线核对。同一原编号可恢复读取丢失的暂停回执，冲突编号和损坏记录均保持关闭。

暂停期间正常业务仍沿自身资源运行。管理暂停本身只说明不再接收新派发和登记修改，已离开派发进程的辅助进程、维护及原结果须逐项确认。只有完成后续所需原事实、原安装和目标代次核对的离线受信操作才能开放派发。正在运行的旧固定程序须按原服务身份核对和暂停，更新后的固定宿主入口与管理写入口均执行本节门槛。

### 离线准备新的登记代次

固定恢复策略钉住原安装、暂停回执、完整原快照、原目录及显式的新登记代次。离线工具持原登记锁，将新代次材料写到独立未开放目录；只读取原快照并保留原始操作、步骤、控制回执和资源记录。未消费计划、活动观察和原运行状态须重新核对，原快照仍供授权查询。新库的外键允许历史代次保有原身份，并禁止将历史操作、步骤或控制回执写成新效果。旧安装与原版本 SQLite 仍按原契约核对。相同策略和原号重复执行核对同一新库；改动、错代次或错凭证拒绝。目标采用、现场资源重新核对及派发开放均需后续受信凭证。

新登记代次的物理安装位于原固定登记根的 `registry-generations/<新代次>`，数据、证明目录和数据库文件均使用新身份。原宿主根与正式锁保持原归属。根安装入口从 R96 已核对的闭态副本逐字节放置 SQLite，发布受保护候选安装锚和回执，活动安装锚保持原指向。候选锚只供固定离线入口显式核对，普通管理入口据活动安装锚识别。实际新库仍须在固定工作身份下验证 WAL 和原开库凭证，现场事实核实后才允许采用与开放。

固定 `ready-registry-recovery` 在新代次取得原登记锁并核对放置回执，先保存原意图，再通过已准入 SQLite 将新库切为 WAL。与原闭态副本对比全部登记表，历史操作、占用和原键保持。原 SQLite、活动锚、外部计划及环境控制分开。相同意图断回复可从新库物理状态继续，文件身份、实际数据或回执不符则保持未采用状态。

在新库原就绪回执固定后，离线工具按原固定锁取得待核对的环境登记、未释放资源、原未决操作和未决步骤。使用受保护清册逐行封存和按文件核对摘要，保留原步骤和资源身份供后续比对。清册不提供现场实际归属或开放资格，方案只在另一步取得宿主证据后才可用于变更活动锚。

宿主核对从已固定的原目录和清册引用进入。关闭状态须由原环境锁、实际控制、数据库和无监听证据确认，仍在运行的实例按原运行证据核对。未能核实的字段保留 UNKNOWN 或明确差异，现场无权推定原操作失败或释放配额。外层目录摘要及宿主事实以独立受保护回执记录。对于清册中的资源，实际比对原已证明环境的根、数据库、锁及套接字地址。只从已核对的原步骤身份推导普通运行和准备单元，使用已固定 systemctl 只读获取运行及 cgroup 成员事实。没有单元或无进程仍保留原操作及占用，有差异或无可信依据继续 UNKNOWN。

固定关闭态选择使用原暂停、新安装与 WAL 就绪凭证，以及同次清册和现场观察。已有可识别的活动准备辅助进程须继续核对并维持暂停。选中时先封存原安装锚字节和原目标元组，再以同一原锁原子切换活动安装锚；管理派发继续暂停，业务控制及旧原库保持。断回执用相同明细找回原选择，不把旧占用释放或未知效果改成成功。重新准入另核对新登记目录、运行与资源处置。

切换之后按原安装顺序读取封存的旧目录和原 SQLite 快照。旧管理请求键和原操作只读查询必须明确选用原登记代次，按旧目录和当时的环境读权限核对，同时保有当前入口的认证身份和权限。无法核实的原证据保留未知。原回执查询保留新库当前请求作用域，不写登记或改变原占用。

操作记录保留当前回执查询，并允许主动查找同管理身份、来源及账号下本机已保留的旧登记请求键。多个匹配代次各自选择，旧回执使用当前认证和明确原代次，只展示原操作、步骤及原控制回执。历史视图不提供重提交、撤回或继续。缺失、无权及无法核实分别显示。

恢复后的管理入口使用独立受保护的新登记目录和管理站配置。固定离线装配核对当前安装锚、原关闭选择、新目录引用、管理站前端索引、入口身份及代理配置，生成新代次的受保护代理候选。候选放在新登记代次下，由 `prepare-registry-recovery-entry` 核对原关闭凭证、登记初始化、独立资产目录、新授权、前端索引和专用套接字目录后原子装配。候选配置只准宿主受信身份读取。网关经 `admit-registry-recovery-entry` 按保护目录身份和候选回执放置。宾主程序分别以受保护入口和独立套接字为边界。须在原暂停下先落原接纳意图，确认配置实际保存后再写接纳回执。恢复代次的正常 `serve` 入口凭该回执及其中的管理目录和前端摘要通过装配，随后读库仍受管理派发暂停约束。切换后的原现场以 `refresh-registry-recovery-observation` 在原锁下重新观察，新观察绑定已选择的新登记锚和选择回执，仍使用原受保护清册与管理目录。活动原目录文件不存在时，以原已封存快照验明的同一字节恢复目录依据，分别核对原保护目录和实际资产。快照或活动文件有变化时保留差异；观察固定来源及目录身份，来源改变时须以新键重核。现场未知及有漂移的资产保持各自原原因。原普通环境仍运行时，在不申请停止的条件下核对活动控制、进程锁、当前资料目录、业务库与 Unix 套接字身份，并在原运行事实未变化时核对各自原占用。`check-registry-recovery-dispatch` 在新登记锁内核对新鲜观察、原未决操作及已接纳网关，给出阻塞类别和可持久引用的判定摘要。原进程或占用未知的情况继续暂停。`inspect-registry-recovery-dispatch` 依相同判定与观察依据分页提供阻塞原对象的定位标识，供宿主受信复核；不改变原结果与占用。无阻塞后，宿主受信 `open-registry-recovery-dispatch` 以保护策略确认新锚、原恢复操作和判定摘要。在原管理锁下重新核对现场并先保存开放意图，再把原暂停标记原子移入新代次归档。活动新锚、开放意图和归档暂停均能读回时才允许管理派发。原锚或缺失任一项保持关闭，新恢复可按活动新锚重新暂停。宿主 `observe-registry-dispatch` 在活动新锚下核对原选择及原暂停，同时返回活动登记与暂停归属，便于持原操作键确认进入、保持及退出暂停。管理站沿第 6.5 节既有 `phase` 返回 `BLOCKED` 表示当前只读，继续开放有权的环境事实和历史回执。浏览器暂停新操作并提供更新状态，更新沿原入口、原账号及原登记范围核对，无自动写请求或重放。旧目录的管理授权不自动转给新入口，重新开启派发仍需复核实际未决效果及原占用。

### 原登记写入覆盖范围

普通一致快照仍可用于备份、关闭态恢复和旧回执核对。恢复目标需要重新派发时，另须核实原登记的完整写入覆盖范围。原库仍可读时，在原暂停及稳定登记锁内捕获快照，凭证记录同一暂停的原操作、固定摘要和时间。正常备份或更早的暂停内快照不构成当前暂停的写入覆盖证据。

若只有较早或普通快照，保留关闭态选择、读回和现场诊断，派发保持暂停。不能因快照中不存在操作记录或现场没有关联进程而认定原库从未登记该操作。不能确认最新写入范围时，须另有可信源依据和明确的逐项处置。旧原操作回执保持只读。

### 原未决操作的处置记录

使用明确准入的登记 Schema 3 承载已核验处置记录。原操作、原请求键、步骤和控制回执继续从原登记读取。处置记录固定到原代次、原操作、版本、输入摘要、同次暂停内快照和受信策略。随后换代须保留处置记录，普通旧格式继续作为可读和关闭态恢复来源。

首个可判定分支是原登记等待容量的 START。只有同一暂停期间的原快照证明一直处于等待、原步骤未派发、无申请发布、无占用及环境围栏时，受信固定入口可按原操作独立登记已核实未派发并结束等待。现场进程缺失不足以证明未派发。处置通过固定 `settle-registry-recovery-disposition` 按当前活动锚、原选定凭证、源快照、确认的原目录身份和原操作落库。登记提交后才封存同一处置的保护回执，断回复由同策略重读并补齐。派发复核核对已封存处置与原清册的代次、版本和意图。处置精确结束该笔原等待，其他阻塞继续显示。之后的快照及换代保留处置，历史记录仍显示原等待事实。管理站原回执经当前和原权限确认后，单独展示已核验的处置和登记时间。

### 管理登记恢复的固定入口

| 当前事实 | 固定入口 | 本阶段需要的原依据 |
| --- | --- | --- |
| 原管理登记可达，开始恢复 | `pause-registry-dispatch`、`observe-registry-dispatch` | 原安装锚、管理根、原恢复操作键 |
| 原管理登记暂停 | `snapshot-registry`、`verify-registry-snapshot`、`prepare-registry-recovery`、`verify-registry-recovery` | 原安装身份、原管理目录和一致快照，显式的新登记代次 |
| 新库只在离线工作区 | `place-registry-recovery`、`ready-registry-recovery`、`inventory-registry-recovery` | 原准备回执、独立新目录、实际 WAL 就绪及原未决清册 |
| 已有原宿主核对，准备选择 | `observe-registry-recovery`、`select-registry-recovery` | 原目录、清册和新鲜宿主观察，选择策略仍绑定原安装锚 |
| 新锚已活动，管理仍暂停 | `prepare-registry-recovery-entry`、`admit-registry-recovery-entry`、`serve` | 新目录、固定前端及专属网关接纳回执，`serve` 按新锚启动并受暂停约束 |
| 已接纳新入口，需处置原事项 | `refresh-registry-recovery-observation`、`check-registry-recovery-dispatch`、`inspect-registry-recovery-dispatch` | 当前安装锚、同一原选择、原清册、新鲜重核及网关回执。其中现场复核仍以明确的原管理目录为根 |
| 完成重核且没有阻塞 | `open-registry-recovery-dispatch`、`observe-registry-dispatch` | 当前安装锚、原恢复操作键、带新鲜观察及网关回执的判定摘要以及受保护开放策略 |

恢复代次在 `registry-generations/<registry_generation>` 下保留原材料、新管理入口及归档暂停。入口输入固定在该代次的 `registry-recovery-entry-inputs/<entry_id>`，包括独立 `management-catalog.v1.json`、`management-web.v1.json` 及摘要已核对的授权配置。账号哈希输入和候选代理只准宿主身份读取。实际网关目标使用独立受保护的同一 `<entry_id>` 目录及网关权限组，候选 `manager.sock` 也使用专属短路径。恢复代次 `serve` 须显式提供新入口接纳回执摘要，正常管理请求仍按当前管理身份和代次核对。

固定入口参数以 `tools/linux_runtime/manage_registry.py --help` 为索引。管理恢复记录与已运行普通应用的部署和数据身份分别核对；宿主整体恢复按下节的固定冻结及逐安装放行进行。Windows 准入与 Linux 原生验证证据分别记录。

### 宿主恢复冻结

固定宿主入口 `enter-host-recovery-hold` 按原受保护策略核对宿主根身份、原冻结摘要或确认缺失，以及本次恢复操作。原安装锁和宿主根锁同时在场时原子发布第 2 格式，宿主冻结从空放行集合开始。同一原策略可通过 `observe-host-recovery-hold` 核对断回复，冲突策略不能接管原冻结。常规启动在准备和最终开放两处读取受信冻结，最终开放和发布冻结使用同一宿主根锁。第 1 格式安装继续核对。既有进程及维护归属不从冻结文件推定，离线诊断须核对原程序、绑定和关闭事实，并且没有业务监听。固定关闭部署核验可在合法宿主冻结期间使用受限私有套接字，维持关闭控制、验证原选中部署及正文。普通入口与已有对外只读入口仍受逐环境宿主许可约束。

固定 `authorize-host-recovery-deployment` 使用受保护策略、相同宿主冻结编号和前态摘要，绑定确已恢复的普通应用安装及固定开放策略。在原环境锁和宿主根锁下核对原操作、稳定维护控制、数据身份、独立关闭核验及活动网关，确认未附模型许可。宿主记录仅附加该安装锚及环境／代次／部署的许可。已有许可按原策略可读回，不能重复替换同一环境的许可。批准动作本身保持业务 CLOSED 和外发冻结，最终由原普通开放入口再核对准备、运行及开放条件。
