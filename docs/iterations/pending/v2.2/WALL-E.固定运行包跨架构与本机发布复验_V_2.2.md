## 兼容凭证从固定中转进入最终封存

构建、候选验证与部署准备沿原管理流程。初始中转的固定索引先供 `record-release-compatibility` 核对源安装、目标应用和等结构 Schema。兼容凭证生成时需要已经存在的固定中转，最终组装必须能采用该凭证，同时保留原中转字节及原候选检查。

- `prepare-release-final-build` 的原保护计划增加可选字段 `additional_compatibility_refs`。字段值为原 `same-schema-compatibility.v1.json` 的受保护 `{path, sha256}` 列表。省略时采用原组装路径。
- 逐项核对原凭证字节、版本和能力集合，以及候选 ID、应用与前端索引、运行包、Schema 清单及契约、程序快照。原证据中的兼容 ID 和摘要按已有格式进入最终清单，重复 ID 拒绝，原中转和原索引保持原字节。
- 既有实际源安装、关闭维护、备份及候选四类检查的部署前复核继续执行。兼容证明对同一工件的补充适用源安装由原部署准备和预检重新核对，封存时不能用它替代任何原候选检查。

## 本机回退实演输入

如首个固定候选实际开放并正常停机，使用同一既有受信 Git 源码分别封存两个独立发布 ID 和物理包。两包各自取得候选应用、浏览器及其他确切工件证据。在同一个隔离集成环境依次部署 A、B，在 B 保存新正文，然后执行原程序回退路径到已留存的 A。按关闭前置、原备份和私有读回、入口核对、执行撤错目标和实际回退反复验证。以数据库、稳定锁、数据代次和新正文／版本历史保持为完成条件。

这项仿真用于验证真实回退程序的目标归属和数据保护。两包程序字节相同，两个不同程序版本的真实回退及目标云宿主仍依最新受信交付与外部范围授权。
