# WALL-E V2.2 开发环境文档 AI 接入

2026-11-27。用户要求在 Mac Linux 的 V2.2 开发环境启用文档 AI，并确认沿用旧版 OpenAI 模型配置。目标为现有开发站点的文档对话、生成和修订。本批范围限于开发环境文档 AI。

## 实施依据

- Mac 开发环境运行 `27905ed` 的固定程序，使用基于 `db20-r50` 的 V2.2 Schema200 派生结构。该程序的 `ModelProfile` 仅支持旧版火山供应方，普通环境入口和 `GuideWorker` 关闭模型派发。前端握手也要求 `DOCUMENT_AI` 为禁用。
- 旧版实际服务使用 `openai-v6`。Windows 本地 `master` 的 `990ed2d` 含 OpenAI 接入和 V2.2 运行框架。该版 `tools/openai-service.py` 使用独立 Schema210，`backend/app/service.py` 对受管环境要求 Schema200 派生布局。两套入口的合并代码仍未连通这条运行路径。
- 静态解析固定 `db20-r50` 与 `db21-r8` 对象清单，二者共用的 299 个对象描述一致，Schema210 另有文档形成对象。V2.2 发布另有环境绑定和快照约束。当前 `FRESH_ONLY` 制品没有升级入口，不能用旧版 Schema210 启动器打开现有开发库。

## 实施与验收顺序

1. 从包含两套实现的固定源码准备候选。先核对文档形成对象与 V2.2 环境绑定、快照约束和既有初始化的组合，再用隔离副本验证结构、数据和绑定。现有开发库保留原位作为回退来源。数据库结构切换和回退流程需先确定并单独演练。
2. 复用 `openai-v6` 的模型、响应、计数和资源准入。以开发环境受信安装配置授予 `DOCUMENT_AI`，同时接通 `GuideWorker` 启停、取消、恢复与审计、文档 AI 的精确 API 路由和前端能力。核对恢复态、错环境、错数据代次和缺凭据时的拒绝。
3. 在隔离开发候选用 Mock 走完对话、生成、修订、取消和重启恢复，验证原文档及历史读回。随后在目标 Linux 用受保护的配置接入 `OPENAI_API_KEY`。真实计数和模型验证次数、预算与重试边界另行确认。
4. 准入通过后按开发环境维护流程切换。用原 HTTPS 地址核对人工文档、业务历史、AI 能力与请求结果，并在集成环境核对原状态。

已完成现场排查、Windows 合成库及 Mac 实际开发库只读副本的 DDL 演练。原 301 个对象和 73 张表内容保留，附加 74 个 Formation 对象通过回滚与完整性复核。开发发布需明确非同结构转换，复用稳定锁、独立数据代次和来源凭证。现有同结构发布只接受前后相同结构，现有普通数据库验证也要求精确的 Schema200 及其迁移记录。下一步实现受管候选的目标结构及转换验证，再接文档 AI 全链路。参见 [现场能力](../../../verification/v2.2/mac-linux-ai-capabilities-2026-11-27.md)和 [结构演练](../../../verification/v2.2/mac-linux-document-ai-schema-rehearsal-2026-11-27.md)。

前端基础指引准入已在独立检出落地。开发编辑身份在普通开放态可接受服务端 `DOCUMENT_AI=READY`，并依连接的最新观察发送已登记的指引请求。其他身份、环境和恢复态仍要求该能力关闭。页面入口、文档进展和建议 API 随受管后端接入再完成。[前端专项](../../../verification/v2.2/document-ai-frontend-admission-2026-11-27.md)

第二批接通开发限定的文档 AI 启动、工作进程、HTTP 及页面。新 Schema 制品以 `runtime.py build-schema --document-ai-schema` 构造，旧数据通过 `extend_document_ai_copy` 在独立副本验证并绑定新数据代次。`serve_environment.py serve` 只接收 root 保护且摘要固定的模型策略，绑定环境、数据代次、部署、配置及讨论和文档两条资源摘要。凭据由开发服务的 systemd 只读挂载独立提供。可选 `local_http_proxy` 沿用已有仅回环的代理校验。已有正文修订仍进入建议审阅，空白人工初稿的允许路径按原规则直接保存。

已通过离线完整 HTTP 流程、前端全量检查及实际开发库副本转换。仍需把新结构转换产物接入受管跨结构切换，保留停写旧库及审计、挂接原网关、拟定反向保全和回退。从源安装原控制识别开发停写窗口，跨结构路径须按新旧固定结构、候选配对及原数据摘要核对，现有同结构模式仍使用原规则。启用前在目标开发身份下复核常驻 OpenAI 出口和独立受信模型策略。真实供应方验证按当前明确授权执行。[链路验证](../../../verification/v2.2/document-ai-development-roundtrip-2026-11-27.md)

恢复层增加开发专用 `document_ai_schema` 引用，固定目标目录、结构摘要和应用程序摘要。它要求带审计资产的备份与明确的维护引用，生成独立的数据转换回执。恢复复核保留原始逻辑摘要，同时记录转换目标的逻辑摘要，检查原有业务行和回执绑定。普通受管选择只接受原同结构结果，跨结构结果继续走专用选择与验收。[恢复副本验证](../../../verification/v2.2/document-ai-recovery-copy-2026-11-27.md)

早期部署预览的 `document-ai-deployment-policy.v1.json` 当时只用于 `describe-restore-deployment`，实际采用以本页后文为准。校验包含开发身份、原部署和代次、恢复操作、新代次、固定程序和结构摘要、恢复证明摘要及外发暂停。通过预览后仍需核对经停写捕获的原备份、转换后的固定目标、独立只读检查和回退证据，再进入实际部署。[部署预览验证](../../../verification/v2.2/document-ai-deployment-preview-2026-11-27.md)

Mac 宿主机代理接通后，先从 Linux 开发服务账号验证直接 TLS。若 VPN 仅覆盖 Mac 代理进程，使用仅绑定虚拟机私有网桥的受限转发。转发只接受开发虚拟机地址对 OpenAI 443 的 CONNECT 请求。常驻转发已安装，双端代理进程恢复已验收。开发模型策略固定 `local_http_proxy` 为 `http://127.0.0.1:17890`。汇合时已复验开发账号的 OpenAI TLS 1.3 和其它域名 CONNECT 403，未调用模型或计数。[实机验收](../../../verification/v2.2/mac-linux-openai-proxy-installed-2026-11-27.md)

### 开发数据库结构切换

采用独立的开发恢复预检策略。在停写前固定目标候选、部署和数据代次、预留目录身份、目标库容量及备份编号。停写后才生成备份清单、截止时间与准备策略摘要，重新核对这些证据是否属于停写前固定的资源。新代次从同一份刚停写的开发备份生成，保留原数据库、原结果索引和计数审计，不选择早先备份覆盖当前开发数据。原结构和目标结构分别核对，准备回执区分原备份逻辑摘要和新库逻辑摘要，后续只读应用以新库摘要验收。

进入实际选择前，用同一固定候选执行只读验证并保留外发暂停。关闭状态下的切换检查旧部署及新代次，未开放时可核实原数据根并回退。只读及回退验收通过前不更新现有服务。

### 切换操作与凭证

1. 从获准的固定源码构建候选并完成现有候选验收。为候选制作启用文档 AI 的固定 Schema 制品。以旧开发安装为源，使用 `describe-restore-deployment` 和 `document-ai-deployment-policy.v1.json` 先取得目标配置摘要。该预览依据候选和目标标识计算。实际部署使用同一策略，并要求转换后的数据代次凭证与该配置摘要一致。
2. 在开发服务停止且持有维护控制后捕获本次备份并封存。策略 `document-ai-restore-preflight.v1.json` 固定目标目录身份和容量。维护确认时，备份编号、源及目标身份、目录身份、候选和目标配置须已知。备份清单引用、截止时间和数据准备策略摘要在捕获后填入正式预检策略。正式 `selected` 与 `preserved` 指向同一已核验的备份。源控制修订号必须与本次捕获一致。
3. 使用同一固定候选程序的 `tools/linux_runtime/manage_registry.py` 执行跨结构维护命令。对需读取旧安装的步骤，`--project` 和 `--program-sha256` 指向旧固定程序，同时传入 `--restore-executor-sha256` 为候选程序快照摘要。命令验证运行程序、旧安装和候选各自的固定身份。选错候选、环境、代次或策略时不变更活动控制。
4. 依次运行 `check-restore-preflight`、`prepare-restore-data`、`prepare-recovery-replica`、`verify-recovery-replica` 和 `check-restore-readiness`。将各命令实际回执供下一步使用。只读副本使用候选程序和前端，核验转换后的数据库字节、逻辑摘要、正文和历史，仍保持外发暂停。
5. 使用 `prepare-restore-generation` 从同一准备副本放置新数据根。启用文档 AI 时使用 `document-ai-generation-policy.v1.json`，指向同一环境、代次、部署和配置的 root 保护模型策略。该摘要随新代次凭证固定。普通恢复仍保持外发暂停。使用同一部署策略运行 `prepare-release-deployment`，随后 `select-release-deployment` 选择新代次。选择后仍处于关闭态，原数据目录与备份保留。
6. 使用既有私有只读检查和 HTTPS 网关证据验证选定部署，再由 `serve-release-open` 在原入口开放。新运行单元沿用保留数据根的 `InaccessiblePaths`，注入开发专用 systemd 凭据，并提供与新代次固定摘要一致的模型策略。缺失或错配时，已固定模型策略的候选不会开放服务。只有这一次独立授权的开发部署开放后，文档 AI 的外发暂停才解除。启动健康检查不触发真实调用。
7. 回退的最后安全窗口在普通服务开放前。还未写入切换回执时沿用维护取消。已记录切换回执时，先停止本次只读候选及相关套接字，使用与原切换策略内容和摘要完全相同、文件名为 `document-ai-restore-revert.v1.json` 的策略调用 `select-release-deployment`。命令复核原数据身份与逻辑摘要，原子恢复原控制并保留两代数据。回退回执写入后，候选不能再次开放；中断后可用原回退策略续跑。普通服务已开放时保全新数据，后续修复必须使用保留该数据的恢复流程。

切换后的普通备份继续支持由开发站已准入文档 AI 命令产生的数据。只扩展固定 Document AI Schema 下已知的数据库内表和命令回执，不承接代码执行、独立测试或其他外部资产。模型计数审计沿用原文件资产路径。已正式开放且接收新数据时，使用新布局的备份和同结构恢复，对旧布局的回退只在普通开放前适用。
