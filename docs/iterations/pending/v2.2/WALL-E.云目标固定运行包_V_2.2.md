# WALL-E V2.2 云目标固定运行包

依据 V2.01 后端 4.11、7.2、8.1.1、8.2 的云目标准入，以及架构评审的宿主与平台划分。现有固定入口只接收 Ubuntu 24.04 ARM64，运行包内容和绝对安装位置已有验证规则。

## R163 云目标构建

在同一构建和准入链路中增加 Ubuntu 24.04 Linux x86_64。构建者明确选择该架构，并核对实际宿主、目标 CPython ABI。独立依赖锁、清单、SQLite、系统库字节及启动校验分别绑定本机。既有 ARM64 调用和清单格式延续，生产控制权限仍按实际宿主与运行能力准入。

完成条件为两种隔离平台合同的正反例、错架构／ABI／依赖清单被拒绝，且云候选后续只接受 x86_64 原生构建和 Linux 实机证据。仓库实施不修改云账户、现有服务、证书或用户数据。

## R164 同平台 wheel 的离线重建

网络采集只用于新构建输入。重建入口接受本机固定架构的原 wheel 清单与显式 SHA256，核对固定的输入版本锁、安装锁、pip 引导 wheel、文件清册和目标标签，再使用既有 `--no-index --require-hashes` 安装。同一闭包可在新固定 prefix 复验，旧构建输入只读。内容差异、跨架构和额外文件一律阻止安装。

## R165 隔离环境的受信 HTTPS 来源

依据后端 6.3、6.5、7.5 和架构评审 3.1。新建普通验证环境可在特权安装工具中配置独立验证域。首个 DNS 标签仍由本环境身份固定为 `e-<environment_id>`，TLS、直接匹配浏览器来源、保护目录、Unix 上游及应用握手继续核对。管理登记从同一受保护访问策略取得来源资源标识，恢复核对也按该值防止转用其它站点。固定包无需针对域名重新构建。入口仍限专用验证环境，继续默认本地站点与回环监听，生产域名、证书和网络发布须实机核验。

## R166 固定候选的受信验证入口

沿原固定候选安装计划增加可选验证域及端口，计划摘要固定该输入。首次安装保存访问策略。重试按原环境／数据／部署和受保护访问策略确认原结果，已存在安装与计划来源不符时保持冲突。候选仍绑定确切发布、记录、固定程序、架构、Schema 与前端索引。

## R175 重开放时复核实际 HTTPS 监听

在受管发布、程序回退或配置切换的锁内重开放前，先按目标安装摘要验证访问策略，再以该来源所指定的实际监听端口复查原网关进程代次和监听 inode。允许的默认 HTTPS 443 与独立验证 9443 适用同一证据。安装摘要、来源、端口或进程不一致时仍阻断开放。
