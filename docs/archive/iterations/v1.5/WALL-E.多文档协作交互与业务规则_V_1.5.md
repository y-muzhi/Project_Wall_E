## 1. 目标、范围与责任

### 1.1 业务目标和已确认边界

用户表达目标，AI主导设计、提出方案和选项，围绕必要问题讨论，主动建议出稿；用户决定是否生成，随后阅读、反馈、要求修订和确认阶段成果。系统保存依据、执行明确操作并保护历史和版本。

| 规则 | 已确认要求 |
| --- | --- |
| R-01 | 需求详情提供独立文档工作区，同一需求允许多文档协作 |
| R-02 | 系统定义需求业务状态，转换由用户手动执行 |
| R-03 | 同步明确来源、目标和处理方式，不因来源变化自动覆盖下游 |
| R-04 | 系统提供预置主线，AI按项目细化主题；主题自动衔接、阶段由用户确认 |
| R-05 | AI提出设计选项、推荐理由及影响，避免把全部设计责任转交用户 |
| R-06 | AI主动建议出稿，用户决定工作稿形成；普通讨论不自动生成或更新文档 |
| R-07 | 明确事实或修改的准确采用由程序执行，不为确认再次调用模型 |
| R-08 | 模型返回保持可读，格式或重复问题不触发自动修复重试 |
| R-09 | 业务对象优先沿用已有对象，不因新增概念就新建一套实体 |
| R-10 | 前后端实现和接口优先复用、扩展；新增入口必须说明现有能力不足 |
| R-11 | 流程保持畅通，避免重复操作、冗长问答及不必要的中间步骤 |
| R-12 | 上下文组织作为重点设计，明确实际发送内容、长期依据及有限上下文下的推进 |

这些边界来自D15记录及既有用户要求。主题评估、模型建议、文档写入、版本确认和需求状态是不同事实，不能互相替代。

### 1.2 本稿给出的具体建议

以下为本次推荐基线，供评审并用于编写前后端设计初稿；尚未作为用户逐项批准的决定登记：

| 建议 | 内容 | 推荐理由 |
| --- | --- | --- |
| B-01 | 三类默认文档：需求说明、设计方案、需求规格；每类可多份 | 区分诉求、解决方式和实施要求 |
| B-02 | 用户同意生成新工作稿后，成功结果直接保存为未确认文档，不再增加一次“采用”才能建文档 | 减少重复操作，用户仍掌握出稿和版本确认 |
| B-03 | 用户明确要求更新指定工作稿时，成功结果形成新的未确认内容版本；仅要求建议或跨文档合入时先保留候选 | 明确改稿不反复审批，跨文档影响仍可审阅 |
| B-04 | 文档使用内容版本和确认记录，不叠加独立审批状态机 | 避免文档状态与版本认可相互矛盾 |
| B-05 | 一次工作只写一个目标，同一需求串行执行活动操作 | 先解决正确性和恢复，再扩展并发 |
| B-06 | 创建需求与首次AI运行分离，不预先填入完整规格占位正文 | 避免创建动作隐含模型调用和模板填空流程 |
| B-07 | 推荐5个需求业务状态；默认“梳理中”，具体枚举见详细规格 | 不设计旧测试数据迁移或状态映射 |
| B-08 | 来源默认固定到执行开始时的选定内容版本，历史请求永不重新生成 | 保证可追溯与前后端一致 |

B-02／03只适用于用户明确发起的一次生成或更新，不建立持续自动写入模式。此前“同意生成只形成运行候选、再采用才创建文档”的默认建议由B-02替代，仍需评审；不能反过来扩大R-06授权。

本稿是V1.0上的增量设计；当前详细定义见[后端设计](../../../design/v1.5/WALL-E.后端设计文档_V_1.5.md)，已取消旧测试数据迁移和兼容，并明确每轮运行结束、卡片不持有占用。其余未细化表述以详细规格为准。新逻辑名称不意味着新建同名表；对象承接见3.5，后端／前端复用边界见7.5。既有能力未在C15新增清单逐一列出，不代表被删除。

本次按用户五项要求收敛：首批保留七类既有业务根，阶段／路线等归Requirement讨论状态，出稿建议归消息／卡片，执行依据归GuideRun，版本归Revision；C15／Q15不是新接口数量。物理字段和两项必要新增资源入口仍是技术设计建议，未实施或单独获批。

### 1.3 首批范围与职责

首批包含：多文档阅读和编辑、需求级对话、任务与参考绑定、分层指引、受用户控制的出稿和修订、单目标合入、版本确认、来源复核、实际请求及用量。旧测试数据迁移和旧客户端兼容不纳入范围，见D15-005。

首批不包含：跨需求引用、多目标批量事务、多人实时编辑、并行写入任务、自定义流程引擎、永久删除、独立项目看板。自定义文档类型及更多模板后置。

AI负责语义理解、设计建议、主题评估、候选和文档内容。用户负责关键取舍、出稿、明确改稿、合入、版本确认及业务状态。程序负责身份、版本、范围、幂等、事务、保存、权限和实际执行结果。程序不宣称能够证明模型结论正确。

## 2. 页面与完整业务场景

### 2.1 页面和对象选择

| 区域 | 内容与交互 |
| --- | --- |
| 需求页头 | 标题、人工业务状态及切换入口，不混入模型运行状态 |
| 文档导航 | 名称、类型、当前内容版本、确认情况和来源更新提示；可收起 |
| 文档工作区 | 正文、大纲、编辑、版本和确认入口；工作稿生成后直接在此阅读 |
| AI对话区 | 当前工作、目标、参考材料、对话、选项、出稿建议、运行结果 |
| 大纲与进展 | 按需展开当前主题、已有结论、依据和未决事项，不变成常驻必填表 |
| 文档记录 | 当前文档的内容历史、确认、合入，以及关联运行和请求详情 |

文档和对话独立滚动。窄窗口切换视图保留输入、草稿、阅读位置；具体宽度沿用现有设计原则并在前端规格确定。

查看文档只切换阅读对象，不改AI写入目标，不自动发送所看全文。对话持续显示实际目标；用户可定位该目标。AI可推荐目标文档和参考材料，系统展示推荐及版本，用户在开始生成／修改时接受绑定；不要求用户为每条讨论消息重新配置。

参考只赋予读取关系。用户未选择的文档不因“同一需求下存在”就全量发送。初始讨论可只读取原始需求、有效依据和指引；后续由AI提出相关材料建议，程序按明确的工作范围装载。

### 2.2 场景契约

| 场景 | 用户输入／动作 | AI及程序行为 | 可见成果及副作用 |
| --- | --- | --- | --- |
| S-01 创建 | 标题、原始描述 | 程序创建需求并设默认状态 | 原始描述和空白工作区；无运行、无占位规格 |
| S-02 开始讨论 | 开始设计或发送目标 | AI解释理解、推荐方向，建立项目化主题 | 大纲和讨论记录；无工作稿生成 |
| S-03 关键选择 | 回答选项、自定义、修正或暂缓 | AI组织结论、更新主题评估，衔接下一主题或建议出稿 | 原始回答及有来源的理解，不改变文档 |
| S-04 建议出稿 | 用户尚未接受 | AI说明文档用途、范围、拟覆盖内容和待定项 | 可执行的出稿建议，不启动生成 |
| S-05 生成新稿 | 用户接受具体建议或主动发起 | 固定目标及来源，执行一次生成；有效结果按B-02保存 | 新工作文档V1，未确认；失败不留下空正式文档 |
| S-06 读稿反馈 | 指出问题或讨论改法 | AI分析并提出修改建议 | 反馈和方案；普通讨论不自动改稿 |
| S-07 明确改稿 | “按这些意见更新这份工作稿”等 | 绑定目标及预期版本，一次修订按B-03提交 | 新未确认内容版本，保留旧版本及变化摘要 |
| S-08 跨文档合入 | 来源、目标、范围和处理要求 | 生成修改候选，展示差异；用户采用后程序提交 | 实际采用项、目标新版本及来源记录 |
| S-09 核对和变更 | 发起差异或影响分析 | 固定材料，提供差异／分析；不自行更新下游 | 分析覆盖范围、冲突及建议 |
| S-10 确认与收束 | 确认文档版本或收束阶段 | 两种独立用户命令，不调用模型 | 版本确认或阶段总结引用，不改需求业务状态 |
| S-11 状态及归档 | 手动切换状态／归档文档 | 程序校验占用并记录 | 人工业务状态或归档记录，不生成正文 |

“可以”“继续”等回答必须关联明确对象，不能同时代表接受方案、生成文档、确认版本和结束阶段。普通问题的正式提交可继续请求AI；接受准确修改、状态切换及查看不需要模型。

### 2.3 工作稿生成后的阅读循环

AI建议出稿→用户同意→生成并保存未确认工作稿→用户阅读→讨论问题或明确要求改稿→AI形成新版本→用户确认具体版本。

B-02下“生成”已经授权保存本次新工作稿，无需再点击保存或采用才看到文档；这不等于确认其内容。B-03下“更新工作稿”授权单次更新，不将之后所有回答都当作改稿指令。

用户只要求“先给改法”时，生成修改候选，不变动文档；用户选择采用后程序原样写入。跨文档合入也使用候选流程，不因用户曾允许更新A就写入B。

## 3. 业务对象、版本和生命周期

### 3.1 复用优先的对象模型

本版继续使用V1.0七类业务根：Requirement、RequirementDocument、Revision、ConversationMessage、GuideRun、SuggestionBatch／Suggestion、Comment。LLMUse仍属于GuideRun内部。新增概念优先作为既有对象的字段、值对象、资源或查询投影，不按概念名称逐一建表／建接口。

| 既有对象 | V1.5承载内容 | 明确不再另建的并行对象 |
| --- | --- | --- |
| Requirement | 原始描述来源、人工业务状态、讨论阶段、焦点、路线、结论索引与discussion_version | 不另建WorkTask、DiscussionOutline、DiscussionTopic聚合；它们是需求的讨论状态 |
| RequirementDocument | 多份正式工作文档、名称／业务类型／归档、当前content_version、人工草稿关联及确认版本引用 | WorkDocument只是业务称呼；EditDraft沿用MANUAL_DRAFT及编辑会话，不另建文档系统 |
| Revision | 沿用不可变快照能力，按文档的CONTENT快照支撑每次正式内容提交；不迁移旧历史 | ContentVersion是内容版本视图，不另建一套版本实体和仓储 |
| ConversationMessage | 原话、卡片、正式回答、出稿／阶段建议；通过message_id＋card_key关联具体建议 | GenerationProposal不作为独立业务根，复用助手结构化消息／卡片 |
| GuideRun／LLMUse | 一次接受、执行、冻结上下文、操作依据、结果、实际供应方调用和用量 | ExecutionAuthorization不独立建表或提供授权接口，作为运行接受时的私有快照 |
| SuggestionBatch／Suggestion | 固定目标、来源版本、补丁、用户决定、差异与实际应用结果 | ChangeCandidate为已有批次的投影，不建第二套候选系统 |
| Comment | 评论内容、状态、区块／选区锚点，新增明确文档归属 | 不把评论改造成另一套待确认事项系统 |

GuideDefinition是现有资源目录管理的版本化指引资源，不是新增业务聚合。Evidence／Issue是从消息、卡片、文档及检查结果取得的来源索引和处理信息；首批归入Requirement讨论状态，只有实际性能和查询需求证明不足时才在后端设计中提出专门投影表。

VersionConfirmation、StageClosure和ApplyRecord分别是确认、阶段收束、实际应用的语义视图：确认引用文档／Revision并记录用户事件；阶段收束更新Requirement讨论状态并保存用户消息／卡片处置；应用沿用document_change_audits及批次结果。不得因为这些名称再创建三条平行的审计链。

### 3.2 需求讨论状态

建议为Requirement扩展discussion_state及其discussion_version，字段的物理形式在后端设计落实。它包含当前阶段与采用指引引用、阶段内主题及成果要求、当前焦点、带来源的结论索引、暂缓／排除／拒绝出稿等处置和阶段收束摘要。主题使用需求内稳定topic_ref，阶段使用需求内phase_ref，不分配独立聚合ID。

讨论状态只保存可追溯的整理结果及引用，不复制全部正文或消息。原始描述优先引用创建时保存的用户消息，读取投影可返回原文，不为方便组装而重复维护多个“初始需求”文本。

用户调整目标或模型提交有效进度时，通过discussion_version做原子复核。讨论状态变化不改变需求业务状态，不产生工作文档，也不形成未来写入许可。

原始消息不可变，讨论状态只作为当前工作投影。每次运行保存当时讨论状态及实际材料快照，重要处置保留消息／卡片或审计来源，不能只覆盖一个JSON后丢失历史。

对话仍归属于需求，可按文档和phase_ref筛选。切换阅读对象不复制消息、不新建会话；一项连续工作可以对应多个GuideRun，不能用供应方session代替这些关系。

### 3.3 文档及Revision承载的内容版本

需求说明、设计方案、需求规格是业务类型；不能覆盖原document_type用于CURRENT／MANUAL_DRAFT实例类别的含义。扩展RequirementDocument以支持同需求多工作文档，保留人工草稿独立身份及真实目标关系。

正式内容变化提交时更新原文档content_version，并以Revision的新增CONTENT类型保存该版本的不可变Markdown／BlockState快照；新1.5数据以按文档的内容版本关联和编号，不再保留旧测试数据编号映射。新库结构见详细规格，不设计迁移。

ContentVersion这一逻辑名指上述版本组合，不意味着新增同职责版本表。现有Revision查询／读取能力继续使用，补充document_id和类型筛选；确认不再保存另一份相同正文。

人工输入仍自动保存到MANUAL_DRAFT／EditSession，完成编辑才形成正式内容版本。改名、归档和确认是元数据／用户事件，不制造正文变化。没有实际内容变化不新增CONTENT快照。

### 3.4 用户控制的生成、确认和回退

新稿生成：用户明确发起或接受消息中的具体出稿建议后，在同一个现有运行接受入口保存用户动作、固定新建目标属性／来源／范围，创建GuideRun。成功事务创建RequirementDocument、V1对应Revision及实际变更审计；失败不留下空工作文档。按B-02仍为待评审建议。

明确更新：固定已有document_id、预期content_version及范围，沿用GuideRun结果提交和文档写入机制形成新版本。普通反馈只讨论；仅要求建议或跨文档合入时仍使用SuggestionBatch，采用准确修改不再请求模型。B-03不扩大为持续自动更新。

确认：RequirementDocument可缓存confirmed_revision_id，必须指向同一文档的真实内容快照；用户确认事件沿用现有审计／消息记录。确认V3后编辑成V4，V3不变，当前V4未确认；不需要VersionConfirmation独立实体或确认服务。

回退：沿用历史快照读取和人工草稿提交路径，把选定历史内容作为新提交，不改旧Revision、不自动确认新版本。首批以归档代替永久删除。

来源固定到明确版本及区块范围，优先推荐已确认内容；选用工作版本时标记未确认。归档不破坏历史读取，来源变化只提示复核，不级联更新。

### 3.5 V1.0承接与必需扩展

| 旧定义 | 保留的实现／约束 | 必需变化及复用边界 |
| --- | --- | --- |
| OBJ-REQ | 身份、编号、标题、活动占用 | 添加讨论状态／版本和新版人工状态解释，不建第二个任务根 |
| OBJ-DOC | Markdown／BlockState一致性、身份、来源、content_version及人工草稿 | 解除需求内唯一正式正文假设，增加名称／业务类型／归档和显式目标 |
| OBJ-REV | 不可变快照、历史说明、旧版本查询 | 增加文档归属与CONTENT类型，不并行维护两套内容版本，不迁移旧BASELINE／MANUAL记录 |
| OBJ-MSG／SHR-CARDS | 原消息、顺序、原题与正式回答绑定 | 结构化卡片增加明确用途，出稿接受和阶段处置复用提交入口；不能把“同意出稿”冒充旧事实CONFIRM |
| OBJ-GUIDE／LLMUse | 运行、取消／重试／恢复、冻结资源、请求与实际用量 | 扩展运行动作及多文档上下文，执行依据放运行快照，不另造工作编排／授权服务 |
| OBJ-BATCH／SHR-PATCH | [批次仓储](../../../../backend/app/infrastructure/batch_repository.py)、补丁、决定、准确应用 | 明确document_id和来源，继续使用既有决定／完成入口 |
| OBJ-COMMENT／SHR-ANCHOR | 评论状态、区块／选区定位及ORPHANED处理 | 命令和查询补充真实文档归属，不能继续隐式选唯一CURRENT |
| 人工编辑会话／来源证明 | 草稿基准、分配证明、原文和创建来源保护 | 按实际document_id绑定，不复制一套编辑系统 |
| document_change_audits | 原目标、前后版本、来源和实际结果 | 扩展确认／合入所需事件与关联，不同时写互不一致的“新ApplyRecord日志” |

后端设计优先扩展既有Repository和应用命令。新字段／值对象不自动拥有CRUD接口；如果提出新根、新表或新接口，必须列出现有承载为什么不足，不能只以“名称更清楚”作为新增理由。

## 4. 状态、权限和执行约束

### 4.1 三种不同的进度

| 维度 | 推荐值／含义 | 谁推动 |
| --- | --- | --- |
| 需求业务状态 | 梳理中、待实施、实施中、已完成、已关闭 | 用户手动转换，默认梳理中；具体集合为B-07建议 |
| 主题评估 | 未展开、讨论中、具备结论、待复核；暂缓／不适用需用户依据 | AI提出评估，程序保存，用户可纠正 |
| 执行状态 | 已接受、准备中、运行中、成功、失败、取消 | 程序按实际运行计算，保留旧协议自身解释 |

文档确认由确认记录派生，不另存与版本可能矛盾的“已确认”布尔值。阶段建议收束是模型评估，实际收束由用户命令记录。

### 4.2 需求状态转换和许可

建议允许用户直接选择其他状态或退回，不强制走完所有状态；同状态操作为无变化。状态命令校验预期状态版本，记录操作者、时间和前后状态。默认初始化不算用户转换。

| 操作 | 未关闭、未归档的可维护需求／目标 | 需求已关闭 | 目标文档已归档 |
| --- | --- | --- | --- |
| 阅读、复制、历史、请求详情 | 允许 | 允许 | 允许 |
| 讨论、生成、编辑、采用、确认 | 满足版本和占用时允许 | 先由用户重新开放 | 读取其历史允许；修改／确认前先恢复目标 |
| 转换需求状态 | 用户操作，不依赖模型完整性评分 | 可手动重新开放 | 文档归档不阻止需求状态操作 |
| 阶段收束 | 用户操作，可保留未决项 | 仅回查旧记录 | 不自动恢复文档 |
| 归档／恢复 | 用户操作并校验元数据版本 | 先重新开放再改资料 | 用户显式恢复 |

“已完成”不隐式冻结全部资料；用户仍可维护并产生未确认版本，系统不自动改回梳理中。关闭或归档时有活动运行／编辑会话，应先明确完成或取消，不静默终止。

未决事项、未确认文档和AI认为“不完整”只是提示，不阻止用户选择业务状态。

切换为其他非关闭状态可在运行中进行，但不取消任务、不修改已发请求的状态快照；新状态用于后续工作。关闭、归档等结束维护操作须无活动操作，以免产生迟到写入。

### 4.3 并发与精确写入

首批同一需求只允许一个活动AI运行、人工编辑会话或合入操作，讨论运行也不与写入并行；阅读、复制、输入草稿和历史不受此占用阻断。串行不意味着运行结束自动释放尚未完成的人工编辑内容。

所有写命令在服务端校验身份、权限、预期版本、范围与占用；界面禁用不能替代服务器检查。指令绑定的任务／建议版本、目标版本和来源不能被模型输出更改。

提交正文、Revision内容快照、既有变更审计及必要锚点复核在同一事务内完成；任一步失败回滚。模型调用在数据库写事务外执行，完成后短事务复核再提交。

取消与成功提交竞争时，以服务端事务中的实际先后为准：取消先提交，迟到结果不写入；内容已经提交成功，取消返回已完成，不回滚用户文档或冒报已取消。

## 5. AI指引、上下文与输出协议

本章5.1—5.7描述目标和原则；[讨论方向指引的执行设计](#discussion-guidance)见5.8—5.14，明确资源结构、项目路线、每轮调度、请求／返回契约、指导文本和页面交接。该部分是本次具体设计建议，尚未创建运行资源或实现代码。

### 5.1 指引资源与项目化

需求收集使用下面的初版通用指引；任务固定采用其版本。方案设计、规格整理、变更复核各自采用匹配的阶段要求，不把需求收集的问题重新问一遍。

| 主线 | 必须能表达的成果 | 必要信息与可先建议的内容 | 追问／建议收束条件 |
| --- | --- | --- | --- |
| 目标与价值 | 面向谁、解决什么问题、期望结果及优先级 | 用户痛点来自用户；AI可以提出优先方向与定位备选 | 只有口号且无法判断要解决什么时给情境选项；能表达具体问题与价值取舍即可总结 |
| 角色与场景 | 主要使用者和至少一条典型使用情境 | 已有角色沿用；无依据不编造真实人数、组织或资质 | 主角色不明影响流程时询问；不为角色列表凑项 |
| 核心业务闭环 | 从触发、输入、处理到结果和后续动作的连贯路径 | AI先设计推荐流程，用户纠偏；必要异常按影响补充 | 关键步骤存在矛盾时追问；主路径能讲清即可建议出稿，不等全部边界穷尽 |
| 关键规则与信息 | 决定核心结果的规则、重要信息来源、未知项及影响 | 已有事实直接引用；技术和交互取舍由AI建议，不逼用户先懂实现 | 缺项改变用户行为或成果时提出选项；不提前追问全部字段和技术参数 |
| 范围与约束 | 本次包含、明确排除、暂缓及已知硬约束 | 不从未勾选推导排除，不把建议预算当成用户事实 | 存在重大范围冲突时说明；其他约束可注明待定 |
| 成功判断 | 至少一个具体成功情境／定性例子，能解释成果是否有价值 | AI给评价方式备选；无依据不编造精确指标 | “好用、准确”等无法区分结果时给例子；定量细化可留后续规格，不阻止需求说明 |

每个主题包含稳定引用、目的、预期文档成果、已有依据、当前理解、待定影响、下一步建议和收束依据。主线→主题两层持久保存；问题与主题关联，不无限创建子树。

“用户尚未明确”“AI认为可建议方案”“必须取得真实事实”分别处理。AI不能为推进伪造事实，也不能把所有设计选择都转交用户。

### 5.2 一轮讨论的行为

1. 按有效任务和当前主题读取相关材料，核对用户修正和已处理事项。
2. 先解释理解或提出设计，涉及取舍时给可比较选项、推荐理由和影响。
3. 以本阶段成果为目标，只问会改变成果方向的关键问题，允许自定义、暂缓及按建议继续。
4. 形成带来源的结论与主题评估；一个回答可以同时补足多个主题。
5. 信息达到可成稿程度时主动提出具体出稿建议，不等用户催促，也不直接生成。
6. 用户决定生成后转入生成任务；读稿反馈用于后续讨论或明确修订。

默认优先一项关键决策，确有独立事项可在同轮少量呈现；不把“一轮一至三个问题”等数值当作已批准硬门禁。无新增依据或重复追问时，先总结卡点、提出方案／暂缓／出稿路径，不继续无界扩展细节。

只有关键矛盾会改变当前成果时才优先澄清。用户希望先成稿时可标注假设和未决项，不要求完成全部主题。

### 5.3 收束与出稿条件

主题具备带来源的预期成果，或用户明确暂缓／判定不适用时，可衔接后续主题。模型评估标明身份；用户修正使结论不再成立时保留原结论并提出复核，不静默重写用户确认。

需求说明可建议出稿的最低条件：能表达问题与目标、主要角色及一条核心流程、初步范围，以及设计建议／用户事实／待定事项的区别。其他主线仍可继续，不要求全部结束。

阶段建议收束要求已有可连贯表达的成果、主要取舍和未决影响；用户可接受剩余边界、继续讨论或提前结束。阶段收束不暗中生成文档，不自动确认已有文档或转换业务状态。

阶段指引的补充：
- 方案设计产出推荐方案、主要取舍和约束对应关系，不能只返回待选题。
- 规格整理产出确定行为、数据／异常边界及可验证条件；缺失事实明确待定，不冒称可实施。
- 变更复核说明实际检查范围、来源变化、影响和建议，不根据局部材料宣称全文一致。

### 5.4 出稿建议与一次性执行依据

出稿建议沿用不可变的助手消息和卡片，以message_id＋card_key定位，并绑定需求讨论状态及来源版本；修订建议形成新消息／卡片，不另建建议实体及版本体系。展示文档类型／名称、用途、拟覆盖范围、依据和待定项。只有程序保存成功且可定位的建议提供生成入口；模型自由文本建议仍可阅读，但不自动成为可执行授权。

用户可直接点击生成，也可对唯一关联的有效建议明确回复“生成”“按这个建议生成”等。程序保存原用户消息和对应建议身份，不用最后一条“继续”无对象地授权。多个建议并存时由用户指定，不能让模型自行挑一个写入目标。

复杂自由文本中包含生成／修改意图但尚无确定绑定时，AI整理操作建议，由用户通过生成入口发起；该限制只防止猜测业务动作，不阻止正常讨论。目标已明确的操作不反复要求用户重新写指令。

执行依据包含用户动作、操作类型、新文档属性或目标身份／版本、需求讨论状态版本、范围、来源版本及建议引用；只允许一次对应执行，不授予未来自动更新。新建议替代旧建议、任务或目标变化时将旧入口标为待复核，浏览其他文档本身不使其失效。

来源在建议后更新时接受命令先展示变化，用户沿用原来源或选择重新准备；执行开始固定版本。之后来源再变不改已发请求，目标再变则阻止提交。

### 5.5 模型输出与程序实际结果

以下为共同语义分区，不是已发布JSON Schema；后端据此定义版本化协议，前端不从自然语言自行推测写入结果。

| 输出部分 | 内容 | 程序允许的动作 |
| --- | --- | --- |
| 可读回复 | 解释、设计、建议和不确定性 | 展示，不等于授权 |
| 问题选项 | 问题、同维度选项、推荐、影响和自定义入口 | 展示并保存原始回答关系 |
| 主题更新建议 | 稳定主题引用、结论、来源、未决影响和下一步 | 验证引用与需求讨论状态版本后保存为AI评估，不写文档 |
| 出稿建议 | 文档属性、范围、依据和待定项 | 保存并提供用户生成入口，不自行运行 |
| 文档结果 | 与已授权目标相符的完整工作稿或指定范围修改 | 仅生成／修订任务可按B-02／03提交 |
| 修改候选／分析 | 目标基准、独立修改单元和依赖，或检查结果 | 候选先审阅；分析不写入 |

讨论返回不允许因夹带文档正文而触发创建或修改；生成任务出现新目标、超范围或无法应用时保留内容但不写入。

结构不识别时不更新进度／文档，原始回复仍可读；不自动请求格式修复。原始消息、解析状态、应用结果和用量分开保存，不能仅用“运行成功”掩盖实际未写入。

### 5.6 材料选择和发送前检查

| 工作 | 必须固定的材料 | 模板／指引 |
| --- | --- | --- |
| 讨论 | 原始需求、精简大纲总览、当前主题、相关有效决定／暂缓项、近期交流 | 阶段指引，不默认完整规格模板 |
| 方案比较 | 相关需求、约束、已有候选及评价依据 | 专题设计要求 |
| 局部生成／修订 | 目标原文、选定来源、相关约束和允许范围 | 目标部分结构规则 |
| 全文生成／核对 | 实际覆盖的完整目标及选定来源，或明确分批计划 | 按任务采用完整结构，不冒称未读部分已检查 |

首批采用显式材料选择，不预设向量检索。原始描述及任务级有效决定摘要常驻，当前主题关联原文及明确选定范围装载；摘要标明AI整理身份并保留可读取的出处。冲突或疑义时补读来源，不把摘要等同完整事实。

发送前预算检查失败则不调用聊天模型，展示哪些材料超出及可缩小范围／分批的方式；不静默裁剪硬约束后继续声称完整覆盖。计数沿用既有可信计数机制，新预算参数在后端资源设计核对，本稿不改变V1.0预算或调用许可。

稳定规则在前、任务材料居中、本轮输入及易变说明在后。程序保留完整私有权限和审计，模型只获当前必要操作说明。实际请求顺序、材料范围、指引版本和用量保存为快照，查看不再计数或调用。

### 5.7 电影案例的执行示例

用户提出记录、评分并推荐电影。AI先推荐产品定位，给出“精准发现下一部影片优先／记录管理优先／二者并重”等同维度选择，允许补充，不先追问算法参数。

用户强调“猜得准”后，AI用具体推荐情境说明并比较熟悉偏好、冷门佳片和探索类型。用户明确三部电影承担不同角色后，保存原话与主题结论，不再换题目重复问整体目标。

目标、主流程和范围能连贯表达时，AI建议形成需求说明并列出待定项。用户未同意前不生成；同意后才按S-05保存V1。用户读稿指出“探索性不够”，AI先解释改法；用户明确“按此修改”后按S-07更新，未明确改稿时仅讨论。

成功判断的精确定量、电影库更新周期和技术失败策略可以后续进入对应方案／规格主题，不淹没当前需求理解。

### 5.8 四层载体：方法、项目路线、成果和本轮任务

讨论方向指引不等于文档填写模板，也不能只是一段“循序渐进、信息足够就结束”的提示。推荐用以下四层共同约束一次工作：

| 层 | 谁提供／维护 | 保存及发送内容 | 作用 |
| --- | --- | --- | --- |
| 通用阶段指引 | 系统版本化资源 | 阶段目标、主线、预期成果、推荐设计方法、追问／收束／转向规则 | 指明应怎样理解和设计，不要求用户逐项作答 |
| 项目讨论路线 | AI按指引提出，程序保存；用户可调整 | 当前项目主题、依赖、优先级理由、当前焦点及版本 | 将通用主线映射到电影推荐等具体业务 |
| 结论与待定记录 | 用户来源、AI整理和程序处理事件 | 已知事实、建议、用户决定、待定影响、原始出处及替代关系 | 表示讨论已取得的成果，而非只统计问了多少题 |
| 本轮工作包 | 程序从上述持久资料装配 | 当前主题详细要求、相关依据、整体短摘要、本轮用户输入和操作模式 | 在有限上下文中给模型明确任务，避免重新从头规划 |

完整资料由系统保存，每轮不全量发送；模型同时获得整体位置和当前分支。项目路线和结论记录是协作元数据，不是已经生成的需求工作稿，不因它们更新就绕过用户出稿决定。

这四层是已有对象中的资源、值对象和读模型，不是四套新实体／服务：阶段指引归原资源目录，路线和结论索引归Requirement，原始依据归消息／文档，实际工作包归GuideRun的冻结快照。

GuideDefinition建议至少定义以下字段。资源沿用V1.0冻结、版本和准入机制，新指引另增版本，不覆盖旧Prompt／Schema：

| 字段 | 具体含义 |
| --- | --- |
| guide_key／guide_version | 稳定引用及不可变版本；名称为拟议协议字段，不代表资源已发布 |
| applicable_phase／goal | 适用工作阶段及本阶段要形成的理解或设计成果 |
| deliverable_types | 可建议形成的文档类型及相应最低成果要求 |
| mainlines | 稳定主线引用、目的与主题细化规则；需求理解采用5.1六条主线 |
| outcome_requirements | 每条主线预期形成的结论及示例，区分用户事实、AI建议和待定项 |
| design_methods | 推荐的分析顺序、方案构造与取舍方法，不只是问题范例 |
| questioning_policy | 哪些歧义值得问、如何提供选项和推荐、何时不再展开细节 |
| convergence_policy | 主题总结、建议出稿、阶段收束及需要复核的条件 |
| redirection_policy | 用户纠正、主动跳转、拒绝出稿、暂缓事项及重复问题的处理 |

主题应包含topic_ref、所属主线、目的、expected_outcomes、已有结论、待定影响、依赖和评估版本。expected_outcomes是可追溯的成果条目，例如“能说明推荐好坏的具体情境”，不能用“回答本题”代替。

### 5.9 项目路线如何产生和调整

用户开始需求讨论后，在首个正常模型响应中完成项目化路线建议及初步设计，不默认额外调用一个“规划模型”。首次模型只使用本次实际提供的原始描述、阶段指引及已有材料。

模型提出主线下的项目主题，例如“推荐价值定位、用户如何记录与评分、推荐主流程、偏好信息、版本边界、推荐效果评价”。程序为有效主题分配需求内稳定topic_ref，保留父主线及discussion_version；它不是新的业务实体或数据库主键。模型新建主题使用临时引用，由程序接受后映射。

已有材料足够支撑的主题直接整理结论，不重新提问。主题之间有依赖时，优先处理会改变后续设计的部分；关系是讨论依据，不是必须逐个打勾的审批路径。

路线调整使用基于当前discussion_version的增量建议。允许补充主题、关联一个回答到多个主题、提出重复主题合并，以及调整焦点；保留旧路线和结论来源，不覆盖重建整个大纲。

AI不能自行把必要主线删除或标成用户已排除。可以说明本任务不涉及的理由，暂缓／不适用等用户处置必须关联真实用户依据。用户明确跳转或修正目标时优先响应，再说明对原路线的影响。

跨阶段转换与主题切换分开：同一阶段主题可自动衔接；从需求理解转向方案设计等阶段转换，由用户接受下一阶段工作建议或直接发起，不因模型自评完成而转换需求业务状态。

### 5.10 每轮怎样选择下一步

每轮由AI提出主行动和依据，程序验证引用、需求讨论状态版本及执行边界后保存；程序不替代AI判断业务语义。推荐采用以下优先顺序，用户本轮明确要求始终优先：

| 优先情形 | AI应做什么 | 程序边界 |
| --- | --- | --- |
| 用户明确生成／改稿／取消／跳转 | 执行或处理该项工作，不继续原问题清单 | 生成与写入仍检查对应用户动作、目标和范围 |
| 用户纠正已有理解或提出具体问题 | 先回答或修正理解，指出受影响主题 | 保留新旧依据，不能把模型改写当成新的用户确认 |
| 存在影响当前成果的真实矛盾 | 对比依据，提出解决方案及必要选项 | 标记实际冲突范围，不按最后时间自动决定胜负 |
| 已具备可连贯表达的阶段成果 | 主动建议出稿并说明待定项 | 将出稿建议保存到助手结构化消息／卡片，等待用户决定 |
| 还缺关键用户事实／偏好 | 给情境、同维度选项、推荐和影响，允许自定义或暂缓 | 保存原问题和回答，不把推荐视为选择 |
| 可以由设计建议推进 | 先给推荐流程或方案，再让用户纠偏 | 标明建议／假设，不将所有取舍都变成必答题 |
| 当前主题有足够结论 | 总结后衔接下一相关主题，说明关联 | 保存主题评估，不改需求状态或授权 |
| 信息不足但反复没有推进 | 总结卡点，提供建议方案、暂缓或先出稿的路径 | 不隐藏返回或自动重试，不扩展成更多无关问题 |

主行动建议使用PRESENT_DESIGN、ASK_DECISION、SUMMARIZE_TOPIC、RECOMMEND_DRAFT、NEED_EVIDENCE、PROPOSE_PHASE_CHANGE等语义类型。它们表达本轮目的，不直接成为业务写命令。

模型提出下一主题须说明为什么它比其他未决项更影响当前成果，不能只按模板章节序号或最早未回答问题选择。优先目标／主流程／核心取舍，详细实现参数只在相应任务中展开。

同一成果缺口再次提出时，对照之前回答，指出新出现的歧义或仍缺的具体内容。程序可观察重复的topic_ref／outcome_ref、问题次数及未变化的结论，但不能凭文本相似度证明业务没有推进。

用户暂缓或拒绝出稿后保存处置，不在每轮机械重复同一建议；用户主动要求、成果范围改变或新信息使出稿建议实质变化时，再说明原因并提出。用户也可随时直接要求生成，不受主题评估阻止。

### 5.11 请求工作包与进度返回的最小契约

下面是前后端共同语义要求，具体JSON Schema由后端设计落实；它不能替代已批准的旧协议，也不要求前端解析模型的自由文本来推进状态。

| 本轮输入分区 | 最少内容 | 装载规则 |
| --- | --- | --- |
| 阶段指导 | guide_ref、适用阶段目标、设计和提问策略、出稿边界 | 固定采用版本，只装当前阶段；由系统资源提供 |
| 总览 | requirement_id／discussion_version、各主线短结论、当前焦点、关键跨主题约束 | 常驻短摘要，不复制全部主题详情 |
| 当前分支 | 需求内topic_ref及当前discussion_version、目的、expected_outcomes、已有结论、待定影响 | 读取当前相关主题详情 |
| 依据 | 相关用户原话、正式回答、选定文档版本／区块、建议身份和来源 | 长期有效依据不依赖最近10条；不把整理摘要冒充原话 |
| 用户输入与工作模式 | 本轮实际消息、DISCUSS／GENERATE／REVISE等模式、程序绑定目标 | 模式由用户动作及程序确定，模型无权切换获得写入许可 |

进度返回至少包含：

| 字段组 | 应返回的内容 |
| --- | --- |
| basis_ref | 采用的guide引用、需求discussion_version和阶段phase_ref，供程序核对迟到结果 |
| topic_updates | 已有主题引用、成果条目、当前结论、支持来源、待定影响及评估；新主题通过增量建议添加 |
| next_step | 主行动类型、当前／建议下一主题、推荐理由，以及关键选项或设计建议 |
| draft_recommendation | 仅建议出稿时提供文档用途、范围、已有成果和待定项；不是生成授权 |
| readable_reply | 面向用户的设计说明、问题和推荐；与内部进度记录分开展示 |

成果评估使用“已有支持、仍不明确、存在冲突”等语义，并附来源；是否具有充分语义支持由AI判断，程序只验证来源存在且属于本次实际提供材料。暂缓／排除等用户决定还须关联用户事件，不能只引用助手建议。

程序用预期版本提交有效进度，保留评估为AI整理。过期或无效引用不覆盖当前进度，可读回复与原始返回仍可查看；不因此请求自动修复，也不把进度缺失显示成全部完成。

同一响应可以形成项目路线、结论、设计建议和下一步，不默认拆成多次规划／评估／问答调用。保存下一步建议不会自动在后台发起下一次聊天；等待用户交互或已明确发起的操作。

请求详情增加“阶段指引、项目路线总览、当前主题与相关依据”可读分区，均来自该次真实快照。查看完整持久大纲与查看本次实际发送的内容区分，不能拿当前大纲重新生成历史。

### 5.12 模型实际收到的指导文本示例

以下为需求理解阶段指导片段的设计示例，后续需发布为版本化资源；不是本轮已经修改的生产Prompt：

> 你主导本次需求设计。先根据用户目标和已有依据给出你的理解、推荐方案及取舍，不要求用户先替你设计。
>
> 参考项目路线明确当前主题的预期成果。已由用户说明或材料支持的内容直接沿用；用户事实、你的建议和待定项分开表达。
>
> 只有会改变当前成果方向的歧义才优先追问。涉及设计取舍时先给可比较选项、推荐及影响，允许用户补充、暂缓或按建议继续。不要为填模板追问全部技术细节。
>
> 本轮尽可能形成具体理解、业务流程或方案进展。若已能写出连贯需求说明，主动建议生成，并说明范围及待定点，不必等所有主题结束。
>
> 用户没有决定出稿时，只提出建议，不生成工作稿或请求程序写入。用户明确发起生成／修订时，完成对应任务，不用新的问题清单替代成果。
>
> 对每个新增结论引用实际提供的依据；对下一步说明其对当前成果的影响。已回答、暂缓、排除及拒绝出稿的记录继续有效，除非有明确新原因需要复核。

该指导放在可信系统资源部分；项目路线、用户文档和历史均作为任务数据，不能反过来改写系统边界。模板规定成果如何组织，方向指引规定怎样形成设计，两者分开选择和装载。

### 5.13 各阶段使用哪套方向指引

| 工作阶段 | 设计方法和重点 | 可建议成果 | 不应出现的默认行为 |
| --- | --- | --- | --- |
| 需求理解 | 价值定位→场景→主流程→核心取舍与范围，结合成功情境复核 | 需求说明 | 从第一轮铺开实现参数，问完全部主线才建议出稿 |
| 方案设计 | 基于需求约束提出可行方案、给推荐理由、比较关键取舍和影响 | 总体／专题设计方案 | 让用户先自己决定所有技术和交互细节 |
| 规格整理 | 将已选方案转成明确行为、数据规则、异常和验收情境，复核一致性 | 需求规格或指定章节 | 再次收集全部目标；把无依据细节写成已确认要求 |
| 变更复核 | 先理解变更目标，对照固定来源分析实际影响，提出局部修改 | 影响说明或修改候选 | 因上游变化自动覆盖全部文档，或凭局部材料宣称全文一致 |

每一阶段采用独立指引引用和版本。阶段选择来自用户开始的工作或接受的阶段切换建议，不能用需求状态自动替用户切换。首批不提供用户自行配置复杂指引引擎；用户通过调整目标、主题和方案来纠偏。

### 5.14 页面反馈和电影例子的推进轨迹

页面在AI区提供可折叠的“讨论进展”，默认只显示当前主题、已形成的结论和建议下一步；完整路线、依据及待定项展开查看。使用正式业务标签，不把guide_key等内部字段堆到用户主流程。

出稿建议展示拟生成文档、范围与待定项，提供生成／继续讨论入口。主题自动衔接可见，用户可调整方向；不能用大纲完成百分比暗示业务已经完整。

| 用户信息或动作 | 本轮设计工作 | 主行动及持久结果 |
| --- | --- | --- |
| 提出记录、评分、电影推荐小程序 | AI先给“记录→偏好形成→推荐→反馈”的推荐闭环，并标明其建议身份 | PRESENT_DESIGN；建立路线和已有结论，不询问全部章节 |
| 强调“猜得准” | 比较“熟悉偏好优先／偏好与探索平衡／探索优先”，说明推荐理由 | ASK_DECISION；聚焦推荐价值主题，不跳到数据库和更新周期 |
| 说明三部电影分别承担最匹配、冷门和探索角色 | 解释该设计如何满足目标，关联价值、流程及成功情境主题 | SUMMARIZE_TOPIC；同一回答补足多个成果，不重复问核心目标 |
| 已能表达目标、主要流程及初步范围 | 建议形成需求说明，列出评价方式等待定点 | RECOMMEND_DRAFT；保存建议，等待用户，不生成稿件 |
| 表示先继续讨论 | 尊重暂缓出稿，处理用户指定主题 | 保存处置，不每轮重复催促生成 |
| 明确同意生成 | 转入已授权生成任务，采用实际绑定材料 | 按S-05及届时采用的工作稿生命周期执行，不重新收集一遍全部需求 |

这份轨迹是未来验收输入，不是本轮新执行的模型对话。前端应能展示轨迹中的动作和依据，后端应从Requirement讨论状态和既有运行／消息恢复相同路线、版本和处置。

### 5.15 上下文的具体装配顺序和去重

沿用现有model_context读取、context_builder组装、context_projection投影、计数及LLMUse审计链路，扩展这些模块的输入，不另建context-build／memory-search／token-estimate接口或平行上下文服务。

| 步骤 | 从现有承载读取什么 | 发送规则 |
| --- | --- | --- |
| 1. 固定本轮事实 | GuideRun接受时的用户动作、Requirement讨论版本、目标／来源文档版本和读取范围 | 先固定快照再组装；后来编辑不改变历史请求 |
| 2. 加载阶段指引 | 冻结Function所引用的当前阶段指引与必要输出约束 | 不把四阶段全部指南和完整设计模板每轮一起发送，输出约束不重复展开 |
| 3. 加载原始目标与长期依据 | 既有用户消息、正式回答及Requirement讨论状态中的有效来源索引 | 原始需求和有效决定不依赖最近10条窗口；明确修正、暂缓及排除继续有效 |
| 4. 给模型整体位置 | 当前阶段、各主线简短结论、当前焦点和跨主题硬约束 | 是短总览，不复制全部主题正文、权限元数据或审计资料 |
| 5. 给当前问题必要材料 | 当前主题成果要求、相关原话／回答，以及选定文档原文 | 局部任务只发送相关区块与必要上下游约束；读取不赋予写入权限 |
| 6. 补充近期交流 | 现有消息读取窗口中对理解本轮有用的记录 | 与已发送原始目标／依据按消息身份去重；不把全量历史当长期记忆 |
| 7. 放入本轮输入 | 实际问题、用户选择及填写内容、程序确定的操作模式 | 放在靠后位置；正式回答带原问题／所选名称／填写内容，不重复回传全部未选项 |
| 8. 计数、检查、保存 | 完整待发送消息及已有计数／预算机制 | 检查真正将发出的完整请求，保存实际分区和读取清单后才调用聊天模型 |

原始材料在请求中只放一份，其他位置保留短引用。文档去重以document_id＋content_version＋block_id为依据；不能仅凭文本相似或含占位符就删除用户已填写内容。新稿生成携带该类文档所需结构；局部修订携带对应规则；完整模板只在任务确实需要时装载。

长期索引中的内容标明USER_STATEMENT、USER_ADOPTED、AI_PROPOSAL等来源身份；模型摘要不能自动升级为用户采用。存在冲突或摘要不足时按引用补读原消息／卡片／版本内容，不再让用户重新回答已经提供过的信息。

近期消息和可选背景不足以容纳时，可按明确策略减少并记录实际未携带范围；原始目标、当前明确指令、有效硬约束、必要目标原文不可静默省略。必要材料自身超预算则停止聊天调用，提示缩小任务或明确分批，不以丢依据换取看似顺畅的回答。

固定系统规则和资源尽量保持顺序稳定，变化内容靠后；复用和缓存不替代真实材料选择。每个分区只展示实际已有计数，缓存计入输入不重复相加，缺失值保持未记录。私有ContextBasis保留完整检查依据，模型不接收整套私有权限和审计。

### 5.16 流程减步与接口复用

首轮讨论直接复用guide-runs，返回理解／设计、少量选项和进度；用户回答走原responses或continue，不能先要求创建一项任务再聊天。

点击明确出稿建议，在一次接受请求中记录正式回答和GuideRun执行依据，随后模型生成；不串联“建立任务→建立建议实体→申请授权→创建运行”四次请求。模型成功后的保存由原结果提交链路处理，不要求前端代写一遍正文。

用户读稿反馈先由AI解释或提出建议，明确要求更新才执行单次修订；跨文档合入继续用现有批次决定／完成。状态、阶段收束、版本确认等程序操作不再经过一次模型问答。

切换阅读文档不改任务绑定、不清空输入、不触发模型或计数。失败保留输入及已产生结果；幂等核实不变成新付费调用。首批没有额外规划模型、摘要模型或后台反复评估循环。

| C15-02 切换需求状态 | PATCH /api/v1/requirements/{requirement_id} | 新状态字段、预期状态版本及用户事件；旧complete／reactivate语义保留 | 无 |

| C15-04 消息／回答 | POST guide-runs、现有continue和消息responses | 保存原输入、真实回答和GuideRun；普通响应更新需求的有效进度 | 有；程序处置除外 |
| C15-05 生成／明确修订／仅建议 | POST /requirements/{requirement_id}/guide-runs及消息responses | 扩展动作、目标和结果模式，接受事务内保存执行依据，不先请求授权接口 | 有 |
| C15-06 人工编辑 | 既有manual-draft开始／保存／完成／取消 | 增加明确document_id，沿用会话、自动保存、来源和未知结果保护 | 无 |
| C15-07 采用候选 | 既有suggestion decision及suggestion-batch complete | 扩展真实目标、来源与单元关系，不另建candidate／apply API | 无 |
| C15-08 确认版本 | 文档元数据PATCH，见6.5必要新增项 | 引用真实Revision，记录用户事件；不生成新正文或新确认根 | 无 |
| C15-09 阶段收束 | 消息responses的明确程序处置用途 | 更新需求讨论状态并保存用户动作，不新建stage-close服务 | 无 |
| C15-10 文本比较／语义复核 | Revision读取＋现有预览；语义复核走guide-runs的REVIEW扩展 | 返回真实覆盖范围；不为分析另建模型入口 | 文本比较无；语义复核有 |
| C15-11 文档管理 | 框架创建／元数据见6.5；回退沿用Revision读取和编辑提交 | 不把创建空框架伪装为人工草稿或模型调用 | 无 |
| C15-12 取消／重试 | /guide-runs/{guide_run_id}/cancel及retry | 沿用实际运行和用户动作、原范围及幂等，不复制执行系统 | 取消无；明确重试可能有 |

同一用户动作只需一次接受请求。例如点击“生成”直接走现有responses或guide-runs扩展：保存用户动作、固定材料、接受运行是同一程序事务，不要求前端先创建任务、再创建授权、再创建运行。

### 6.2 查询优先扩展现有投影

| 逻辑查询 | 首选既有读取 | 返回边界 |
| --- | --- | --- |
| Q15-01 需求和文档导航 | GET /requirements/{requirement_id} | 新契约返回文档摘要及讨论摘要，不夹带所有正文 |
| Q15-02 文档及版本 | GET current-document、manual-draft、revisions及单Revision | 多文档模式显式指定document_id；current-document读取指定文档当前版本，不更改旧默认 |
| Q15-03 指引和讨论进展 | 需求详情的可选讨论展开投影 | 需要时返回完整相关主题；默认短摘要，不另建outline／topic CRUD |
| Q15-04 消息、运行和实际调用 | 既有messages、guide-runs、model-calls | 增加文档／阶段筛选，保留按需读取快照和可见性轮询 |
| Q15-05 出稿建议、候选及来源变化 | 既有结构化消息、suggestion-batch及文档来源投影 | 建议由message_id＋card_key定位，候选仍用batch_id／suggestion_id |

阶段指引由既有ResourceCatalog冻结给运行，前端查看通过讨论投影／实际请求快照，不单独引入指引管理服务。查询、搜索、复制、切换文档和轮询不启动模型或计数。

### 6.3 标识、执行依据与契约更新

沿用requirement_id、document_id／content_version、revision_id、guide_run_id、llm_use_id、message_id、batch_id／suggestion_id。新增discussion_version以及需求内phase_ref／topic_ref；出稿建议用message_id＋card_key定位。取消独立task_id、outline_id、proposal_id、authorization_id和candidate_id这些默认新增业务身份，避免多份数据记录同一个事实。

新建目标在GuideRun执行依据快照中固定名称、业务类型、新建模式和来源范围；已有目标固定document_id和预期版本。模型不能替换绑定目标，也不能把建议或推荐变成用户接受。

命令沿用Idempotency-Key和既有命令核实机制，不另造operation_token或重试SDK。响应区分已接受、实际模型返回、解析和应用结果；未写入不拿后来最新版本冒充本次写入结果。

现有前后端严格校验字段，新1.5请求／响应在原HTTP边界与客户端同步更新，不开发legacy协商、旧字段回退或平行路由。用户已取消旧测试数据迁移；新版明确document_id等字段，具体契约见详细规格第6章。

多文档模式显式指定目标，不承担旧消息／运行恢复。既有精确事实CONFIRM能力的原文／行范围校验继续复用，新出稿接受／阶段收束使用不同卡片用途，不能凭外观相同复用事实写入分支。

部分合入继续由批次保证依赖和原子性；仅独立单元可部分采用。剩余项保留旧基准，复核现文后再采用，不静默重新生成。

### 6.4 失败与流畅性

| 情况 | 程序处理 | 用户继续路径 |
| --- | --- | --- |
| 操作尚未明确 | 讨论继续，AI提供方案和具体建议；不扩大写入 | 在已有建议上接受或补充，不要求反复配置全部上下文 |
| 版本／讨论状态过期 | 保留输入、候选及返回，不覆盖新结果 | 重新读取并复核；不自动请求模型 |
| 目标关闭／归档／活动占用 | 显示实际对象和原因，不静默终止 | 完成、取消、恢复或只读查看 |
| 模型格式／进度无法解析 | 原始回复仍可读，无效进度／正文不应用 | 修改目标或人工处理，不自动修复调用 |
| 预算不足或供应方失败 | 区分未发请求与已发失败，保存实际用量及原因 | 缩小范围、明确分批或主动重试 |
| 接受／提交结果未知 | 保留原幂等身份 | 查询或重放原请求，不换新身份重复生成 |
| 取消与成功竞争 | 按实际事务先后判断 | 已成功不冒报取消，取消成功后迟到返回不再写入 |

不把普通答题、接受方案、决定出稿、确认版本叠成每轮多个弹窗。用户明确要求生成／更新一次即可启动对应操作；精确采用和阶段收束由程序处理，不再请求模型“确认一下”。

### 6.5 实际路由复用审查

以下路径已对照7个现有api.py静态核查，公共前缀为/api/v1；“扩展”不表示现在代码已经支持新版参数。

| 用途 | 已有方法和路径 | V1.5处理 |
| --- | --- | --- |
| 创建／读取／修改需求 | POST /requirements；GET／PATCH /requirements/{requirement_id} | 复用，扩展讨论状态和新契约；原GET列表与旧生命周期入口保留 |
| 文档当前内容 | GET /requirements/{requirement_id}/current-document | 扩展document_id选择；新版必填document_id，不再隐式选择唯一CURRENT |
| 人工编辑 | GET／POST／PUT／DELETE /requirements/{requirement_id}/manual-draft；POST .../manual-draft/complete | 复用并显式绑定document_id，沿用草稿会话 |
| AI接受／继续 | POST /requirements/{requirement_id}/guide-runs；POST /guide-runs/{guide_run_id}/continue | 复用动作／范围扩展，不为聊天、规划、评估、生成各造入口 |
| 正式卡片回答 | POST /conversation-messages/{message_id}/responses | 扩展卡片用途；讨论回答走AI，生成接受走一次运行接受，阶段收束走程序 |
| 运行与调用观察 | GET /requirements/{requirement_id}/guide-runs；GET /guide-runs/{guide_run_id}；GET .../model-calls；GET /model-calls/{llm_use_id} | 复用分页、轮询和懒加载，扩展新快照分区 |
| 取消／重试 | POST /guide-runs/{guide_run_id}/cancel；POST .../retry | 复用，显式动作不复制任务服务 |
| 候选处理 | GET /suggestion-batches/{batch_id}；PUT /suggestions/{suggestion_id}/decision；POST .../complete及discard | 复用既有批次流程，不增加通用apply服务 |
| 历史内容 | GET／POST /requirements/{requirement_id}/revisions；GET /revisions/{revision_id} | 扩展document_id、CONTENT类型及筛选，保留旧标记行为 |
| 评论 | 既有comments及comment-index路径 | 保留，适配文档归属，不重建评论接口 |

详细规格首批采用以下两种真正缺少资源入口的新增方法，而不是按C15数量新增接口：

1. POST /api/v1/requirements/{requirement_id}/documents：用户新建空白／框架文档。现有创建需求或人工草稿不等于创建另一份工作文档，不能错误复用。
2. PATCH /api/v1/documents/{document_id}：名称、归档／恢复、引用已有Revision进行版本确认等文档元数据。原有接口没有独立文档元数据修改能力；正文编辑仍走原编辑／运行路径。

文档导航列表先由需求详情摘要返回，正文／历史按既有入口显式选择；不为方便再增加独立document-list、work-task、outline、topic、proposal、authorization、context-build、token-estimate系列接口。

新增或放弃上述任一接口前必须给出“现有入口→不足→最小扩展”的证据。也不为凑零新增接口，把不同资源硬塞成一个允许任意action的万能PATCH。
