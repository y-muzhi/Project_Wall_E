## 1. 系统目标、版本范围与依据

### 1.1 本版本目标

WALL-E在需求下已有多文档与文档级AI协作能力。V2.1本次增量让每份文档具备可追溯的形成路线：清楚说明正在讨论哪里、预期形成什么、哪些内容已经真实保存、尚有哪些缺口，以及如何继续推进。

AI负责理解目标、组织路线、提出方案、评估实际成果和建议下一步；用户决定采用正文、重大范围变化、结束步骤及暂缓／放弃等取舍。程序负责真实身份、来源、权限、版本、事务和回执。三种责任不能用模型文字相互替代。

这份大纲限定本次“文档形成主线与阶段性写入”增量。V1.5既有文档生成／编辑／版本／确认及V2.0其他模块按其实际基线承接，不因本文存在被宣布完成、重设计或验收通过。

### 1.2 首版包含与排除

| 包含 | 确定边界 |
| --- | --- |
| 单文档形成路线 | 目标、动态步骤、预期成果、依赖、讨论定位、历史及来源 |
| 持续讨论与支线 | 普通说明／主线推进／已有承接／真正独立分支分开，支线有出处与返回点 |
| 阶段性写入 | 独立可用内容形成后可提出精确只读预览，用户确认原样应用 |
| 路线维护与调整 | 既定目标内细化／重排，重大调整展示影响后由用户采用 |
| 用户结束与后续继续 | AI建议、用户结束；允许带遗留；保留历史并支持明确重开 |
| 内容变化后复核 | 关联追溯与AI充分性分开，在相关正常讨论中按需复核 |
| 恢复与增长 | 暂缓问题恢复、已有结果支线继续、在途完整目标、历史分页与同文档持续形成 |

本次不增加项目级自动跨文档同步或依赖编排，不引入工单自主编码协作，不增加“写入并结束”联合按钮、预览内编辑器或后台自动历史压缩。跨文档对齐仍由用户维护；原显式GENERATE／REVISE及候选审阅保持原职责。

R01—R08的已确认原则、Q03／Q04的本会话确认，以及B01—B03闭环补充均已纳入本文。正文表达当前规则，不要求读者按修订时间拼接多个“下一步”。来源与摘要见附录A。

## 2. 共同规则、责任与事实

### 2.1 六项相互独立的事实

| 事实 | 正式依据 | 不能混同的行为 |
| --- | --- | --- |
| 当前正文 | 实际Markdown／BlockState、content_version及Revision | 对话说过、AI提出或用户认可想法不代表正文已改 |
| 步骤状态 | 真实开始／暂停／结束／重开／放弃事件 | 讨论焦点、AI评估及写入次数不决定步骤状态 |
| 当前讨论目标 | 所属文档、步骤、支线及明确进入／恢复意图 | 查看详情不是选择讨论；本地下一轮目标不是在途运行依据 |
| AI评估与建议 | 带实际读取覆盖和版本的Assessment／Recommendation | 建议结束不等于用户结束，SUFFICIENT不等于文档确认 |
| 提案与采用 | 不可变卡片、实际用户动作及程序结果 | 保存卡片不授予正文写权限，收起不等于暂缓 |
| 历史与当前匹配 | 不可变事件／Closure／原始关联，以及当前投影 | 曾经写入不代表当前仍在；复核不回写旧完成历史 |

### 2.2 用户、AI和程序的权限

- AI可以在既定目标内补充步骤、细化描述、调整顺序及必要关系，并保留依据；不借细化扩大目标、删原要求、取消步骤或改用户决定。不能判断是否越界时提出方案。
- 改变目标、取消／替换步骤、改变既定成果要求、重开、暂缓／放弃和恢复用户处置均由明确用户动作产生。AI可整理方案，用户无需填写内部映射表。
- 普通讨论可维护有效进展、提出卡片和评估，但不写正文、不完成步骤、不改需求业务状态。确认精确写入由程序执行，不再生成不同文字。
- 真实归属、权限、来源、版本和事务由程序执行；Schema、提示词、摘要或模型宣称都不能替代程序保证。

### 2.3 版本、幂等与操作范围

| 标识 | 含义与变化 |
| --- | --- |
| D：discussion_version | 所属文档讨论／用户命令并发依据；形成写入与其同事务，每个实际变化事务至多加1 |
| F：formation.version | 路线、焦点、关联、评估或提案处置有实际变化的版本；同批多个事件只加一次 |
| V：content_version／Revision | 真实正文变更的版本；只规划、切换、恢复或结束不增加V |
| Goal.version | 文档目标的实质变化；旧用途重新核对 |
| Step.definition_version | 特定步骤的成果要求／依赖等实质变化；纯展示改名、排序和生命周期变化不机械递增 |

新写动作携带最新已读取的D，并使用原Idempotency-Key机制。先查同输入的成功回执，命中即重放，再校验新动作当前条件；同key异输入拒绝。无实际状态变化不制造版本、事件或Revision；幂等成功重放也不重复产生副作用。

写操作沿原需求级互斥与IDLE规则，不因文档局部引用而自行增加并行写通道。用户可在占用期间查看或保留下一轮目标，不能据此绕过实际写入和运行占用。

## 3. 业务对象、关系与状态

### 3.1 对象职责

| 对象 | 内容与归属 | 关键约束 |
| --- | --- | --- |
| WorkDocument／Revision | 既有文档及真实内容版本 | 复用原文档根与内容提交，不能另建平行正文事实源 |
| FormationState／Goal | 每文档一条逻辑形成路线、用途与版本、焦点、局部身份高水位 | 逻辑聚合不要求终身全量JSON持久化；无路线与未加载／损坏分开 |
| Step／ExpectedResult | 动态步骤、标题、定义版本、CONTENT或ANALYSIS成果、依赖及状态 | 稳定身份；可跨旧指导阶段，不必等同文章章节；未取消步骤形成有序有效路线 |
| Branch | 独立讨论问题、相关性、状态、结果及来源 | origin不可改；return表示当前处理／返回步骤，显式调整才迁移 |
| Issue | 未解决问题、影响、当前步骤／可选支线、用户处置 | 用户暂缓／放弃不能由AI默默撤销；双向归属一致 |
| ArtifactLink | 步骤成果与真实Revision／区块及写入或关联事件的关系 | 原始来源不变，当前匹配另核实；复用已有内容不是本轮新写 |
| Assessment／Recommendation | AI充分性判断和下一步建议、实际依据及覆盖 | 与生命周期分开；不修改旧判断冒充看过新全文 |
| WriteProposal／PathProposal | 原ConversationMessage内不可变精确内容或路线调整卡片 | 身份为message_id＋card_key；新内容用新卡，不原地替换 |
| FormationEvent／Closure | 原审计上的真实变化、完成时事实快照及来源 | 追加且不可变，同批版本一致；保留旧目标／定义／结果与原因 |
| GuideRun／ProgramReceipt | 原模型执行快照和程序动作事实回执 | 调用结束不等于业务完成，成功回执不是当前最新状态 |

旧阶段指引仍负责指导维度，topic仍是讨论主题；Step.topic_refs关联它们，不把旧mainlines直接复制为步骤或状态门禁。继续复用现有messages、cards、content、progress、audit和idempotency，不因逻辑名称增加平行业务根或服务。

### 3.2 状态与讨论目标

| 对象 | 状态 | 转换规则 |
| --- | --- | --- |
| 步骤 | PLANNED／IN_PROGRESS／PAUSED／COMPLETED／CANCELLED | 自动首步；实际接受讨论或显式操作才开始／恢复；用户结束、重开或放弃；CANCELLED重新采用需新身份 |
| 支线 | OPEN／RESOLVED／DEFERRED／DROPPED | 有真实结果才RESOLVED；用户暂缓／放弃；DEFERRED或RESOLVED可明确继续为OPEN；DROPPED不原地复活 |
| 问题 | OPEN／RESOLVED／DEFERRED／DROPPED | 有依据解决；用户明确处置；DEFERRED可同身份恢复；DROPPED重新提出建有旧来源的新问题 |
| 成果匹配 | CURRENT／NEEDS_REVIEW／REMOVED | 只表示当前内容可追溯程度，不表示语义充分；全部关联消失才REMOVED |
| AI评估 | SUFFICIENT／GAPS_REMAIN／UNCERTAIN | 反映实际已读内容与要求，展示是否陈旧；不决定用户结束权限 |
| 写入提案处置 | PENDING／APPLIED／NO_CHANGE／DEFERRED／SUPERSEDED／INVALIDATED | 来自真实采用／处置或当前用途有效性；needs_revision另表示用户已要求调整 |

current_step_ref是唯一讨论节点指针，允许为空或指向同文档历史节点；IN_PROGRESS不要求唯一。active_branch_ref若非空必须指向OPEN支线，且其return为当前步骤。可切回已结束／已放弃节点讨论而不重开；已放弃节点不画回有效路线。

SUBMITTING／UNKNOWN／ERROR等是前端请求状态，不混入业务生命周期或提案持久状态。

### 3.3 关系和来源不变量

步骤／支线／问题／成果局部身份不跨文档复用，不回收历史编号；模型新项先声明临时引用，程序核实后统一分配真实身份。依赖及替代关系不能循环，当前依赖不得悬空指向已放弃前置。

问题的所属步骤与步骤的问题关系一致；仍OPEN且关联同支线的问题归属须与支线当前返回点一致。历史origin、来源消息、原Revision和旧Closure不因迁移而重写。

CONTENT成果以真实文档内容为依据；ANALYSIS可用有来源的分析结果，无需伪造正文。两种类型不能在结束时偷偷互换。关联、要求去向和新写入是三个不同事实。

## 4. 完整业务流程与闭环

### 4.1 空白或已有文档建立路线

1. 打开页面、读取、查看历史不调用模型、不自动建线。无路线显示所属业务空态；已有正文可正常阅读编辑。
2. 用户通过原讨论输入说明形成目的，明确发送一次DISCUSS。目的不足时AI解释缺口或提供必要选择，不硬造路线；普通术语解释或无关聊天不强制建线。
3. 目的足够时，同一正常回复可返回INITIALIZE_PATH。程序核实真实用户依据及步骤／成果／临时引用，建立F1，直接将首个有序步骤设为IN_PROGRESS及当前讨论，其余PLANNED；不追加开始按钮或第二次Chat。
4. 已有正文只能按实际已读区块关联，事件标“关联已有内容”；不能声称本轮写入或推断旧需求已完成。路线首次三至五步只是表达建议，不是凑数限制。

### 4.2 正常讨论、自由切换与在途目标

用户可继续讨论或选择任一步骤“在此讨论”。切换只改讨论目标，清除不匹配支线，不暂停、完成或重开旧节点，不受前置依赖门槛限制，不填跳转理由。仅点标题查看详情不改变目标。

实际接受对PLANNED／PAUSED节点的讨论时记录其开始／恢复；已结束／放弃节点讨论保持旧状态。明确选择整份文档讨论时步骤与支线均为空。

完整目标由discussion_step_ref、discussion_branch_ref、branch_intent表示：整文档为全空；仅步骤时支线和意图为空；OPEN支线为真实处理步骤＋支线＋ENTER；用户明确继续暂缓或已有结果支线为对应步骤＋支线＋RESUME。

在途期间按文档保留最后一次明确的下一轮完整目标，不改变原运行依据、不取消旧调用或立即恢复支线。下一次发送或运行结束后选择生效时核实最新状态，同事务保存所需恢复与目标。原ENTER目标若已非OPEN，不自动升级为RESUME；保留输入、说明变化、由用户重新选择。

本轮回复／提案／评估均属于接受时冻结的步骤与支线，显示相应归属。晚到结果只更新原文档，不抢下一轮目标、不清其他文档草稿。

### 4.3 支线判定、返回与继续

模型在同一次正常讨论中结合Goal、当前预期成果、真实已读正文、既有路线／支线、当前输入及必要上下文判断：普通解释直接回答；推进当前成果继续主线；已有步骤／支线可承接则复用；只有相关且需要独立探讨或留待跟踪的问题才登记支线，并说明问题、影响、触发来源和返回点。不确定时保守留在正常讨论，不增加分类Chat。

支线标题点击只查看；“讨论此支线”原子选择其真实处理步骤与OPEN支线，无须先结束／暂停别的步骤。返回主线只清支线焦点，不宣称解决。已有结果需真实结果摘要和来源，正常总结影响并回到约定主线；不按轮数强制返回，不自动写正文或结束父步骤。

| 用户后续意图 | 确定结果 |
| --- | --- |
| 暂缓／放弃OPEN支线 | 保存真实用户处置及原因；清对应焦点，保留未决影响与来源 |
| 继续DEFERRED支线 | 同身份恢复OPEN，追加BRANCH_RESUMED；可同时选择进入 |
| 继续同问题的RESOLVED支线 | 同身份OPEN，追加BRANCH_REOPENED；旧结果保留在历史，当前结果置空，另显“上次结果” |
| 继续DROPPED支线或提出不同问题 | 不覆盖旧放弃／结果；建立有旧来源的新支线 |

恢复请求明确step_ref／branch_ref和enter_after_resume；return须有效且属于同文档未放弃步骤，可以是已结束步骤。恢复不自动重开父步骤、不写正文、不Chat。原返回点已放弃时先由用户明确调整返回点及相关问题归属；无合法去向则拒绝，不能猜第一步。

### 4.4 问题暂缓与恢复

用户明确暂缓／放弃问题，保留原因与事件。DEFERRED的问题可通过“继续处理”执行RESUME_ISSUE，同身份／描述／来源及有效归属恢复OPEN；原暂缓留历史，当前处置指针／原因不再冒充当前决定。不触发正文修改、父步骤重开或相关支线恢复。

归属已放弃时，用户在同一次路线调整明确迁移与恢复；如关联OPEN支线，同批核实返回点一致。任一部分失败整批回滚。OPEN恢复请求按幂等／无变化处理；RESOLVED不能借恢复暂缓动作伪装未解决，DROPPED不复活原身份。

### 4.5 阶段性精确写入

讨论形成逻辑独立可用的一段、多段、列表或表格后，AI即可主动提出STAGED_WRITE，无需等节点结束，也不要求每轮出卡。原显式GENERATE／REVISE继续原直接保存语义；本流程新增的是普通讨论中的精确提案采用。

预览说明目标文档／步骤／成果、实际基准版本、作用范围及完整拟写正文或差异。预览只读；用户可确认原提案、明确发送调整或暂不写入。手动改正文使用既有编辑能力，不新增第二套编辑器，不允许客户端替换卡片中的精确文本。

| 写入种类 | 前提与行为 |
| --- | --- |
| FILL_EMPTY | 真实解析无业务区块，卡片带完整拟写Markdown；程序再次核实空状态并保存同文档的新Revision |
| PATCH_EXISTING | 有真实区块／章节，按精确原文、范围及补丁应用，保留模板与标题保护 |

固定框架有标题／占位内容不算空文档。无法精确表达时缩小范围，不以覆盖全篇代替小范围修改。

用户确认后，程序从不可变卡片核实最新D、目标V／Revision、Goal／相关定义、原文／范围、来源、占用及权限；同事务保存正式回答、正文／Revision、真实DocumentEffect、成果关联、提案处置、事件及成功回执。任何失败无半份保存；不再Chat，不自动结束步骤。

正文未变记NO_CHANGE，不造新Revision；合法新关联或正式消费仍可有真实D／F变化与事件。原文相同、摘要相似或“用户已确认”都不能绕过当前版本／来源校验。

### 4.6 提案暂缓、调整与有效性

暂不写入通过原生命令保存DEFERRED，不提前消费单卡apply机会；关闭预览只是收起。恢复需当前用途和基准仍匹配，不自动生成新内容。

“继续调整”明确proposal_ref和proposal_intent后由用户发送DISCUSS。实际接受才标needs_revision，禁用已被用户反对的旧内容；新卡成功保存才SUPERSEDED。模型失败保留旧卡和输入，可继续调整或明确撤回；撤回须重新核实当前用途／原文／来源，不能偷偷重基。

纯讨论焦点或无关F变化不单独使适用提案失效；正文V、目标／成果定义、来源或实际用途变化继续核实并重新准备。路线卡保存导致F变化时保留模型原basis与程序实际发布依据，不把新F伪装成模型已读过的旧输入。原卡不可改写。

路线提案purpose为FORMATION_PATH_CHANGE，只有用户采用后才调整路线；同一回复不得先带非空formation_delta把待确认路线提前修改。阶段性写入卡不得与同轮目标步骤实质定义修改冲突。DISCUSS的进展、形成和新卡构成一个原子结构单元，任一非法不能先保存半份可执行卡。

### 4.7 路线细化、拆分、合并与放弃

正常目标内的AI补充／细化／重排直接维护并留事件；改变目标、取消／替换步骤或改变既定成果要求时展示完整影响，由用户明确采用。人工调整仍有编辑、预览及保存入口，不被强制改为AI操作。

预览必须包含节点及顺序变化、旧成果要求去向与真实内容复用、问题及支线去向、受影响提案／评估、当前焦点是否清除。未写成果仍标未写，要求承接不能冒充内容落地。

- 拆分／合并未结束步骤时保留旧身份为CANCELLED，建立新步骤及replaces关系。
- 被取消步骤每项原成果恰好有REPLACED或明确NOT_REQUIRED去向；类型不能借映射偷换，语义取舍由用户核对。CONTENT复用仍需核实已有正文并新建关联，不改旧Artifact或造新写入。
- 未决问题、OPEN支线及后续依赖必须有合法去向；支线origin不变，return可明确迁移；问题／支线双向一致，当前图无环。
- CANCEL_STEP只作为完整ADJUST_PATH内变化，不保留独立简化取消入口。已结束节点不直接拆并；可新增后续步骤或明确重开，切回讨论本身不重开。
- 同一批全部验证后原子保存；预览只读、不分配正式身份，不占用模型或消费卡片。基准变化保留草稿并重新核对，不自动换版本提交。

### 4.8 用户结束、遗留与重开

AI可整理实际成果、遗留及推荐节点的简短收束建议，用户点“结束步骤／结束并继续”，不二次弹相同确认、不额外Chat。没有AI建议时仍允许用户主动结束，程序按真实状态补齐快照，不要求手填内部覆盖表。

PLANNED／IN_PROGRESS／PAUSED的未放弃步骤都可明确结束。完整性以提示为主；未写、待复核或无法核实的成果记OUTSTANDING，未明确处置的问题／支线记KEEP_OPEN，保留原要求和归属，不自动暂缓、放弃或转交。直接结束PLANNED不伪造开始事件。

Closure保存当时Goal／定义／Revision、真实成果与遗留、用户来源及选定下一步。明确转交／暂缓／放弃仍校验合法性；所有处置、双向关系、结束及可选下一步在同事务。缺真实身份、版本冲突或伪造证明仍拒绝，不能以“允许结束”绕过程序保证。

“结束并继续”直接定位推荐节点，不发送新讨论；未结束目标可开始／恢复，历史目标只定位。没有下一步时保存结束结果；路线所有步骤结束不自动确认文档定稿或改变需求状态，待处理事项继续可见。

已结束节点可继续讨论并明确采用仍适用的写入提案，无需为写入先重开；原Closure不回写。需要重新推进时用户明确REOPEN_STEP，旧完成记录保留，其他节点不隐式暂停。已放弃节点重新采用使用新身份，不能抹掉旧取消事实。

### 4.9 正文修改与成果复核

人工编辑、原REVISE、候选应用、历史恢复及新卡应用均经统一内容提交，核对实际受影响成果；无关区域修改不使全部成果失效。身份和原文仍可证明匹配时关联继续有效，部分改变／无法证明对应关系提示NEEDS_REVIEW，全部消失才REMOVED。

下一次涉及该成果的正常讨论中，使用实际已读最新正文、原成果要求及变化依据按需复核。程序核实可追溯关联，AI判断语义充分；材料未读完整或无法核实则保留待复核，无关聊天不自动清提示。不为复核后台发Chat，不要求每改几个字逐项确认。

新关联保留原始来源，不能凭相似文本复活已删除身份或把重新关联说成本轮新写。关联已核实但语义有缺口时分别显示具体缺口，不混用同一“需复核”标签。复核不改正文、不自动重开；旧评估保留原依据，并显示陈旧原因或确实可证明的覆盖未变。

### 4.10 失败、取消与恢复

| 情况 | 确定行为与用户恢复 |
| --- | --- |
| 结构／身份／范围／来源或版本校验拒绝 | 不提交半份业务，保留草稿／预览及具体原因；明确已知未成功后才能创建不同输入的新动作 |
| 写入超时／提交结果未知 | UNKNOWN保留原method／path／body／key，先核实原动作；不能直接认失败再写一次 |
| 已成功但后续读取失败 | 显示“已保存，显示待刷新”，恢复只刷新读取；旧成功回执不覆盖更新快照 |
| AI失败／中断或用户取消运行 | 原已保存成果保留，沿原运行取消／租约终态核实；输入可恢复，下一次模型调用由用户明确发起 |
| DISCUSS结构单元非法 | 保留合法可读回复及pending，进展／形成／新卡一起拒绝，明确未应用，不修复性Chat |
| 显式GENERATE／REVISE正文合法但讨论结构非法 | 主结果按原独立职责保存，说明组件结果；正文引起的强制成果匹配仍随正文事务维护 |
| 目标在其他页变化／晚到回执 | 不覆盖当前输入或另一文档选择，刷新后明确核对；不暗中恢复／重开／改目标 |
| 状态损坏／来源不可读 | 明确损坏或来源不可用，限制依赖该事实的动作；不当作无路线自动覆盖，不伪造原话 |

## 5. 页面、交互与浏览器状态

### 5.1 页面布局与阅读入口

复用所属文档进展面板承载形成路线，不增加平行任务看板或长期占据对话输入区。默认纵向有序节点、当前讨论标记、支线缩进、独立已放弃历史入口；窄环境单列，展开视图在空间允许时路线／详情分栏。

节点显示标题、真实生命周期、少量成果／待复核提示及最近关键事件。当前讨论与进行中分开，已放弃历史不接回有效主线实线；状态有文字或图标辅助，不能只靠颜色。标题查看、定位当前、选择讨论分别独立。

详情为概览／事件记录／关联内容，可看创建／实际开始／写入／结束／放弃及其来源、当时版本和当前对应位置；从未开始就没有开始事件。来源不可读取保留身份与原因，不拿当前文本替代。

### 5.2 操作与反馈

| 区域 | 必须可达的操作与反馈 |
| --- | --- |
| 路线及节点 | 规划、在此讨论、明确暂停／恢复／结束／重开、调整路线；依实际状态和占用说明禁用原因 |

### 5.3 特殊状态与可访问性

初始加载、已读空数据、正常内容、失败／无权限、筛选无匹配／分页越界、恢复后状态分别展示。成功空区域复用公共EmptyState，图标／短文案由业务区域提供；加载／错误／未选择／未加载不当空态。

SUBMITTING／UNKNOWN／保存成功显示待刷新有各自说明与恢复入口；历史页失败不清已有路线。晚到消息不抢焦点、滚动或输入，隐藏／切文档不丢原命令，不以查看触发模型或正文变化。

键盘可达、弹层关闭返焦点、减少动态效果、窄宽与多行布局、真实禁用／处理中／人工编辑／历史／占用状态均为后续实际页面验收条件。旧离线原型仅是已认可方向，不能替代真实产品证据。

## 6. 接入边界与操作契约大纲

### 6.1 入口职责

沿现有/api/v1前缀，软件V2.1不等于HTTP版本变更。复用已有入口优先，新增只读／预览能力不产生平行写通道。

| PATCH requirements/{id} | 严格FORMATION命令联合，最新D及原幂等；原生操作不创建GuideRun |

### 6.2 操作集合与边界

原生FORMATION共15种：START_STEP、PAUSE_STEP、RESUME_STEP、SWITCH_STEP、COMPLETE_STEP、REOPEN_STEP、ADJUST_PATH、ENTER_BRANCH、RETURN_FROM_BRANCH、DISPOSE_BRANCH、RESUME_BRANCH、RESUME_ISSUE、DEFER_WRITE_PROPOSAL、RESUME_WRITE_PROPOSAL、WITHDRAW_PROPOSAL_ADJUSTMENT。动作含义由第4章定义，统一幂等、归属、锁、版本与事务；无第二次Chat。

ADJUST_PATH的14种变化为SET_GOAL、ADD_STEP、RENAME_STEP、MOVE_STEP、SET_DEPENDENCIES、UPDATE_RESULT、ADD_RESULT、CANCEL_STEP、LINK_CONTENT、MOVE_ISSUE、SET_BRANCH_RETURN、DISPOSE_ISSUE、DISPOSE_BRANCH、RESUME_ISSUE。取消／拆并完整处置与依赖同批，不能以少发字段删除旧要求或历史。

模型formation_delta共12种：INITIALIZE_PATH、ADD_STEP、UPDATE_STEP、MOVE_STEP、ADD_BRANCH、UPDATE_BRANCH、SET_BRANCH_FOCUS、ADD_ISSUE、UPDATE_ISSUE、ASSESS_STEP、RECOMMEND、ASSOCIATE_CONTENT。它不包含用户结束／重开／暂缓／放弃／恢复决定，不接受任意整对象覆盖。ADD／UPDATE只在既定目标与真实已读范围内；超出则提出用户采用方案。

### 6.3 卡片、私有依据与结果

两种新purpose均单组单卡CONFIRM，正式选项只有apply；客户端不替换payload，程序固定对应操作文案，不能用“确认写入”掩盖重新生成。私有binding核实真实消息／运行／所属、payload摘要、相关定义／目标、原Revision／来源头及用途，模型不见也不能补填程序权限。

发布与执行版本各保留真实身份；纯焦点变化不因F绝对值不同拒绝适用提案。正文、目标、范围、来源及相关实质状态变化仍须核实。具体摘要／读取算法随分记录存储的完整协议细化，不能把未采用v5的探索算法当已定案。

ProgramReceipt返回PROGRAM处理、真实D／F／V、DocumentEffect／形成及提案结果、事件及必要新身份映射，不复制全状态。回执重放是原动作成功证据，随后最新状态另读。模型调用终态、正文主结果、progress／formation／proposal组件结果分别说明，不能用一个成功图标遮蔽部分未应用。

验证／业务拒绝、版本／状态冲突、占用、重复回答、存储不可用与内部不一致分别由安全错误投影登记；不透传私有栈／凭据／正文。未知结果保留原命令查证；新字段／错误白名单尚需实现，不以本文表格代替现有程序登记。

## 7. 存储、模型上下文、来源与升级

### 7.1 持久化、分页与容量

头部Goal／F／焦点／身份高水位、步骤及顺序／依赖、问题／支线、成果关联和不可变历史分开承载。逻辑FormationState属于同份文档，不要求一个终身全量JSON；旧单JSON列及整份1MiB方案不再是当前持久化决定。

历史增长不按累计200步骤／1000支线或问题／2000关联迫使用户换文档。分页／过滤只控制读取范围，不删历史、不改身份、不把暂缓／已结束事项当消失。完整计数及跨页存在性、依赖图、双向关系和处置完整性由同一真实数据库快照核实，不能用首屏数组当全量。

单次请求／页面／变化批次及模型材料仍有技术预算；参数由可执行协议与容量验证固定，旧数值只是工程输入。超限整批拒绝、保留状态／草稿、说明本次需要缩小范围；分批也必须独立合法，不截断半批或自动结束。真实部署存储不足如实报告并明确扩容／恢复，不承诺无限资源。

### 7.2 统一事务与来源链

| 单元 | 必须同事务提交 |
| --- | --- |
| 原生路线／焦点／恢复／结束 | 实际用户动作、实体与关系变化、D／F、事件、Closure或旧结果快照、幂等成功回执 |
| DISCUSS接受 | 实际输入／pending、完整讨论目标及所需恢复／开始、冻结依据、原运行占用与202回执 |
| DISCUSS合法结果 | 助手消息、统一进展／formation／新卡与binding、事件和运行终态，先共同验证再提交 |
| 确认精确写入 | 正式CARD_RESPONSE、正文／Revision、真实来源、强制成果匹配、卡片处置、事件及回执 |
| 其他真实正文提交 | 原正文主结果及全部受影响关联维护；不能只新按钮维护匹配 |

准备阶段不提前修改仓储，事务内不调用模型。无提交不造成功记录；未知提交结果不武断当回滚。事件可同批多条共享版本，但各有真实身份与顺序；角色和时间由程序产生，用户时区展示，存储UTC。

精确采用的受信任来源为CARD_RESPONSE，source_id指向实际回答／命令；区块、Revision、原AI卡及审计来源链一致。需要扩展原内容提交权限与新资源枚举，不伪装GUIDE_RUN、不暴露跳过守卫参数；关联已有内容也不变成新写入。

### 7.3 模型上下文与返回接收

原读取→装配→Canonical／ContextBasis→Wire→计数→审计链路复用。接受时冻结最新已保存正文的实际版本、Goal、完整讨论目标、相关步骤／支线／问题、用户输入及必要长期依据／近期历史／提案；私有快照只保存真实选入对象与覆盖说明，不每轮复制终身全量主线。

Wire区分旧指导stage_overview与formation；正文在文档材料中只存一份，成果用真实引用。有界路线概览不代表读过所有定义，标题不代表读过正文；省略范围明确。无当前节点时按Goal、相关问题和输入组织材料，不猜测完成。

程序按关系和状态确定选材，不额外调用模型做相关性排序；先去重和移除可选背景，不能裁掉用户硬约束或必要正文后宣称完成。必要材料仍超预算时不Chat，说明缺口／分批范围。NEED_MATERIAL是建议，由用户下一次明确工作补齐，不隐藏补读调用。

模型返回保持原九个根字段与自然阐述自由，在新资源的progress_delta增加formation_delta，无更新为null；来源短别名须来自本轮真实清单，临时身份统一解析。任何进展／形成／新卡语义非法，DISCUSS结构单元整体拒绝；合法可读回复与pending保留。显式正文主结果沿原独立职责处理，实际内容变化仍维护关联。

历史回复携带来自真实程序结果的effect_state，区分用户输入／动作、讨论、实际应用、结构拒绝或未知；模型说“已保存”不制造业务事实。模型语义上是否值得建支线、是否充分满足要求需要真实效果评测，程序结构校验不能证明。

### 7.4 新资源、旧数据与升级
