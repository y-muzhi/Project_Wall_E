# 事实证据与卡片可读等价补充稿（待确认）

## 原依据与实际缺口

用户原请求第4节要求影响数据含义或关键技术保证的算法先确认。后端4.7 INITIALIZE、SHR-CARDS及已批准resources-v1/BUSINESS-VALIDATION要求“真实USER/正式CARD_RESPONSE逐字证据且事实一致”与“可读content和卡片等价”，没有定义自然语言一致性的可执行证明。简单包含关系不是该证明。

[实库诊断](../verification/fact-evidence-2026-10-05T05-30-45-950128+00-00.json)从真实创建/C03/冻结Schema/当前范围验证两例：用户否定或仅假设部门经理，候选只引用“审批人”或“部门经理”，便能通过Schema、实际Patch权限和逐字包含，同时提出错误肯定事实。数据库完整事实保持不变，未调用模型、未采用正文；这不是通过的AI业务验收。

还需明确卡片message与完整结构如何等价。不能丢掉不一致的message或删字段修成成功，也不能以模型第二次自报“核验通过”作为事实证明。

## 推荐的闭合算法

推荐保留原六Function、全部五种Patch、状态/占用/版本/范围/事务、Schema字段和既有容量；采用可复现的完整确认声明和完整卡片文本格式。v1资源不改字节，后续以新版本Prompt/签名协议明确这些规则，已有运行继续恢复原版本；无证据的候选保留失败审计并重生成/失败，不写正文。v1的未闭合自动事实采用保持不可启用，不能把这当作删除该功能。

### 一、事实补丁须有完整的用户确认声明

程序从已验证Patch与当前真实目标构造唯一声明，目标标识/完整章节路径、操作、完整旧内容、完整新内容全部来自当前真实基线和候选；标题/解释/impact不充当事实证据。声明只核对用户明确确认的变更，不证明现实世界中的事实真实性。

声明格式固定，标签和顺序不可换：

```text
确认事实变更
目标区块：{真实block_id}
章节：{章节路径的JSON字符串数组}
操作：{替换区块|在区块前插入|在区块后插入|删除区块|替换表格行}
原文：
{完整原区块或原表格行Markdown}
确认的新正文：
{完整proposed_markdown，删除时为“（删除，无新正文）”，行操作为完整cells的JSON字符串数组}
```

五种操作分别一一对应REPLACE_BLOCK/INSERT_BEFORE/INSERT_AFTER/DELETE_BLOCK/REPLACE_TABLE_ROW；行操作另在“操作”之后插入“原表格：\n{完整原表格Markdown}\n行选择：{实际selector的紧凑JSON}”，禁止猜行或拼接部分cells。插入的“原文”是实际锚定区块，方向明确；删除明确展示被删除的完整事实，不由否定词推断删除意图。

允许的用户证据只有以下两路：

1. 实际已读取USER TEXT的整条content恰为完整声明；不接受子串截取、把多个消息碎片拼成声明、从助手话语抽事实或把疑问/条件改为断言。普通自然语言仍可以指导模型提问与建议，但不是已证明的直接正文采用。
2. 已读取的真实USER CARD_RESPONSE引用不可变的完整原助手卡片。该原卡片card_type=CONFIRM，question恰为完整声明再加“\n是否确认以上事实和变更写入需求？”。两个option_key依次confirm/defer，label分别“确认以上事实和变更”/“尚未确认”，custom_answer关闭、推荐null、selection_rule min=max=1。原卡片related_spec_context须包含恰一个实际目标的完整原区块快照；该来源目标和候选当前目标/原文逐字一致。正式回答实际选择confirm、未跳过、无自定义才构成确认；defer/跳过/推荐不构成。其完整可读回答content须与现有程序生成的正式摘要一致。

实际message_id必须在本次已读取并记录的Manifest。USER TEXT的evidence须一条完整引用整条声明；正式CARD_RESPONSE的摘要可能较长，其evidence须引用该完整摘要按Unicode码点每10000字符切成的全部连续片段，均带同一个实际message_id、按原顺序，最多10条；拼回必须逐字等于完整实际摘要，不接受任选短关键词或缺片/乱序。每项Patch还须与实际已选择confirm的对应原卡完整声明精确匹配；同一整组回答可以证明其中多个已确认卡片分别对应的Patch，不将未确认卡片或推荐转成事实。每项完整Patch分别验证，仍共同验证组合和同事务采用；不能用证明更改目标/操作/内容。

比较声明时仅使用已批准SHR-TEXT的CRLF/CR到LF及外侧Unicode空白规范化；不做大小写、标点、词序、Markdown或单元格语义重写。被采用Patch本身继续保留原始字节并逐字检查actual original_content、单区块/表格/选区外不变、初始化标题锁。声明中的全部原文和新内容对用户可见，不裁剪或隐藏链接目标等源码。超既有输入/卡片/证据容量时拒绝并要求更小的事实项，不能把截断摘要算完整确认。

此方案不新增公开请求字段或持久事实对象，使用既有不可变消息/正式回答和实际Manifest证明。卡片由模型按新Prompt形成，并先经过完整结构/来源/等价校验；程序不把非法事实补丁改成另一输出分支、也不生成伪造的用户确认。

### 二、卡片message按完整结构生成的固定文本逐字核对

程序有唯一纯函数card_text(cards)。按数组顺序展开全部卡片，包含问题、上下文、类型、必答、min/max、自定义开关/容量、每个选项的键/标签/说明/影响/风险、推荐键/理由、每条真实相关区块ID和完整snapshot。文本使用带JSON字符串值的固定标签行，明确换行/转义；无推荐/无上下文也显式列出null或空数组，推荐标为“建议（尚未选择）”。不把推荐写成答案。

精确格式为每卡一组：第一行“卡片：{card_key的JSON字符串}”，随后固定顺序question/context/card_type/required/selection_rule/custom_answer，每行“{字段名}：{紧凑JSON值}”；随后每个完整option按“选项：{按option_key,label,description,impact,risks排序的紧凑JSON对象}”；再“建议（尚未选择）：{完整recommendation或null的紧凑JSON}”；随后每条“相关需求原文：{按block_id,content_snapshot排序的紧凑JSON对象}”，空集合写“相关需求原文：[]”。卡片之间仅一个LF空行。ensure_ascii=false、不改字段文本、只用JSON格式显示其转义内容。

对INITIALIZE_CARDS/CLARIFY_CARDS，模型原message必须逐字等于该固定函数结果，且满足既有message容量，才可信；不在接收阶段替换message、删未知字段、补默认或隐藏不一致。related_spec_context必须逐条来自真实读取区块，snapshot等于完整原Markdown，不给邻域写权限。原正常消息与正式CARD_RESPONSE行为保持。固定格式便于任何前端在结构损坏时仍读到完整等价文本。

### 三、发布与验收门禁

确认后先起草独立签名资源版本（包括六Prompt对规范的确切指导与格式例子）并记录与v1逐项差异；不改变预算/模型或偷偷原地改已使用资源。同一Run继续固定版本，新的Run使用明确激活版本；计数兼容须另按context-budget-compatibility-v1证明。该补充的批准不等于真实模型支持、效果通过或付费预算批准。

实际原候选、原Schema、实际上下文及当前事实共同校验后才生成内部可信产物；审计脱敏版本不是校验输入。成功产物C07仍实际事务重查owner/当前版本/调用归属及最新触发消息，取消或版本变化胜出则拒绝。程序无能力证明自然语言声明/卡片等价时OUTPUT_INVALID，按总三attempt或失败处理，原始已发生调用审计保留。

专项将覆盖负向/条件/引用助手/推荐未选/仅短证据/缺整组/错误目标与方向/截断/表格同键和列/删除、Unicode及旧版本继续；必须实际SQLite/正式CARD_RESPONSE/真实C07共同验证，不把模拟模型成功当效果。真实模型样本另检查格式可生成性与用户完成路径，不由纯测试宣布质量。

## 阻塞与可继续范围

需用户确认的是完整证据算法、卡片可读等价格式及必要的独立协议发布。当前阻塞非空INITIALIZE事实采用及可信卡片产出；零事实INITIALIZE文本、ASK文本、REVIEW正式引用检查、MODIFY建议/组合、C07其他分支、ORCH/后台启动、页面和其余验收继续实现。现有Q-预算补充仍独立待确认/真实证明；两者不互相当作已经获批。
